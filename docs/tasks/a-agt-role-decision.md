# A18-D · AGT 역할과 규칙 관리 결정 요청

2026-10-13 QA 지적 3번 대응. **미확정**이며 A·B·C 합의와 사용자 결정이 필요하다.
사용자(A)는 2026-10-13에 AGT 역할과 규칙 관리 경로 결정을 보류하고 2026-10-14 회의에서 정하기로 했다. A·B·C 합의는 아직 없다.
이 문서는 선택지와 트레이드오프만 정리한다. 이번 수정에서 규칙 형식·로딩 코드는 바꾸지 않았다.

## 현재 사실

- 어댑터 규칙은 `(server_id, tool_name, ToolKind) -> allow/deny` 정확 일치뿐이다
  (`adapters/agt_real.py`). SDK에는 이 세 값을 해시한 키만 전달한다.
- 규칙 값은 `examples/synthetic_app.py`에 합성값으로 고정돼 있다
  (`allow-tools`·`deny-send`·`deny-all`). 제품용 규칙 파일·로더·관리 화면은 없다.
- Registry는 이미 등록된 서버와 도구 지문만 통과시키고, Guard 정책 코어는 등급·경계·ASK를 판정한다.
  그래서 현재 AGT는 "등록된 도구 중 일부를 끄는 허용 목록"에 가깝고, Registry와 대부분 겹친다.
- AGT 허용은 Guard의 ASK·DENY를 완화하지 못한다(설계 10.3). AGT가 줄 수 있는 것은 추가 거절뿐이다.

## 선택지

### 1. AGT를 운영자 차단 목록으로 축소

규칙 형식은 그대로 두고 역할을 "등록된 도구를 운영 중 빠르게 끄는 차단 목록"으로 명시한다.
기본은 전부 허용하고, 운영자가 거절 항목만 추가한다.

- 장점: 현재 코드와 검증을 그대로 쓴다. 입력이 최소라 I1·I3·I9 위험이 늘지 않는다.
- 단점: Registry의 등록 차단(`BLOCKED`)과 기능이 거의 같다. AGT SDK를 둘 이유가 약하다.
- 남는 결정: 차단 목록을 바꿀 권한자, 변경 감사 위치.

### 2. 조건 규칙으로 확장해 Registry와 겹치지 않는 판정 추가

Guard가 신뢰하는 메타데이터만 SDK 입력에 더한다. 예: 도구 종류, 서버 경계 tier,
Task의 유효 등급, Task당 호출 횟수, 인자 바이트 크기, 시간대.
규칙은 "외부 tier SEND는 Task당 3회까지", "CONFIDENTIAL Task의 일반 외부 READ 금지" 같은 조건식이 된다.
원문 인자·문서·인증정보는 여전히 넘기지 않는다.

- 장점: Registry가 못 하는 호출 빈도·조합 제한을 AGT가 맡는다. SDK를 붙인 의미가 생긴다.
- 단점: 입력이 넓어져 I-불변식을 다시 검토해야 한다. 조건식 주입을 막는 규칙 형식 검증이 필요하다.
  등급·경계 판정은 B의 정책 코어와 겹칠 수 있어 역할 경계를 다시 나눠야 한다.
- 남는 결정: 허용할 입력 필드 목록(B 계약 변경), 조건식 문법 상한, C 공격 테스트 범위.

### 3. 규칙을 서명된 정책 파일로 운영 관리

규칙 형식은 1번 또는 2번을 따른다. 규칙을 앱 밖의 버전 정책 파일로 두고, 보안 담당자가 서명한다.
앱은 시작할 때 서명·버전·해시를 검증하고 실패하면 real 모드를 시작하지 않는다.
규칙 버전은 감사에 기록한다(B6 영속 감사).

- 장점: "누가 어디서 관리하는가"가 해결된다. 규칙 변경과 감사가 결속된다.
- 단점: 서명 키 보관·배포·교체 절차가 필요하다. 파일 경로 검증은 C의 위험 연산 모듈 범위다.
- 남는 결정: 서명 주체, 키 저장 위치, 재시작 없이 규칙 교체를 허용할지.

## 권장 검토 순서

1. 1번과 2번 중 AGT의 역할을 먼저 고른다. 2번이면 B가 입력 필드 계약을 제안한다.
2. 어느 쪽이든 제품에서는 3번 같은 관리 경로가 필요하다. 합성 하드코딩은 데모 전용으로 남긴다.
3. 결정 후 A가 규칙 로더와 형식 검증을 구현하고, C가 거절·형식 오류·주입 시도의 dispatch 0을 인수한다.
