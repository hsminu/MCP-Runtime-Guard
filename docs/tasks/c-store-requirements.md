# C1.1 · Store 계약 요구 초안

상태는 **C 요구 초안 작성, B 검토·A·B·C 합의 미완료**다. 이 문서는 B가 `domain/*`와 `ports.py`를 정의할 때 검토할 저장소 요구다. 연산 이름은 개발문서에서 가져왔으며, 실제 시그니처·반환 모델·오류 타입·스키마 변경은 미확정이다. 구현과 테스트는 미실행이다.

기준은 [기술 설계](../technical-design.md) 3.4·6–8·9.4·11·14.3절과 [공통 계약 체크리스트](../contracts.md)다. 담당 작업은 [C 체크리스트](c-security-platform.md)의 C1.1이며, 작성 C·리뷰 B, 공통 계약 확정은 A·B·C다.

2026-10-12 사용자 결정으로 SQLite 구현·스키마·복구·저장소 단위 테스트는 [B6](b-sqlite-store.md)로 이관했다. 이 문서는 B의 설계 검토와 C의 독립 인수 기준으로 유지한다. 담당 변경은 확정됐지만 아래 API 세부 사항의 합의와 실제 구현·검증은 별도다.

후속으로 B 커밋 `0c02b61`의 실제 domain·ports·B1–B5 코드를 확인하고 `f3c2d2b`의 C-B-01 수정·대역 회귀도 확인했다. [B 초안 확인 기록](c-b-review.md)에 검증 재현·결함·수정·U1–U8 대조를 남겼다. READ의 TaskState 반환, 소비의 정확한 bool ACK·관계 검사·감사 원자성 등 구현 초안은 존재하며 합의는 미완료다. 아래 요구는 해당 B 제안과 대조해 검토한다.

미확정 항목의 구체적인 C 권장 규칙은 [Store 계약 처리 제안 v1](c-store-proposal.md)에 작성했다. 보안 버전·원자 승인·ACK/취소·시계·복구의 선택과 B 변경·검증 계획을 제시하며, 아래 U1–U8은 실제 합의 전까지 미확정으로 유지한다.

## 1. 책임과 호출 경계

| 영역 | 책임 |
| --- | --- |
| B domain·ports | 요청·상태·감사 모델, Store의 메서드·반환·오류 계약 정의 |
| B Guard·승인·응답 게이트 | Task 직렬화, 신뢰 요청 해석, 승인자·사본·시간 검증, 분류·등급 병합 의미, 오류의 도메인 결과 변환, 결과 공개 |
| B Store | DB 관계·기대 상태·버전 검사, 원자적 저장, 충돌·저장소 실패 전달, 민감 원문을 제외한 기록 |
| C 독립 검증 | 저장소 리뷰, 동일 Store/Fake 계약, 관계·원자성·장애·복구·실제 실행/공개 계수 검증 |
| A transport | 예약을 통과한 요청의 실제 호출과 host dispatch 관측 |

Store의 입력은 Guard·Catalog·응답 게이트가 만든 신뢰 맥락에서 온다. Task ID·epoch·호출 순번·등급·승인자·사본 해시를 모델이나 도구 출력의 주장으로 채우지 않는다(I7). READ 출처 분류와 승인 재평가는 B의 경로가 수행하며, Store는 그 의미를 새로 정의하지 않는다.

승인 대기에는 Task lock과 DB 트랜잭션을 유지하지 않는다. 승인 후 재평가부터 응답 커밋까지는 submit과 같은 Task lock을 유지한다. DB 트랜잭션은 저장 작업만 포함하며 사람 응답·MCP 실행을 기다리지 않는다(7.2·8.3절).

## 2. 공통 저장 요구

- 백엔드 단일 writer가 연결을 소유한다. WAL·foreign_keys·synchronous FULL과 명시적 `BEGIN IMMEDIATE`를 사용하며, 실제 연결 설정을 검증한다(11.1절).
- SQL은 `storage/sqlite_store.py`의 바인딩 파라미터로 실행한다. 문서의 SQL 블록은 참고 설계다.
- `requests(task_id, call_seq)`와 `approvals.request_id`의 UNIQUE, 필요한 외래키를 적용한다. 없는 상태를 기본 Task·PUBLIC 등급·승인으로 보충하지 않는다(11.2절, I6).
- `row_revision`은 DB 갱신 충돌을, `security_version`은 승인에 영향을 주는 보안 변경을 구분한다. 기존 revision 필드가 있는 행의 변경은 revision 검사·증가를 포함한다. 상태 전이의 보안 버전 규칙은 미확정 항목 U2에서 확정한다.
- B의 등급 병합 규칙을 사용한다. C가 별도 정책·taint 구현을 복제하지 않는다.
- 문서·인자·결과·인증정보·승인 사본 원문을 DB와 로그에 기록하지 않는다. `ResolvedRequest` 전체 직렬화도 저장 payload로 사용하지 않는다. 감사는 허용된 ID·코드·등급·해시·시각·제한된 메타데이터로 구성한다(11.4절, I9).

C의 추가 검토 제안은 다음과 같다. 아래 조건의 표현 방식과 필요한 스키마는 B 계약 초안에 반영해 합의한다.

- 개별 ID의 존재뿐 아니라 승인 → 요청 → Task의 관계와 요청 순번·epoch 맥락을 확인한다. 서로 다른 정상 레코드의 ID를 섞은 호출도 거부한다.
- 조건부 UPDATE의 영향 행 수가 정확히 1인지 각각 검사한다. 0 또는 예상 밖의 행 수는 성공으로 반환하지 않는다.
- 이미 완료된 요청의 중복 커밋은 새 결과 공개 권한이 되지 않게 한다. 다른 본문을 같은 request ID로 다시 공개하거나 감사·승격을 중복 기록하지 않는다.
- DB 잠금 대기·시간초과·취소·rollback 실패가 호출자를 무한 대기시키지 않도록 실패 계약을 정한다. DB 처리 실패를 이유로 MCP 호출을 반복하지 않는다.

## 3. `commit_observation` · READ 관측 커밋

근거는 6.1–6.3·11.3절, 관련 불변식은 I4·I5·I6·I7·I9다.

### 입력과 전제

- 신뢰 해석된 READ 요청의 식별·출처 맥락과 B가 분류한 `Label` 또는 미분류 결과를 받는다. 정확한 인자 타입은 B가 정의한다.
- `None`은 READ 분류 실패만 뜻한다. 결과를 전혀 받지 못한 READ 전송 실패를 미분류 관측으로 대신 기록하지 않는다(6.2절).
- 기존 요청이 해당 Task·순번에 속하고 관측 커밋을 받을 상태인지 확인한다. 정상 경로의 요청 상태는 `DISPATCHING`이다. 취소·긴급 차단과 응답 도착의 경쟁에서 허용할 상태는 U8로 남긴다.
- `resource_id` 불일치·출처 규칙 없음은 B 응답 게이트의 분류 실패로 전달한다. Store가 결과의 자체 등급 주장을 신뢰하지 않는다.

### 한 트랜잭션에 포함할 변경

| 관측 | Task 변경 | 승격 근거 | 감사·요청 상태 |
| --- | --- | --- | --- |
| 현재 high-watermark보다 높은 등급 | high-watermark·last_read_label 갱신, security_version 증가 | 해당 요청의 승격 1건 | OBSERVED 감사, 요청 SUCCEEDED |
| 같거나 낮은 등급 | high-watermark 유지, 필요하면 last_read_label 갱신. 이 변화만으로 security_version을 올리지 않음 | 추가 없음 | OBSERVED 감사, 요청 SUCCEEDED |
| 미분류 | 기존 high-watermark 유지, unclassified 설정, Task HALTED, B 규칙에 따른 security_version 갱신 | 등급 승격과 구분 | 미분류 관측 감사, 요청 WITHHELD |

Task를 갱신할 때 기대 row_revision과 영향 행 수를 검사한다. Task·승격 근거·감사·요청 상태는 함께 커밋되거나 함께 rollback한다. 감사 삽입 실패나 요청 상태 충돌만 발생해도 등급만 따로 남기지 않는다.

### 결과와 실패 의미

성공은 커밋 완료가 확인됐다는 뜻이다. 정상 분류 결과는 그 확인 이후에만 응답 게이트가 공개한다. 미분류 커밋은 성공했어도 Task는 HALTED이며 본문은 공개하지 않는다(I5).

커밋 실패는 미공개와 Task 정지로 연결한다(T07). 관측 트랜잭션을 rollback하면 HALTED도 함께 취소될 수 있으므로, 실패 후 Task 정지 기록은 B의 별도 containment 경로와 연결해야 한다. 그 기록까지 실패하면 Guard의 global halt로 이후 실행을 중단한다(7.1절). rollback만 수행하고 Task 실행을 계속하는 것으로 실패 처리를 끝내지 않는다.

## 4. `commit_send_outcome` · SEND 결과 커밋

근거는 6.3·6.4·11.3절, 관련 불변식은 I4·I5·I6·I8·I9다.

### 입력과 전제

신뢰 해석된 SEND 요청과 저장할 결과 의미를 받는다. 정상 완료 예시는 요청·감사 커밋으로 충분하지만, 명확한 업무 실패를 같은 연산에 포함할지와 필요한 outcome 인자는 U5에서 정한다. 응답 본문을 저장 인자로 직렬화하지 않는다.

해당 요청의 Task 관계와 기대 요청 상태를 검사한다. READ 요청을 이 연산으로 처리하거나 SEND를 `commit_observation`에 넣는 호출은 계약 위반으로 구분한다.

### 한 트랜잭션에 포함할 변경

- 정상 SEND 완료의 요청 상태 SUCCEEDED와 SEND_COMPLETED 감사를 함께 확정한다(11.3절).
- Task의 high-watermark·last_read_label·unclassified·security_version·status를 변경하지 않는다. SEND 응답에 READ 병합을 적용하지 않는다. 정상 완료 다음 호출도 같은 Task에서 진행할 수 있어야 한다(T35).
- 요청 갱신이나 감사 삽입이 실패하면 해당 DB 변경을 함께 rollback한다. DB rollback은 이미 일어난 원격 부작용을 취소했다는 뜻이 아니다.

### 결과와 실패 의미

성공은 SEND 결과 기록의 커밋 완료가 확인됐다는 뜻이다. 도구 결과는 그 확인 후에만 응답 게이트가 공개한다.

저장 실패 시 결과를 공개하지 않고 오류를 B에 전달한다. 이미 예약·dispatch된 SEND를 DENY·전송 0건으로 보고하거나 자동 재전송하지 않는다. 알려진 SEND 결과의 StoreError 처리와 예상하지 못한 dispatch 이후 예외의 UNKNOWN_OUTCOME 처리는 U5에서 구분한다. Store 자체가 Guard 결과를 임의로 선택하지 않는다.

## 5. `consume_and_reserve` · 승인 소비와 실행 예약

근거는 7.2·8.1–8.5절, 관련 불변식은 I2·I3·I6·I7·I8·I9·I10이다.

### 입력과 호출자 전제

설계에 제시된 승인 ID·사본 해시·요청 ID·Task ID·기대 security_version·현재 UTC 시각을 기반으로 한다. epoch·순번·revision 등 추가 맥락의 전달 방식은 U1·U3에서 합의한다.

B 승인 경로는 호출 전에 다음을 검증한다.

1. 사람 전용 채널의 승인자와 메모리 사본이 유효하다. 재시작으로 사본이 없으면 기존 승인을 실행 권한으로 복원하지 않는다.
2. 동일 Task lock 안에서 현재 정책·등록·지문·목적지로 재평가한다. 결과는 ASK이고 현재 사본 해시가 승인 사본과 일치한다. ALLOW로 바뀌었어도 기존 승인은 무효다.
3. 프로세스의 monotonic deadline을 확인한다. Store는 DB UTC 만료 비교를 추가 수행한다. UTC 표현·비교 규칙은 U6에서 확정한다.

Store는 재평가·사람 인증을 대신하지 않으며, 전달된 성공 주장만으로 DB 조건 검사를 생략하지 않는다.

### DB 조건과 한 트랜잭션의 변경

| 대상 | 필요한 조건 | 변경 |
| --- | --- | --- |
| 승인 | 지정 승인·요청 관계, APPROVED, 사본 해시 일치, expires_at_utc가 now_utc보다 큼 | CONSUMED, 소비 시각, 기존 row_revision 갱신 |
| 요청 | 지정 요청·Task 관계, WAITING_APPROVAL | DISPATCHING, 예약 시각 |
| Task | 지정 Task, WAITING_APPROVAL, 기대 security_version 일치, 합의된 epoch·충돌 조건 | RUNNING, row_revision 갱신. security_version 처리는 U2 |
| 소비 감사 | C 제안: 동일 승인·요청·Task를 식별하는 허용 메타데이터 | 소비·예약 감사 삽입을 같은 트랜잭션에 포함 |

승인·요청·Task UPDATE 각각의 영향 행 수가 1이어야 한다. 하나라도 불일치하거나 감사 기록이 실패하면 전체를 rollback한다. 소비 감사의 원자적 포함은 원문 8.3절 SQL에 없는 C 제안이며 U4에서 검토한다.

### 결과와 실패 의미

성공은 승인 1건 소비와 실행 예약의 커밋 완료가 확인됐다는 뜻이다. 실제 dispatch는 이후 Guard가 수행한다. 예약 감사에 실제 전송 완료를 기록하지 않으며, host_dispatch는 A worker의 실제 진입으로 별도 확인한다(9.4절).

조건 불일치는 실행 권한을 얻지 못한 결과다. 저장소 장애·커밋 확정 불가와 구분해 전달한다. `bool`·결과 모델·전용 예외 중 어떤 API로 표현할지는 U1에서 정한다. 조건 불일치 이후 INVALIDATED·EXPIRED 등 승인 종착 상태의 처리는 B 승인 경로가 담당한다.

더블클릭·이벤트 재전달에서도 소비·예약은 최대 1회다. 커밋 성공을 확인한 호출자만 dispatch로 진행하며, 같은 Task lock은 응답 커밋까지 유지한다(T12·T37).

## 6. 실패·rollback과 공개 경계

아래 분류는 요구 의미이며 확정된 오류 클래스 이름이 아니다. 원문 SQL·인자·DB 경로·예외 메시지 원문은 공개 오류나 감사로 전달하지 않는다.

| 분류 | Store 요구 | B 실행 경로의 요구 |
| --- | --- | --- |
| 관계·상태·해시·만료·버전 불일치 | 성공 반환 없음. 변경이 시작됐다면 rollback | 승인 소비 실패는 dispatch 없음. 응답 커밋 충돌은 결과 미공개이며 현재 Task 상태를 확인 |
| 커밋 전 실패와 rollback 완료가 확인됨 | 해당 연산의 부분 변경 없음, 구분 가능한 실패 전달 | 예약 전은 실행 없음. 응답 처리 구간은 이미 나간 요청과 실패를 구분해 containment |
| DB 잠금·쓰기·감사 기록 실패 | 실패를 조건 불일치로 숨기지 않음. 가능한 rollback 수행 | 결과 미공개, 정해진 정지·결과 불명 처리. MCP 자동 재전송 없음 |
| COMMIT·ROLLBACK 완료 여부를 확정할 수 없음 | rollback 완료·커밋 성공을 단정하지 않음. 확정 불가를 별도 전달 | 새 dispatch 권한으로 사용하지 않음. Task/global halt와 복구 정책을 B와 합의 |
| 커밋 후 호출자 오류·프로세스 중단 | 이미 커밋된 사실과 미커밋 실패를 구분 | 소비·예약을 다시 수행하거나 쓰기를 자동 재전송하지 않음. 재시작 정책은 U7 |

세 연산의 DB 성공은 결과 공개의 필요 조건이다. READ 미분류, Task 정지, 승인 맥락 손실 등 별도의 공개·실행 금지 조건까지 해제하는 의미는 아니다.

## 7. B 계약 초안에서 확정할 항목

모두 **미확정**이다. C 제안 검토와 합의 근거는 공통 계약 문서에 기록한다. 제공받은 기술 설계 원문을 합의된 것으로 수정하지 않는다.

| 항목 | 근거·불명확한 지점 | 필요한 결정 |
| --- | --- | --- |
| U1 · 메서드·반환·오류 | 원본 설계는 전체 포트 정의가 없지만 B ports 초안은 READ→TaskState, SEND→None, 소비→정확한 bool과 StoreError를 제안함 | B 실제 시그니처·추가 실패 연산 검토, 조건 충돌·저장 실패·커밋 확정 불가·취소·ACK 의미 합의 |
| U2 · 상태와 보안 버전 | 3.4절과 8.3절의 상태 버전 의미는 미확정. B 코드는 WAITING 반환 상태로 사본을 생성해 원문 예시의 생성 순서를 보완하고 소비 후 버전 유지·1 증가 모두 허용함 | 상태별 증가 규칙과 소비 후 상태 갱신을 하나의 의미로 확정. 승인 생성·종결의 원자 묶음도 검토 |
| U3 · 레코드 관계·epoch·revision | B 소비 포트는 승인→요청→Task 관계와 변경 행 수 1을 요구함. 실제 SQL 구현은 없고 원문 requests에는 epoch·row_revision 열이 없음 | 관계 검사 위치, epoch 전달·검증, 중복 커밋·충돌 조건, 필요한 스키마 변경 여부 |
| U4 · 소비 감사 원자성 | 8.3절 SQL에는 감사·승인 revision이 생략됐으나 B 소비 포트는 승인·예약·Task·감사의 원자 커밋을 명시함 | 이 B 제안의 합의, 감사 사건명·허용 메타데이터·revision·실패 rollback을 실제 저장소로 검증 |
| U5 · SEND 결과·커밋 실패 | 원문 6.3절의 공통 HALTED와 달리 B 응답 게이트는 SEND 오류·형식 실패·StoreError를 UNKNOWN_OUTCOME으로 처리하고 성공만 commit_send_outcome에 전달함 | 이 보수적 실패 의미 합의, commit_request_failure 상태 쌍·reason_code와 원자성 검증 |
| U6 · DB 대기·시간·실패 | 8.4절은 monotonic과 UTC 이중 확인만 제시함 | UTC 정규 표현·만료 경계, DB 잠금 대기 상한·취소, COMMIT/ROLLBACK 확정 불가 전달·연결 처리 |
| U7 · 재시작·containment | 7.1절은 정지 기록 실패 시 global halt, 8.1절은 승인 사본 메모리 보관, ADR-4는 재시작 승인 무효 | 재시작 시 PENDING·APPROVED 승인과 DISPATCHING 요청·Task의 처리, 정지·결과 불명 기록에 필요한 Store 계약. 승인·쓰기 자동 실행 없음 |
| U8 · 제어와 응답의 경쟁 | B 승인 생성·종결은 Task 전이와 별도 Store 호출이며 원자 묶음이 미합의. C-B-01은 f3c2d2b 수정·대역 회귀 확인 | 실제 SQLite의 식별자 결함 검증, 생성·종결 원자성·제어 경쟁, 정지/불명/종료 Task의 실행 복귀 방지 |

## 8. 후속 검증 인수 기준

아래는 작성할 테스트 요구이며 **모두 미실행**이다. 저장소 단위 테스트는 B가 작성하고 C가 리뷰한다. 계약·통합·결함 주입 검증은 C가 작성하고 B가 리뷰한다. B의 정책·taint 단위 테스트를 복제하지 않고 연결된 저장·공개·실행 결과를 확인한다.

| 검증 묶음 | 확인할 증거 | 연결 I/T/S |
| --- | --- | --- |
| READ 정상·낮은 등급·미분류 | DB 등급·버전·승격·감사·요청 상태가 일치. 미분류 본문 공개 0, high-watermark 감소 없음 | I4·I5·I7, T05·T33·T34 |
| READ 부분 실패 | Task 갱신·승격·감사·요청 갱신 각 단계의 커밋 전 실패에서 부분 저장 없음. 결과 공개 0, HALTED 또는 정지 기록 실패 시 global halt | I5·I6, T07 |
| SEND 정상 커밋 | Task 보안 필드 불변, 요청·감사 동시 확정, 다음 호출 진행 가능 | I4·I5, T35 |
| 승인 관계·조건 변조 | 서로 다른 승인·요청·Task의 ID 조합, 잘못된 해시·상태·버전·epoch·만료에서 소비·dispatch·wire·부작용 0 | I2·I3·I7·I10, T09–T11 |
| 승인 부분 실패·경쟁 | 각 UPDATE·감사 삽입 실패는 전체 rollback. 정상 승인·더블클릭 시 소비·dispatch·wire·수신 부작용 각각 1 | I3·I6, T12 |
| 커밋 후에도 Task 직렬화 | 승인된 READ 결과 커밋까지 같은 Task의 다음 판정이 대기하고, 갱신된 등급으로 판정 | I4·I5, T37 |
| dispatch 이후 저장·변환 실패 | 이미 나간 READ/SEND 계수를 DENY의 0건으로 덮지 않음. 결과 미공개·정지/불명 처리, 쓰기 추가 전송 0 | I5·I6·I8, T07·T14·T15·T36. U5 결정 반영 |
| 커밋 확정 불가·프로세스 중단 | 재개방해 관측한 DB 상태와 실행 계수를 기록. 확인 못한 rollback·내구성을 통과로 단정하지 않고 자동 실행 없음 | I3·I6·I8, T11·T36의 저장소 상세 케이스 |
| SQL·감사·로그 | 특수문자를 포함한 저장 필드가 바인딩으로 처리되고 원문·토큰·TEST_SECRET 표지가 DB·기본 로그에 남지 않음 | I9, S03·S04·T19 |

관측 커밋 실패 테스트의 해당 READ는 이미 dispatch됐을 수 있다. 공개 0과 이후 실행 중단을 검사하며, 그 READ의 host_dispatch가 0이어야 한다고 기대하지 않는다. DB 검사만으로 wire·수신 부작용까지 검증했다고 보고하지 않는다(9.4절).
