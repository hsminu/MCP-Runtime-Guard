# A의 UI 명령·이벤트·조회 계약 제안

기준: 2026-10-12. [A05](a-prompts/01-contracts.md#a05)의 **제안**이다. 근거는 [기술 설계 8.5·12장](../technical-design.md), [A의 B 계약 요구](a-port-review.md), [A의 C 연동 요구](a-platform-review.md), [HTML 시안](../../ui-preview/README.md)이다. 작성 당시 UI용 backend 계약이 확정되지 않았다. 이후 B 포트와 A bridge 타입이 추가됐지만 아래 메시지 이름과 필드 묶음은 여전히 협의 대상이며 확정 API가 아니다. 구현·합의의 현재 상태는 [A 작업 현황](a-progress.md)을 따른다.

## 공통 경계

- UI는 bridge를 통해 불변 명령을 보낸다. Task/승인/Registry/감사 상태는 backend가 확정한 조회 결과와 이벤트로만 바꾼다. UI는 DB·transport·Guard를 직접 호출하지 않고 등급·경계·승인 만료를 판정하지 않는다(I1·I3·I7).
- `actor_id`·`task_id`·`request_id`·`approval_id`·`server_id`의 신뢰 출처는 B/C가 정의한 backend 맥락과 저장된 레코드다. 모델·도구 출력, 화면 텍스트, `stdio`/localhost로 신뢰를 정하지 않는다. UI는 조회 키를 돌려줄 수 있지만 그 키의 권한을 만들지 않는다.
- 실행 명령과 사람 전용 승인·거절·취소·긴급 차단 명령은 별도 큐다. 명령 접수(`accepted`)는 실행/승인 소비/등록 활성화 완료와 다르다. 제어 큐가 가득 차거나 종료 중이면 확정 실패를 돌려주고 조용히 버리지 않는다.
- 일반 조회·이벤트·CSV·오류에는 문서 본문, 비밀, 전체 인자, 예외 원문, raw MCP 결과가 없다(I5·I9). 승인 대상 전체 인자는 B가 관리하는 승인용 메모리 사본의 명시적 상세 조회에서만 반환하고, 사본 만료·해결 시 접근을 거부한다. Qt는 일반 텍스트로 전체를 표시한다(T18).
- 시간은 backend가 생성한 UTC 시각과 명시적인 시간대/offset으로 전달하고, UI에서 공통 날짜 포맷(연·월·일 시·분·초·시간대)으로 표현한다. 값이 없으면 `미제공`으로 표시한다. 시간은 표시·정렬 자료이며 상태 순서 또는 승인 만료 판정의 근거가 아니다.

## 제안하는 메시지 외피

| 속성 | 필요한 의미와 출처 | 누락·중복·지연 처리 |
| --- | --- | --- |
| `command_id`, `event_id` | backend가 접수·발행한 불변 식별자. 호출자가 재전달한 동일 제어 명령을 구별할 수 있어야 함 | 중복 명령이 와도 B의 승인 원자성과 C 저장소가 최종 1회 집행. UI는 ack와 적용 결과를 별개로 표시 |
| `task_id`, `request_id`, `approval_id`, `server_id` | 각 레코드의 신뢰 식별자. 해당하지 않는 메시지에는 명시적 null/없음 | 선택 중인 항목과 다른 ID의 지연 이벤트는 현재 상세를 덮어쓰지 않음 |
| `generation` 또는 `row_revision`, `security_version`, `policy_version` | B/C가 정의한 상태 변화 순서. Task/승인/Registry 객체별 범위와 증가 규칙을 명시 | 오래된 이벤트를 timestamp만으로 결정하지 않고, revision 갭/순서 불명은 snapshot 재조회 |
| `occurred_at_utc`, `recorded_at_utc` | backend의 사건 시각과 기록 시각. 둘을 혼동하지 않음 | 시간 미제공이면 미제공. 지연/역순 도착을 시각으로 임의 정렬해 상태를 되돌리지 않음 |
| `status`, `reason_code`, `public_message` | 확정 상태, 안전한 코드, 표시 가능한 고정 문구는 B/C가 제공 | 알 수 없는 상태·코드는 안전한 일반 오류/새로고침 필요로 표시. 예외 원문을 노출하지 않음 |
| `source_mode` | 실제/mock AGT·모델·Scanner 여부의 안전한 메타데이터(해당 화면만) | 없으면 `미확인`이며 실제 연동으로 표시하지 않음 |

`TaskCreated`, `ApprovalPending`, `RegistrationChanged` 등 설계 12.2절의 이름은 예시다. 필요한 것은 위 신뢰·순서·공개 의미이며 실제 타입/이름은 B·C가 합의해야 한다.

## 누적 승인 대기와 집계

- B가 대기 상태의 조회·만료·무효화·처리 이력을 책임진다. A는 검색어·서버/상태 필터·기본 오래된 순 정렬·페이지 또는 커서·총건수·선택 요청 상세의 입력/응답 계약을 요청한다. 안정적인 정렬 키와 조회 snapshot/revision을 제공해 페이지를 넘기는 사이 항목 이동·중복을 감지해야 한다. 화면의 6건 페이지 크기와 30분 표식은 **표시 설정**이며 승인 보존/만료 정책이 아니다.
- 처리 후 현재 페이지가 비면 유효 페이지 또는 조회 snapshot을 요청한다. 대기와 이력은 서로 다른 필터/조회로 나누고, 재시작 이후 B가 복원하지 않은 메모리 승인 사본은 UI에서 재구성하지 않는다.
- 현황의 `활성 MCP 서버`는 C Registry에서 `ACTIVE`로 확정된 서버 수다. `연결됨`은 별도의 세션 관측 상태다. `승인 대기`는 B가 현재 유효하다고 반환한 건수다. `차단된 호출`은 C 감사에서 기간과 reason/status 집계 기준을 명시한 값이다. 집계 기간, 시간대, 중복 제거 키, 실패/부분 자료 처리 방식은 B·C 결정이 필요하다.
- 확인 항목은 안정적인 ID와 발생 근거로 중복 제거하고, 해결/무효/만료 이벤트 또는 재조회 결과로 제거한다. 목록 순서는 사람의 조치 필요성·시각 기준을 계약으로 정한다. UI의 시계만으로 보안 상태를 바꾸지 않는다.

## bridge의 접수, 이벤트, 재동기화 요구

1. 모든 명령은 `command_id`와 기대 revision을 포함하고, bridge는 `접수 거절/접수됨`을 우선 반환한다. 실제 Guard 승인 소비·Registry 전이는 별도의 `적용됨/거절됨` 확정 결과로 보낸다. 전송 중 취소는 원격 부작용 취소를 보장하지 않는다.
2. UI 시작 시 backend snapshot과 그 기준 revision/커서를 구독한다. 이후 이벤트를 같은 범위의 revision으로 적용한다. 중복·오래된 이벤트는 무시하고 갭·재연결·프로세스 복구 시 해당 조회를 다시 수행한다. 재조회는 읽기이며 Run/Approve/SEND를 재발행하지 않는다.
3. snapshot 실패는 `불러오지 못함`으로 남기고 재시도 가능하게 한다. 오래된 항목은 별도로 표기한다. 승인/차단/전송 성공/서버 ACTIVE를 클릭 직후 낙관 표시하지 않는다.
4. 이벤트 payload는 화면 공개 허용 필드만 담는다. 모델·UI에 공개 가능한 READ 내용은 B의 `Released` 이후에만 건넨다. 승인 메모리 사본은 별도 접근 수명을 가지며 일반 상태 캐시·감사·CSV에 복제하지 않는다.
