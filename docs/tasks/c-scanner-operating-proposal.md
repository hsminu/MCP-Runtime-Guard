# C · Scanner 운영 설정 일괄 추천안 v1

2026-10-13 사용자의 "이런 자잘한 거 다 추천하는 거 적어봐" 요청으로 남은 작은 설정을 모았다. **기존 사용자 결정은 유지하고, 추가값은 초기 추천안으로 제시한다.** 이 문서 작성은 새 추천값의 승인이나 제품 구현을 뜻하지 않는다. 입력 크기·개수·시간·동시성의 수치는 각각의 상한이며 어느 하나로 나머지를 대체하지 않는다.

근거는 [실제 MCP 정의 조사](c-real-mcp-metadata-survey.md), [Luna low 제품 연결과 측정](c-cisco-luna-connection.md), 현재 C 소스와 설치된 SDK다. 실제 서버 표본의 최대 도구 수는 91개·최대 단일 정의는 8,360바이트·최대 정규화 페이지 result는 259,485바이트였다. 작성 당시 추가값을 적용한 성능 실험은 하지 않았다. 후속 사용자 요청의 [운영 추천안 검증](c-scanner-operating-validation.md)에서 실제 정의 144개의 동시 LLM 4개·YARA worker 1개 검사와 stdio/HTTP 경계 관찰 22개·YARA timeout 실험을 수행했다. 256개 도구의 실제 모델 검사·제품 수신 제한·전체 deadline 인수는 남아 있다. 공식 프로토콜 한도나 통계적으로 최적인 값으로 보고하지 않는다.

시간·동시성 값은 첫 운영 설정이다. 기존 Luna low 28건의 p50 4.991초·p95 7.212초는 순차 API 측정이며 동시 요청 4개의 지연이나 전체 10분 내 완료를 증명하지 않는다. 후속 실제 정의 144개 실험은 69.764초·HTTP 200 144건·LLM p95 3.220초였다. 이는 실험 배치이며 제품 전역 동시성·256개 도구·전체 deadline의 검증이 아니다. 계정의 요청·토큰 제한을 알 수 없으므로 동시 4개가 모든 환경에서 성공한다고 보장하지 않는다. 제품 통합 검증에서 실제 429·실패율·전체 시간을 측정하고 조정한다. 큰 정상 서버가 제한에 걸리면 경고를 확인하고 해당 설정을 올릴 수 있게 한다.

MCP 목록 시간 제한은 업무 `tools/call` 시간 제한을 바꾸지 않는다. 전체 검사 deadline이 끝나면 이미 완료한 분석 결과는 보존하고, 실행 중·미실행 항목은 완료로 표시하지 않는다. 따라서 도구 256개가 매번 전부 검사된다는 보장은 아니다.

두 분석기 모두 개별 도구에서 완료했을 때만 그 도구의 검사를 완료로 표시한다. 한쪽만 완료하면 다른 쪽의 실패·미실행 상태와 함께 부분 완료로 표시한다. 전체 입력 준비를 못 한 도구에는 분석기를 실행한 것처럼 기록하지 않는다. 유효한 완료 결과의 Finding 0개와 검사 미완료는 구분한다. 위험·미완료 경고는 기존 결정대로 Scanner만을 이유로 자동 사용 차단하지 않으며, 수집되지 않은 새 정의를 추정해 등록·호출하는 의미는 아니다.

현재 Cisco 4.8.6 YARA `analyze`는 `async` 함수 안에서 `self._rules.match(data=content)`를 동기로 호출하며 timeout을 넘기지 않는다. YARA 공식 Python API에는 `match(..., timeout=...)`와 timeout 예외가 있지만, 현재 C/Cisco 경로에는 5초 제한을 연결하지 않았다. worker·SDK 호출 보정·오류 집계는 구현과 검증이 필요하다. [YARA Python 공식 문서](https://yara.readthedocs.io/en/stable/yarapython.html).

OpenAI SDK의 `max_retries=0`은 자동 재시도를 끄는 설정이며 현재 설치된 OpenAI 2.54.0과 C 코드에서도 명시했다. HTTP timeout과 작업 전체 deadline은 별도 개념이므로 둘 다 유지한다. [OpenAI Python SDK 공식 문서](https://developers.openai.com/api/reference/python). 모델 선택은 사용자가 정한 Luna low를 유지하며 모델 교체·프롬프트 변경·API 방식 변경은 이 제안에 포함하지 않는다.

| 정렬 | 상단에 수집/검사 미완료 요약, 아래에 위험도 높은 순서의 Finding 묶음 |
| 완료 문구 | "검사 완료·발견 0건". 무탐지를 "안전 보장"으로 표현하지 않음 |
| 실패 문구 | "LLM 검사 실패", "YARA 미완료", "목록 수집 미완료"처럼 실제 단계와 고정 사유 표시 |
| 진행 정보 | 수집된 도구 수·목록 수집 완료 여부, 분석기별 완료/실패/미실행 수, 경과 시간, 대기·취소 상태 |
| 알림 | 개별 Finding마다 팝업을 띄우지 않고 검사 요약 알림 1회와 목록 표시 |
| 원문 처리 | SDK evidence·raw_response·전체 정의·API 키·예외 원문은 기본 화면과 로그에 노출하지 않음. 표시 이름·안내는 일반 텍스트로 렌더링 |
| 요약 기록 | 신뢰 설정의 서버 식별자, 검사 식별자·대상 지문/버전, 분석기·설정, 건수·상태·고정 오류 코드·시간만 기록. 영속화는 B Store 계약으로 연결 |

현재 B ScanReport 미연결 지시를 유지한다. 이 표는 표시 의미와 필요한 정보의 제안이며 새로운 공통 DTO·필드 이름·SQL 경로를 정의하지 않는다. 정의 지문의 추가 필드 범위와 저장 계약은 B·C 검토가 필요하다. 초기에는 결과 캐시를 꺼 두며 캐시 TTL·재사용 계약은 이 작은 설정 목록에서 억지로 정하지 않는다.

## 설정 적용과 구현 순서

숫자 설정은 신뢰하는 앱 운영 설정에서만 읽는다. MCP metadata나 모델 출력으로 상한·등급·승인자·Task 식별자를 바꾸지 않는다. 개수·바이트·토큰은 양의 정수, 시간은 유한한 양수로 검증하고 페이지 수신 상한이 조회 누적 상한보다 크지 않게 한다. 0·음수·무한값·형식 오류를 무제한으로 해석하거나 임의 기본값으로 숨기지 않는다. 잘못된 Scanner 설정은 검사 실패 경고로 기록하고 Guard의 fail-closed 규칙은 유지한다.

1. 이 추천안의 추가값을 일괄 결정하고, 승인된 값만 공통 결정 기록에 옮긴다. 문서 작성 요청 자체를 일괄 승인으로 기록하지 않는다.
2. C는 기본 입력 상한·설정 검증, LLM/YARA 실행·부분 실패 집계·취소를 구현한다. 모델 요청의 기존 60초·4,096토큰·재시도 0은 유지한다.
3. A는 목록의 수신 바이트·개수·페이지·시간 제한과 원문 필드 보존을 구현한다. API 세부 변경은 공통 계약 절차로 검토한다.
4. A의 경고/진행 UI와 C 내부 검사 결과를 연결한다. B ScanReport와 영속화는 현재 제외 지시·별도 Store 계약을 따른다.
5. C는 경계·초과·다중 페이지·반복 cursor·부분 실패·취소·원문 비노출과 실제 정의 입력 보존을 검증한다. 관련 I7·I9·I10, T17·T19·S04이며 정의 변경 연결은 T10이다. 미실행 상태와 실제 계수를 기록하고 B가 C 테스트를 리뷰한다.

이 추천안 작성 자체에서 제품 소스·환경 설정·공통 API를 변경하거나 새 모델 요청·YARA scan·성능 테스트를 실행하지 않았다. 후속 사용자 "검증 ㄱㄱ" 요청의 실제 실행 결과는 [검증 보고](c-scanner-operating-validation.md)에 구분해서 기록했다. 관리자 활성화·지문 범위·Guard 집행·B Store/ScanReport 계약은 이 운영 설정 제안이나 실험으로 임의 확정하지 않는다.
