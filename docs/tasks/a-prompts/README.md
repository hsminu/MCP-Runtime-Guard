# A 담당 실행 프롬프트 모음

작성 기준: 2026-10-12, `feat/a-application`에서 확인한 작업 트리. **A의 남은 작업 42개와 B·C에게 전달할 계약 요청 초안 2개**다. 이 문서를 작성한 것과 각 작업을 실행·완료한 것은 별개다.

범위는 MCP Runtime Guard의 **A 역할 전체**다. B의 보안 코어와 C의 저장소·Scanner·보안 유틸·통합 테스트를 A가 대신 구현하는 계획이 아니다. 사용자 요청에 따라 프롬프트만 작성했으며, 아래 구현 작업이나 다른 담당에게 메시지 전송을 실행하지 않았다.

**후속 구현 현황:** 사용자가 A 전체의 가능한 범위와 B 브랜치 활용을 지시한 뒤 A 소유 transport·AGT mock·모델 변환·Runner·Qt 현황/서버 읽기 화면·bridge 커널을 구현했다. 등록 로컬 초안, 승인 일반 텍스트 상세, Task 상태 읽기 화면과 검사·승인 목록·호출 로그의 읽기 화면도 추가했다. 아래 표는 프롬프트 작성 당시 출발점이며 최신 작업별 판정과 검증은 [A 진행 현황](../a-progress.md)을 본다. B/C 공동 계약, 실제 stdio/HTTP·AGT·모델 연동과 C 계수 검증은 별도다.

문서별 용도는 [A 문서 길잡이](../README.md)에 정리했다.

## 2. 사용하는 방법

1. 우선 **A01, A02**를 실행해 현재 상태와 SDK 근거를 확인한다.
2. **A03–A06**에서 계약·환경 결정에 필요한 A의 제안을 준비한다. B·C의 자료가 이미 있으면 검토하고, 없으면 전달 가능한 요구사항을 작성한다.
3. 번호만 보고 일괄 실행하지 않는다. 각 프롬프트의 **선행 조건에 적힌 실제 산출물**이 준비된 작업부터 실행한다.
4. 한 번에 한 작업의 코드 블록을 복사하거나 아래 실행 요청에서 ID를 지정한다. 외부 의존성이 없다는 이유만으로 여러 에이전트를 자동 실행하지 않는다.
5. 같은 파일을 수정하는 작업은 순차 진행한다. 특히 A09–A16은 같은 transport 모듈, A24–A27은 같은 bridge/시작 경로를 공유한다.

복사해서 사용할 짧은 실행 요청:

```text
MCP-Runtime-Guard 저장소에서 docs/tasks/a-prompts/README.md의 공통 실행 규칙을 읽고, 작업 색인에서 A01 프롬프트를 찾아 실행해줘.
선택한 작업만 수행하고 선행 조건과 실제 계약을 먼저 확인해줘. 이미 끝난 부분은 증거를 재사용하고, 미확정 계약을 만들어서 진행하지 마.
다른 담당의 자료가 없으면 독립적으로 가능한 부분과 전달용 요구사항까지 완성하고, 필요한 담당·산출물·재개 조건을 구체적으로 남겨줘.
마지막에는 공통 완료 보고 형식으로 실제 변경과 검증 결과를 보고해줘.
```

`A01`을 원하는 ID로 바꾸면 된다. 모든 코드 블록은 이 README의 규칙을 포함하도록 지시하므로, 전체 공통 규칙을 매번 붙일 필요가 없다.

## 3. 모든 프롬프트에 적용할 실행 규칙

### 3.1 착수와 소유권

- 저장소의 `AGENTS.md`, `AGENT.md`, `README.md`, `docs/team-workflow.md`, `docs/contracts.md`, `docs/tasks/a-application.md`와 해당 설계 절을 읽는다. 먼저 브랜치·작업 트리·기존 사용자 변경을 확인한다.
- 이 프롬프트를 **실행하라는 후속 요청**은 해당 A 작업의 구현 지시다. 프롬프트 파일이 존재하는 것만으로 구현을 시작하거나 모든 작업을 수행하지 않는다.
- 제품 경로는 `src/guard_app/` 기준이다. A는 `adapters/mcp_transport.py`, `adapters/agt.py`, `adapters/model_client.py`, `services/runner.py`, `services/bridge.py`, `ui/*`, `__main__.py`와 해당 단위 테스트·UI T18을 맡는다. 필요한 파일만 만든다.
- B의 `domain/*`, `ports.py`, Guard·Catalog·정책·승인·응답 게이트를 복제하지 않는다. C의 Registry·Scanner·storage·security 유틸·fixture·통합/공격/결함 주입/실험/CI도 대신 만들지 않는다.
- 설정·패키징·lock의 편집 담당은 아직 미정이다. 실제 역할 배정이 확인된 범위만 수정한다. 계약 변경은 B의 제안과 A·B·C 합의 또는 사용자의 명시적 결정을 근거로 한다. 동의가 없는데 합의 표를 채우지 않는다.
- 저장소를 공유할 수 있으므로 다른 사람의 변경을 되돌리지 않는다. 자동 브랜치 전환·reset·기존 환경 삭제·원격 게시·다른 채팅/담당자에게 전송은 이 프롬프트들의 기본 동작에 포함하지 않는다.

### 3.2 계약과 의존성

- 각 작업의 선행 ID는 **관련 산출물을 찾는 위치**다. 앞 작업의 제목이나 체크 표시가 실제 계약·소스·fixture 존재를 대신하지 않는다.
- 미확정 계약 때문에 종속 구현을 할 수 없으면 가능한 조사·A 측 제안·테스트 요구사항을 끝내고 재개 조건을 적는다. 전체 작업을 완료로 표시하거나 보안 경로를 우회하지 않는다.
- 단위 테스트 대역은 합의된 포트에 맞추고 테스트 안에 격리한다. 제품의 보안 판정·Registry·저장소를 대역으로 대체해 실제 연동이라고 표시하지 않는다.
- 설계 문서의 코드와 이벤트 이름은 참고안이다. 실제 시그니처는 합의된 코드와 설치된 패키지 또는 공식 자료로 확인한다. 오래된 후보 버전을 그대로 확정하지 않는다.
- AGT 실제 연결이 불가능한 경우 설계 10.3절의 mock 경로와 실제 실패 근거를 남긴다. 실제 연동과 mock의 검증 결과를 합치지 않는다.

### 3.3 실행 경로와 데이터

- I1–I10을 지킨다. 관리 대상 `tools/call`은 Guard가 평가·예약한 경로로만 실행한다. UI·Runner·AGT가 transport를 직접 호출하지 않는다.
- SDK 호환성 왕복은 C와 합의한 격리된 합성 fixture/harness 안에서 수행한다. 실서버 직접 호출을 허용하는 제품 우회 코드를 만들지 않는다. harness가 없으면 필요한 인터페이스와 재현 조건을 전달한다.
- READ는 격리·분류·상태 커밋 후 `Released`만 공개한다. SEND 결과 불명은 재시도하거나 성공/차단으로 바꾸지 않는다. 최종 Task 상태는 B의 Guard가 결정한다.
- 등급·경계·Task ID·승인자·지문은 신뢰 계약의 출처에서 얻는다. `stdio`, localhost, 서버가 주장한 등급, 모델 출력으로 신뢰를 추정하지 않는다.
- 기본 로그·감사·호출 상세·CSV·오류 보고에는 문서 원문·인증정보·전체 인자·예외 메시지 원문을 기록하지 않는다. 승인 대상 전체 인자는 승인용 메모리 사본을 일반 텍스트로 보여주는 별도 경로다.
- 넓은 예외 처리는 설계의 세 경계 `fail_closed`, `after_dispatch`, `ServerWorker._execute`에 제한한다. A가 다른 모듈에 포괄 catch를 추가하거나 Guard의 예외 판정을 복제하지 않는다.
- 모델 제공자·환경이 미정이면 임의로 선택하지 않는다. 실제 모델 시험은 승인된 환경과 합성 데이터로 수행한다. 비밀 값을 채팅·소스·보고서에 붙여넣지 않는다.

### 3.4 검증과 완료

- A 모듈의 의미 있는 단위 테스트와 T18은 A가 작성한다. 계약·통합·공격·결함 주입·실험은 C가 작성하고 A는 재현·관측·자기 모듈 수정으로 협력한다. C 소유 테스트 리뷰는 B의 책임도 포함한다.
- 관련 I/T/S 번호는 [설계 14장](../../technical-design.md)의 실제 의미와 연결한다. 번호가 없는 화면 요구에 임의의 T 번호를 붙이지 않는다. 스타일 변경에 구현을 그대로 복제하는 테스트를 추가하지 않는다.
- 계수는 `approval_consumed / host_dispatch / wire_tools_call(=wire_post) / receiver_effect`를 구분한다. `initialize`, `tools/list` 등은 `tools/call` 계수와 분리한다. READ의 receiver_effect 의미는 C의 fixture 계약을 따른다.
- 실제 실행 결과만 통과로 보고한다. 화면 상태만 보고 전송 0을 증명하지 않는다. `실행 실패`, `미실행`, `검증 불가`, `합의 대기`를 구별하고 원인을 적는다.
- 도구 접근 제한은 우회하지 않는다. 기존 file URL 차단을 다른 URL/표면으로 바꾸어 우회하지 않으며, 현재 허용된 검증 수단이 없으면 실제 화면 검증은 미실행으로 남긴다. 정적·대역 테스트를 실제 UI 검증으로 부르지 않는다.
- 필요한 검사만 실행하고 새 실패·변경이 없으면 같은 검사를 반복하지 않는다. 검증에 필요한 환경이나 계약이 없다고 무조건 테스트를 통과시키거나 skip을 성공으로 요약하지 않는다.

## 6. 공통 완료 보고 형식

```text
작업 ID / 판정: 완료 | 부분 완료 | 선행 조건 대기
근거: 브랜치·검토한 계약/소스 버전·관련 설계 절·I/T/S
변경: 실제 수정 파일과 그 이유
검증: 실제 명령·환경/정확한 버전·결과·증거 위치
계수: 해당 시 요청별 approval_consumed / host_dispatch / wire_tools_call / receiver_effect
미실행·검증 불가: 항목별 이유와 재현에 필요한 조건
계약: 변경 여부·실제 합의 근거 또는 미확정 제안
다음 단계: 필요한 담당·산출물·재개 조건·바로 수행 가능한 작업 ID
```

코드가 완성되어도 실제 연동 검증·담당 리뷰가 없으면 그 부분은 미완료다. 사용자에게 필요한 결정이 있으면 선택이 필요한 **정확한 항목**을 제시하고, 이미 결정된 내용을 다시 묻지 않는다.

## 7. 협업 요청 초안

[B·C 전달용 프롬프트](07-handoffs.md)는 A03–A06에서 자료가 부족할 때 사용할 초안이다. 실제 전달은 사용자가 요청했을 때만 한다. 별도 채팅 생성, 메시지 전송, 담당자 동의 기록을 이 문서 작성으로 대신하지 않는다.
