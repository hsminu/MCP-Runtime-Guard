# A110 · 정리 미확인이면 잠금을 쥔 채 프로세스 종료

2026-10-27. B6.17 8.1(#37 B 답변)의 A 몫이다. 앱을 닫을 때 정리가 확인되지 않으면 단일 실행 잠금을 먼저 풀지 않고 프로세스를 끝낸다.

## 고친 문제

- 창을 닫으면 Qt 루프는 백엔드 스레드가 끝날 때까지 기다렸다. 그 스레드(`guard-backend`)는 daemon이 아니다. 그래서 백엔드가 멈추면 창은 사라졌는데 프로세스는 계속 남았다.
- `main`은 끝날 때 정리 결과와 관계없이 `app.lock`을 풀었다(A102의 `finally`).
  - 정리가 확인되지 않은 채 잠금을 풀면, 두 번째 실행이 잠금을 잡고 같은 DB를 연다.
  - 그 사이 첫 프로세스의 백엔드나 Codex가 아직 살아 있을 수 있다. REC-01(DB 단일 소유)에 어긋난다.

## 한 일

- `__main__`
  - 창을 닫은 시각부터 브리지 종료 상한(`shutdown_timeout`, 기본 3초)에 `CLOSE_OBSERVATION_S`(5초)를 더한 만큼만 기다린다. 백엔드가 끝나거나 이 시간이 지나면 Qt 루프를 끝낸다.
  - 루프가 끝난 뒤 남은 시간 안에서 백엔드가 끝났는지와 정리가 확인됐는지 본다. 세션 종료처럼 다른 곳에서 앱이 끝난 경우도 같다.
  - 확인됐으면 전처럼 잠금을 풀고 정상 종료한다.
  - 확인되지 않았으면 잠금을 풀지 않는다. 고정 문구 한 줄을 stderr에 남기고 `os._exit(3)`(`EXIT_CLEANUP_UNCONFIRMED`)으로 바로 끝낸다.
    - 잠금 핸들은 프로세스가 끝날 때 OS가 닫는다. 남은 Codex는 C2.12 Job Object가 함께 끝낸다.
    - 정상 종료를 쓰면 인터프리터가 멈춘 백엔드나 작업 스레드(A103 삭제 스레드 포함)를 기다리므로 쓰지 않는다.
  - `_run`이 예외로 끝나면 전처럼 잠금을 푼다(백엔드가 시작되기 전 실패).
- `services/bridge.py`: `cleanup_unconfirmed`, `shutdown_timeout`, `wait_done(timeout_s)`를 추가했다. 모두 읽기 전용이다.

## 검증

- `test_codex_preparation.py`
  - 실제 앱 폴더와 잠금으로 확인했다. 정리 미확인이면 프로세스 종료 함수가 불릴 때 잠금이 아직 잡혀 있고, 종료 코드는 3, 문구는 고정이다.
  - 정리가 확인되면 `main`이 0을 돌려주고 잠금이 풀린다.
  - 수정 전 코드에서 둘 다 실패한다.
- `test_bridge.py`: 정상 종료 뒤에는 `cleanup_unconfirmed`가 False이고, 정리 실패 뒤에는 True다. 두 경우 모두 `wait_done`이 True다.
- 전체 검사(A 브랜치, Windows 11, Python 3.12.15): 단위·contract 4,485개 통과, 1개 생략(기존 경고 5개). Ruff·포맷·mypy(85개 파일) 통과.

## 남은 한계

- Store의 비차단 `close()`와 daemon writer는 B6.13 구현 전이다. 지금 SQLite는 백엔드 루프 스레드에서 닫힌다.
- Qt 창을 띄워 실제로 닫는 종료 흐름(타이머, 루프 종료 뒤 대기)은 단위 테스트로 직접 돌리지 않았다. `main`의 판단과 브리지 상태만 확인했다.
- 실제 프로세스를 강제로 끝냈을 때 잠금이 풀리는지와 다음 시작이 이를 판별하는지는 C의 독립 인수 항목이다(B6.17 AIV).
