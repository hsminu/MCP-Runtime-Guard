# A117 · 겹친 서버 접근 변경이 앞 변경을 잃지 않게 함

2026-10-27. A112에서 찾은 문제를 고쳤다.

## 문제

- `change_server_access`가 현재 정책 문서를 정책 잠금을 잡기 **전에** 읽었다.
- bridge는 `policy_access` 명령을 control 작업자로 보낸다. control 작업자는 기본 4개라, 서버 접근 변경 두 개가 동시에 돌 수 있다.
- 겹치면 뒤의 변경은 잠금을 기다린 뒤 앞의 변경이 저장한 문서가 아니라, 앞의 변경이 대체한 문서로 준비한다. 그 결과는 둘 중 하나다.
  - **조용히 빠짐:** 준비한 결과가 옛 문서와 같으면 "바뀐 것 없음"으로 판단해 저장하지 않고 끝난다. 재현 테스트에서 확인했다. 첫 변경이 `read`를 거부하고 둘째 변경이 다시 허용하면, 둘째는 저장되지 않고 거부가 남는다. 순서가 반대면 사용자가 요청한 거부가 빠진다. 돌려주는 화면은 실제 규칙을 보여 주지만 요청은 아무 표시 없이 빠진다.
  - **저장 뒤 적용 거부:** 결과가 옛 문서와 다르면 옛 문서 기준으로 만든 문서를 저장한다. Guard는 기준 버전이 현재와 다르다며 적용을 거부한다(`previous_policy_version` 검사). 그러면 A104대로 Guard를 닫고 재시작을 안내하는데, 재시작하면 앞의 변경이 빠진 파일을 읽는다. 이 경우는 코드로만 확인했다.
- 화면에서 활성화 대화상자 두 개를 실제로 겹쳐 보낼 수 있는지는 확인하지 않았다(미확정). bridge 단계에서는 겹칠 수 있다.

## 고친 것

- `TaskPolicy.change_server_access`가 정책 잠금을 잡은 **뒤에** 문서를 읽는다. 잠금을 기다린 변경은 앞 변경이 저장한 문서에서 시작한다.
- 거부 순서는 그대로다: 사용 불가 → 허용·거부 겹침 → (잠금) 재시작 필요 → 준비 오류.

## 검증

- 재현 테스트 `test_overlapping_server_access_changes_build_on_each_other`
  - 첫 변경을 저장하는 동안 둘째 변경을 시작하고, 둘째가 잠금에서 기다리는 것을 확인한다.
  - 고치기 전에는 실패했다. 둘째 변경이 저장되지 않았다.
  - 고친 뒤에는 통과하고, 5번 반복해도 통과했다. 저장 순서는 거부 → 허용이고, 둘째 결과는 `read` 허용이며 정책 버전이 바뀐다.
- 전체 테스트 4,624개가 통과했다(skip 1). Ruff, format, mypy(strict)도 통과했다.
