# C6.29 · 목록 변경 알림 뒤 대기 중 호출 차단 (#120, B6.19)

관련: #120(A 재현·C 요청), LIST-01, B6.19, I2·I6·I8·I10, C5.4 계수 하니스.

## 문제

- LIST-01은 `notifications/tools/list_changed`를 받은 서버를 이번 실행에서 PENDING으로 본다. 새 호출은 예약 전에 거부한다.
- 그러나 Guard의 마지막 확인(`_dispatch_and_commit`의 `catalog.aresolve`)과 worker의 실제 `session.call_tool()` 사이는 원자적이지 않았다.
- worker(`ServerWorker._serve`)는 호출을 하나씩 처리하고, `_execute`는 보내기 직전에 등록 상태를 보지 않았다. 그래서 그 사이에 알림이 오면, 이미 예약된 호출이 PENDING이 된 뒤에도 서버까지 갔다.
- A가 #120에서 전송을 붙잡는 방식으로 재현했다. 예약된 SEND와 승인 소비 뒤 SEND 모두 서버 수신·효과가 1이었다.

## 운영 경로 재현 (정지 장치 없음)

- **조건**
  - 같은 서버를 두 Task가 쓴다.
  - 악성 서버가 Task 2의 READ를 받고 0.8초 뒤 목록 변경 알림을 보내고, 0.5초 뒤에 답한다(하니스 `notify-slow`).
  - 그 사이 Task 1의 SEND는 Guard 확인을 통과해 그 서버 worker 대기열에서 READ 뒤에 선다.
- **결과(고치기 전):** stdio·HTTP 각각 10/10 SEND가 서버에 닿았다.
- 공격자가 정하는 것은 자기 서버의 응답 시점뿐이다. 한 Task 안에서는 Task lock 때문에 READ 커밋 뒤에 SEND를 판정하므로 생기지 않는다.

## 수정

1. **worker 전송 직전 확인(A 파일, 사용자 결정으로 C가 수정)**
   - `ServerWorker(dispatch_gate=...)`, `McpTransport(dispatch_gate=...)`
   - `_serve`가 대기열에서 꺼낸 호출을 `_execute`에 넘기기 직전에 동기로 확인한다.
   - 거절이면 한 바이트도 보내지 않고 `DispatchError(NOT_DISPATCHED)`로 끝낸다. `_execute` 진입 전이라 host_dispatch(`on_dispatch`, C 하니스 계수 지점)도 0이다.
   - 제품 조립은 `LiveCheckedRegistry.allows_dispatch`를 넘긴다. "서버가 이번 실행에서 아직 ACTIVE이고, live 지문이 요청 지문과 같은가"를 본다. 알림·서버 실패·지문 불일치면 거절이다.
   - 확인은 `self._active = item` 뒤 `try` 안에서 한다(A 리뷰 제안 2). 확인 함수가 예외를 내면 기존 `finally`가 그 호출을 `WorkerInterrupted`로 끝낸다(SEND 결과 불명·READ 미공개 정지). 예외는 owner 종료로 이어져 남은 대기열도 `WorkerClosed`로 끝난다. Task lock을 쥔 채 끝나지 않는 호출이 남지 않는다.
2. **보내지 않음 확정 결과(B 파일, B 리뷰 필요)**
   - `domain/errors.NOT_DISPATCHED = "NotDispatched"`: worker가 실행 전에 거절했을 때만 쓰는 종류다.
     - `_execute`는 SDK 예외를 클래스 이름으로 옮긴다. 이름이 `NotDispatched`이면 `Exception`으로 바꾼다(A 리뷰 제안 1). `call_tool` 안에서 난 예외는 이미 보냈을 수 있으므로 표지가 될 수 없다(I8).
   - Guard `_contain_post_dispatch`는 이 종류만 `_settle_not_dispatched`로 보낸다.
     - 요청 FAILED·Task RUNNING·`Denied(REG_NOT_ACTIVE)`다.
     - 소비한 승인은 되돌리지 않는다.
     - 읽은 자료가 없으므로 등급은 그대로다.
     - 실패 감사(`after_dispatch`, `NotDispatched`)를 남긴다.
     - 다른 예약 뒤 실패(`WorkerClosed` 등 포함)는 지금처럼 SEND 결과 불명·READ 미공개 정지다.
   - 저장소 `commit_request_failure`는 SEND의 (FAILED, RUNNING)을 `exception_type == NOT_DISPATCHED`이고 사유가 `REG_NOT_ACTIVE`일 때만 받는다. 그 밖의 SEND 쌍은 지금처럼 (UNKNOWN_OUTCOME, UNKNOWN_OUTCOME)뿐이다.

## 한계

- 확인과 SDK의 실제 바이트 쓰기 사이에는 SDK 내부 `await`가 있다. 그 순간에 알림이 처리되면 막지 못한다.
  - 공격자가 조절할 수 있던 창(대기열 대기 + 다른 호출 처리 시간)은 닫혔다. 남은 창은 이벤트 루프 한 번의 스케줄링 수준이다.
  - 완전히 원자적이려면 같은 확인을 A 전송 계층의 `tools/call` 쓰기 직전에도 둔다(후속).
- generation 토큰은 두지 않았다. 이번 실행에서 PENDING은 다시 ACTIVE로 돌아가지 않는다. 재검토 뒤에는 A218 `_reconnect_guard`가 이전 세션을 멈추고 이전 Guard를 닫은 뒤 새로 조립하므로 이전 대기열이 남지 않는다. 같은 실행 안에서 다시 ACTIVE가 되는 경로가 생기면 그때 더한다.
- 붙잡힌 호출이 서버 경계 판정 뒤 같은 실행에서 다른 서버로 바뀌는 경우는 없다. 요청은 서버 ID로 묶여 있다.

## 시험

- **하니스(`tests/unit/c_counting.py`):** stdio·HTTP 서버에 `notify`(바로 알림)와 `notify-slow`(늦은 알림·늦은 응답)를 더했다. HTTP는 GET 알림 스트림으로 보낸다.
- **`tests/unit/test_c_list_changed_race.py`(stdio·HTTP 각각, 8개)**
  - 예약 뒤·전송 전 알림: `Denied(REG_NOT_ACTIVE)`, 요청 FAILED·Task RUNNING, 네 계수 0. 그 DB로 다시 시작해도 B6.8 시작 점검이 통과한다.
  - 승인 소비 뒤·전송 전 알림: 같고, 승인 소비만 1이다.
  - 알림 뒤 새 SEND: 예약 전 거부, 네 계수 0
  - 정지 장치 없는 경로: 같은 결과, 10/10
  - 고치기 전에는 앞의 세 경우가 `xfail(strict, raises=StillSentError)`였다. 커밋 `796a18f`에서 재현을 고정했다.
- **`test_mcp_transport`:** 줄 서 있는 동안 거절된 호출은 `call_tool` 없이 `NOT_DISPATCHED`이고, worker는 계속 동작한다. `dispatch_gate` 형식 검사도 넣었다.
  - A 리뷰 반영 시험 2개(둘 다 고치기 전 코드에서는 실패):
    - 확인 함수가 예외를 내면 꺼낸 SEND는 `WorkerInterrupted`, 남은 호출은 `WorkerClosed`, 닫기는 `WorkerOwnerFailed`로 끝나고, 보낸 것은 없다.
    - `call_tool` 안에서 난 `NotDispatched` 이름의 예외는 `Exception`이다.
- **`test_sqlite_lifecycle`:** SEND (FAILED, RUNNING)은 표지·사유가 둘 다 맞을 때만 받는다(3가지). 기존 잘못된 쌍 거부 시험은 그대로 통과한다.
