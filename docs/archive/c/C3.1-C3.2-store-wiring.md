# C3.1·C3.2 · 실제 Store 연결로 본 단일 writer·명시적 트랜잭션·바인딩 SQL·스키마 제약

2026-10-30 · 관련: 개발문서 11.1·11.2, B6-02(#76, "바인딩 SQL·관계·epoch·revision 독립 검증은 C3.2"), I6.

## 배경

- B 단위 시험은 저장소 함수를 하나씩 본다. C 독립 검증은 다른 쪽에서 본다.
- 제품 조립 Guard와 실제 stdio·HTTP 서버로 시나리오를 돌리는 동안 Store가 **실제로 실행한 SQL 전부**를 기록하고, 그 기록으로 판정한다.
- 시나리오는 T01(ALLOW), T02(ASK 승인), T03(DENY), C5.6 응답 유실이다.

## 한 일

`tests/unit/test_c3_store_wiring.py`(시험 함수 3개, 4건)를 더했다. 제품 코드는 바꾸지 않았다.

- **기록 방법:** `sqlite3.connect`가 만드는 모든 연결에 기록용 연결 클래스를 끼운다. `execute`·`executemany`마다 SQL·바인딩 값·스레드·`in_transaction`을 남긴다. 시험 쪽 읽기 전용 연결(`mode=ro`)은 판정에서 뺀다.
- **C3.1(stdio·HTTP)**
  - Store 연결은 `isolation_level=None`, `check_same_thread=True`로 열린다.
  - 연결의 처음 두 문장이 `PRAGMA foreign_keys=ON`·`PRAGMA synchronous=FULL`이다.
  - DB 파일은 WAL이다(별도 연결로 `journal_mode` 확인).
  - 쓰기 SQL(INSERT·UPDATE·DELETE·REPLACE)은 모두 명시적 트랜잭션 안에서 실행된다. 밖에서 실행된 것은 0건이다.
  - 연결마다 쓰기 스레드는 하나이고, 이벤트 루프 스레드가 아니다.
- **C3.2 바인딩(stdio·HTTP)**
  - DB에 남은 Task·요청·승인 ID 전부가 SQL 문 텍스트에 한 번도 나오지 않는다.
  - 대신 바인딩 값에는 모두 나온다. 기록이 제대로 동작한다는 양성 대조다.
  - 전송 인자 표지(`C32MARK`)는 SQL 텍스트에도 바인딩 값에도 없다. 인자는 원문 대신 digest로만 간다.
- **C3.2 스키마 제약:** 시나리오를 마친 DB를 Store를 닫은 뒤 검사했다.
  - `integrity_check`는 ok, `foreign_key_check`는 0건이다.
  - 외래 키를 켠 별도 연결로 아래 9가지를 직접 쓰면 모두 `IntegrityError`다. 각 시도는 savepoint로 되돌렸다.
    - 없는 Task를 가리키는 요청
    - 같은 Task·순번을 두 번 쓰는 요청
    - 요청 하나에 두 번째 승인
    - 없는 요청을 가리키는 승인
    - 모르는 요청 상태
    - 모르는 요청 종류
    - 범위 밖 등급
    - 등급을 낮추는 승격 이력
    - 원문 모양의 digest
- **C3.2 revision·epoch(API 수준)**
  - 낡은 revision으로 `set_task_status`를 부르면 `STATE_COMMIT_FAILED`이고 Task 행은 그대로다.
  - 다른 epoch로 `submit`하면 DENY이고 계수는 0이다.

**SQL 실행 위치 조사:** `storage`의 `execute`·`executemany` 143곳 중 134곳이 문자열 리터럴이다. 나머지는 모두 모듈 상수에서 나온 값이다.
- 스키마 상수
- `_REQUESTS_V3.replace(...)`
- `PRAGMA user_version={SCHEMA_VERSION}`
- `PRAGMA foreign_keys={원래 값}`
- 리터럴 둘 중 하나를 고르는 `BEGIN`

값을 SQL 문자열에 넣는 곳은 없다. 위 실행 기록 시험이 같은 결론을 실제 경로로 확인한다.

## 결함 주입 확인

`storage/sqlite_store.py`를 한 줄씩 바꾸고 시험을 돌린 뒤 원래 바이트로 되돌렸다(SHA-256 일치 확인).

| 바꾼 것 | 결과 |
| --- | --- |
| 연결의 `isolation_level=None` 제거 | 2건(stdio·HTTP) 실패 |
| `PRAGMA foreign_keys=ON` 제거 | 2건 실패 |

## 남는 것

- `synchronous=FULL`의 실제 내구성(전원 차단)은 관찰하지 않았다. 설정이 적용되는 것까지만 본다.
- writer 연결 하나 밖의 쓰기 경로가 생기는지는 이 기록 시험과 import-linter(`sqlite3`는 `storage`만)가 함께 막는다.
