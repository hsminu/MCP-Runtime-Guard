# C2.13 · 앱 폴더 경로·권한과 Task 폴더 수명

관련: I9, T43 전제, C-CODEX-01, #21 6번, 개발문서 10.4절 "실행 환경과 경로"·11.4절. REC-01의 단일 실행 잠금 중 C 몫(안전 연산)을 함께 넣었다.

## 한 일

- `security/paths.py`를 새로 만들었다. C2.3 `safe_path`도 나중에 같은 모듈에 둔다.
- **폴더 구성**: 루트 `%LOCALAPPDATA%\MCPRuntimeGuard`(환경변수가 아니라 Windows 알려진 폴더 API로 구한다) 아래에 다음을 둔다.
  - `codex\<버전>`, `codex_home`, `tasks\<task_id>`, `config`(`settings.json`은 C2.14)
  - `app.lock`
  - `AppPaths`가 경로만 계산한다. `codex_install(version)`은 `숫자.숫자.숫자` 형식만 받는다.
- **권한**
  - 루트와 관리 폴더 4개에 보호된 DACL을 건다. 현재 사용자 FA, SYSTEM FA이고 하위로 상속(OICI)된다. 그 안의 파일·폴더는 이 둘만 물려받는다. Administrators는 뺐다. 개발문서의 "사용자 전용 권한"을 이렇게 해석한 것이고, 2026-10-26에 사용자가 확인했다.
  - 새로 만들 때는 소유자를 현재 사용자로 적는다. 관리자 권한으로 실행하면 기본 소유자가 Administrators가 되기 때문이다.
  - 이미 있는 폴더는 소유자가 현재 사용자가 아니면 거부한다. 소유자가 맞으면 같은 DACL을 다시 건다. 그래서 넓어진 권한(예: Everyone 읽기)이 시작 때 되돌려지고, 상속받은 하위 항목도 함께 바뀐다.
  - 권한을 건 뒤 DACL을 다시 읽어 확인한다. 허용 ACE만 있어야 하고, 대상이 사용자와 SYSTEM뿐이어야 하고, 사용자는 전체 권한이어야 한다.
- **`prepare_app_folders()`**: 앱 시작 때 한 번 부른다. 순서는 다음과 같다.
  1. 루트 확인과 권한
  2. 단일 실행 잠금. `app.lock`을 공유 없는 핸들로 연다. 두 번째 인스턴스는 `APP_ALREADY_RUNNING`이다.
  3. 관리 폴더 권한
  4. 이전 실행이 남긴 `tasks` 아래 항목을 모두 지운다.
  - 하나라도 실패하면 잠금을 풀고 고정 오류를 낸다. 링크·junction인 루트·관리 폴더는 거부한다. 남은 항목 중 링크는 대상이 아니라 링크만 지운다.
- **`AppFolders`**
  - `create_task_folder(task_id)`: Task ID는 영문·숫자로 시작하고 영문·숫자·`_`·`-`만 쓴다. 128자 이하이고, `CON`·`NUL`·`COM0`–`9`·`LPT0`–`9` 같은 장치 이름은 안 된다. 같은 이름이 있으면 다시 쓰지 않는다(`TASK_FOLDER_EXISTS`).
  - `remove_task_folder(task_dir)`
    - `tasks` 바로 아래의 실제 폴더만 받는다.
    - 읽기 전용 표시만 풀어 다시 시도하고, 그 밖의 실패는 `TASK_FOLDER_CLEANUP_FAILED`다. Codex가 아직 DB 파일을 쥔 경우가 여기에 해당한다. 삭제 뒤에는 폴더가 정말 없는지 다시 확인한다.
    - 안쪽 junction은 따라가지 않는다(Python 3.12 `shutil.rmtree`, 테스트로 확인).
    - `LaunchedProcess.close()`가 True일 때만 부른다.
  - `close()`는 잠금을 푼다. 닫은 뒤에는 `APP_FOLDERS_CLOSED`다.
- **오류:** `AppPathError`는 고정 코드만 가진다. 경로는 넣지 않는다. Windows 전용이다.
- **단위 테스트 38개**(`tests/unit/test_paths.py`): 루트를 임시 폴더로 바꿔 돌렸다.
  - 루트·관리 폴더의 보호된 DACL과 소유자, Task 폴더 파일의 상속 권한
  - Everyone·Administrators가 든 기존 권한이 시작 때 사용자·SYSTEM만으로 바뀜
  - 두 번째 인스턴스 거부와 해제 뒤 재획득
  - 남은 Task 폴더 삭제. 읽기 전용 파일과 안쪽·최상위 junction이 있어도 바깥 파일은 남음
  - 열린 파일이 있으면 시작 거부, 실패한 시작이 잠금을 남기지 않음
  - 링크·파일·상대 경로 루트 거부, 다른 소유자 거부(현재 사용자 SID 조회는 대역), junction인 관리 폴더 거부
  - 잘못된 Task ID 14종, 재사용 거부
  - `tasks` 밖·안쪽 폴더·링크 삭제 거부, 열린 파일 삭제 실패 뒤 재시도 성공
  - 닫은 뒤 사용 거부, 버전 형식, 오류에 경로 없음
  - launcher와 묶은 수명: 폴더 생성 → 실행 → `close()` → 삭제
  - 3번 반복해 모두 통과했다.

## 실제 검증([근거](../evidence/c2.13-app-folders-2026-10-26.json))

제품과 같은 조건이 되도록 TEMP 밖인 `%LOCALAPPDATA%\MCPRuntimeGuard-c213-smoke`를 루트로 썼다. codex.exe 0.162.1은 C6.13 설치본을 `codex\0.162.1`에 복사했다. 처음 쓰려던 npm tarball 사본은 스크래치 정리로 지워져 있었다. 해시는 launcher가 실행마다 대조한다.

- **권한:** 루트와 관리 폴더 4개는 보호된 DACL(사용자·SYSTEM)이었다. 복사한 codex.exe와 Task 폴더는 그 둘만 상속했다.
- **실행:** Task 하나를 실행한 뒤, Task 두 개를 동시에 실행했다. 세 번 모두 결과가 같았다.
  - `sqlite_home`은 각 Task 폴더였다.
  - stdin EOF로 스스로 끝났고(종료 코드 0), `close()`는 True였다.
  - Task 폴더 삭제는 성공했다.
  - TEMP 밖이라 stderr 경고가 없었다(0바이트).
- **CODEX_HOME:** 종료 뒤 `config.toml`·`installation_id`·`model_catalog.json`과 빈 `tmp\arg0` 폴더가 있었고, CODEX_HOME 확인은 통과했다. `tmp\arg0` 보조 파일은 종료 뒤 남지 않았다. C6.16에서 실행 중 내용과 함께 다시 본다.
- **재시작:** 같은 루트로 다시 시작하니 지울 Task 폴더가 0개였고 잠금이 다시 잡혔다. 실험 루트는 지웠다.
- **전체 검사**(main `58afdd4` 병합본, Windows 11, Python 3.12.10)
  - Ruff·포맷·mypy(84개 파일)·`pip check`가 통과했다.
  - contract 41개가 통과했다.
  - 단위 4,252개가 통과하고 1개는 건너뛰었다. 건너뛴 것은 기존 링크 권한 테스트다.

## 남은 한계

- 지운 파일의 디스크 복구 가능성과 Task 실행 중 평문 존재는 C-CODEX-01의 한계 그대로다.
- 권한은 같은 사용자의 다른 프로세스를 막지 않는다. 같은 사용자 권한의 공격자는 위협 모델 밖이다(개발문서 0.3절).
- 단일 실행 잠금은 C 쪽 안전 연산이다. 잠금을 앱 시작 순서에 연결하는 것과 DB 단일 소유를 어떻게 묶을지는 A(REC-01)와 B가 정한다.
- 아직 연결되지 않은 것:
  - DB 파일 위치는 A가 실행 인자로 받는다. 앱 폴더 안에 둘지는 A·B가 정한다.
  - `tools/install_codex.py`의 기본 경로는 아직 `LOCALAPPDATA` 환경변수로 계산하고, 권한은 앱 시작 때 루트에서 다시 맞춰진다. 이 모듈의 `app_root()`로 바꾸는 것은 후속이다.
- A 연결(`SessionPreparation` 어댑터, 다음 단계): 다음 네 가지를 이 모듈과 launcher로 묶는다.
  - 앱 시작: `prepare_app_folders()`
  - `prepare_task`: `create_task_folder` → `CodexLauncher.launch`
  - `confirm_exit`: `close()`
  - `cleanup_task`: `remove_task_folder`

리뷰: B(`security/*`), A(시작 순서·잠금 연결).
