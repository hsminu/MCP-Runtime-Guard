# C2.18 · 실행 이미지 대조와 잠금 뒤 권한 재적용

관련: I9·I11, T22, C2.12·C2.13, #35 B 리뷰(`security/launcher.py` 1번, `security/paths.py` 2번).

## 배경

- **B launcher 1번**
  - launcher는 실행 파일을 쓰기·삭제를 막는 핸들로 연 채 해시를 대조하고, 그 핸들을 프로세스 생성까지 쥔다.
  - 그런데 CreateProcess는 경로 문자열로 파일을 다시 연다. 그래서 상위 경로가 그 사이에 바뀌면 검사한 파일과 다른 파일이 실행될 수 있다.
  - 제안은 재개 전에 실제 이미지와 검사한 핸들의 파일 ID를 대조하는 것이었다.
- **B paths 2번**
  - 루트 DACL은 잠금 전에 다시 걸렸다. 그러면 하위 항목 전체로 전파된다.
  - 그래서 `APP_ALREADY_RUNNING`으로 끝날 두 번째 실행도, 실행 중인 첫 인스턴스의 `codex_home`·`tasks`를 훑고 다시 썼다.
  - 결과 권한은 같아서 보안 문제는 아니었다.

## 실측([근거](../evidence/c2.18-image-check-2026-10-27.json))

- **검사 핸들을 쥔 동안**
  - 파일 이름 변경은 공유 위반으로 막힌다.
  - 상위·그 위 폴더의 이름 변경도 접근 거부로 막힌다.
- **상위 경로에 있는 junction은 대상을 바꿀 수 있다.**
  - 바꾸면 CreateProcess가 다른 파일을 올린다.
  - 이때 프로세스 이미지 이름(`QueryFullProcessImageNameW`)은 junction을 푼 실제 경로다. 그래서 바뀐 쪽 경로가 보인다.
- **우회 재현:** 해시 대조 직후 상위 junction을 다른 Python 설치 폴더로 바꿨다.
  - 대조가 없으면 해시를 검사하지 않은 그 실행 파일이 실제로 돌았다.
  - 대조가 있으면 재개 전에 `LAUNCH_EXECUTABLE_MISMATCH`로 막혔고, 그 실행 파일은 한 줄도 실행되지 않았다.
- **경로 비교 형식**
  - NT 형식으로 비교한다. 이미지 이름은 `PROCESS_NAME_NATIVE`, 핸들 경로는 `VOLUME_NAME_NT | FILE_NAME_OPENED`다.
  - 이 형식이면 일반 경로·junction 경유·8.3 짧은 이름 세 경우 모두 정확히 같았다.
  - DOS 형식이나 정규화 이름은 일부 경우에 달랐다. 그래서 정상 실행이 거부될 수 있다.

## 한 일

- **`security/launcher.py`**
  - `_Job.adopt`는 이제 Job에 넣기만 한다.
  - `launch_process`의 순서는 Job에 넣기 → `_check_image` → `_resume_initial_thread`다.
  - `_check_image`가 보는 두 가지:
    - 이미지 이름이 검사 핸들의 경로와 같은지
    - 그 이름으로 속성만 읽는 핸들을 다시 열어 읽은 파일 ID(`FileIdInfo`: 볼륨 일련번호와 128비트 ID)가 검사 핸들의 ID와 같은지
  - 결과에 따른 처리:
    - 다르면 `LAUNCH_EXECUTABLE_MISMATCH`다. API가 실패하면 `LAUNCH_IMAGE_UNVERIFIED`다.
    - 둘 다 재개 전이다. Job을 닫으면 프로세스는 실행되지 않고 끝난다.
  - **실패 정리 보완**
    - 프로세스를 만든 뒤 실패하면 `_reaped`로 프로세스가 실제로 사라질 때까지 기다린 뒤(상한 2초) stderr 파일을 지운다.
    - 전에는 물려받은 stderr 핸들 때문에 파일이 남을 수 있었다. 대조 전부터 있던 Job·재개 실패 경로도 같은 문제였다.
- **`security/paths.py`**
  - `prepare_app_folders`가 이미 있는 루트를 다루는 방식이 바뀌었다.
    - 잠금 전에는 링크와 소유자만 본다(`_ensure_private_dir(..., reapply=False)`).
    - DACL 재적용과 확인은 잠금을 잡은 뒤에 한다.
  - 루트가 없을 때는 전처럼 보호된 DACL로 만든 뒤 잠근다.

## 남은 한계

- **ID 대조는 혼자서는 하드링크에 속을 수 있다**(#41 B 리뷰 3번).
  - ID 대조는 이미지 이름으로 파일을 다시 열어 읽는다. 그래서 프로세스를 만든 뒤 그 자리에 검사한 파일의 하드링크를 놓으면 ID만은 맞출 수 있다.
  - 이름 대조가 이를 막는다. 이미지 이름이 검사 핸들의 경로와 같으려면 프로세스를 만들 때 그 자리에 검사한 파일이 있었어야 한다. 그런데 그 파일은 핸들이 이름 변경·삭제를 막고, 상위 폴더 이름 변경도 막힌다(실측).
  - 이 전제는 NTFS 실측 기준이다. 다른 파일 시스템은 확인하지 않았다.
- **대상과 위협 모델:** 대상은 앱 폴더(사용자·SYSTEM 전용) 안의 고정 설치본이다. 위 전제를 깨려면 `codex\<버전>`에 쓸 수 있는 같은 사용자 권한이 필요하다. 같은 사용자 권한 공격자는 위협 모델 밖이다.
- 다른 #35 B launcher 의견은 C6.16에서 다룬다. TEMP·TMP를 Task 폴더 아래로 둘지(2번)와 stderr 크기 상한(3번)이다.
