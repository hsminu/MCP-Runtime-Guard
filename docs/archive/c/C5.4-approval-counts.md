# C5.4 · 요청별 계수와 인수 기준 1·2

관련: c-status 인수 기준 1("DENY와 승인 전·거절·만료 ASK에서 dispatch·wire·부작용 0")·2("승인 1회와 더블클릭에서 consumed·dispatch·wire·부작용이 각각 1"), README 검증 목표, I2·I3·I8, NOTIFY-01(만료 확정은 Guard 타이머), 개발문서 12.3(승인 버튼 중복), C6.9(#56).

## 배경

- 인수 기준 다섯 개가 모두 비어 있었다. 1·2는 승인 경로의 계수라, C6.9(#56)에서 만든 계수 하니스(제품 조립 Guard·C `ServerRegistry`·실제로 띄운 stdio·HTTP 서버)를 그대로 쓸 수 있다.
- C6.9는 계수를 도구 이름별로 셌다. 같은 실행에 요청이 여럿이면 어느 요청이 보냈는지 가르지 못한다. C5.4는 계수를 요청별로 잇는 일이다.

## 남는 한계

- Guard 입구(`submit`·`approve`·`reject`·`cancel`)를 직접 부른다. Codex 세션을 거치는 같은 계수는 제품 연결 뒤 T/S 인수(C6.8)에서 다시 본다. Guard가 관리 대상 도구 실행의 유일한 입구라(I1) 계수의 의미는 같다.
- 화면의 더블클릭·Enter 반복은 A의 UI 테스트(`test_runtime`)가 본다. 여기서는 그 결과로 Guard에 같은 승인이 겹쳐 들어와도 1회만 실행되는지를 본다.
- 표지는 테스트가 고른 고유 인자 값이다. 서버 쪽 wire·효과를 Guard `request_id`와 직접 잇는 MCP 필드는 없다.
- HTTP 서버는 테스트와 같은 프로세스다(stdio는 별도 프로세스). `tools/call`이 아닌 HTTP 메시지(초기화·알림·POST 전체 수)는 세지 않는다. C5.3·C5.5에서 다룬다.

리뷰: B(승인 상태·사유 의미), A(하니스의 제품 조립 사용 방식).
