# C4.19 · Registry 쓰기 결과를 모를 때 닫기

관련: I10, #46 B 리뷰 1번, B6.13(SQLite writer 스레드), `ports.RegistryStore` 설명("커밋 실패 시 그 서버를 사용하지 않는다", "COMMIT ACK 불명이면 … 자동 실행/재시도하지 않는다"), [C4.10](C4.10-server-registry.md).

## 배경

- C4.10 `ServerRegistry`는 저장이 성공하면 반환 사본으로 캐시를 바꾸고, 실패하면 이전 사본을 뒀다. `StoreError`를 잡는 곳은 `observe` 하나였다. 그 서버를 이번 실행 동안 PENDING(`_unrecorded`)으로 봤다.
- B6.13은 SQLite 쓰기를 전용 writer 스레드로 옮긴다. 이미 시작한 쓰기는 끝까지 실행하고, 그 뒤에 `CancelledError`를 돌려줄 예정이다. 그러면 DB에는 커밋됐는데 호출자는 반환 사본을 받지 못한다(#46 B 리뷰).
  - `block`: DB는 BLOCKED인데 캐시는 ACTIVE로 남는다. 이번 실행 동안 `status()`가 ACTIVE다.
  - `observe`: DB는 PENDING(정의 변경)인데 캐시는 ACTIVE다. A의 실시간 지문 대조가 막지만 캐시 자체는 틀렸다.
- 지금 SQLiteStore의 async 메서드에는 안에 await가 없어서 실제 저장소로는 재현되지 않는다. 그래서 대역으로 확인한다.

## 한 일

- **`observe`:** 기록 호출이 결과를 돌려주지 않으면(`StoreError`·`CancelledError`·예상 밖 예외) `_unrecorded`에 넣는다(B 제안에서 예외 범위만 넓힘). 그 서버는 이번 실행 동안 PENDING이고 활성화를 거부한다.
- **제어 쓰기**(`register`·`activate`·`block`·`request_review`·`save_reviewed_descriptions`): 저장 호출이 사본을 돌려주지 않으면(`StoreError`·`CancelledError`·예상 밖 예외) 그 서버를 `_stale`("캐시가 DB와 다를 수 있음")로 표시하고 오류를 그대로 올린다.
  - **동기 조회:** `_unrecorded`·`_stale` 서버의 ACTIVE를 PENDING으로 돌려준다. PENDING·BLOCKED는 그대로 둔다. 둘 다 실행되지 않으니 BLOCKED를 PENDING으로 보일 이유가 없다. 전에는 `_unrecorded`이면 BLOCKED도 PENDING으로 보였다.
  - **다시 읽기:** 그 서버의 다음 제어 연산(`register`·`observe` 포함)은 먼저 B `load_registration`으로 행을 다시 읽어 캐시를 맞추고 표시를 푼다. 행이 없으면 캐시에서 뺀다.
  - **`refresh(server_id) -> RegistryEntry | None`(새 입구):** 같은 다시 읽기를 화면이 부른다. `_unrecorded`는 풀지 않는다. 그 서버는 다음 시작에서 다시 대조한다.
  - `load()`는 두 표시를 모두 지운다.
  - **표시 방식:** 예외를 잡지 않고, 저장 호출만 감싼 `try/finally`에서 성공 플래그로 표시한다. 넓은 예외 처리를 세 경계로 제한한 규칙(AGENTS.md)에 걸리지 않으면서 모든 예외를 덮는다(#53 B 리뷰 2번).
  - lock을 기다리다 취소되면 아무것도 쓰지 않았으므로 표시하지 않는다.
- **`_unrecorded`를 쓰지 않은 이유:** `_unrecorded`는 재시작 전까지 활성화를 막는다. revision 충돌(`APPROVAL_RACE`)처럼 평소에 생기는 확실한 실패에도 표시하면 그 서버를 재시작 전까지 올릴 수 없다. 저장소 사유 코드로 "확실한 실패"와 "결과 불명"을 나누지는 않는다. 모든 실패를 결과 불명으로 보고 다시 읽기로 맞춘다.
- **저절로 다시 읽지 않는다.** 결과를 모르는 활성화가 사용자 조작 없이 실행으로 이어지지 않게 하기 위해서다(`RegistryStore`). 다시 읽은 결과가 ACTIVE면 재시작 뒤 `load`와 같고, 연결마다 하는 `observe` 대조도 그대로다.
- **`observe` 무효화 도중 취소:** 남은 도구는 무효화하지 않는다. 캐시는 이미 ACTIVE가 아니고 지문도 바뀌었다. 그래서 그 도구의 대기 승인은 재판정에서 거절된다(#47 표: 지문 변경은 `APPROVAL_STALE`). 코드는 그대로 두고 docstring에 적었다.
- **테스트** `tests/unit/test_server_registry.py` 19개 → 31개
  - **대역:** 실제 SQLiteStore에 위임해 커밋한 뒤 반환 전에 멈춘다. 그동안 호출자 Task를 취소한다(B6.13 동작).
  - **쓰기 5개 각각:** 커밋 뒤 취소하면 캐시가 ACTIVE로 보이지 않고, `refresh`는 DB 사본과 같은 사본을 돌려준다.
  - **취소된 `block`**
    - 상태는 PENDING으로 보인다.
    - 다음 `request_review`는 DB부터 다시 읽는다. 옛 revision은 거부되고 캐시는 BLOCKED 사본이 된다.
    - DB revision으로는 성공한다.
  - **취소된 `register`:** 다시 등록하면 행을 다시 읽고 `REG_SERVER_EXISTS`다.
  - **취소된 `observe`:** 이번 실행 동안 PENDING이고, `refresh` 뒤에도 활성화를 거부한다(`REG_SERVER_UNRECORDED`).
  - **실패한 `block`(옛 revision)**
    - 상태는 PENDING으로 보이고, `refresh` 뒤에는 ACTIVE다.
    - 올바른 revision의 `block`은 성공한다.
    - 기존 "실패해도 캐시 유지" 테스트를 이렇게 바꿨다.
  - 기존 기록 실패 테스트에 "`refresh`가 `_unrecorded`를 풀지 않음"을 더했다.
  - **무효화 도중 취소:** 첫 도구만 무효화되고, 캐시는 DB와 같은 PENDING이다. 다시 확인하면 활성화된다.
  - **lock 대기 중 취소:** 표시하지 않는다(ACTIVE 그대로).
  - **예상 밖 예외:** 저장소가 커밋한 뒤 `RuntimeError` 계열을 던져도, `block`은 PENDING으로 보이고 `refresh` 뒤 BLOCKED다. `observe`는 이번 실행 PENDING·활성화 거부다. 바꾸기 전 코드에서는 이 2개가 실패한다.
  - **고치기 전 코드:** `refresh`만 임시로 넣고 돌리면 6개가 실패한다. 실패한 `block`, 취소된 `block`·`request_review`, 다음 조작의 다시 읽기, 취소된 `register`·`observe`다.

## A·B 연결

- **A:** 제어 연산이 예외로 끝나면, 화면은 `refresh(server_id)`로 현재 행과 revision을 다시 읽어 보여 준다. 실패 뒤 `entry()`는 옛 사본일 수 있다.
- **B:** B6.13의 "커밋 뒤 `CancelledError`" 동작이 들어오면 대역 대신 실제 저장소로 같은 경우를 다시 확인한다.
