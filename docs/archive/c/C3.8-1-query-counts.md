# C3.8-1 · 화면 조회와 요청별 C 계수 대조 (Store 포트까지)

2026-10-29 · 관련: [#76](https://github.com/hsminu/MCP-Runtime-Guard/issues/76) C 조건 6, [#86 C 리뷰](https://github.com/hsminu/MCP-Runtime-Guard/pull/86#issuecomment-6494025432) 2번, [B6.16 기록](../b/B6.16-store-queries.md), C5.4·C5.6, T01·T02·T03.

## 배경

- #86 C 리뷰에서 B6.16 조회(`list_calls`·`get_call`·`list_approvals`)를 C 계수와 대조했다. 그때는 저장소에 넣지 않은 임시 시험이었다.
- 리뷰 결과 두 가지를 B가 #86에서 반영했다.
  - `COMMITTED`의 뜻(결과를 기록함, 성공 여부는 `status`)
  - Task를 지정하지 않은 목록의 같은 시각 순서(감사 rowid)
- 이 기록은 그 대조를 정식 시험으로 옮긴 것이다.
- A 화면이 이 조회를 아직 연결하지 않았다. 그래서 대조 범위는 Store 포트까지이고, C3.8은 열어 둔다.

## 한 일

`tests/unit/test_query_counts.py`를 더했다. 시험 함수 1개를 stdio·HTTP로 돌린다. 하니스는 `c_counting`이다(제품 조립 Guard, C Registry, 실제 서버).

**Task 넷으로 요청 7개를 만든다**

| Task | 시나리오 | 판정 · 상태 · 승인 · 단계 | 계수(승인 소비·dispatch·wire·효과) |
| --- | --- | --- | --- |
| task-1 | 읽기(PUBLIC) | ALLOW · SUCCEEDED · 없음 · DECIDED→DISPATCHING→OBSERVED, 관측 등급 PUBLIC | 0·1·1·1 |
| task-1 | T01 전송(일반 외부) | ALLOW · SUCCEEDED · 없음 · DECIDED→DISPATCHING→COMMITTED | 0·1·1·1 |
| task-2 | 읽기(INTERNAL) | ALLOW · SUCCEEDED · 없음 · …→OBSERVED, INTERNAL | 0·1·1·1 |
| task-2 | T02 전송(승인된 외부) | ASK · SUCCEEDED · CONSUMED · DECIDED→WAITING_APPROVAL→DISPATCHING→COMMITTED | 1·1·1·1 |
| task-3 | 읽기(CONFIDENTIAL) | ALLOW · SUCCEEDED · 없음 · …→OBSERVED, CONFIDENTIAL | 0·1·1·1 |
| task-3 | T03 전송(일반 외부) | DENY · DENIED · 없음 · DECIDED | 0·0·0·0 |
| task-4 | 응답 유실(C5.6 `hang-`) | ALLOW · UNKNOWN_OUTCOME · 없음 · DECIDED→DISPATCHING→COMMITTED | 0·1·1·1 |

**확인하는 것**

- 각 요청의 조회 값과 계수가 위 표와 정확히 같다.
  - 계수 자체를 고정하므로, 0=0만 맞는 대조가 되지 않는다.
- 요청마다 다음 셋이 같다.
  - `DISPATCHING` 단계가 있음 = Guard host_dispatch = wire `tools/call` = 수신 효과
  - `approval_status`가 CONSUMED = DB 승인 소비
- `get_call`의 행이 `list_calls`의 행과 같다.
- 목록의 건수와 순서
  - `total_count` = 행 수 = 7
  - Task를 지정하지 않은 OLDEST가 제출 순서이고, NEWEST는 그 역순이다.
  - `task_id="task-2"`는 그 Task의 두 요청이다.
- 기대 revision
  - PENDING 목록의 `row_revision`보다 1 큰 값으로 승인하면 `APPROVAL_RACE`이고 계수는 모두 0이다.
  - 맞는 값으로 승인하면 Released다.
  - 끝에 PENDING 목록은 비고, HISTORY에는 그 승인 한 행(CONSUMED, revision 2)이 있다.

**READ의 단계**

- 처음 기대값에는 READ에도 COMMITTED를 넣었다.
- 실제는 DECIDED→DISPATCHING→OBSERVED였다. B `_call_stage`에서 READ의 결과 기록은 분류·등급 반영을 한 번에 커밋하는 `OBSERVED` 감사(I4)이고, `REQUEST_*`·`SEND_COMPLETED`는 쓰지 않는다.
- 그래서 결함이 아니라 기대값이 틀린 것으로 보고 기대값을 고쳤다.

## 돌연변이 확인

B `_call_stage`를 하나씩 바꾸고 시험을 돌린 뒤 원래 파일로 되돌렸다. 되돌린 뒤 SHA-256 일치를 확인했다.

| 바꾼 것 | 결과 |

| `CONSUMED` 감사를 DISPATCHING으로 보이지 않음 | 2건(stdio·HTTP) 실패 |
| `REQUEST_*` 감사를 COMMITTED로 보이지 않음 | 2건 실패 |
