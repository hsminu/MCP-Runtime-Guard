# C3.5·C3.6 · Store 연산 도중 프로세스 강제 종료와 잠금 대기 실측

2026-10-30 · 관련: B6-01(#76, "부분 상태 0을 Store 연산 단위로 센다, C 독립 결함 주입 인수"), B6-03("잠금 대기 등 시간값은 C 측정 뒤 확정"), B6.9(#89), 개발문서 11.5 REC-02, I4·I6.

## 배경

- **B 단위 시험:** `test_atomic_approval_store`·`test_sqlite_lifecycle`이 같은 경계에서 SQL 오류를 일으킨다. 이때는 B 코드가 롤백을 실행해 부분 상태 0을 만든다.
- **C 인수의 차이:** 롤백 코드가 돌 틈 없이 **프로세스 자체가 끊길 때**를 본다. SQLite 저널(WAL)과 다음 시작의 복구만으로 원자성이 지켜져야 한다.
- **이미 있는 C 근거:** 동시 승인 중복 소비는 C5.4가 실제 서버로 봤다. 연속 2회·동시 2회·5회 승인 모두 승인 소비·dispatch·wire·효과가 각 1이었다. 이번에는 새로 만들지 않았다.

## 한 일

`tests/unit/c_store_kill.py`(자식 프로세스)와 `tests/unit/test_c3_store_kill.py`(시험 함수 2개, 6건)를 더했다. 제품 코드는 바꾸지 않았다.

**자식 프로세스**
- B 시험 도우미(`test_sqlite_decisions`·`test_sqlite_lifecycle`)로 연산 직전 상태를 만든다.
- 연산 하나를 돌리면서 그 트랜잭션 안의 SQL을 센다.
- 지정한 문장 직전·직후에 `os._exit(86)`으로 끝낸다.

**순서(연산마다)**
1. 기준 실행: 끊지 않고 연산 안의 SQL 순서와 연산 전·후 상태(Task·승격 이력·요청·승인·감사·순번 표 전체)를 얻는다.
2. 쓰기·트랜잭션 문장(BEGIN·INSERT·UPDATE·COMMIT)마다 직전·직후에서 끊는다.
3. 끊긴 DB를 다음 시작처럼 열어 상태를 읽는다. COMMIT이 실행되기 전에 끊겼으면 "전"과, 실행된 뒤면 "후"와 **표 전체가 정확히 같아야** 한다.
4. B6.8 명시 시작으로 복구한다. 미해결·격리는 0이어야 한다. 살아 있는 승인(PENDING·APPROVED)과 실행 상태 Task(READY·RUNNING·WAITING_APPROVAL)가 남지 않아야 한다. 소비 커밋 뒤에 끊겼으면 예약된 READ는 WITHHELD여야 한다(REC-02).

**C3.6 잠금 대기 실측**
- 다른 연결이 `BEGIN IMMEDIATE`로 쓰기 잠금을 쥔 동안 Store 쓰기(`create_task`)를 5회 시도했다.
- 쓰기는 중앙 1.172초(최소 1.156, 최대 1.187)를 기다린 뒤 `StoreError`로 끝났다. 1.172초는 busy timeout 1000ms에 writer 왕복 시간이 더해진 값이다.
- 같은 동안 WAL 읽기(`load_task`)는 최대 0.016초로 막히지 않았다.
- 잠금이 풀리면 같은 Store로 다시 쓸 수 있었다. 잠금 대기 실패가 Store를 닫지 않는다.
- B6-03의 미측정 제안값 1000ms는 이 측정으로 "1초 안팎에서 고정 실패, 읽기 영향 없음"을 확인했다. 확정은 B·사용자 결정이다.

## 결함 주입 확인

- `consume_and_reserve`의 승인 UPDATE 뒤에 `COMMIT`·`BEGIN IMMEDIATE`를 끼워, 한 연산을 트랜잭션 둘로 쪼갰다.
- 그러면 소비 시험이 실패했다. 중간 COMMIT 뒤에 끊긴 상태가 연산 "전"과 다르다(반쪽 상태).
- 시험 뒤 원래 바이트로 되돌리고 SHA-256 일치를 확인했다.

## 남는 것

- **전원 차단 수준 내구성:** `synchronous=FULL`·fsync가 실제로 디스크에 내려가는지는 관찰하지 않았다. 프로세스 종료까지만 본다.
