## 계획과 다르게 확인된 것

1. **판정기 일반 예외는 Task를 정지하지 않는다.** `INTERNAL_ERROR` DENY이고, Task 정지는 판정기가 `CancelledError`를 던질 때뿐이다(`guard._pre_dispatch_failure`, `ports.AccessChecker` 설명). 둘 다 I6("DENY 또는 작업 정지")을 만족한다. #47 본문의 "판정기 예외(CancelledError 포함)는 … 그 Task만 정지"는 일반 예외에는 맞지 않으므로, 코드와 `ports.py` 설명을 기준으로 본다.
2. **승인 대기 중 서버 차단은 `REG_NOT_ACTIVE`다.** 승인 재판정이 등록 상태를 다시 보고 거부한다. `APPROVAL_STALE`은 판정기 실행 도중 Registry가 바뀐 경우이고 B `test_sync_access`가 본다.
3. **정책 변경은 대기 승인을 취소한다.** `apply_policy_change`가 Task를 POLICY_CHANGED로 정지시키면서 대기 승인을 CANCELLED로 만든다. 그 뒤 사람의 승인은 이미 처리된 승인에 닿아 `APPROVAL_RACE`다.

## 남는 한계

- HTTP 서버는 테스트와 같은 프로세스·같은 이벤트 루프다. 계수는 서버의 ASGI 층과 도구 함수에서 세서 Guard 쪽 계수와 섞이지 않지만 별도 프로세스는 아니다. stdio 서버는 별도 프로세스다.
- 판정기 예외·잘못된 반환·async 판정기는 `AccessRulesChecker.check_access`를 바꿔 끼워 만든다. 실제 판정 함수(`core.access_rules`, 순수 함수)가 이런 값을 내는 경로는 없다.
- Guard 입구(`submit`·`approve`)를 직접 부른다. 실제 Codex 세션과 모델을 거치는 인수는 C 인수 기준에서 따로 한다.
- 옛 `AGT_*` 행을 새 코드로 읽는 저장소 해석은 B2.10 뒤 contract 테스트에서 본다.
