# C4.10 · Registry 본체(C4.11·C4.18 포함)

관련: I10, T10, 개발문서 10.1절, 2026-10-15 "DB ACTIVE만으로 실행하지 않는다" 결정, B6-06 `RegistryStore`(#32), C4.12 지문.

## 배경

- B의 `RegistryStore`(SQLite 구현)는 등록 레코드를 저장한다. C가 지킬 순서도 정해 뒀다.
  1. 저장
  2. 반환 사본으로 동기 캐시 즉시 교체(사이에 await 금지)
  3. 바뀐 도구마다 `GuardService.invalidate_tool`
- Guard·Catalog는 `ports.Registry`의 동기 조회(`registration`·`status`·`fingerprint`)를 쓴다. 그런데 C 구현이 없어서 제품 조립(`ProductInputs.registry`)을 만들 수 없었다.
- A의 `LiveCheckedRegistry`는 연결 직후 실제 목록과 등록 지문을 대조해서 이번 실행 동안 맞지 않는 서버를 막는다. 등록 쪽을 PENDING으로 내리는 것은 C 경로다(10.1, A 문서).

## 한 일

- **`services/registry.ServerRegistry`**
  - **동기 조회(`ports.Registry`):** 캐시에서 답한다.
    - `fingerprint(tool)`은 같은 서버·같은 이름의 등록 지문이다.
    - `entry(server_id)`는 화면용 저장 사본이다(최근 검사·revision). 실행 허가가 아니다.
  - **제어:** 하나의 `asyncio.Lock`으로 직렬화한다. 저장이 성공하면 반환 사본으로 캐시를 바로 바꾸고, 실패하면 이전 사본을 둔다. 저장소 오류는 B의 `StoreError`(고정 사유)를 그대로 올린다.

    | 연산 | 하는 일 |
    | --- | --- |
    | `load()` | 앱 시작 때 `list_registrations`로 복원한다. DB의 ACTIVE만으로는 실행하지 않는다. A의 대조가 끝나기 전에는 `LiveCheckedRegistry`가 지문을 None으로 막는다 |
    | `register(server_settings, listing)` | 신규 서버를 PENDING으로 등록한다(C4.11). 아래 "등록 레코드" 참고. 이미 있으면 `REG_SERVER_EXISTS` |
    | `observe(server_settings, listing, invalidate_tool=None)` | 연결 직후 대조(I10). 아래 참고 |
    | `activate(server_id, *, expected_row_revision, reviewed_by, reviewed_scan_id=None)` | 사용자 확인 뒤 ACTIVE(C4.11). 넘기는 지문은 캐시의 등록 지문, 곧 사용자가 화면에서 본 것이다. 이번 실행에 대조를 기록하지 못한 서버는 `REG_SERVER_UNRECORDED`로 올리지 않는다 |
    | `block`·`request_review`·`save_reviewed_descriptions` | 저장소에 넘기고 캐시를 교체한다 |

  - **등록 레코드(`register`)**
    - 설정 파일의 서버 레코드(경계·도구 종류·인자)와 실제 목록(스키마·지문)을 합친 것이다(10.1).
    - 목록에는 있지만 설정에 종류가 없는 도구는 `OTHER`로 등록한다. 정책은 `TOOL_UNSUPPORTED`로 거부하고 Catalog는 노출하지 않으므로, 지문 변경만 잡고 쓰이지 않는다.
    - 등록에서 빼면 A의 대조가 "등록에 없는 도구"로 그 서버를 항상 막는다.
    - 설정에만 있고 목록에 없는 도구는 등록하지 않는다.
  - **연결 직후 대조(`observe`)**
    - 설정 경계가 등록과 다르면 `REG_SETTINGS_MISMATCH`다.
    - 목록이 미완료·형식 오류면 쓰지 않고 `RegistryError`다. A의 대조가 그 서버를 이번 실행 동안 막는다.
    - 그 밖에는 `record_fingerprint_change`를 부른다. 바뀐 것이 있으면 ACTIVE가 PENDING이 된 사본으로 캐시를 바꾸고, 바뀐 도구마다 `invalidate_tool`을 부른다.
    - Guard가 아직 없는 앱 시작 직후에는 대기 승인도 없으므로 `invalidate_tool=None`으로 둔다.
    - **기록이 실패하면** 그 서버를 이번 실행 동안 PENDING으로 보고 `StoreError`를 올린다. `RegistryStore` 설명의 "커밋 실패 시 그 서버를 사용하지 않는다"를 따른 것이다.
  - **서버 ID(C4.18):** `register`·`observe`는 `ServerSettings` 검증과 별도로 B의 `valid_server_id`를 다시 쓴다(`REG_SERVER_ID_INVALID`).
  - **그 밖의 오류**(서버 텍스트 없음): `REG_SETTINGS_INVALID`, `REG_SERVER_UNKNOWN`, `REG_TOOL_SCHEMA_INVALID`, `REG_TOOL_INVALID`, `REG_REGISTRATION_INVALID`, C4.12의 목록 코드
- **`tests/unit/test_server_registry.py`**(19개): 가짜가 아니라 B의 실제 `SQLiteStore`(임시 DB)로 돌린다. 설정은 B와 같은 엄격 JSON 검증으로 만든다.
  - 등록 내용: 경계, 종류·인자, `OTHER`, 스키마·지문, 저장 사본 = 캐시
  - 중복 등록, 서버 ID 재검사, 설정 아닌 입력, 쓸 수 없는 목록 → 아무것도 저장 안 함
  - 활성화가 본 지문으로 올림. 낡은 revision은 `StoreError`이고 캐시는 그대로
  - 재시작 복원
  - 변경 없는 대조: 쓰기 없음, 캐시 같은 객체, 무효화 0회
  - 정의 변경·도구 삭제·도구 추가(`OTHER`): ACTIVE→PENDING, 바뀐 도구별 무효화
  - 미완료 목록은 기록 안 함, 경계 불일치·모르는 서버
  - 기록 실패: DB는 ACTIVE여도 캐시는 PENDING, 활성화 거부, 다음 `load`에서 다시 대조
  - 차단·재검토·검토 설명
  - 제어 연산 직렬화: 대조 중 들어온 차단은 대조가 끝난 뒤 실행되고, 올라간 revision 때문에 실패한다
  - **B Catalog와 맞물림:** 등록 → 활성화 → `load_profile_settings`에서 설정에 있는 도구만 보임(`docs__read`·`docs__send`, `OTHER` 제외) → 정의를 바꿔 `observe` → 다시 읽으면 도구 목록이 빔
  - 오류에 서버 텍스트 없음

## 남은 것과 A·B에 정할 것

- **A 연결**
  - 앱 시작: `ServerRegistry(store)` → `await registry.load()` → `ProductInputs.registry`
  - `assemble_guard`에서 transport 연결 뒤, `seal` 전에 서버마다 `await registry.observe(settings, transport.tool_listing(id))`를 부른다. `RegistryError`·`StoreError`인 서버는 이번 실행에 쓰지 않는다. A의 대조도 그 서버를 막는다.
  - 등록 화면: `register` → (C4.9 검사) → 사용자 확인 → `prepare_server_access_change` → 설정 저장 → `apply_policy_change` → `activate` 순서다(`RegistryStore` 설명).
  - (선택) `live_fingerprints`가 C4.12 `listing_fingerprints`를 쓰면 등록과 대조의 계산이 한 곳이 된다.
- **설정에서 도구 종류를 바꾸는 경로(A·B와 정해야 함)**
  - 등록된 도구의 종류나 인자를 설정에서 바꾸면 다음 시작 때 Catalog가 "등록과 설정 불일치"로 설정 읽기를 거부한다. 그래서 `observe`까지 가지 못한다.
  - C 제안:
    - A: 설정 변경 흐름에서 C의 갱신 입구를 불러 등록을 PENDING으로 내리고 사용자가 다시 확인하게 한다.
    - B: 저장 연산을 정한다. 지금 `record_fingerprint_change`를 다시 쓰면 감사 사유가 "지문 변경"(`TOOL_FINGERPRINT_CHANGED`)으로 남는다.
  - 정해지면 C가 입구를 더한다.
- **C4.9:** 검사 결과(`record_scan_report`)를 등록에 붙이는 일은 Scanner 번역과 함께 한다.
- **진행 중 예약·전송 경쟁(S03):** `RegistryStore` 설명대로 이 순서만으로는 해결되지 않는다. C6.10 결함 주입에서 본다.

리뷰: B(`services/registry.py`, `RegistryStore` 사용 순서), A(연결 방법, 종류 변경 경로 제안).
