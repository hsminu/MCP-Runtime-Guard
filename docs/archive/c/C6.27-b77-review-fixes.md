# C6.27 · B7.7 B 리뷰 반영: 파일 서버 fd 누수, L2 두 번째 요청 도구 목록, Semgrep 예외 위치, 하니스 대역 범위

관련: [#102 B 리뷰](https://github.com/hsminu/MCP-Runtime-Guard/issues/102), [C2.11](C2.11-file-server.md), [C6.14](C6.14-codex-l2.md), [C2.9](C2.9-ci-static-checks.md), C5.4.

B 결함 2건(D1·D2)은 C가 main `13d5da5`에서 같은 결과로 재현했다. 참고 2건(N1·N2)도 반영했다. 위험 R1(지문 변경과 진행 중인 예약·소비·전송의 원자 경계)은 C 결함이 아니고 B6.19(3인 합의 대기)로 남는다.

## 1. B77-D1 · 파일 서버가 READ마다 CRT fd를 남김

- **증상:** `_read`가 핸들을 `msvcrt.open_osfhandle`로 CRT fd에 등록하고 `closefd=False` 파일 객체로 읽었다. 핸들은 `_opened`가 `CloseHandle`로 닫지만 CRT fd 슬롯은 풀리지 않았다.
- **C 재현:** 20번 읽으면 다음 fd가 3 → 23. 8,190번째 읽기에서 `OSError(errno=24)`가 `_call`·`handle_line` 밖으로 나가 서버 프로세스가 끝난다. 내용이 새지는 않는다. 가용성 문제다.
- **수정:** CRT fd를 만들지 않고 `ReadFile`로 핸들에서 직접 읽는다(`_read_handle`). 핸들을 닫는 것은 `_opened` 하나다. `closefd=True`로만 바꾸면 fd와 `_opened`가 같은 핸들을 두 번 닫으므로 택하지 않았다.
  - `ReadFile` 실패는 `FILE_READ_FAILED`다.
  - `_call`은 예상 밖 `OSError`도 고정 코드(`read_file`은 `FILE_READ_FAILED`, 목록은 `FOLDER_READ_FAILED`)로 답하고 서버를 계속 둔다. OS 메시지는 경로를 담을 수 있어 싣지 않는다. 새 코드는 만들지 않았다.
- **시험:**
  - 50번 읽어도 다음 fd가 그대로다. 수정 전 코드에서 실패한다.
  - `ReadFile` 실패와 경로 표지를 담은 `OSError`가 고정 코드로 오고, 표지가 응답에 없고, 다음 읽기는 정상이다.
- **수정 뒤 실행:** 10,000번 읽기에서 오류 0, 다음 fd 그대로(3 → 3).

## 2. B77-D2 · L2가 두 번째 모델 요청의 도구 목록을 보지 않음

- **증상:** `input.additional_tools`의 허용 집합 대조가 첫 요청에만 있었다. 두 번째 요청에 `exec_command`를 더하거나 블록을 지워도 실패 코드가 없었다(C 재현 같음). 실제 Codex 0.162.1이 그렇게 한다는 근거는 아니고 L2 판정의 빈틈이다(I11·T22·T39).
- **수정:** 모든 요청의 `input`을 같은 허용 집합(`_OFFERED_TOOLS`)과 대조한다. 블록이 없거나 둘 이상이어도 `L2_TOOLS_UNEXPECTED`다.
- **시험:** 변형 2개(두 번째 요청에 도구 추가, 블록 삭제). 수정 전 코드에서 둘 다 실패한다.
- **실제 실행:** 실제 codex.exe 0.162.1 L2 5회 모두 통과. 실제 두 번째 요청도 같은 블록을 보낸다.
- **바뀌지 않은 것:** 두 번째 요청의 메시지 순서는 여전히 보지 않는다. 금지 프롬프트 표지·최상위 `tools`·`instructions` 검사는 전부터 모든 요청에 있다.

## 3. B77-N1 · Semgrep 예외 검사가 위치를 보지 않음

- **수정:** `tools/ci/check_semgrep_exceptions.py`가 규칙·파일·결과를 감싼 함수(클래스 안이면 `클래스.함수`)로 센다. 줄 번호는 보지 않아 코드가 위아래로 움직여도 그대로다. Windows의 `\` 경로도 `/`로 읽는다.
- **확인:**
  - 지금 결과는 `SEMGREP_EXCEPTIONS_OK 10`이다. 함수가 대장 SG-01–04(`SQLiteWriter._execute`, `SQLiteStore._transaction`, `defang_scanner_text`, `BackupTarget.discard`)와 설계 경계(`fail_closed` 2, `after_dispatch` 3, `ServerWorker._execute`)와 같다.
  - B 재현처럼 결과 줄을 모두 9000번대로 옮기면 실패한다.
  - 단위 시험 5개(`test_semgrep_exceptions_check.py`).
- **남은 것:** 같은 함수 안에서 다른 `except`로 옮긴 것은 잡지 않는다. 그 함수들은 승인된 경계라 리뷰 범위로 둔다.

## 4. B77-N2 · 계수 하니스의 대역 범위

- `tests/unit/c_counting.py` 머리말에 적었다.
  - `next_call_seq`는 메모리 계수기, `failure_audit`는 목록 추가다.
  - 결과는 승인·전송 계수(C5.4·C5.6)의 근거다.
  - 영속 call_seq와 허용된 실패 감사의 내구성(B6.8)은 C3.10·B6.8 C 인수로 따로 본다.

## 5. 정리

- C6.14-2(#98)에서 이름을 바꾼 C 쪽 시험 `test_a_l2_failure_codes_are_the_c_constant`를 지웠다. A174 `test_a151_l2_startup.py::test_l2_codes_reexport_the_c_constant`가 네 곳을 같은 객체로 본다.
- [C6.14-2 기록](C6.14-2-l2-real-runs.md)은 A 사본을 "이 PR에서 바꿨다"고 적었다. 실제로는 #99(A174)가 먼저 병합됐고, #98의 충돌은 A 쪽 파일로 해소됐다. 결과 코드는 같다. 병합된 기록이라 고치지 않고 c-status C6.26 줄에 적었다.
