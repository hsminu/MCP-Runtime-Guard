# C2.8 · 로그 마스킹 마지막 방어와 감사 원문 점검

관련: I9("문서 원문·인증정보·전체 인자·예외 메시지 원문을 로그로 내보내지 않는다"), S04, 개발문서 13.2절 `security/redact.py`(마스킹 필터는 2차 방어), [C2.1](../tasks/c-cisco-luna-connection.md)(Scanner 호출 중 OpenAI SDK 로그 차단), A `adapters/mcp_transport/sdk_logging.py`(SDK 작업 범위의 MCP 로그 제거).

## 배경

- 1차 방어는 원문·인자를 로그에 넘기지 않는 것이다. `guard_app`에는 지금 로그 호출이 없다.
- 이미 있던 2차 방어는 두 범위만 덮었다.
  - Scanner 호출 중 OpenAI SDK 로그(C2.1)
  - A transport의 SDK 작업 범위 안 MCP 로그(A, 레코드 생성 함수 감싸기)
- 그 밖은 비어 있었다.
  - 범위 밖 라이브러리 로그: litellm은 자기 로거에 handler를 붙이고 전파를 끈다.
  - asyncio의 "Task exception was never retrieved": 메시지에 예외 repr을, traceback에 예외 메시지를 싣는다.
  - 처리되지 않은 예외: `sys`·`threading` excepthook이 traceback 원문을 stderr로 쓴다.
  - `warnings`
- 앱은 로그 handler를 정하지 않아서, WARNING 이상은 Python 기본 출력(stderr)으로 간다.

## 한 일

- **`security/redact.py`**
  - **`install_log_redaction()`:** 앱 시작 때 한 번 부른다. 레코드 생성 함수를 한 번만 감싸서, 레코드가 만들어질 때 바로 정리한다. 그래서 root handler와 라이브러리가 직접 붙인 handler 모두 정리된 레코드만 받는다.

    | 레코드 | 남는 것 |
    | --- | --- |
    | `guard_app` 로거 | 메시지를 만든 뒤 인증정보 모양을 가리고 500자로 자른 것. 형식 오류면 `LOG_FORMAT_INVALID` |
    | 그 밖의 로거(SDK·라이브러리·asyncio·`py.warnings`) | `LOG_WITHHELD`. 라이브러리는 서버 응답·요청 원문을 메시지에 넣기도 한다(예: mcp `Raw result: ...`, `Message was: ...`) |
    | 모든 레코드의 예외 | 형식 이름만 `[ValueError]`처럼 붙인다. 메시지·traceback·stack은 버린다. 이름이 ASCII 식별자·64자 이하가 아니면 `[Exception]`이다(감사 `exception_type`과 같은 규칙) |

  - **처리되지 않은 예외도 로그로 보낸다.** `sys.excepthook`·`threading.excepthook`·`sys.unraisablehook`이 `guard_app.uncaught` 로거로 `UNCAUGHT_EXCEPTION`·`UNCAUGHT_THREAD_EXCEPTION`·`UNRAISABLE_EXCEPTION`을 남긴다. `logging.captureWarnings(True)`로 warnings도 같은 규칙을 따른다.
  - **`mask_secrets(text)`:** 이름은 남기고 값만 `***`로 바꾼다.
    - 가리는 것: `authorization`·`bearer`·`token`·`api_key`·`secret`·`password` 뒤 값(`=`·`:`·JSON 따옴표·공백, `Bearer`/`Basic` 접두어 포함), `sk-`로 시작하는 키, `TEST_SECRET_*` 표지
    - 그대로 두는 것: `tokenizer`·`passwords: 3`처럼 이름이 다른 단어
  - **handler는 정하지 않는다.** 로그를 어디에 쓸지는 A 몫이다.
  - **A `sdk_logging`과 어느 순서로 감싸도 된다.** SDK 범위 안에서는 둘 중 하나가 지운다.
  - **이미 있던 Scanner 범위 필터(C2.1)는 그대로다.**
- **구조화 감사 점검(코드 확인)**
  - `storage/sqlite_store.py`에서 `audit_events.detail`을 만드는 곳은 7곳이다. 키는 다음뿐이다.
    - ID·개수: `server_id`·`row_revision`·`scan_id`·`tool_count`·`changed_count`·`call_seq`·`run_id`·`epoch`
    - 복구 개수 6종
    - `exception_type`(형식 이름), `source`(고정 문자열 `guard_expiry`)
  - 행의 다른 열은 ID·사건 종류·이유 코드·등급·시각이다. 인자·결과·문서 본문을 담는 열은 없다.
  - 실제 실행에서 원문이 저장되지 않는지(DB 전체의 표지 0)는 C3.7(검증 세션)이 본다.
- **테스트** `tests/unit/test_log_redaction.py` 15개
  - `guard_app` 로그의 인증정보 가림(API 키·Bearer 토큰·표지), 예외는 형식 이름만(traceback 없음)
  - 동적으로 만든 예외 형식 이름(공백·비ASCII·65자, 표지 포함)은 `guard_app`·라이브러리 로그 모두 `[Exception]`. 고치기 전 코드에서는 3개 모두 실패
  - 라이브러리 로그 제거: `httpx`, mcp `Raw result`
  - 라이브러리가 직접 붙인 handler(전파 끔)도 정리된 레코드를 받음
  - 500자 자르기, 형식 오류
  - 처리되지 않은 예외 3종: 스레드, `sys.excepthook`, `__del__` unraisable. stderr에 표지 0
  - warnings 제거
  - **실제 asyncio 경로:** 실패한 작업을 결과를 읽지 않고 버렸다.
    - 대조군: 방어를 끄면 표지가 실제로 출력된다.
    - 방어를 켜면 `asyncio|ERROR|LOG_WITHHELD [ValueError]` 한 줄만 남는다.
  - A `sdk_logging`과 함께 설치해도 SDK 범위의 표지가 나가지 않음, 다시 불러도 한 번만 감쌈
  - 마스킹 모양 9가지

## A 연결

- 앱 시작(`__main__` 또는 제품 조립 맨 앞)에서 `install_log_redaction()`을 한 번 부른다.
- 로그 handler(파일·화면)를 두게 되면 이 함수 뒤에 붙이면 된다. 정리는 레코드를 만들 때 끝난다.

## 남는 한계

- **로그가 아닌 출력은 막지 않는다.** 라이브러리의 `print`(C-CISCO-02)와 `sys.stderr` 직접 쓰기, 자식 프로세스 stderr(C2.6이 서버별 파일로 격리)가 그렇다.
- **마스킹은 모양 기반이다.** `guard_app` 로그에 문서 원문을 넘기면 가려지지 않는다. 1차 방어(넘기지 않기)가 우선이다.
- **asyncio 루프의 예외 처리기를 바꾸는 코드:** A bridge는 자기 처리기를 두지만, 그 경우에도 로그로 가는 것은 같은 규칙을 따른다.
