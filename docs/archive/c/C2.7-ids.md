# C2.7 · ID·토큰 생성 단일 지점

관련: 개발문서 13.1(ID·토큰 생성은 `security/ids.py`, 다른 곳의 `random.*`은 Semgrep 경고)·13.2 `new_id` 예시. c-status 항목: "암호학적 난수, 비밀값 누락은 전용 예외".

## 점검 결과(바꾸기 전)

- `src`·`examples`의 모든 난수는 이미 암호학적 난수였다(`uuid4`·`secrets`·`os.urandom`). `random` 모듈은 쓰는 곳이 없었다.
- `security/ids.py`가 없어서 파일 12개(C 6개, A 6개)가 ID·토큰을 각자 만들었다.
- 승인 ID는 추측돼도 쓸 수 없다. 승인·거절은 A 화면이 쥔 `HumanControl`로만 부를 수 있다.
- L2 가짜 모델(`codex_l2.MockModel`)은 인증 헤더를 `!=`로 비교했다. 루프백·실행마다 새 토큰이라 영향은 작다.

## 한 일

- `security/ids.py`를 만들었다. 운영체제 암호학적 난수(`secrets`)만 쓴다.
  - `new_id(prefix)`: `<prefix>-<소문자 16진수 32자리>`(128비트). 접두어는 소문자로 시작하는 소문자·숫자 1–32자다. 아니면 `ValueError`다.
  - `new_suffix()`: 접두어 없는 16진수 32자리. 임시 파일·로그 파일 이름에 붙인다.
  - `new_token(nbytes=32)`: URL 안전 base64 비밀 토큰. 16–64바이트만 받는다.
  - `token_matches(expected, received)`: `secrets.compare_digest`로 비교한다. 문자열이 아니거나 기대값이 비면 False다.
- C 파일 6개의 직접 생성 7곳과 토큰 비교 1곳을 바꿨다.

| 위치 | 전 | 후 |
| --- | --- | --- |
| `services/scanner.py` 검사 ID | `scan-{secrets.token_hex(16)}` | `new_id("scan")`(같은 모양) |
| `security/codex_l2.py` 가짜 모델 토큰 | `secrets.token_urlsafe(32)` | `new_token(32)` |
| `security/codex_l2.py` Task 폴더 기본 이름 | `l2-{secrets.token_hex(8)}`(64비트) | `new_id("l2")`(128비트) |
| `security/codex_l2.py` 가짜 모델 인증 비교 | `!=` | `token_matches` |
| `security/launcher.py` 연결별 stderr 파일 | `os.urandom(16).hex()` | `new_suffix()` |
| `security/codex_home.py`·`secrets.py`·`settings_io.py` 임시 파일 | `uuid.uuid4().hex`(122비트) | `new_suffix()`(128비트) |

- 파일 이름은 모두 16진수 32자리 그대로다. 앱 시작 정리 규칙(`paths.SETTINGS_TEMP` 등)과 stderr 이름 시험을 바꾸지 않았다.

## 13.2 예시와 다른 점

- 예시는 `f"{prefix}_{secrets.token_urlsafe(16)}"`다. 구분자 `-`와 16진수를 썼다. 엔트로피는 128비트로 같다.
  - 지금 저장되는 ID가 `request-<hex32>`·`approval-<hex32>`·`audit-<hex32>`(A 조립)이고 검사 ID도 `scan-<hex32>`다. 같은 모양이라 A가 바꿔 끼워도 저장 형식·화면·시험이 그대로다.
  - Task ID는 Task 폴더 이름이 된다(`AppFolders.create_task_folder`). NTFS는 대소문자를 구분하지 않아 base64는 충돌 공간이 줄어든다. 16진수는 소문자만 쓰므로 줄지 않는다.

## 비밀값 누락

13.2 예시의 `SecretMissing` 대신 기존 고정 코드로 지킨다. 새 예외 클래스는 만들지 않았다. 제품 비밀값은 지금 Scanner 키 하나다. Codex 로그인 자격증명은 Codex가 관리한다(C-CODEX-08).

- `load_scanner_key`: 없으면 None이다. 읽기 실패와 형식 밖 값은 `ScannerKeyError` 고정 코드다.
- `scanner_key_environ`: 없거나 읽지 못하면 빈 dict다. 기본값·프로세스 환경·`.env`로 대신하지 않는다.
- LLM 분석기는 빈 키에서 `ScannerLLMError("SCAN_LLM_KEY_MISSING_OR_INVALID")`로 준비 실패하고 YARA만 돈다(기능 비활성).
- 근거 시험
  - `tests/unit/test_scanner_key_store.py::test_environ_for_the_scanner_comes_only_from_the_store`(프로세스 환경의 키 0회 사용)
  - `tests/contract/test_scan_service_sdk.py`(진단 `SCAN_LLM_KEY_MISSING_OR_INVALID`)

## 남은 것

- **A 요청**: A 모듈은 아직 `uuid4().hex`를 직접 쓴다. 모두 암호학적 난수라 약점은 아니고 단일 지점 규칙(13.1)만 어긋난다.
  - `services/product_assembly.py` 요청·승인 ID → `new_id("request")`·`new_id("approval")`(같은 모양)
  - `services/session_runtime.py` 세션 Task ID·감사 ID → `new_id("session")`·`new_id("audit")`(같은 모양)
  - `services/bridge.py`(`_id` 생성), `services/codex_preparation.py`(Task 자원 토큰), `ui/runtime.py`·`ui/sessions.py`(명령 ID) → `new_suffix()`
  - `examples/synthetic_app.py`도 같다. 예제라 강제 대상 밖이다.
- C2.9·C6.3에서 Semgrep 규칙으로 옮긴다. `random.*` 경고와 `security/ids.py` 밖의 `uuid`·`secrets.token_*`·`os.urandom` 차단이다. 그때 A 모듈도 대상이 된다. 그 전까지 `test_ids.py`는 C 모듈만 막는다.
- 새 C 모듈을 만들면 `test_ids.C_MODULES`에 더해야 한다(C2.11 파일 서버 등).
- `token_matches`는 길이가 다르면 바로 끝나 길이는 드러날 수 있다. 토큰 길이는 고정 값이라 비밀이 아니다.
