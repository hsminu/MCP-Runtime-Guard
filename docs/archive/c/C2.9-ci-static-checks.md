## 사용자 선택(2026-10-29, 계획 보고에서 추천대로)

- **uv:** 로컬에 0.13.0을 설치해 lock을 다시 만든다.
- **Semgrep:** Windows wheel이 없고 의존성 고정이 프로젝트 lock과 맞지 않는다. 그래서 CI Linux 작업에서 해시 고정 요구 파일로 따로 설치한다.

- **writer 넓은 예외 경계:** 예외로 등록한다. AGENTS·설계의 "세 경계" 문구 수정은 사용자에게 따로 제안한다.
- **pip-audit:** 이 작업에서 분리한다. 의존성을 정리한 뒤 실패로 막는 단계로 넣는다. litellm은 예외로 등록한다.

- **`tools/ci/semgrep.yml`(규칙 10개, 개발문서 13.4절)**
  - 규칙: 동적 실행, launcher 밖 프로세스, `shell=True`, storage 밖 `sqlite3.connect`, `src`의 assert, 예외 삼키기, 허용 위치 밖 넓은 예외, pickle·`yaml.load`, `verify=False`, MD5·SHA-1
  - **넓은 예외 규칙:** 설계 예시는 `try` 구조 패턴으로 `Exception`과 맨 `except:`만 잡았다. 이 규칙은 `except` 절의 글자를 정규식으로 본다. 결과는 `except` 줄에서 시작한다.
    - 걸리는 것: 맨 `except:`, 절 안에 `Exception`이나 `BaseException`이 단어로 있는 경우(`builtins.Exception`, 튜플의 어느 자리, 여러 줄 튜플 포함)
    - 걸리지 않는 것: `ExceptionGroup`·`BaseExceptionGroup`·`CustomException`
    - **구조 패턴을 버린 이유:** 튜플 처리기를 믿고 잡지 못한다. 처음 PR의 구조 패턴에 처리기 형식을 정규식으로 보는 패턴을 더해 CI 규칙 시험을 돌렸다(`fe0466e`).
      - 첫 원소가 `Exception`인 `(Exception, asyncio.CancelledError)`는 걸렸다.
      - 둘째 원소인 `(OSError, BaseException)`·`(OSError, builtins.Exception)`은 놓쳤다.
      - Semgrep이 튜플의 첫 원소만 보는 것으로 보인다(추정, Semgrep 내부는 확인하지 않음).
      - 처음 PR이 `failclosed.py`의 튜플 다섯 곳을 잡았는지는 확인되지 않았다. 그 파일이 제외돼 있었다. 이 문제는 #72 B 리뷰 참고 1을 반영하다가 찾았다.
    - **한계:** 글자를 보므로 docstring 안에서 줄 맨 앞에 `except ... Exception ...:`가 오면 오탐이 난다. 여러 줄 튜플 안 주석에 `:`가 있으면 놓친다.
  - **파일 단위 제외 없음:** 설계 경계 파일(`failclosed.py`·`worker.py`)을 통째로 빼지 않는다. 경계의 `except` 줄 끝에만 `# nosemgrep`을 단다(`# noqa: BLE001` 뒤). 그래서 같은 파일에 넓은 예외가 새로 생겨도 걸린다(#72 B 리뷰 참고 1).
  - **예외 삼키기 규칙:** `except X as e: pass`도 잡는다. 설계 예시는 `as`가 없는 형태만 잡았다.
  - 검사 대상은 `src/`다. 테스트·공격 fixture는 이 API를 일부러 쓴다.
  - `tools/ci/semgrep.in`·`semgrep-requirements.txt`: Semgrep 1.182.1과 의존성 66개를 Linux(manylinux_2_34)·Python 3.12 해시로 고정했다.
  - **규칙 시험 `tools/ci/semgrep.py`(`semgrep --test`):** 규칙마다 걸려야 하는 줄을 두고, 필요한 곳에는 걸리면 안 되는 줄도 두었다. 처리기가 두 개인 `try`·맨 `except`·`BaseException`·`yaml.safe_load`·SHA-256을 포함한다. 넓은 예외 표시는 결과가 시작하는 `except` 줄 바로 위에 둔다. 튜플 네 가지(첫 원소·둘째 원소·`builtins.Exception`·여러 줄)는 걸리고, `ExceptionGroup`·`BaseExceptionGroup`·`CustomException`과 `except_count` 같은 이름은 걸리지 않는다. `as`가 붙은 삼키기도 넣었다.
  - **예외 일치 확인 `tools/ci/check_semgrep_exceptions.py`:** 예외 주석을 끈 검사(`--disable-nosem --json`)가 SG-01–04 네 곳과 설계 경계 여섯 곳만 잡아야 통과한다. 출력에는 규칙과 경로만 쓴다.
  - assert 규칙의 `paths.include: src/`는 뺐다. CI는 `src`만 검사하므로 같다.
- **예외 4곳:** 사유 주석 한 줄과 `# nosemgrep`을 달았다(삼키기는 `try` 줄, 넓은 예외는 `except` 줄). 동작 변경은 없다. 대장 [규칙 예외 기록](../../weakness_register.md#규칙-예외-기록) SG-01–04다.

## 남는 것

- **C6.3 pip-audit 단계:** 의존성 정리 PR(간접 3개 lock 갱신, mcp 1.30.0은 A·B 합의, litellm 예외) 뒤에 실패로 막는 단계로 넣는다.
- **"세 경계" 문구:** AGENTS·개발문서는 넓은 예외 처리를 `fail_closed`·`after_dispatch`·`ServerWorker._execute` 세 경계로 적는다. B6.13 writer `_execute`는 네 번째다. B는 네 곳으로 고치는 데 동의했다(#72 B 리뷰). 문구를 고칠지는 사용자 결정이다.
- **규칙이 보지 않는 것**
  - `contextlib.suppress(...)`: 예외 삼키기 규칙은 `try`/`except`만 본다. #70 병합 뒤 `src`에 13곳이 있고 모두 좁은 형식이다(#72 B 리뷰 참고 2, B가 셀 때는 11곳).
  - `except X: ...`처럼 본문이 `...`인 처리기
- **로컬에서 다시 돌릴 때:** Semgrep의 `paths` 제외는 git 저장소 기준으로 적용된다. `git archive`로 푼 폴더처럼 git이 아닌 곳에서 돌리면 제외가 빠진다. 그러면 storage의 `sqlite3.connect`와 launcher의 `subprocess`가 위반으로 나온다. CI는 체크아웃이라 괜찮다(#72 B 리뷰 참고 3).
- **동적 import 규칙:** 개발문서 2장은 동적 import도 Semgrep으로 막는다고 하지만 13.4절 목록에는 없어 넣지 않았다. 넣으면 Cisco 어댑터 두 파일(SDK 지연 import, C-CISCO-05)이 예외가 된다.
- **mypy `--strict`:** 13.5절의 domain·core·security 범위는 이번 범위가 아니다.

리뷰: B(예외 주석 3곳·`failclosed.py` 경계 표시 5줄·규칙), A(CI·`ui`·transport 계약·`worker.py` 경계 표시 1줄).
