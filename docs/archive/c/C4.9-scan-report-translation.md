# C4.9 · Scanner 결과를 B ScanReport로 번역 (C4.15·C4.17 포함)

관련: SCAN-01(B `ScanReport`·`Finding`·`AnalyzerDiagnostic`, #32), 2026-10-15 Scanner 결정 3건(SDK severity 그대로·자체 평가는 참고, 경고 표시와 `threat_summary`, 운영 상한), C4.12 지문, C4.10 Registry, I6·I9·T17·T19. 앞선 C 작업: [내부 집계](../tasks/c-cisco-internal-aggregation.md), [Luna 연결](../tasks/c-cisco-luna-connection.md).

## 배경

- C 내부 집계(`InternalMetadataScanner` → `MetadataScanResult`)는 분석기 실행과 도구별 결과까지만 만들고, B `ScanReport`로 옮기지 않았다. 이를 부르는 제품 코드도 없다.
- B 쪽은 준비돼 있다.
  - `ScanReport`(SCAN-01 필드 포함)
  - `RegistryStore.record_scan_report`
  - `activate(reviewed_scan_id)`: 활성화 때 검사의 서버·지문 집합이 등록과 같은지 대조한다.
- contracts의 "필수 분석기·완료/생략/실패·지문·severity 번역 계약"은 미결이었다. 이 기록의 규칙이 C 제안이다(B 동의 대기).
- 내부 집계는 SDK finding에서 severity·category·threat_type만 남겨서 LLM 자체 평가(`overall_risk`)와 모델 설명(`threat_summary`)을 버렸다(C4.15·C4.17 미구현).

## 한 일

- **SDK 확인(Cisco Scanner 4.8.6, 설치본):**
  - 위협 분석 프롬프트(`threat_analysis_prompt.md`)는 `threat_analysis.overall_risk`(`HIGH|MEDIUM|LOW|SAFE`)·`threat_summary`·`primary_threats`·`malicious_content_detected`를 요구한다.
  - `LLMAnalyzer._create_findings_from_threat_analysis`는 severity를 SDK 위협 표에서 정하고, `summary`를 "Detected N threats: …"로 다시 만든다. 모델의 두 값은 finding 필드에 없다.
  - 대신 응답 전체가 `details["raw_response"]`에 들어 있다.
- **`adapters/cisco_aggregation.py`**
  - **자체 평가 보존(C4.15·C4.17):** LLM finding에서 `details["raw_response"]["threat_analysis"]`의 두 값만 꺼낸다.
    - `overall_risk`는 `defang_scanner_text(max_length=64)`, 비면 None이다.
    - `threat_summary`는 `defang_scanner_text`(300자)다.
    - 모양이 다르거나 무해화가 실패하면 비운다. finding과 실패 사실은 그대로 둔다(B `defang_scanner_text` 설명).
    - `FindingSummary`에 두 필드를 더했다(`repr` 제외).
    - 판정·정렬·severity에는 쓰지 않는다. 모델이 SAFE라 해도 SDK의 HIGH는 그대로다.
  - **`scan_report(result, tools, *, scanned_at_utc) -> ScanReport`(C4.9):** `tools`는 검사에 넘긴 목록 순서의 (도구 이름, 등록 지문)이다. Registry 등록과 같은 `listing_fingerprints` 결과를 넘긴다.

    | ScanReport 필드 | 규칙 |
    | --- | --- |
    | `server_id` | 집계 결과의 서버 ID(신뢰한 호출자가 준 값) |
    | `fingerprint_set` | `tools`의 지문, 목록 순서. 검사하지 못한 도구도 포함한다. 그래서 활성화 대조는 등록 목록 전체와 맞는다 |
    | `analyzers_required` | `LLM`·`YARA` |
    | `analyzers_completed` | 준비 실패가 없고 모든 도구에서 `completed`인 분석기. 도구가 0개면 완료다 |
    | `analyzers_failed` | 그 밖의 분석기 |
    | `analyzers_skipped` | 비움. 사용자가 끈 분석기라는 개념이 아직 없다 |
    | `analyzer_diagnostics` | 준비 실패: 분석기 하나에 도구 없는 진단 하나. 준비 뒤 도구별 실패·미검사: (분석기, 도구 이름, 지문, 코드). 완료가 아닌 분석기가 끝내지 못한 도구에는 반드시 진단이 있다(코드가 비면 `SCAN_<분석기>_FAILED`). 코드는 B `ScanErrorCode`로만 옮기고, 모르는 코드는 `SCAN_<분석기>_FAILED`다 |
    | `findings` | SDK finding 하나에 하나. `analyzer`·`source`는 분석기 이름, `code`는 SDK `threat_type`(없으면 category)이고 영문·숫자·`_`·공백 64자 밖이면 `SCAN_CODE_UNRECOGNIZED`, `severity`는 SDK 값 그대로(`UNKNOWN` 포함), 도구 이름·지문, LLM이면 자체 평가 두 값. `description`은 비운다(SDK 원문 비복사) |
    | `max_severity` | 내부 집계의 `maximum_observed_severity` 그대로. 아는 값 중 최고이고, finding이 모두 모르는 값이면 `UNKNOWN`이다 |
    | `scanner_version` | `cisco-ai-mcp-scanner-4.8.6`(`SCANNER_VERSION`, 설치본과 테스트로 대조) |
    | `overall_risk`·`threat_summary`(보고서 수준) | 비움. 서버 단위 모델 출력이 없다 |

    - 개수·이름이 집계와 맞지 않으면 `SCAN_REPORT_INPUT_MISMATCH`, B 검증을 통과하지 못하면 `SCAN_REPORT_INVALID`다(`ScanReportError`).
    - 일부만 담은 보고서는 만들지 않고, 오류에 원인 예외를 달지 않는다.
- **`services/registry.py`: `ServerRegistry.record_scan(scan_id, report) -> RegistryEntry`**

  - 보고서가 아니면 `REG_SCAN_INVALID`, 모르는 서버면 `REG_SERVER_UNKNOWN`이다.

## B 리뷰 반영(#57)

- B는 번역 규칙에 동의했다. 검사하지 못한 도구도 `fingerprint_set`에 넣는 것, 준비 실패는 도구 없는 진단 하나로 두는 것이다. 조건은 두 가지였다.
- **조건 1(진단 누락 없음):** 끝내지 못한 도구에 진단이 빠지면 화면이 그 도구를 검사된 것으로 볼 수 있다.
  - 집계기는 실패에 늘 코드를 붙인다. 그래도 번역에서 코드가 비면 `SCAN_<분석기>_FAILED`로 진단을 남기게 했다.
  - 이 성질을 hypothesis로 번역 함수 전체에 대해 검사한다.
- **조건 2(`code` 형식):** LLM 분석기의 `threat_type`은 모델 응답에서 왔을 수 있다. 영문·숫자·`_`·공백 64자 밖이면 `SCAN_CODE_UNRECOGNIZED`로 바꾸고 원문은 싣지 않는다. B는 SCAN-01 정리 때 `Finding.code`에 같은 형식을 넣는다(B1.9).

## 남는 것

- **2단계(C4.14):** 검사 서비스 입구(`ScanService`)와 앱 전체 예산. 서버 검사 1건·대기 8건, 작업 10분, LLM 동시 4개, YARA worker 1개.
- **YARA 5초 상한:** 엔진에 실제로 걸리는지는 2단계에서 확인한다.
- **LLM 키:** 제품의 키 공급은 C2.10이다. 그 전까지 제품 검사는 LLM 준비 실패로 YARA만 완료된다.
- **보고서 수준 자체 평가:** 위협이 없다고 판단한 도구(finding 없음)의 자체 평가는 보고서에 자리가 없어서 남지 않는다. 지금은 표시할 위험이 없는 경우다.
