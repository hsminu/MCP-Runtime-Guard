# C2.12 · codex.exe 실행 launcher

관련: I9·I11, T19·T22·T43 전제, #21 2번·5번, 개발문서 10.4절 "실행 환경과 경로". C-CODEX-07을 새로 기록했다.

## 한 일

- `security/launcher.py`를 새로 만들었다. 외부 프로세스 실행의 단일 지점이다. 공통 핵심 `launch_process(LaunchSpec)`와 codex.exe 입구 `CodexLauncher`가 있다.
- **실행 파일**
  - 절대 경로의 `.exe`만 받는다. `.bat`·`.cmd`는 Windows가 cmd.exe로 인자를 다시 해석하므로 거부한다.
  - 링크·junction·폴더는 거부한다. 해시 없는 실행은 받지 않는다.
- **해시 대조**
  - 읽기만 공유하는 핸들로 열어 크기와 SHA-256을 대조한다. 이 핸들은 프로세스를 만들 때까지 쥐고 있다.
  - 그동안 파일 쓰기·교체·삭제와 상위 폴더 이름 변경이 막힌다(테스트로 확인). 그래서 검사한 파일과 실행한 파일이 다를 수 없다.
  - 해시 계산은 스레드에서 한다. codex.exe(333MB)는 처음 약 2초, 이후 약 0.4초 걸렸다.
- **프로세스 생성**
  - `CREATE_SUSPENDED`로 만들어 Job Object에 넣은 뒤 첫 스레드만 재개한다. Job 설정은 `KILL_ON_JOB_CLOSE`·`DIE_ON_UNHANDLED_EXCEPTION`이다.
  - 그래서 Job에 넣기 전에 생긴 자식은 없다. 앱이 끝나 Job 핸들이 닫히면 남은 자식까지 함께 끝난다.
  - 콘솔 창은 띄우지 않는다.
- **환경·인자·stderr**
  - 환경은 명세의 값만 쓰고 부모 환경을 물려주지 않는다.
  - codex.exe는 10-18 허용 목록 7개와 앱 경로로 채운 `CODEX_HOME`만 받는다.
  - 인자는 `app-server -c sqlite_home='<Task 폴더>'`다. TOML 리터럴 문자열로 넘긴다. 큰따옴표로 감싸면 경로의 `\U`·`\t`가 이스케이프로 해석되기 때문이다. `'`나 제어 문자가 든 경로는 거부한다.
  - stderr는 Task 폴더의 `codex-stderr.log`로 보낸다. 파일은 새로 만들고, 이미 있으면 거부한다. 앱 로그로는 가지 않는다.
- **반환값 `LaunchedProcess`**
  - `read_bytes(limit)`·`write_bytes(frame)`·`drain()`을 제공한다. A `CodexPipes`의 형식과 같다.
  - 닫힌 파이프에 쓰면 조용히 버리지 않고 `LAUNCH_PIPE_CLOSED`를 낸다.
  - `close()`는 stdin을 닫고 기다린다. 안 끝나면 Job째 종료한다. Job에 남은 프로세스가 0개인 것을 본 때만 True를 돌려준다. Job을 조회할 수 없으면 기다리지 않고 False를 돌려준다.
  - 여러 번 부르거나 동시에 불러도 정리는 한 번만 한다. 부른 쪽이 취소되어도 정리는 끝까지 한다.
- **`CodexLauncher`**
  - 실행 직전에 `verify_codex_home`으로 CODEX_HOME 묶음 해시를 대조한다.
  - `launches`는 실제로 만든 프로세스 수다(C1.9 관측).
- **오류:** `LaunchError`는 고정 코드만 가진다. 경로·인자·예외 원문은 넣지 않는다. 코드는 `LAUNCH_EXECUTABLE_INVALID`·`_MISMATCH`, `LAUNCH_SPEC_INVALID`, `LAUNCH_CWD_INVALID`, `LAUNCH_STDERR_INVALID`, `LAUNCH_TASK_DIR_INVALID`, `LAUNCH_CODEX_HOME_INVALID`·`_MISMATCH`, `LAUNCH_PINS_INVALID`, `LAUNCH_FAILED`, `LAUNCH_JOB_FAILED`, `LAUNCH_RESUME_FAILED`, `LAUNCH_PIPE_CLOSED`, `LAUNCH_READ_INVALID`, `LAUNCH_WRITE_INVALID`, `LAUNCH_UNSUPPORTED`다.
- **단위 테스트 31개**(`tests/unit/test_launcher.py`): 실행 파일은 이 Python의 기본 python.exe로 대신했다.
  - 파이프 왕복과 stdin EOF 종료
  - stderr가 격리 파일에만 쓰임
  - 공백·따옴표·`&`·`%PATH%`·`^`·`|`·빈 문자열 인자가 그대로 전달됨(shell 미사용)
  - 부모에 심은 `OPENAI_API_KEY`·`CODEX_SQLITE_HOME`·`HTTPS_PROXY`가 자식에 없음
  - 해시·크기가 다르면 실행 0회
  - `.cmd`·상대 경로·폴더·없는 실행 파일 거부, 잘못된 환경 거부, 이미 있는 stderr 파일 거부
  - 대조 중 파일 교체·삭제·상위 폴더 이름 변경 차단, 해시 불일치 시 핸들 해제
  - 손자 프로세스까지 종료, Job 핸들만 닫아도 종료(앱 비정상 종료 흉내)
  - 정리 공유와 닫은 뒤 쓰기 거부, 해시 계산 중 취소 시 늦게 열린 핸들 닫기
  - Task 폴더의 `'`·상대·없음·junction 거부
  - CODEX_HOME·고정값·실행 파일 불일치 시 실행 0회, 고정값을 맞춘 실행의 계수
  - 같은 테스트를 5번 반복해 모두 통과했다.

## 실제 검증([근거](../evidence/c2.12-codex-launcher-2026-10-19.json))

C6.13 설치본 codex.exe 0.162.1을 `CodexLauncher`로 띄웠다. 부모 환경에 `OPENAI_API_KEY`·`CODEX_SQLITE_HOME`·`HTTPS_PROXY`를 심고, Task 두 개를 차례로 실행했다.

- **시작과 설정**
  - 허용 목록 환경만으로 시작했고 `initialize`가 성공했다.
  - `configRequirements/read`는 null이었다.
  - `config/read`의 `sqlite_home`은 Task 폴더였다. `model`은 `gpt-6.1-sol`, `web_search`는 `disabled`였다.
  - 심은 `CODEX_SQLITE_HOME` 폴더는 생기지 않았다.
- **종료**
  - stdin을 닫으면 0.06초 안에 스스로 끝났다. 종료 코드는 0이고, `close()`는 True였다.
  - `launches`는 2였다.
- **남은 파일**
  - Task 폴더에는 `codex-stderr.log`와 DB 5종(logs·state·goals·memories·queue)이 생겼다. 각 DB의 `-wal`·`-shm`은 종료 뒤에도 남았다. Task 폴더 삭제(C2.13)로 지운다.
  - Codex가 끝난 뒤 CODEX_HOME 확인은 통과했다(`config.toml`·`installation_id`·`model_catalog.json`).
- **stderr:** 경고 1줄이었다. CODEX_HOME이 TEMP 아래라 PATH 보조 실행 파일을 만들지 않는다는 내용이다. 제품 경로에서는 `tmp\arg0`이 생긴다(C6.19·C6.16).
- **원격 제어(C-CODEX-07)**
  - 시작 직후 `remoteControl/status/changed`가 왔고, 상태는 `disabled`였다. `remoteControl/status/read`도 `disabled`였다.
  - 0.162.1 소스로 확인한 점은 다음과 같다.
    - 이 기능은 stdio 클라이언트의 `remoteControl/enable`이나 state DB의 저장된 설정으로 켜진다.
    - RPC까지 막는 것은 시스템·MDM requirements의 `allow_remote_control=false`뿐이다. 앱이 L1으로 넣을 수 없다.
    - `CODEX_INTERNAL_APP_SERVER_REMOTE_CONTROL_DISABLED=1`은 시작 상태만 끈다.
  - A 세션 관리자는 지금 이 알림을 무시한다.
- **전체 검사**(main `013ecec` 기준, Windows 11, Python 3.12.10)
  - Ruff·포맷·mypy(61개 파일)·`pip check`가 통과했다.
  - contract 41개가 통과했다.
  - 단위 3,085개가 통과하고 1개는 건너뛰었다. 건너뛴 것은 링크 생성 권한이 필요한 기존 테스트다.
- **첫 전체 실행에서 발견한 것**
  - `test_mcp_http.py`의 루프 정지 단언(`max_gap < 0.5`) 1건이 실패했다. 원인을 좁히니 바로 앞의 Job 핸들 테스트가 10초를 쓰고 있었다. Job을 조회할 수 없을 때 `close()`가 대기 시간을 다 쓴 탓이다.
  - `close()`가 바로 False를 돌려주게 고친 뒤 통과했다.
  - 단순히 10초 기다리는 asyncio 테스트를 앞에 둬도 같은 단언이 실패한다. 이 단언이 앞 테스트의 실행 시간에 영향을 받는다는 뜻이고, 측정된 정지는 그 테스트의 io 시간 제한과 같은 0.5초였다. A에 알린다.

## 남은 한계

- CODEX_HOME 파일은 실행 직전에 대조하지만, Codex가 읽는 시점까지 잠그지는 않는다. 같은 사용자 권한의 공격자는 위협 모델 밖이다(개발문서 0.3절).
- Task 폴더 생성·사용자 전용 권한·삭제는 C2.13이다. launcher는 폴더의 형태(절대 경로·실재·링크 아님)만 본다.
- stdio MCP 서버도 같은 `launch_process`를 쓴다. 다만 `servers.yaml` 등록 값 검증과 그 실행 파일 해시를 어디서 받을지는 C2.6에서 정한다.
- L2 가짜 모델용 `-c` 덮어쓰기는 C6.14에서 별도 경로로 둔다. 제품 입구는 `sqlite_home` 하나만 넘긴다.
- 로그인(keyring)과 실제 모델 호출을 이 환경 목록으로 실행하는 것은 이번에 확인하지 않았다. C6.13 스모크는 같은 7개로 가짜 모델 turn까지 돌았다. T43·C6.14에서 확정한다.
- 이벤트 루프는 Windows Proactor여야 한다. A bridge가 만드는 `new_event_loop`가 Windows 기본값(Proactor)이다. 다른 루프면 `LAUNCH_FAILED`로 닫힌다.
- **A 연결**
  - `prepare_task`가 `LaunchedProcess`를 `TaskResources.handle`로 넘기고, `confirm_exit`는 `close()` 결과를 쓰면 된다.
  - `SessionPreparation` 어댑터는 C2.13·C6.14 뒤에 만든다.
  - A의 `ConfigurationReceipt`는 config·실행 파일·모델 정보 해시를 따로 받는다. 묶음 해시를 돌려주는 `write_codex_home`과의 차이는 어댑터에서 맞춘다.

리뷰: B(`security/*`), A(파이프 형식·연결 방식).
