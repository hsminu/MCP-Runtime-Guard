# C6.8-1 · Guard 경로 T 시나리오 계수(T01·T09·T10·T11·T26·T30)와 T28 지연

관련: C6.8(C 담당 T/S), 개발문서 14.3 T 목록·14.4 지표(`decide_ns`), C5.4 계수 하니스, B6.8 명시 시작·복구, I2·I3·I10.

## 배경

- C 담당 T/S 41개 가운데 Guard 입구로 확인할 수 있는데 C 독립 검증이 없던 항목이다. A·B 단위 시험에는 일부가 있지만 실제 서버 계수로는 보지 않았다.

- Codex 세션을 거치지 않는다. Guard 입구(`submit`·사람 채널)를 직접 부른다.

## 관찰

1. **저장된 승인 기록을 바꾸면 Guard 전체가 멈춘다.** 사유는 `INTERNAL_ERROR`이고 다른 Task의 새 호출도 같은 사유로 거부된다. 그 Task의 `APPROVAL_STALE`·`HALTED`가 아니다. DB 승인 행은 `PENDING`, Task는 `WAITING_APPROVAL`로 남고 다음 시작 복구가 정리한다. 실행 0이라 실패 쪽으로 닫힌다. DB 변조는 같은 사용자 권한이 필요해 위협 모델 밖이며, 결함 주입으로만 확인했다.
2. **정상 종료와 비정상 종료가 다르게 정리된다.** Guard를 닫으면(`aclose`) 대기 승인이 `CANCELLED`가 되어 복구 보고의 승인 변경은 0이다. Guard를 닫지 않고 Store만 끊으면 복구가 대기 승인을 `EXPIRED`로 바꾼다(변경 1). 두 경우 모두 이전 승인은 실행되지 않는다.

## T28 정책 평가 지연

- 구간: 판정 구간(`decide_ns`)은 `Catalog.resolve` + `GuardService._evaluate_request`(Registry 상태·지문, 사전 판정, 접근 규칙, 최종 판정)다. 개발문서 14.4의 정의와 같다. submit 전체는 여기에 Task 조회·영속 call_seq·판정 기록 커밋(`synchronous=FULL`)이, ASK는 승인 생성 커밋이, ALLOW는 예약과 실제 MCP 왕복이 더해진다.
- 조건: 모드 `accumulate`, 경로별 500회(준비 20회 제외), Windows 11 10.0.26200, Python 3.12.10, Intel 12세대(Family 6 Model 154). 측정 시점 main `9a8c117` 위 이 브랜치.

| 경로 | 연결 | 판정 구간 p50 / p95 (ms) | submit 전체 p50 / p95 (ms) |
| --- | --- | --- | --- |
| DENY (CONFIDENTIAL→일반 외부) | stdio | 1.79 / 3.91 | 4.73 / 7.79 |
| DENY | HTTP | 2.08 / 3.51 | 5.08 / 7.71 |
| ASK (INTERNAL→승인된 외부) | stdio | 1.95 / 4.15 | 10.18 / 14.23 |
| ASK | HTTP | 2.13 / 4.04 | 10.47 / 14.96 |
| ALLOW (PUBLIC 읽기, MCP 왕복 포함) | stdio | 3.21 / 5.48 | 13.46 / 17.51 |
| ALLOW | HTTP | 3.57 / 5.99 | 16.81 / 23.78 |

- 같은 Task에 호출이 쌓일 때: 처음 50회와 마지막 50회 판정 구간 중앙값 차이는 최대 약 1.2ms(HTTP DENY 1.29→2.51)이고, stdio ASK는 오히려 줄었다(1.91→1.54). 500회 안에서 일관된 증가로 보기 어렵다. 더 긴 Task는 재지 않았다.
- 한계: 한 PC, 한 번 실행이다. 모델 추론·사람 승인 대기는 포함하지 않는다. 판정 구간을 재려고 두 메서드를 감쌌으므로 감싼 비용(수 µs)이 들어 있다.
