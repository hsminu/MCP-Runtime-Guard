# C2.11 · 읽기 전용 파일 MCP 서버 (C2.4 포함)

관련: 2026-10-15 사용자 결정(로컬 파일은 우리 읽기 전용 파일 MCP 서버(stdio)로만, 폴더 목록·파일 읽기, READ로 대상 경로 등급, `safe_path`, 결과 `structuredContent.resource_id`, UTF-8 텍스트만, 응답 게이트 상한), [C2.3](C2.3-safe-path.md)(#63), [C2.6](C2.6-mcp-server-launch.md)(실행 입구·EXE-01), B `services/response_gate.py`(256KiB, 본문+`structuredContent`)·`catalog_sources`(일치 규칙의 최고 등급), 개발문서 4.2·13.2·14.2절, T33.

## 배경

- 결정은 "로컬 파일은 우리가 만든 읽기 전용 파일 서버를 Guard에 등록해서만 읽는다"였다. 공식 `server-filesystem`은 쓰기·이동 도구가 있고 `resource_id`를 내지 않는다.
- 개발문서 14.2절 참고 서버는 fixture용이었다.
  - `mcp` SDK(FastMCP)를 쓴다. 설계 규칙상 SDK는 A transport와 fixture만 import한다.
  - 검사-열기 경쟁(C2.4)을 다루지 않는다.
  - 결과 크기를 제한하지 않는다.

## 사용자 선택(2026-10-28, 계획 보고에서 추천대로)

- **구현:** 표준 라이브러리만으로 줄 단위 JSON-RPC를 직접 처리한다(SDK 없음).
- **루트 기록:** 설정 레코드의 `args`(`--root <절대 경로>`)에 둔다. C가 같은 레코드에서 루트를 꺼내 Guard 해석기에 넘긴다. B 설정 형식은 바뀌지 않는다.
- **루트 목록:** 별도 도구 `list_root`(도구 단위 READ)로 둔다. B Catalog는 일치하는 규칙의 **최고** 등급을 쓴다. 그래서 루트 규칙(`prefix: []`)을 `list_folder`에 걸면 모든 목록의 하한이 된다. 결정 문구보다 도구가 하나 늘었다.
- **실행:** 앱의 `python.exe -I -m guard_app.servers.file_server --root <루트>`. 지문은 인터프리터만 고정한다.

## 한 일

- **`src/guard_app/servers/file_server.py`(새 패키지 `guard_app.servers`)**
  - **프로토콜**
    - `initialize`: 요청 버전이 `2025-11-25`·`2025-06-18`·`2025-03-26`·`2024-11-05` 중 하나면 그대로, 아니면 `2025-11-25`. capabilities는 `tools.listChanged: false`
    - `ping`, `tools/list`, `tools/call`
    - 알림에는 답하지 않는다.
    - 오류 코드: JSON이 아니면 -32700, 형식이 틀리면 -32600, 모르는 메서드는 -32601, 잘못된 params·모르는 도구는 -32602
    - 한 줄은 64KiB까지다. 넘으면 그 줄을 버리고 -32600으로 답한 뒤 다음 줄을 처리한다.
    - 표준 출력에는 응답만 쓰고, 오류에 요청 경로·내용을 싣지 않는다.
  - **도구(모두 READ, 읽기 전용 annotations)**

    | 도구 | 인자 | 결과 |
    | --- | --- | --- |
    | `list_root` | 없음 | 루트 바로 아래 목록. `resource_id`는 `""` |
    | `list_folder` | `path` | 폴더 목록. 본문은 한 줄에 이름 하나(폴더는 `/`), `structuredContent`는 `{resource_id, entries:[{name, kind}], truncated}` |
    | `read_file` | `path` | 본문은 파일 텍스트, `structuredContent`는 `{resource_id, bytes}` |

    - `resource_id`는 C2.3 `safe_path`의 루트 기준 POSIX ID(디스크 실제 이름)라서 Guard가 요청 인자로 계산한 기대 ID와 정확히 대조된다(T33).
  - **읽기 규칙**
    - 192KiB까지 읽는다. B 응답 게이트가 본문과 `structuredContent`를 합쳐 256KiB까지 받으므로 그 안에 들어간다.
    - 상한+1바이트만 읽어 넘으면 `FILE_TOO_LARGE`다.
    - UTF-8만 받는다. BOM은 떼고, 디코딩 실패나 NUL이면 `FILE_NOT_TEXT`다.
  - **목록 규칙**
    - `safe_path`가 받는 이름만 보인다. 링크·junction·하드링크 파일·쓸 수 없는 이름은 빠진다.
    - 이름순으로 정렬하고 1,000개까지 보인다. 1만 개를 넘게 훑지 않는다. 넘으면 `truncated: true`다.
  - **도구 오류:** `isError: true`와 고정 코드 텍스트 하나다.
    - `PATH_*`(C2.3), `PATH_NOT_FILE`, `PATH_NOT_FOLDER`, `ARGUMENT_INVALID`, `FILE_TOO_LARGE`, `FILE_NOT_TEXT`
    - `FILE_OPEN_FAILED`(다른 쪽이 쓰는 중 등), `FILE_CHANGED`, `FILE_READ_FAILED`, `FOLDER_READ_FAILED`
  - **설정 도우미(A 등록 화면·조립용)**
    - `file_server_args(root)`: 레코드의 `args`. 루트는 실제 경로로 푼다.
    - `file_server_root(args)`: 이 서버 형식의 `args`면 루트, 아니면 None
    - `FILE_SERVER_TOOL_SETTINGS`: 레코드의 `tools`. `list_root`는 `resource_arg` 없음, 나머지 둘은 `path`
- **C2.4 검사-열기 경쟁**
  - `safe_path` 뒤에 `FILE_FLAG_OPEN_REPARSE_POINT` 핸들로 연다. 파일은 `FILE_SHARE_READ`만(쓰기 금지)이고, 폴더는 `FILE_FLAG_BACKUP_SEMANTICS`로 삭제·이름 변경을 금지한다.
  - 핸들의 정보로 다시 확인한다. 다음 중 하나라도 어긋나면 `FILE_CHANGED`다.
    - reparse point가 아님
    - 파일·폴더 구분이 요청과 같음
    - 파일이면 하드링크가 하나
    - `GetFinalPathNameByHandleW` 실제 경로가 검사한 경로와 같음
  - 목록은 폴더 핸들을 쥔 채 만든다.
  - **실측:** 검사 직후 상위 폴더를 루트 밖 junction으로 바꿔치기했다.
    - 대조가 있으면 `FILE_CHANGED`이고 밖의 파일 내용은 나가지 않는다.
    - 대조를 끄면 밖의 파일 내용이 그대로 읽혔다.
  - `security/paths.py`의 `real_root`(C2.3의 루트 풀이)를 공개해 서버도 같은 루트 풀이를 쓴다.
- **테스트** `tests/unit/test_file_server.py` 30개(실제 NTFS)
  - **프로토콜**
    - 버전 응답 3가지, 도구 목록·ping·알림 무응답
    - 형식 오류 7가지, JSON이 아닌 줄 2가지
    - `serve`가 너무 긴 줄을 버리고 다음 줄을 처리
  - **도구**
    - 실제 이름 ID로 읽기
    - 192KiB 경계(정확히·BOM 포함·+1), UTF-8이 아님, NUL
    - 목록에서 junction·하드링크 제외, 정렬, `list_root`와 잘림
    - 거부 10가지(경로 원문 없음), 링크 대상
    - 쓰기 중인 파일, 검사-열기 바꿔치기
    - 설정 도우미 왕복(junction 루트 포함)과 거부 4가지
  - **끝에서 끝까지(실제 프로세스):** C2.6 입구로 venv `python.exe -I -m guard_app.servers.file_server`를 띄웠다.
    - A transport로 `tools/list`를 받고, C `ServerRegistry`에 등록·활성화했다. 세 도구 모두 READ다.
    - B Catalog와 C2.3 해석기(`file_server_root`로 같은 레코드에서 루트)로 `transport.call`했다.
    - 출처 규칙대로 `Public` 읽기는 PUBLIC, `personal` 읽기는 INTERNAL, `list_root`는 PUBLIC으로 분류됐다.

## A·B 연결

- **A 등록 화면**
  - 파일 서버 추가는 다음으로 레코드를 만든다.
    - `command`: 앱의 `python.exe`
    - `args`: `file_server_args(루트)`
    - `tools`: `FILE_SERVER_TOOL_SETTINGS`
    - 지문: `pin_executable(command)`(EXE-01)
  - 하위 폴더별 출처 규칙(`read_file`·`list_folder`의 접두어)과 `list_root` 규칙을 받는다. 어느 규칙에도 맞지 않으면 Unclassified로 Task가 멈춘다(결정).
- **A 조립:** `ProductInputs.resource_resolver = file_resource_resolver({id: file_server_root(server.args)})`. 연결은 C2.6 `launch_mcp_server`다.
- **B:** 변경 없음. 테스트 리뷰

## 남는 한계

- **지문 범위:** 인터프리터만 고정된다. 서버 코드의 무결성은 Guard 자체 코드처럼 앱 설치본에 맡긴다(EXE-01 인터프리터형 한계와 같다).
- **OS 격리 없음:** 서버는 사용자 권한으로 돈다. 노출은 `safe_path`를 통과한 것뿐이다.
- **목록의 이름 노출:** 목록은 그 폴더 등급으로 분류되지만, 하위 항목 이름이 그 등급으로 보인다. 등급이 다른 하위 폴더의 이름도 상위 목록 등급으로 보인다.
- **숨김·시스템 파일:** 속성으로 거르지 않는다. 링크·하드링크만 거른다.
- **클라우드 파일:** OneDrive 등 자리표시자 파일은 열 때 내려받기가 일어날 수 있다. 측정하지 않았다.
- **심볼릭 링크 마지막 조각 바꿔치기:** 이 PC에 권한이 없어 실측하지 못했다. 그 경우 링크 자체가 열리고 reparse point 확인에서 거부된다.

리뷰: B(테스트), A(등록 화면·조립).
