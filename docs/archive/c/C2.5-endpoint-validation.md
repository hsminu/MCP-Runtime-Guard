# C2.5 · HTTP MCP 서버 URL 검증

관련: URL-01(2026-10-27 사용자 결정, #49), CFG-01 `ServerSettings.url`(B3.11), 개발문서 4.3·10.1·13.1·13.2절, A transport `_endpoint_url`·등록 화면 `_url_error`, I9.

## 배경

- C2.14에서 분리한 설정 파일 HTTP 서버 `url` 검증이다. 허용 범위는 URL-01로 정했다.
- 지금 URL 검사가 A 쪽 두 곳에 있고 규칙이 서로 다르다.
  - transport(`adapters/mcp_transport/streams.py` `_endpoint_url`): https는 어디든, http는 `127.0.0.1`·`::1`만, 쿼리·fragment 거부
  - 등록 화면(`ui/server_add.py` `_url_error`): http를 아무 호스트에나 허용, 링크 로컬·미지정·멀티캐스트 IP와 ASCII 밖 호스트 거부
  - 그래서 화면에서 저장한 `http://10.0.0.5/mcp`를 연결 때 transport가 거부한다.
- 개발문서 13.2절 참고 코드를 그대로 옮기면 생기는 문제를 실측했다(Python 3.12.10).
  - `urlsplit`이 탭·줄바꿈을 조용히 지운다. `https://ev<탭>il.com`의 호스트가 `evil.com`이 된다.
  - `parts.port or 80`이라 포트 0이 80이 된다. `:abc`·`:99999`는 `ValueError`가 그대로 나간다.
  - 내장 `idna` 코덱은 IDNA 2003이다. `faß.de`가 다른 도메인인 `fass.de`가 된다. IDNA 2008은 `xn--fa-hia.de`다.
  - 쿼리를 보지 않고 `Endpoint`에 담지도 않아 `?k=1`이 조용히 사라진다.
  - `normpath`가 원문 `..`를 풀고(`/a/../mcp` → `/mcp`) `//mcp`는 그대로 둔다.
  - `IPv6Address("::ffff:127.0.0.1").is_loopback`이 True라 http 루프백 검사를 통과한다.
  - IPv6의 `is_reserved`는 `::1`을 포함한 `::/8`이라, 특수 주소 검사에 쓰면 루프백까지 막힌다.
  - 그래서 참고 코드는 #49(`67763dc`)에서 빼고, 13.2절이 10.1절 규칙과 이 모듈을 가리키게 바꿨다.

## 한 일

- **`security/endpoints.py`**(새 모듈). 파일·네트워크 접근과 이름 해석을 하지 않는다. 이벤트 루프에서 바로 불러도 된다.
  - **`normalize_endpoint(url) -> Endpoint`:** 검사하고 정규형을 돌려준다. 등록 화면이 저장 전에 쓴다.
  - **`canonical_endpoint(url) -> str`:** 정규형과 정확히 같은 문자열만 통과시킨다(`URL_NOT_CANONICAL`). 설정 로더와 transport가 쓴다. 조용히 고쳐 쓰지 않아서 Registry·transport·설정 파일이 같은 문자열 하나를 본다.
  - **`Endpoint(scheme, host, port, path)`와 `.url`:** host는 ASCII 소문자 이름·점 십진 IPv4·압축 IPv6(대괄호 없이)이고, port는 기본값을 채운 실제 포트다. `.url`은 기본 포트를 생략한다.
  - **`EndpointError(ValueError)`:** 메시지는 고정 코드 하나다. 입력 원문을 싣지 않고, 입력 문자를 담는 idna 오류를 원인으로 달지 않는다(I9).
  - `ENDPOINT_REJECT_CODES`(12개), `MAX_URL_LENGTH`(2048, transport와 같음)
  - 개발문서 13.2절의 `EndpointRejected`는 Ruff N818(예외 이름은 `Error`로 끝남) 때문에 `EndpointError`로 했다.

## B 리뷰 반영(#50)

- **보이지 않는 문자:** UTS #46이 무시하는 문자를 `idna.encode`가 지워서, `exa`와 `mple.com` 사이에 U+200B를 넣은 호스트가 오류 없이 `https://example.com/`이 됐다. "조용히 고쳐 쓰지 않는다"는 원칙과 B의 숨은 문자 표시 규칙에 맞게, IDNA 전에 서식 문자(Cf)와 UTS #46이 지우는 문자를 `URL_HOST`로 거부한다. 판정은 `idna.uts46_remap`으로 문자 하나씩 한다.
  - B는 idna 3.10에서 U+180E가 `URL_IDNA`로 거부된다고 봤다. 고정 버전 3.20에서는 U+180E도 지워지는 문자라 이번 수정 전에는 통과했다. UTS #46 표가 idna 버전마다 다르므로 전수 검사로 확인한다.
  - U+200C·U+200D·U+202E 같은 서식 문자는 전에는 `URL_IDNA`였고 이제 `URL_HOST`다.
- **IPv4를 담은 IPv6:** B가 찾은 SIIT(`::ffff:0:0:0/96`, `https://[::ffff:0:7f00:1]/`)가 `ipv4_mapped` 범위 밖이라 통과했다. 같은 이유로 남는 한계에 있던 NAT64·6to4와 Teredo까지 한 목록으로 막는다. 모두 결정 문구의 "IPv4를 담은 IPv6"에 들어가고, https 정상 endpoint가 이 주소를 쓸 일은 없다.
- **B 연결 방식:** 아래 "A·B 연결"의 B 항목을 B 제안대로 서버별 실패로 바꿨다.

## A·B 연결

- **B(`services/catalog.py` `ServerSettings`, B 리뷰에서 합의):**
  - 설정 형식(문자열 여부·길이, transport별 필드 유무)은 지금처럼 파일 전체 검사다.
  - `url` 값은 서버별로 `canonical_endpoint`를 부른다. 실패하면 그 서버를 "URL 확인 필요"(C 고정 코드 그대로)로 표시하고 Catalog·Registry 등록·연결에서 뺀다. 다른 서버와 앱은 계속 동작한다(URL-01·EXE-01의 "검증에 실패한 서버만 연결하지 않는다").
  - field validator에서 부르면 `EndpointError`가 파일 전체 손상(`CatalogConfigError`)이 된다. 그러면 규칙이 엄격해질 때(idna 갱신, 주소 범위 추가) 예전에 정상으로 저장된 URL 하나 때문에 앱이 시작하지 못한다.
- **A transport(`_endpoint_url`):** 맨 앞에서 `canonical_endpoint`를 부른 뒤 `httpx.URL`을 만든다. 지금 규칙보다 넓어지는 것은 http `127.0.0.0/8`(URL-01)뿐이다.
- **A 등록 화면(`_url_error`):** `normalize_endpoint`로 정규형을 만들어 보여 주고 그 값을 저장한다. 거부는 `ENDPOINT_REJECT_CODES`의 코드별 문구로 보여 준다. 입력과 정규형이 다르면(IDNA 변환 등) 저장 전에 정규형을 보여 주어 동형 문자가 `xn--`로 드러나게 한다.

## 남는 한계

- 이름 해석을 하지 않는다. 등록한 https 이름이 나중에 사설·루프백·메타데이터 주소로 풀려도(DNS 재바인딩) 막지 않는다. 신뢰 판단은 등록 여부로만 한다(개발문서 4.3절).
- https에서는 `localhost`·`foo.localhost` 같은 이름이 통과한다. http만 루프백 IP 리터럴로 제한한 결정과 같다.
- 보이지 않는 문자 집합은 idna의 UTS #46 표를 따른다. idna를 올리면 전수 검사 테스트가 새 표로 다시 확인한다.
- 경로에 `%`가 필요한 endpoint는 등록할 수 없다.
- 리다이렉트·프록시·쿠키·주변 인증은 transport 범위다(개발문서 9장).

리뷰: A(transport·등록 화면 연결), B(`ServerSettings.url` 연결).
