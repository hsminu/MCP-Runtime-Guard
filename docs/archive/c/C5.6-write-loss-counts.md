# C5.6 · 쓰기 응답 유실과 리다이렉트(인수 기준 3)

관련: c-status 인수 기준 3("쓰기 응답 유실 후 UNKNOWN_OUTCOME, 새 호출 ID·재연결로도 추가 전송 0"), I8(결과 불명 쓰기 자동 재전송 금지), README "redirect·자동 인증·POST 재시도를 사용하지 않는다", 개발문서 9장, C5.4(요청별 계수 하니스), C6.9(#56).

## 배경

- SEND가 서버에서 실행된 뒤 응답을 잃으면 Guard는 결과를 모른다. 이때 그 Task를 UNKNOWN_OUTCOME으로 잠그고, 어떤 경로로도 같은 쓰기를 다시 보내지 않아야 한다(I8).
- C5.4의 계수 하니스(제품 조립 Guard, C `ServerRegistry`, 실제 stdio·HTTP 서버, 요청별 계수)에 서버 쪽 유실 동작을 더해 끝까지 센다.

## 한 일

- **`tests/unit/c_counting.py`**
  - 서버 동작을 SEND `body` 표지의 머리말로 고른다.
    - `hang-`: 실행한 뒤 응답하지 않는다.
    - `late-`: 실행한 뒤 3초 늦게 응답한다. 호출 시간 제한(1.5초)이 지난 뒤 도착한다.
    - `exit-`(stdio): 실행한 뒤 서버 프로세스가 끝난다.
    - `error500-`(HTTP): 실행한 뒤 응답 대신 500을 보낸다.
    - `redirect307-`·`redirect308-`(HTTP): 실행하지 않고 `/redirected`를 가리킨다. 그 경로에 온 요청은 따로 센다.
  - 호출 시간 제한(`call_timeout_s`)을 정할 수 있다. Guard를 같은 Store에 새 연결(stdio는 새 프로세스)로 다시 조립할 수 있다(`close_guard` → `assemble(create_tasks=False)`). call_seq는 실행 전체에서 하나를 쓴다.
  - `close_guard`는 Guard를 닫을 때 transport가 알린 `DispatchError`의 종류(`exception_type`)를 `close_errors`에 남기고 계속한다. `str()`은 언제나 Reason `POST_DISPATCH_ERROR`라 종류를 구분하지 못한다(A 리뷰 1번).
  - 하니스는 끝날 때 Store 종료를 확인(`wait_closed`)한 뒤 앱 잠금을 푼다(REC-01, B 리뷰 1번).

## 확인된 것: Guard를 닫을 때의 transport 실패 보고(A 확인 사항)

- HTTP에서 실패한 요청(500, 307·308)이나 닫을 때 진행 중인 요청(응답 없음)이 있으면, Guard를 닫을 때 `AssembledGuard.aclose()` → `McpTransport.close()`가 `DispatchError`를 던진다. 종류(`exception_type`)는 `SessionCloseFailed`이고 `str()`은 Reason `POST_DISPATCH_ERROR`다. stdio의 같은 경우와, 늦은 응답이 도착한 뒤(3.5초 대기) 닫은 HTTP에서는 던지지 않는다.
- 결과 불명 처리와는 별개다. 위 계수와 Task 잠금은 모두 기대대로다.
- 원인(A 리뷰 2번, mcp 1.29.0): SDK `streamable_http_client`는 요청마다 task group 작업을 띄우고 그 안에서 `raise_for_status()`를 부른다. 작업이 오류로 끝나면 세션 전체가 취소되고, 닫을 때 예외 묶음(`ExceptionGroup`)이 올라온다. httpx 클라이언트 닫기와 세션 종료 요청은 그 전에 끝나므로 정리는 실제로 된다.
- 제품 종료 경로에서는 `SessionRuntime.close()`가 `aclose()`를 먼저 부르고 `finally`에서 Store를 닫는다. `aclose()`가 실패해도 Store는 닫힌다. 예외는 그대로 올라가 bridge의 `_cleanup_bindings`가 정리 실패로 보고 `CLEANUP_UNCONFIRMED`가 되며, A110에 따라 앱은 종료 코드 3으로 끝난다.
- A132(#52 `ac1ebad`)는 `httpx.HTTPError`만 담은 예외 묶음을 정리 완료로 본다. 세션이 실패한 사실(worker FAILED, 그 뒤 호출 거부)은 그대로다. 들어가면 이 경우 `close_errors`는 `[]`가 되고 종료 코드 3 경로도 없어진다. 그때 C가 기대값 4개(`CLOSE_ERRORS` 2개, 리다이렉트 시험 2개)를 바꾼다.
- 지금 main의 제품 모드는 Guard를 조립하지 않아(`ProductInputs` 연결 대기) 실제로 나타나지 않는다.

## 남는 한계

- Guard 입구(`submit`)를 직접 부른다. Codex 세션을 거치는 같은 경우는 제품 연결 뒤 T/S 인수(C6.8)에서 다시 본다.
- 연결 중간에 TCP를 끊는 유실은 만들지 않았다. HTTP 쪽 유실은 응답을 보내지 않거나(시간 제한), 늦게 보내거나, 500·307·308로 바꾸는 방식이다. stdio는 응답 없음·늦은 응답·프로세스 종료다.
- C5.6의 나머지(정의 변조, stderr·progress 유출)는 이번 범위 밖이다.
- HTTP 서버는 테스트와 같은 프로세스다(stdio는 별도 프로세스).
- A133 뒤: "죽은 연결 뒤 다른 Task는 예약 전 DENY, 잠금 0, wire 0"을 계수로 확인한다(A 리뷰 3번).
- B6.8 뒤: 하니스의 실행 전체 call_seq 계수를 `store.allocate_call_seq`로 바꿔 제품 순번 경로까지 센다(B 리뷰 2번).
