# C2.11-2 · 파일 서버 인정 조건을 C 함수 하나로(`trusted_file_server_root`)

관련: [#94](https://github.com/hsminu/MCP-Runtime-Guard/issues/94)(출처 규칙, B 답 3번), [#110 C 리뷰](https://github.com/hsminu/MCP-Runtime-Guard/pull/110)(A199), [C2.11](C2.11-file-server.md), [C2.3](C2.3-safe-path.md), EXE-01.

## 왜

- #94에서 정한 것: 자원형 출처 규칙(비어 있지 않은 prefix)은 Guard가 기대 자원 ID를 계산하고, 신뢰 코드가 응답 ID를 만드는 서버에만 쓴다. 지금 그런 서버는 C 파일 서버뿐이다.
- 지금까지 A 조립은 `file_server_root(args)`, 즉 args 모양만 보고 파일 서버 루트를 인정했다. 다른 실행 파일이 같은 args를 흉내 내면 그 서버가 보고하는 자원 ID가 출처 규칙에 쓰일 수 있었다.
- #110 A199가 "command가 앱의 Python일 때만" 조건을 A 조립(`services/product_assembly.py`)에 넣었다. 그러려고 `os`·`sys`를 들였는데, 이 모듈은 위험 연산 통로를 쓰지 못하게 정해 둔 곳이라 A 구조 규칙 시험(`test_module_security_rules`)이 실패했다.
- 인정 조건이 여러 곳에 흩어지면, 다른 호출부가 args만 보고 인정하는 실수가 다시 생길 수 있다.

## 무엇

- `servers/file_server.trusted_file_server_root(transport, command, args) -> Path | None`
  - stdio가 아니면 None
  - `command`가 문자열이 아니거나 비었거나, `os.path.normcase(command) != os.path.normcase(sys.executable)`이면 None
  - 그다음 `file_server_root(args)`(형식 대조)
- 파일 시스템을 읽지 않는다. 같은 파일을 다른 표기(8.3 짧은 이름·정션)로 적으면 인정하지 않는다. 그 서버는 일반 서버가 되어 자원형 READ가 예약 전에 거부되는 닫힌 쪽이다. 등록 화면은 `command`에 `sys.executable`을 그대로 적으므로, 화면으로 등록한 파일 서버는 표기가 같다(#110 A 답).
- 실행 파일 내용은 EXE-01 지문(등록 때 크기·SHA-256, 실행마다 대조)이 맡는다.
- `file_server_root(args)`는 형식 대조로 남는다. 등록 확인(`bridge_registration`)이 사용자가 고른 루트와 args 루트가 같은지 볼 때 쓴다. 인정 판단에는 쓰지 않는다.

## A가 할 것

- #110 A199의 `_file_server_root`를 `trusted_file_server_root(server.transport, server.command, server.args or ())` 호출로 바꾸고, `product_assembly`의 `import os`·`import sys`를 뺀다.
- A199의 회귀 시험(다른 실행 파일이면 `Denied(INTERNAL_ERROR)`, 예약 0·`tools/call` 0)은 그대로 쓴다.

## 시험

- `test_trusted_root_needs_stdio_and_the_apps_own_python`
  - 앱 Python은 그대로, 대문자로, `/` 구분자로 적어도 인정한다.
  - 같은 폴더의 `pythonw.exe`, 경로 뒤에 글자를 더한 것, None·빈 값·숫자, http·None 전송은 인정하지 않는다.
  - args 모양이 틀려도 인정하지 않는다.
