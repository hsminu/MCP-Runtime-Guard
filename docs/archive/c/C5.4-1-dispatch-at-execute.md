# C5.4-1 · host_dispatch를 `ServerWorker._execute` 진입에서 세기

2026-10-30 · 관련: [#106](https://github.com/hsminu/MCP-Runtime-Guard/issues/106) B1.5([C 답변](https://github.com/hsminu/MCP-Runtime-Guard/issues/106#issuecomment-6505180007)), 개발문서 계수 표(`host_dispatch` = `ServerWorker._execute` 진입 수), [C5.4](C5.4-approval-counts.md), I8·I10.

## 배경

- 개발문서 계수 표는 `host_dispatch`의 측정 위치를 `ServerWorker._execute` 진입으로 정한다.
- 그런데 C5.4부터 공용 하니스 `c_counting.count_dispatches`는 그보다 앞인 `McpTransport.call` 진입을 셌다.
- 그래서 worker가 실행 전에 거절·정리한 명령도 1로 셌다.
  - transport가 닫혀 있거나(`WorkerClosed`), 서버를 모를 때(`UnknownServer`)
  - worker 대기열이 가득 찼을 때(`WorkerQueueFull`)
  - 사람이 멈춘 Task의 대기 명령을 `discard_queued`로 정리했을 때(`DispatchStopped`)
- #106에서 B가 "문서대로 `_execute` 진입에서 세도록 하니스만 정렬"을 물었고, C가 오늘 맞추기로 답했다. 그때까지 전체 계수 인수 완료 표시는 보류하기로 했다.

## 한 일

- **`tests/unit/c_counting.py`:** `count_dispatches`가 `ServerWorker._execute`를 감싸 진입마다 기록한다. worker의 `on_dispatch` 콜백과 같은 지점이다. 기록하는 값(요청 ID·도구·인자 표지)은 같으므로 이 하니스를 쓰는 시험은 고치지 않았다.
- **`tests/unit/test_dispatch_count_point.py`(새 시험, stdio·HTTP 2건):** 두 지점이 갈리는 경우를 제품 경로로 만든다.
  1. 응답 없는 SEND(`hang-`)가 서버 worker를 쥔 동안 다른 Task의 SEND가 대기열에 들어간다.
  2. 제품의 Task 정지 순서(A `bridge_commands._stop_task`)대로 `discard_queued` 뒤 취소한다.
  3. 대기했던 SEND는 `McpTransport.call`에는 들어갔지만 host_dispatch·wire·효과·승인 소비가 모두 0이다.
  4. 응답 없는 SEND는 각 1이다(같은 계수가 실행은 센다는 양성 대조). 결과는 `OutcomeUnknown`이다.

## 결함 주입 확인

- `c_counting.py`를 main(`McpTransport.call` 진입) 판으로 되돌리고 새 시험을 돌렸다. stdio·HTTP 모두 "대기했던 요청 ID가 dispatch 기록에 있다"로 실패했다.
- 시험 뒤 원래 바이트로 되돌리고 SHA-256 일치를 확인했다.

## 영향

- 이 하니스를 쓰는 시험 12개 파일(153건)이 바뀐 계수로 모두 통과했다. 지금까지의 C 계수 결론(C5.4·C5.6·C6.8·C6.9·C3.x)은 바뀌지 않는다.
- 0을 단언한 시험은 앞 지점이 더 엄격했으므로 결론이 같다.
- 1을 단언한 시험은 wire·효과도 1이라 실제로 실행된 경우다.

## 남는 것

- 제출 범위의 전체 계수 인수 완료 표시는 B가 #106 기준으로 이 PR 병합 뒤 판단한다.
