# C4.21 · 설정에서 바꾼 도구 종류·인자를 Registry에 반영 (`apply_settings`)

2026-10-29 · 관련: [#46](https://github.com/hsminu/MCP-Runtime-Guard/issues/46) B·C 합의(`record_settings_change`), B6.20([B3.15·B3.16 기록](../b/B3.15-B3.16-server-settings.md)), [#86 C 리뷰](https://github.com/hsminu/MCP-Runtime-Guard/pull/86#issuecomment-6494025432) 2번, A155, I10, T10.

## 배경

- 지금 A155는 다음 순서로 도구 종류 변경을 반영한다.
  1. ACTIVE를 `request_review`로 내린다.
  2. 설정을 저장한다.
  3. 재시작 때 `observe`가 종류 변경을 기록한다.
- 그 사이에는 설정이 Registry보다 앞선다.
  - B Catalog는 그 서버를 `REG_SETTINGS_MISMATCH`로 숨긴다.
  - B는 `observe`가 따라올 수 있게 그 서버를 시작 목록(`startable_servers`)에 남겨 둔다.
- #46에서 정한 순서는 Registry 갱신(`record_settings_change`) → 설정 저장 → 정책 적용 → 다시 활성화다. 이 기록은 C가 맡은 첫 단계다.

## 한 일

### `ServerRegistry.apply_settings`

시그니처: `apply_settings(server, *, expected_row_revision, invalidate_tool=None) -> FingerprintChange`

다른 제어 연산과 같은 잠금을 쓰고, 결과 불명 표시가 있으면 먼저 다시 읽는다.

**쓰기 전 거부(캐시·DB 그대로)**

| 경우 | 코드 |
| --- | --- |
| 설정이 `ServerSettings`가 아님 | `REG_SETTINGS_INVALID` |
| 서버 ID 규칙 위반 | `REG_SERVER_ID_INVALID` |
| 등록에 없는 서버 | `REG_SERVER_UNKNOWN` |
| 경계(`tier`·`max_label`)가 등록과 다름 | `REG_SETTINGS_MISMATCH` |

경계 변경을 저장하는 경로는 B 기록대로 이번 합의 범위 밖이다.

**넘기는 값**

- 등록 도구마다 저장된 정의·지문은 그대로 두고, 새 설정의 `kind`·`destination_arg`·`resource_arg`만 얹는다.
- 설정에 없는 등록 도구는 `OTHER`가 된다. 등록에 없는 설정 도구는 넘기지 않는다. `register`·`observe`와 같은 규칙이다.
- 설정 값은 `ToolSettings`가 이미 검증했고, B 저장소가 입력 전체를 다시 검증한다.

**성공**

- 반환 사본으로 캐시를 바꾼다. 반환과 교체 사이에 await는 없다.
- 그 뒤 바뀐 도구마다 `invalidate_tool`을 부른다. `observe`와 같은 순서다.
- 실제 변경과 상태 전이는 B가 한 트랜잭션에서 한다.
  - ACTIVE는 PENDING이 된다. BLOCKED·PENDING은 그대로다.
  - 바뀐 도구의 검토 설명은 비워진다.
  - 바뀐 것이 없으면 쓰지 않는다.

**결과를 모를 때**

- 저장 호출이 사본을 돌려주지 않는 경우가 대상이다: revision 충돌(`APPROVAL_RACE`), 취소, 예상 밖 예외.
- 이때는 C4.19의 다른 제어 쓰기와 같다. 다시 읽을 때까지 그 서버를 PENDING으로 본다.
- 이를 위해 `_write`가 `RegistryEntry`와 `FingerprintChange`를 모두 받도록 일반화했다.

### 시험

**`tests/unit/test_server_registry.py`:** 실제 SQLiteStore로 시험 함수 7개(9건)를 더하고, 기존 커밋 뒤 취소 시험 2개에 `apply_settings` 매개변수를 하나씩 더했다.

| 시험 | 확인한 것 |
| --- | --- |
| 종류만 바뀌고 ACTIVE가 PENDING | `changed_tools`, 무효화 호출, 캐시 = 반환 = DB, 지문·스키마 그대로, 바뀐 도구의 검토 설명만 비움, 같은 지문으로 다시 활성화 가능 |
| 바뀐 것 없음 | 쓰기·무효화 없음, ACTIVE 유지 |
| 설정에서 빠진 도구·등록에 없는 설정 도구 | 빠진 도구는 OTHER, 없는 도구는 무시 |
| BLOCKED | 종류는 바뀌고 BLOCKED 유지 |
| 쓰기 전 거부 3가지 | 경계 변경·모르는 서버·설정 아님에서 DB·캐시 그대로 |
| 낡은 revision | `APPROVAL_RACE`, DB는 ACTIVE 그대로, 다시 읽기 전에는 PENDING, `refresh` 뒤 ACTIVE |
| B Catalog와 맞물림 | 아래 표 |
| 커밋 뒤 취소(감싼 저장 호출·실제 B6.13 writer) | DB는 PENDING, 결과를 못 받아 캐시는 ACTIVE로 보이지 않음, `refresh`가 DB와 맞춤 |

B Catalog와 맞물리는 단계는 A 순서를 따랐다.

| 단계 | Catalog 결과 |
| --- | --- |
| 반영 전, 새 설정 | `REG_SETTINGS_MISMATCH` |
| 반영 뒤, 설정 저장 전(이전 설정) | 등록이 PENDING이라 노출 없음 |
| 저장 뒤 | 불일치 없음, PENDING이라 노출 없음 |
| 다시 활성화 | 새 종류의 도구까지 노출 |

**`tests/unit/test_guard_path_counts.py`(T10 변형):** 실제 Guard와 stdio·HTTP 서버를 썼다.

- INTERNAL 자료를 읽은 뒤 SEND가 ASK로 대기하는 중에, 사용자가 `send`를 `kind: other`로 바꾼다.
- A가 부를 형태(`invalidate_tool=guard.invalidate_tool`)로 `apply_settings`를 부르면 다음과 같다.
  - 사람이 누르기 전에 대기 승인이 CANCELLED로 닫힌다.
  - 그 뒤의 승인은 `APPROVAL_RACE`로 거부된다.
  - Task는 HALTED다.
  - 승인 소비·dispatch·wire·수신 효과가 모두 0이다.

## 관찰 (막지 않음)

- Guard `invalidate_tool`로 닫힌 대기 승인은 CANCELLED다.
- 기존 T10 시험(정의 변경 `observe`, 무효화 호출 없이 승인)에서는 재판정 때 INVALIDATED다.
- 두 경로 모두 실행은 0이다. 화면에서 둘을 다르게 보일지는 A·B가 정한다.

## 넘길 것

- **A:** A155를 다음 순서로 옮긴다: `apply_settings`(`invalidate_tool=guard.invalidate_tool`) → 설정 저장 → 정책 적용 → 사용자 확인 뒤 `activate`.
  - ACTIVE를 내리던 `request_review` 단계는 필요 없다. 같은 트랜잭션에서 PENDING이 된다.
  - 결과 불명(StoreError·취소)은 지금처럼 등록 쓰기 불명 latch와 재시작으로 처리하고, 재시도하지 않는다.
  - `APPROVAL_RACE`는 쓰지 않은 것이지만, C는 다시 읽을 때까지 PENDING으로 본다. `refresh` 뒤 다시 확인받는다.
- **B:** A가 옮긴 뒤 `startable_servers`에서 `REG_SETTINGS_MISMATCH`도 제외한다(B3.15 기록의 계획).
- **범위 밖(B 기록과 같음):** 경계 변경 저장 경로, 저장소 수준의 종류·인자 조합 검사.
