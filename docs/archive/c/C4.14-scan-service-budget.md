# C4.14 · 검사 서비스 입구와 앱 전체 예산

관련: 2026-10-15 Scanner 운영 상한 결정(서버 검사 1건·대기 8건, 작업 10분, 도구별 LLM 60초·YARA 5초, LLM 동시 4개·YARA worker 1개, 재시도·주기 재검사·캐시 없음), [운영 추천안](../tasks/c-scanner-operating-proposal.md), [C4.9](C4.9-scan-report-translation.md), C4.10 Registry, I6·I9·T17·T19.

## 배경

- C4.9(#57)로 검사 결과를 B `ScanReport`로 옮기고 Registry에 저장할 수 있게 됐다. 하지만 등록 화면이 부를 검사 입구가 없었다.
- 결정한 예산 중 이미 있던 것은 도구별 LLM 60초뿐이었다.
  - **YARA 5초:** SDK 4.8.6 `YaraAnalyzer`는 `self._rules.match(data=content)`를 시간 제한 없이 부르고, C도 상한을 연결하지 않았다(추천안의 "연결 미구현").
  - **LLM 동시 4개:** 집계기가 도구를 하나씩만 검사해서 쓸 수 없었다. Luna p50 약 5초 기준으로 256개 도구는 20분이 넘어 작업 상한을 넘는다.
  - **작업 10분:** 집계기가 끝에 한 번에 반환해서, 시간으로 끊으면 그때까지 끝난 결과도 사라졌다.
  - 대기열과 YARA 전용 작업자도 없었다.

## 한 일

- **`services/scanner.py`(새 모듈): `ScanService`(앱 전체 하나)**
  - **`scan(server_id, listing) -> ScanOutcome(scan_id, report, entry)`**
    1. 목록 지문(`listing_fingerprints`)이 지금 등록과 같은지 본다. 다르면 검사하지 않는다. 대기 전과 차례가 온 뒤에 두 번 본다.
    2. 대기열에서 차례를 기다린다.
    3. 검사기를 열어 검사한다.
    4. `scan_report`로 번역한다.
    5. `ServerRegistry.record_scan`으로 저장한다.
    - `scan_id`는 `scan-<128비트 난수 16진>`이다. 10분 검사 동안 Registry lock은 잡지 않는다.
  - **오류 코드(`ScanError`, 모두 기록 없음)**

    | 코드 | 경우 |
    | --- | --- |
    | `SCAN_QUEUE_FULL` | 대기 8건이 찬 상태에서 새 요청 |
    | `SCAN_SERVER_UNKNOWN` | 등록되지 않은 서버 |
    | `SCAN_LISTING_NOT_REGISTERED` | 목록이 지금 등록과 다름 |
    | `REG_LISTING_*` | 목록을 지문으로 만들 수 없음 |
    | `SCAN_JOB_TIMEOUT` | 검사기 연결이 멈춰 상한 뒤 30초 여유까지 넘김 |
    | `SCAN_REPORT_*` | 번역 실패 |
    | `SCAN_BUDGET_INVALID` | 예산 값이 잘못됨 |

  - **`cisco_connector(environ=None)`:** 제품 검사기 연결이다.
    - LLM 키는 넘긴 값으로만 받고, `.env`나 프로세스 환경을 읽지 않는다.
    - C2.10 전에는 빈 값이라 LLM은 `SCAN_LLM_KEY_MISSING_OR_INVALID`로 준비 실패하고 YARA만 돈다.
  - `close()`로 YARA 작업자를 정리한다. `waiting`은 대기 수(진행 중 1건 제외)다.
- **예산 구현**

  | 결정 | 구현 |
  | --- | --- |
  | 서버 검사 1건 + 대기 8건 | `asyncio.Lock` 차례와 대기 수. 깨어난 대기자가 아직 lock을 잡기 전에도 대기로 세서 9건을 넘지 않는다. 대기 중 취소는 자리를 돌려준다 |
  | 작업 10분 | 실행 시작부터 잰다(대기 제외). 집계기에 마감 시각을 넘긴다. 끝난 분석기 결과는 남고, 끊긴 분석기는 시작했으면 failed, 시작 전이면 not_run이며 둘 다 `SCAN_INCOMPLETE`다. 이 미완료 보고서를 기록한다 |
  | LLM 동시 4개 | 앱 전체 세마포어. 집계기는 도구 4개까지 동시에 검사하고 결과 순서는 그대로다 |
  | YARA worker 1개 | 서비스가 가진 `ThreadPoolExecutor(max_workers=1)`. 검사기 연결이 이 작업자를 YARA 실행에 쓴다 |
  | 도구별 YARA 5초 | SDK 분석기의 `_rules`를 `_TimedRules`로 감싸 `match`에 `timeout=5`를 넣는다(SDK 파일 수정 없음). 넘으면 native `TimeoutError` → `SCAN_YARA_TIMEOUT`. `_rules`가 없으면 `SCAN_YARA_SDK_SETUP_FAILED` |
  | 도구별 LLM 60초, 재시도 0 | 기존 그대로 |
  | 주기 재검사·결과 캐시 | 없음. 새로 붙이지 않았다 |

- **취소 처리(사용자 선택: 추천안)**
  - 사용자 취소·앱 종료로 검사가 취소되면 보고서를 기록하지 않는다. 그 검사로는 활성화할 수 없고, 다시 검사하면 된다.
  - 진행 중 LLM 요청은 바로 끊긴다. YARA 스레드는 강제로 멈출 수 없어서 native 상한 안에 끝난다.
  - 운영 추천안의 "완료 결과 보존"은 작업 시간 초과에만 적용했다.
- **`adapters/cisco_aggregation.py`**
  - `InternalMetadataScanner.scan(…, deadline=, tool_concurrency=, llm_slots=)`. 기본값(마감 없음, 동시 1, 슬롯 없음)이면 예전과 같이 한 도구씩 돈다.
  - 분석기의 예상 밖 예외는 그 도구의 다른 분석기를 기다린 뒤 올리고, 다른 도구는 취소한다.
  - `connect_metadata_scanner(…, yara_executor=, yara_timeout_s=5)`
- **A 구조 테스트(`tests/unit/test_a_architecture.py`):** 새 모듈 `scanner`를 `OTHER_SERVICES`에 넣었다(A 리뷰 필요).
- **YARA 상한 실측(2026-10-28, yara-python 4.5.4)**
  - 일치 위치마다 이중 반복하는 규칙으로 64KB(정의 상한) 입력을 돌렸다. `timeout=1`은 1.001초, `timeout=5`는 5.003초에 `TimeoutError`가 났다.
  - 512바이트 입력은 0.0009초에 끝난다.
  - [근거](../evidence/c4.14-yara-timeout-2026-10-28.json)
- **테스트**
  - **`tests/unit/test_scan_service.py`: 15개.** 실제 집계기·SQLiteStore·Registry에 분석기 대역을 쓴다.
    - 기록과 그 `scan_id`로 활성화, 상태는 검사로 바뀌지 않음
    - 목록 다름·모르는 서버·미완료 목록은 분석기·연결 0
    - 도구 12개에서 LLM 최대 동시 4, YARA 최대 동시 1(스레드 안에서 잼)
    - 1건 실행 중 8건 대기, 10번째는 `SCAN_QUEUE_FULL`, 대기 중에는 검사기를 열지 않음
    - 대기 중 취소는 자리를 돌려줌
    - 작업 시간 초과: 끝난 결과와 `SCAN_INCOMPLETE` 진단을 기록하고, 붙잡힌 LLM 4개는 취소. 시작 못 한 도구는 두 분석기 모두 미완료
    - 사용자 취소: 기록 0, 다음 검사 정상
    - 멈춘 연결: `SCAN_JOB_TIMEOUT`, 기록 0
    - 예산 값 검사 5가지, 기본값이 결정값
  - **`tests/unit/adapters/test_yara_budget.py`: 4개.** 실제 yara-python 느린 규칙이 1초 상한에 끊긴다. 호출자의 timeout을 덮는다. 전용 작업자에서 `SCAN_YARA_TIMEOUT`이 된다.
  - **`tests/contract/test_scan_service_sdk.py`: 3개.** 실제 Cisco SDK·native YARA, HTTP만 대역이다.
    - 서비스 입구부터 끝까지 두 분석기 완료, 활성화 성공. 공격 문구·키는 보고서에 없다.
    - 제품 연결은 프로세스 환경의 키를 읽지 않는다.
    - 실제 SDK 분석기의 `_rules`가 감싸져서 느린 규칙이 1초에 끊긴다.
  - `tests/unit/adapters/test_scanner_event_loop.py`의 YARA 준비 대역을 새 인자에 맞췄다.

## A·B 연결

- **A 조립:** 앱 시작 때 `ScanService(registry, cisco_connector(environ))`를 하나 만들고, 끝낼 때 `close()`를 부른다. C2.10 전에는 `environ` 없이 만든다.
- **A 등록·재확인 화면**
  1. transport로 `tools/list`를 받는다.
  2. `registry.register(server, listing)`
  3. `scan_service.scan(server.id, listing)`
  4. `outcome.report`로 경고를 보인다(C4.13 자료).
  5. 사용자가 확인하면 `activate(…, reviewed_scan_id=outcome.scan_id)`
  - 정의가 바뀌어 PENDING이 되면 같은 순서로 다시 검사한다.
  - `SCAN_QUEUE_FULL`은 "검사 요청 미접수, 나중에 다시"로 보인다.
- **B:** C 소유 테스트 리뷰

## 남는 것

- **진행 표시:** 추천안의 진행 정보(도구 수·분석기별 완료 수·경과 시간)는 아직 입구가 없다. A 화면 요구가 나오면 더한다.
- **LLM 동시 4개 실측:** 실제 API에서 계정 요청 한도 안인지, 256개 도구가 10분 안에 끝나는지는 실제 키로 재야 한다(C4.16과 함께).
- **연결 중 멈춤:** SDK 첫 import는 수십 초 걸릴 수 있다. 연결이 멈춘 경우의 강제 중단은 작업 상한 뒤 30초 여유에서 일어난다.

리뷰: B(테스트), A(조립·등록 화면, 구조 테스트 분류).
