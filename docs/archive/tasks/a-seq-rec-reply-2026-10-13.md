## SEQ-01 · 계수 의미 — 동의

- B 권장안에 동의한다. Task ID가 같은 동안 계수가 증가하고, epoch가 바뀌어도 0으로 되돌리지 않는다. 첫 신규 값은 1이고 공백을 허용한다. 커밋된 배정은 회수하지 않는다.
- A 영향:
  - UI는 `call_seq`를 `model_call_id`나 화면의 호출 번호와 섞어 표시하지 않는다. 지금은 `call_seq`를 화면에 노출하지 않는다.
  - 새 Task 생성은 이미 bootstrap의 `create_task` → `load_task` 확인 경로를 쓴다(`7ed173d`).
- A 임시 처리 종료 조건: 영속 할당기가 들어오면 "실행마다 새 Task + 메모리 카운터"([B-SQL-01](a-b-sqlite-requests-2026-10-13.md))를 제거한다.

## SEQ-02 · 호출 입구·오류 — 동의(조건부)

- 기존 `next_call_seq(task_id) -> Awaitable[int]` 콜백을 유지하는 데 동의한다. A bootstrap은 같은 `SQLiteStore` 인스턴스에 묶인 B 할당기를 주입한다. Store Protocol 메서드인지 별도 객체인지는 B가 정해도 된다. A는 이름에 의존하지 않는다.
- `expected_epoch`는 추가하지 않는 쪽에 동의한다. 반환된 int를 epoch 결속의 증거로 쓰지 않는다는 B 설명을 받아들인다. epoch 결속은 기존 `record_decision`과 승인 CAS에 남는다.
- 조건(A 요청):
  1. 할당 실패나 rollback이 확인된 경우는 예약 전 실패로 처리한다. Guard가 `Denied`로 돌려주면 A Runner는 이미 정지 처리한다.
  2. **할당 COMMIT 불명은 메모리 전역 정지만으로 끝나면 안 된다.** A의 UI와 Runner가 권위 상태(Store 조회)로 알 수 있어야 한다. 이 요청은 [B-QA-03](a-b-qa-requests-2026-10-13.md)과 같은 문제다.
  3. 실패 Reason은 고정 코드로 정한다. A는 이 코드를 UI의 고정 문구에 연결한다.
- A 변경: `examples/synthetic_app.py`의 `sequence()` 메모리 카운터를 주입된 할당기로 바꾼다. 할당기 생성 실패는 시작 게이트 실패로 처리한다.

## SEQ-03 · 저장 구조·이관 — 동의, 질문 2개

- 독립 계수 테이블과 Task 행 비변경 원칙에 동의한다. 이관 COMMIT과 복구 COMMIT을 별도 단계로 보고하는 데도 동의한다.
- 지원 범위: 같은 파일의 통상 재시작만 보장한다. 오래된 백업 복원은 지원하지 않는다는 B 안에 동의한다.
- 질문:
  1. v1→신규 스키마 이관을 `SQLiteStore` 생성자가 자동으로 하는가, 아니면 별도 명시 단계인가?
     A는 이관 시점에 대한 입장을 정하지 않고 B의 선택을 묻는다. 어느 쪽이든 이관 실패, 미지원 버전, 변조 스키마를 구분하는 고정 코드가 필요하다. A는 이 코드로 시작을 막고, UI에는 "DB 버전 미지원/이관 실패"만 표시한다.
  2. 이관 전 백업 사본이 필요한가? 필요하다면 파일 복사는 C 안전 파일 연산 소관이다. B와 A가 직접 만들지 않는다.
- A가 이미 만든 v1 DB(`7ed173d` 이후 데모 실행본)는 이관 대상이다. 옛 비종결 Task는 복구로 정지되며, 정지돼도 A 쪽에 문제는 없다.

## REC-01 · 시작 barrier·단일 소유 — 동의(수정 요청 포함)

- 현재 A 사실:
  - bridge는 `READY` 전에 실행·제어 큐를 만들지 않는다. 그 전의 요청은 `NOT_READY`로 거부한다(`services/bridge.py:357`, 681–689).
  - 재시작 후 옛 approval_id로 승인하면 `CONTROL_DENIED_QUERY_REQUIRED`가 나고 dispatch는 0이다(`7ed173d` QA).
- A 시작 순서 제안. B 4절 순서에 맞추고 A 담당 단계를 구체화했다.

  ```text
  bridge STARTING (실행·제어 접수 차단, 기존 동작)
    → [C] DB 인스턴스 단일 소유 잠금 획득        ← C 안전 연산 필요
    → [B] SQLiteStore 열기·스키마 검사/이관
    → [B] 시작 복구 트랜잭션·성공 ACK(RecoveryReport)
    → [C] Registry/지문 준비 (현재 B 대역)
    → [A] AGT 시작 → MCP transport 시작
    → [A] 새 Task 생성·확인 → 새 Guard·Runner
    → bridge READY (실행·제어 개방)
  어느 단계든 실패·확정 불가 → STARTUP_FAILED, 이미 만든 자원은 역순 정리
  ```

- 수정 요청과 의견:
  1. **단일 인스턴스 소유**: A는 앱 수명 동안 잠금을 쥐고 마지막에 해제하는 방식을 원한다. 잠금은 AsyncExitStack에 맨 처음 등록한다. 잠금 획득과 해제는 C 안전 파일·프로세스 연산으로 제공해 달라고 C에 요청한다. 제공 전에는 "같은 DB에 앱 두 개 실행은 미지원, 검증 불가"로 문서화한다. A가 임시 잠금을 직접 구현하지는 않는다(사용자 결정).
  2. **Store 쪽 이중 차단**: A barrier와 별도로, Store도 복구 ACK 전에는 실행 연산을 거부하는 안에 동의한다. A barrier에만 의존하지 않는다.
  3. **같은 프로세스 재초기화**: 이전 bridge가 `CLOSED`(정리 확인)일 때만 새로 시작한다. `CLEANUP_UNCONFIRMED`면 같은 프로세스에서 다시 시작하지 않고 프로세스 재시작을 안내한다. 이 경로는 **A 구현과 검증이 필요하다**(현재 미검증).
  4. 시작 중 UI는 고정 진행·실패 코드만 표시한다. DB 행은 읽어 보여 주지 않는다.

## REC-02 · 상태 표·split 중단·v1 종류 유실 — 부분 동의, 대안 선호

- 5절 상태 표와 우선순위(신뢰 DISPATCHING SEND의 UNKNOWN_OUTCOME > 그 외 HALTED)에 동의한다. PENDING과 APPROVED 승인의 실행 권한 폐기, CONSUMED 보존, RUNNING 복귀 금지에도 동의한다.
- A 표시 요구:
  - 옛 Task는 읽기 전용 목록에 HALTED나 UNKNOWN_OUTCOME으로 표시한다. 다시 실행하는 버튼은 두지 않는다. 이를 위해 목록 조회 API가 필요하다([B-SQL-03](a-b-sqlite-requests-2026-10-13.md)).
  - 결과 불명 SEND는 "결과 불명 · 수신처에서 직접 확인 필요"로 표시한다. 자동 재전송과 재확인 전송은 하지 않는다.
  - 사람 확인 행위가 상태 전이를 만드는지는 미결이다. A 1차 구현은 표시만 한다.
- **v1 종류 유실 DISPATCHING 행**:
  - B 기본안은 게이트를 닫는 것이다. 이 경우 행이 하나라도 있으면 앱을 쓸 수 없고, 운영자의 해제 절차도 정의돼 있지 않다.
  - A는 **격리 대안을 선호한다**: 종류 미확정 요청을 결과 불명으로 격리하고 새 Task만 허용한다. 조건은 다음과 같다.
    - READ로 추정하지 않는다. 결과를 공개하지 않는다.
    - 추가 SEND와 자동 재시도는 0이다.
    - UI에 "종류 미확정·결과 불명"으로 따로 표시한다.
    - 격리 사실을 감사에 남긴다.
  - 게이트를 닫는 안을 유지한다면 운영자 해제 절차를 함께 정해 달라고 요청한다.
- U8(HALTED/CLOSED + DISPATCHING SEND)의 예외 전이와 별도 격리 중 무엇을 고를지는 B·C 판단에 맡긴다. A의 요구는 어느 쪽이든 UI가 SEND 결과 불명을 볼 수 있어야 한다는 것뿐이다.

## REC-03 · epoch와 새 Task 관계 — B안 선호

- A는 재시작 때 Task ID를 재사용하지 않는다. 대화·캐시·Runner도 Task ID 단위로 격리한다. 그래서 **B안을 선호한다**: 옛 종결 Task의 epoch를 보존하고, 새 Task ID와 새 회차의 관계를 영속으로 기록한다.
- A 영향:
  - 새 Task는 빈 대화로 시작한다. 옛 대화와 결과 원문을 복원하지 않는다(현행 동작).
  - 옛 Task나 옛 승인 ID로 오는 명령은 거부한다.
    - 옛 승인 ID 승인이 Denied가 되고 dispatch가 0인 것은 `7ed173d`에서 검증했다.
    - 옛 Task ID 실행 명령의 거부는 아직 검증하지 않았다.
  - 관계 기록이 생기면 UI에 "이전 작업 → 새 작업" 연결을 읽기 전용으로 표시할 수 있다. 필수 요구는 아니다.

## REC-04 · 버전·반복 적용·RecoveryReport — 동의

- ACK와 projection을 분리하는 데 동의한다. A는 RecoveryReport 성공 ACK와 다른 구성 요소의 준비가 **모두** 끝나야 `READY`로 둔다.
- A가 읽을 Report 필드 후보(원문 없음): 스키마 버전, 복구 run 식별자, 변경된 Task·요청·승인 수, UNKNOWN_OUTCOME 수, 격리 수(REC-02 대안을 채택할 때), 미해결 수.
- 미해결 수가 0보다 크면 A는 게이트를 닫는다. REC-02 격리 대안을 채택하면, 격리된 항목은 해결된 것으로 센다.
- UI에는 고정 코드와 개수만 표시한다.

## REC-05 · 실패·예산 — 동의, 예산 질문

- 동의 범위:
  - 복구나 이관이 실패하면 닫힌 상태를 유지한다.
  - COMMIT 불명이면 연결과 bindings를 폐기하고 같은 프로세스에서 자동 재시도하지 않는다. 재시작을 안내한다.
  - ACK를 잃은 뒤 새 인스턴스가 DB를 다시 읽어 판별하는 방식에 동의한다.
- 예산 질문:
  - bridge 시작 timeout 기본값은 10초다(`services/bridge.py:167`). 큰 DB에서는 복구가 10초를 넘을 수 있다. 그러면 지금은 `STARTUP_FAILED`와 정리 경로로 간다.
  - B가 측정한 복구 시간 상한을 받으면 A는 시작 timeout을 복구 단계용으로 따로 설정한다.
  - `busy_timeout_ms=1000`과 COMMIT I/O 상한을 제품 예산으로 정하는 일은 B·C 측정을 따른다.
