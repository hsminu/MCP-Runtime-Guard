# 4단계 · Qt bridge와 앱 수명

[공통 규칙](README.md)을 적용한다. 네 작업은 `services/bridge.py`와 시작 경로를 공유하므로 순차로 연결한다.

## A24

### Qt 메인 스레드와 asyncio backend 분리

```text
A24를 실행해줘. docs/tasks/a-prompts/README.md의 공통 실행 규칙을 적용해.

목표: Qt UI는 메인 스레드, asyncio 실행은 backend 스레드에서 동작하는 실제 연결 기반을 구현한다.
선행 조건: A02의 Qt/API 근거, A05의 합의된 불변 명령/이벤트 계약, 필요한 패키징 담당 배정. HTML 시안을 웹앱으로 제품화하는 작업이 아니다.
수정 범위: services/bridge.py, 필요한 ui 진입부와 __main__.py, A 소유 단위 테스트. 실제 필요한 코드만 만들고 전체 예정 구조의 빈 파일을 만들지 않는다.

작업:
1. Qt 객체 수명·signal/slot 전달과 backend event loop/thread 수명을 설치 버전에 맞춰 구현해.
2. UI에서 네트워크 future.result/join 같은 동기 대기를 하지 않고 비동기 명령과 확정 이벤트로 상태를 갱신하게 해.
3. thread를 넘어가는 payload는 합의된 불변 메시지로 제한해. session·transport·DB connection·mutable raw result를 UI에 넘기지 마.
4. 준비 중/준비 완료/시작 실패를 구별하고 준비 전 실행 요청은 계약대로 거절하거나 제어해. 예외 원문을 UI로 보내지 마.

완료 기준: 실제 Qt 앱이 뜨고 backend 지연에도 UI event loop가 동작한다. worker thread가 위젯을 직접 수정하거나 UI가 backend future를 동기 대기하는 경로가 없다.
검증: 스레드 소유·메시지 전달·시작 실패의 단위 검증과 가능한 실제 Qt 스모크를 실행해. 실제 GUI 실행 불가면 대역 검증과 분리 보고해.
연결: 설계 2·12.1절, I1·I5·I9, T08의 구조 요구.
```

## A25

### 실행 큐와 사람 전용 제어 큐 분리

```text
A25를 실행해줘. docs/tasks/a-prompts/README.md의 공통 실행 규칙을 적용해.

목표: 승인 대기나 느린 실행 중에도 사람이 승인·거절·취소·긴급 차단을 처리할 수 있게 한다.
선행 조건: A24, B의 승인/취소/차단 API와 신뢰 사람 주체 계약.
수정 범위: services/bridge.py와 A 소유 단위 테스트. 승인 소비·Task lock은 B 구현을 사용한다.

작업:
1. 일반 실행 명령 큐와 사람 전용 제어 큐를 분리하고, 제어 큐가 실행 worker의 사람 승인 대기를 기다리지 않게 해.
2. 승인자·Task·요청 식별자는 신뢰 UI/backend 맥락에서 가져와. 모델/도구 출력이 제어 명령을 생성하거나 승인자 값을 정하지 못하게 해.
3. 명령 접수/처리 중/적용 완료/거절을 구별해 이벤트로 전달하고 같은 제어 명령 재전달은 합의된 식별자·원자성 경계로 처리해.
4. 큐가 차거나 종료 중일 때의 제어 명령 처리 계약을 적용해. 보안 제어를 조용히 버리거나 UI에서 적용 완료로 낙관 표시하지 마.

완료 기준: WAITING_APPROVAL에서 취소·긴급 차단이 backend에 도달하고, 처리 확정이 UI로 돌아온다. 실제 전송 중 취소를 원격 부작용 취소로 오인하지 않는다.
검증: 느린 실행과 승인 대기 상태에서 제어 큐 처리·중복 명령·종료 경합을 단위 검증해. C의 T20과 T12로 실제 교착 없음/1회 소비를 확인해. lock 소유 규칙은 B 리뷰 결과와 대조해.
연결: 설계 7.2·8.5·12.1절, I1·I3·I7·I8, T12·T20.
```

## A26

### 확정 이벤트 기반 상태 갱신과 재동기화

```text
A26을 실행해줘. docs/tasks/a-prompts/README.md의 공통 실행 규칙을 적용해.

목표: UI가 backend 확정 상태만 보여주고 중복·역순·지연 이벤트로 상태를 되돌리지 않게 한다.
선행 조건: A24/A25, A05에서 확정된 snapshot/이벤트/조회·ID/리비전 계약.
수정 범위: services/bridge.py와 ui의 표시 상태 모델, 해당 단위 테스트. 저장소 조회 구현이나 정책 판단은 만들지 않는다.

작업:
1. Task·요청·승인·등록·세션·검사·감사 상태의 신뢰 원천과 표시 모델을 분리해. 클릭 결과를 실행 성공·ACTIVE·연결 성공으로 즉시 바꾸지 마.
2. 계약된 ID/리비전/순서 근거로 중복·오래된 이벤트를 처리하고, timestamp만으로 최신 여부를 임의 결정하지 마.
3. snapshot 조회와 실시간 이벤트의 연결, 누락 감지/재조회, 선택 항목 삭제/무효화, 조회 실패/재시도 표시를 구현해. 재조회는 읽기이며 실행 명령 재전송으로 연결하지 마.
4. 공개가 허용된 메타데이터만 UI 모델에 보관해. 승인 메모리 사본은 별도 수명으로 관리하고 raw result를 일반 상태 저장소에 넣지 마.

완료 기준: 늦은 승인/연결/스캔 이벤트가 현재 상태를 덮어쓰지 않고, 조회 실패가 '0건/안전/성공'으로 표시되지 않는다. 화면 간 집계·선택·상세가 같은 확정 상태를 참조한다.
검증: 중복·역순·다른 Task·오래된 서버 세대·조회와 이벤트 경합·누락/재동기화·빈 데이터와 오류를 구분하는 단위 테스트를 작성해.
연결: 설계 8·10.1·12장, I3·I5·I7·I9·I10, T10–T12·T29의 표시 요구.
```

## A27

### 앱 시작·부분 실패·종료 순서

```text
A27을 실행해줘. docs/tasks/a-prompts/README.md의 공통 실행 규칙을 적용해.

목표: 실제 구성요소를 조립하고 시작 실패와 종료 중에도 불명 SEND·승인·future·DB 수명이 올바르게 처리되게 한다.
선행 조건: A10/A21/A24–A26, B 구성 API, C DB 단일 writer/Registry 수명 계약, 합의된 설정 로더.
수정 범위: __main__.py, services/bridge.py, 필요한 A worker/Runner 정리부와 단위 테스트. DB 종료를 A가 직접 다른 스레드에서 수행하지 않는다.

작업:
1. 신뢰 설정 검증, 저장소/서비스 준비, backend 시작, UI 사용 가능 전환의 의존 순서를 실제 계약대로 연결해. 부분 준비 상태에서 Run이 열리지 않게 해.
2. 시작 단계별 실패에서 이미 열린 A 자원을 닫고 안전한 오류 코드를 표시해. 예외 원문이나 비밀 설정을 출력하지 마.
3. 종료 요청 시 새 실행을 막고, 대기/진행 명령의 상태를 확정하며, worker 세션을 소유 task에서 닫고 backend 큐/loop/thread와 C DB를 합의된 순서로 종료해.
4. 진행 SEND의 종료/취소를 성공이나 미실행으로 확정하지 마. 결과 불명은 B에 전달하고 승인 사본은 재시작 시 복원하지 않아야 해.

완료 기준: 정상 시작/종료와 부분 초기화 실패 경로가 모두 정리된다. 무기한 종료 대기·미확정 future·다른 thread의 세션/DB close가 없다.
검증: 준비 실패 지점별 cleanup, READY/실행 중/승인 대기/SEND 응답 대기 종료를 단위 및 실제 스모크로 확인해. C와 T11/T14/T20/T36 관련 통합을 실행하고 관측 한계를 남겨.
연결: 설계 8.4·9·11.1·12.1절, I3·I6·I8·I9.
```
