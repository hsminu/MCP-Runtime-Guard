## 새 공개 API 제안

모든 메서드는 async다. SQLiteStore 구현은 내부 await 없이 같은 백엔드 스레드의 단일 연결을 사용한다. C는 앱이 쓰는 동일한 SQLiteStore 인스턴스를 RegistryStore로 주입받고 별도 SQL 연결/경로를 만들지 않는다.

| API | 입력·반환과 의미 |
| --- | --- |
| `list_registrations() -> tuple[RegistryEntry, ...]` | 한 읽기 트랜잭션의 전체 사본, server_id 순서. 실행 허가가 아님 |
| `load_registration(server_id) -> RegistryEntry \| None` | 없는 서버는 None, 잘못된 ID는 오류 |
| `register_server(registration, *, at_utc) -> RegistryEntry` | PENDING·revision 0·빈 검토 설명의 RegisteredServer 입력. 저장 revision은 1. 중복 거부 |
| `record_scan_report(scan_id, report, *, at_utc) -> RegistryEntry` | 전역 고유 scan_id와 ScanReport 저장, 마지막 검사 연결. 상태는 유지, 미등록·중복 거부 |
| `activate_server(server_id, *, expected_row_revision, tool_fingerprints, reviewed_by, at_utc, reviewed_scan_id=None) -> RegistryEntry` | PENDING만 ACTIVE. 신뢰 운영자 ID, 사용자가 본 이름→지문 전체 Mapping, 선택한 검사 ID를 받음 |
| `record_fingerprint_change(server_id, tools, *, at_utc) -> FingerprintChange` | 관측 ToolSpec tuple을 revision 전제 없이 저장. 추가·삭제 포함 변경 이름과 전체 사본 반환 |
| `block_server(server_id, *, expected_row_revision, at_utc) -> RegistryEntry` | ACTIVE/PENDING → BLOCKED |
| `request_review(server_id, *, expected_row_revision, at_utc) -> RegistryEntry` | ACTIVE/BLOCKED → PENDING |
| `save_reviewed_descriptions(server_id, descriptions, *, expected_row_revision, at_utc) -> RegistryEntry` | PENDING에서 이름→검토 설명 Mapping으로 부분 갱신. 미등록 도구·기존 2,000자 한계 위반 거부 |

명시하지 않은 상태 전이는 거부한다. 활성화·차단·재검토·설명 저장은 expected_row_revision을 비교한다. 신규 등록에 ACTIVE나 기존 revision을 넣어 우회할 수 없다. `reviewed_by`는 모델·SDK에서 얻지 않는 신뢰된 운영자 ID이며 실제 사람 확인은 A 제어 경로의 책임이다.

기존 최소 연산 이름은 유지했다. 설명 저장 이름은 `save_reviewed_descriptions`로 정했고, 메타데이터와 커밋된 사본을 함께 주기 위해 반환을 감쌌다. A/C가 별도 재조회 없이 동기 캐시를 바꾸는 목적이다.

| 새 DTO | 필드 |
| --- | --- |
| `StoredScanReport` | scan_id, report(ScanReport), stored_at_utc |
| `RegistryEntry` | registration(RegisteredServer), last_scan(StoredScanReport 또는 None), reviewed_scan_id, reviewed_by, updated_at_utc. last_scan_id는 읽기 속성 |
| `FingerprintChange` | entry(RegistryEntry), changed_tools(정렬된 고유 이름 tuple) |

DTO는 기존 Frozen 기반의 strict·frozen·extra forbid다. 시간은 UTC-aware이고 마지막 검사의 서버 소유를 검사한다. 등록·검사·검토자·변경 이름 등 원문이 섞일 수 있는 사본은 새 DTO repr에서 숨겼다. ToolSpec의 input_schema·reviewed_description과 ScanReport의 threat_summary도 기존 repr 비공개를 유지한다.

설명 저장은 PENDING에서만 허용한다. 검토 설명을 바꾸면 현재 승인·모델 노출과 다시 확인할 설명이 섞이지 않게 하고, ACTIVE에서는 먼저 재검토 요청을 하게 하기 위한 보수적 제안이다. 설명 저장으로 자동 활성화하지 않는다. 신규 등록도 검토 설명은 별도 신뢰 입력 단계에서 저장한다.

## 지문·검사 처리

서버 ID는 B의 `valid_server_id`를 그대로 호출한다. 지문은 64자 소문자 hex만 받는다. C가 tools/list 원본 전체를 `digest.tool_fingerprint`에 넣어 계산하고, 저장소는 다시 계산하지 않는다. ToolSpec의 종류·인자·경계는 신뢰 설정에서 온 값이어야 하며 원격 annotation을 등록 권한으로 삼지 않는다.

활성화는 사용자가 본 도구 이름과 지문 전체가 현재 저장 값과 정확히 같아야 한다. 검토 scan_id를 주면 존재·서버 소유·fingerprint_set의 현재 집합 일치를 검사한다. 마지막 저장 검사와 사람이 검토한 검사는 서로 다를 수 있어 별도 포인터로 보관한다. 검사 경고·실패·생략·미완료는 그대로 보관하며 활성화를 자동 거부하거나 안전으로 바꾸지 않는다. 오래된 검사 저장 자체는 허용하지만 현재 지문과 맞지 않는 검사를 선택해 활성화할 수 없다.

관측 변경은 도구 추가·삭제·지문 변경을 잡고, 공급된 지문이 같더라도 스키마·종류·인자 정의가 달라지면 보수적으로 변경으로 취급한다. 단순 도구 목록 재정렬은 변경 이름에 넣지 않는다. 정의 안의 배열 순서 변경은 C의 전체 Tool 지문 계산에서 잡는다.

변경 시 ACTIVE는 즉시 PENDING, BLOCKED는 BLOCKED다. 새/변경 도구의 검토 설명은 빈 값으로 저장하고 원격 관측의 설명은 사용하지 않는다. 그대로인 도구는 기존 검토 설명을 보존한다. 마지막/검토 검사 포인터와 이전 활성화 검토자는 비워 현재 검사로 오인하지 않게 한다. 과거 검사 행은 삭제하지 않는다. 변화가 없는 관측도 성공한 쓰기이므로 revision·감사를 남기고 기존 상태·검토·검사 연결은 보존한다. 차단·재검토는 이전 활성화 확인 메타데이터를 지우고 마지막 검사는 보존한다.

SDK 원문 비복사의 예외는 C4.17의 threat_summary뿐이다. 검사/발견의 threat_summary는 report_json에 보존하고 감사·예외·repr·로그에 복사하지 않는다. 레거시 Finding.description이 비어 있지 않으면 새 저장 입구는 INVALID_ARGUMENTS로 거부한다. C는 SDK 원문을 그 필드에 전달하지 말아야 한다. 검토 설명과 input_schema는 각각 도구 행의 지정 열에만 저장한다.

## 트랜잭션과 오류

각 쓰기는 `BEGIN IMMEDIATE` 안에서 현재 등록 조회·상태/CAS 확인·서버/도구/검사 변경·row_revision +1·감사 INSERT·반환 사본 검증을 끝낸 뒤 COMMIT한다. 모든 변경과 감사는 같은 트랜잭션이다. 읽기는 BEGIN으로 서버·도구·검사 사본의 동일 시점을 보장한다. 기존 WAL·foreign_keys ON·synchronous FULL 설정과 COMMIT 실패 시 writer 연결 폐기 규칙을 유지한다.

감사는 `REGISTRY_REGISTERED`, `REGISTRY_SCAN_RECORDED`, `REGISTRY_ACTIVATED`, `REGISTRY_FINGERPRINT_CHANGED`/`REGISTRY_FINGERPRINT_OBSERVED`, `REGISTRY_BLOCKED`, `REGISTRY_REVIEW_REQUESTED`, `REGISTRY_DESCRIPTIONS_REVIEWED`다. task_id/request_id/label은 NULL이고 detail은 server_id·row_revision·scan_id·tool_count·changed_count뿐이다. 스키마·설명·검사 원문·전체 인자·예외 문구를 넣지 않는다. 감사 ID 공급자가 없거나 INSERT가 실패하면 전체 쓰기를 롤백한다.

새 Reason은 없다. 잘못된 입력/상한은 INVALID_ARGUMENTS, 없는 저장 대상은 STATE_MISSING, 중복·CAS 충돌은 APPROVAL_RACE, 잘못된 상태는 REG_NOT_ACTIVE, 활성화의 지문/검사 집합 불일치는 TOOL_FINGERPRINT_CHANGED다. SQL·손상·감사·커밋 실패는 INTERNAL_ERROR다. 공개 오류는 기존 StoreError로 원문·cause/context를 제거해 전달한다.

COMMIT ACK 유실은 실제 DB 커밋 후에도 발생할 수 있다. 오류를 성공으로 바꾸거나 자동 재시도하지 않고 연결을 폐기한다. C는 캐시를 반환받지 못했으면 그 서버 실행을 차단한다. DB 상태가 PENDING이라고 단정하지 않는다. 실제 커밋 뒤 오류를 주입해 revision과 감사가 한 번만 남고 사본은 반환되지 않음을 확인했다.

## 스키마 v2와 이관

| 테이블 | v2 구성 |
| --- | --- |
| registrations | server_id, status, boundary_id, tier, max_label, last_scan_id, reviewed_scan_id, reviewed_by, row_revision, updated_at_utc |
| registration_tools | 서버 FK, 이름, 순서, 종류, destination_arg/resource_arg, input_schema_json, fingerprint, reviewed_description. (서버, 이름) PK·(서버, 순서) UNIQUE |
| scan_reports | scan_id PK, 서버 FK, report_json, scanned_at_utc, stored_at_utc |

registrations의 검사 포인터도 scan_reports FK다. 읽을 때 검사 포인터의 서버 소유와 report 내부 서버·검사 시각을 다시 대조한다. 모든 테이블은 STRICT다. 나머지 tasks·escalations·requests·approvals·audit_events의 SQL 정의는 v1 그대로 보존했다. startup_inventory는 v2 스키마를 재확인하되 Task/요청/승인 조회의 의미는 그대로다. 미기록 요청 epoch/kind/revision은 추정하지 않는다.

새 DB는 바로 user_version 2로 만든다. 기존 DB는 application_id와 모든 schema 문장이 정확한 알려진 v1이고 **registrations와 scan_reports 양쪽이 비었을 때만** 연다. BEGIN IMMEDIATE에서 비었는지 확인하고 두 테이블을 교체하며 도구 테이블을 추가하고 버전을 올린다. 다른 다섯 테이블과 행은 그대로 둔다. 둘 중 한 테이블에 행이 있거나 스키마/태그가 다르면 수정 없이 StoreError로 거부한다. 교체 중 실패하면 DROP과 user_version까지 롤백한다. 현재 v2도 정확한 스키마만 다시 열고 미래 버전은 거부한다. 이관 시점·백업 책임·비어 있지 않은 v1의 변환은 SEQ-03 미결로 남아 있다.

JSON은 JCS 정규화 UTF-8 텍스트로 저장하고 다음 상한을 적용한다. 읽을 때도 크기·정규화 바이트·DTO를 검사한다.

| 대상 | 상한 | 이유 |
| --- | --- | --- |
| 도구 하나의 input_schema | 256 KiB | 큰 단일 정의가 UI/DB 메모리를 차지하는 것을 제한 |
| 서버 하나의 도구 메타데이터 합계 | 8 MiB | 이름·종류·인자·스키마·지문·검토 설명을 포함한 등록 크기 제한 |
| 검사 report_json 하나 | 1 MiB | 경고/진단이 무한히 쌓인 단일 보고서를 제한 |

상한은 저장소의 보수적인 운영 제안값이며 네트워크 수신 상한이나 성능 측정값이 아니다. threat_summary·reviewed_description의 기존 도메인 문자 제한도 함께 적용한다. 개별 보고서 수/DB 전체 용량·보존 기간·삭제 API는 이번 범위가 아니다.

JCS는 finite binary64를 허용하되 unsafe Python int 입력은 기존 JCS 함수처럼 거부한다. `1e20`의 JCS 출력은 정수 표기이므로 읽을 때 큰 정수 표기를 binary64로 복원해 바이트 일치를 검사한다. -0·1.0·큰/작은 유한 실수도 재개방 때 손상으로 오인하지 않음을 확인했다. 지문 자체는 이 정규화로 재계산하지 않는다.

## C·A 연결 순서

### 지문 변경과 재시작

1. C가 연결 직후 실제 tools/list를 등록 정의와 대조한다. 이 연결은 검증 완료 전까지 실행에 쓰지 않는다.
2. 변경 관측을 `await store.record_fingerprint_change(...)`로 커밋한다. revision이 오래됐다는 이유로 하향 적용을 건너뛰지 않는다.
3. 반환 `change.entry.registration`으로 C 동기 Registry 사본을 **즉시 교체한다. 커밋 반환과 교체 사이에 await를 넣지 않는다.** C의 연결/캐시 발행도 서버별로 직렬화해 오래된 작업이 새 사본을 덮지 않게 한다.
4. 그 뒤 `change.changed_tools`의 각 이름에 `await guard.invalidate_tool(server_id, name)`을 호출한다. 삭제된 이름도 포함한다. NOTIFY-01의 대기 승인 정지·무효화·최종 알림을 연결한다.
5. 저장/사본 교체/무효화 실패를 정상 연결로 표시하지 않는다. 그 서버의 admission을 차단하고, 반환 없는 COMMIT ACK 불명도 자동 실행하지 않는다. 캐시 교체 전 실패면 옛 ACTIVE 사본이 남을 수 있으므로 C의 실패 게이트가 필요하다.

재시작은 `list_registrations()`의 사본으로 캐시를 복원한다. DB ACTIVE는 연결 전 실행 권한이 아니다. 실제 연결마다 지문을 다시 대조하고 경로·실행 파일·endpoint 등 C 검증을 통과해야 한다. 이번 DTO는 등록 경계/도구 정의이며 검증된 프로세스 명령·인증정보를 저장하는 새 API는 아니다. 검증된 연결 설정의 결속·ACTIVE 목록 제공은 C 서비스 연결에서 검토한다.

### 사용자 활성화와 정책 저장(#26)

1. A가 PENDING 화면에서 도구별 허용/거부, 실제 표시한 이름→지문 전체, 검토 scan_id·revision을 고정하고 사람 확인을 받는다.
2. `prepare_server_access_change`로 준비한다. A/C가 설정 문서를 저장하고 `apply_policy_change` 성공 ACK를 받는다. A는 준비/저장/적용/활성화와 새 Task 생성을 직렬화한다.
3. 그 다음 `activate_server`를 호출하고 성공 반환으로 C 캐시를 await 없이 교체한다. CAS/지문 충돌이면 갱신된 화면에서 다시 확인받는다.

| 부분 성공/실패 | 처리 |
| --- | --- |
| 설정 저장 실패 | 정책 적용·활성화를 호출하지 않음. Registry PENDING 유지 |
| 설정 저장 성공, 정책 적용 실패 | 활성화하지 않음. Registry PENDING, Guard global halt/복구 흐름 유지 |
| 정책 적용 성공, 활성화가 커밋 전에 거부/롤백 | Registry PENDING. 새 규칙이 있어도 등록 게이트가 실행을 막음. 정지된 옛 Task를 재개하거나 정책을 자동 되돌리지 않음 |
| 활성화 COMMIT ACK 불명 | DB는 ACTIVE일 수도 있음. writer 폐기, C 캐시는 실행 차단 상태 유지. 재조회만으로 자동 허가하지 않고 연결 재검증·상태 조정 필요 |
| 활성화·캐시 교체 성공 | 새 정책·현재 지문으로 확인된 등록. 새 Task만 새 정책 버전으로 시작 |

역순으로 먼저 ACTIVE를 만들면 아직 옛 접근 규칙이 적용된 동안 등록 게이트가 열릴 수 있다. 정책 저장과 Registry는 하나의 트랜잭션이 아니므로 위 순서와 실패 게이트를 A/C가 반드시 연결해야 한다. 이번 B 작업만으로 그 통합 보장을 구현했다고 주장하지 않는다.

## S03 경쟁 분석 — 이번에는 수정하지 않음

소스 기준으로 `reserve_dispatch`와 `consume_and_reserve`는 요청·Task·승인 결속을 검사하지만 registrations/registration_tools를 조회하지 않는다. SQLite 단일 writer와 BEGIN IMMEDIATE는 쓰기 순서를 정할 뿐, 옛 지문의 요청이 새 PENDING 상태에서 예약/소비되지 않게 하는 조건은 아니다. 지문 저장은 승인 원문/메모리 핸들을 직접 무효화하지 않으며 C가 후속 invalidate_tool을 호출해야 한다.

현재 Guard는 접근 판정 await 뒤 Registry 상태/지문을 재검사한다. 예약 뒤에도 `_dispatch_and_commit`이 Task를 읽고 Catalog.resolve로 ACTIVE·도구/지문과 요청 동등성을 확인한 후 Transport를 호출한다. **현재 SQLiteStore 메서드에는 내부 await가 없어**, 같은 이벤트 루프의 최종 평가→동기 SQLite 기록/예약→전송 직전 재해석 사이에 await 표기가 있다는 이유만으로 매번 태스크 전환이 일어나는 것은 아니다. 즉시 캐시 교체 규칙은 이 경로의 오래된 캐시 창을 줄인다. 다른 스레드/연결·차후 I/O writer·콜백 재진입의 원자 보장으로 확대해서는 안 된다.

남는 구간과 한계는 다음과 같다.

| 구간 | 현재 동작과 위험 |
| --- | --- |
| 지문 COMMIT 뒤 캐시 발행 전 | 중간 await/다른 발행 순서가 생기면 C의 옛 ACTIVE를 읽을 수 있음. 즉시 사본 교체·서버별 직렬화 필요 |
| 최종 평가 뒤 예약/승인 소비 | Store 자체에는 Registry 조건이 없어 DB 단위로 옛 요청 예약/소비를 거부하지 않음. 현재 단일 루프 동기 실행의 특성에 의존하는 부분과 분리해서 계약해야 함 |
| 예약 뒤 전송 직전 Catalog 확인 | 캐시가 이미 PENDING/새 정의면 거부해 기존 after_dispatch 경계로 처리함. DB만 갱신되고 캐시가 오래됐으면 이 확인도 옛 정의를 볼 수 있음 |
| 전송 직전 확인 뒤 worker 큐/SDK 대기 | A의 ServerWorker.call은 명령을 큐에 넣고 future를 await하며 worker가 나중에 session.call_tool을 호출함. 그 사이 변경이 커밋돼도 큐 명령에는 새 등록 세대 검사/서버별 폐기 연결이 없음. 옛 요청이 wire로 나갈 수 있는 구간이 남음 |
| 승인 실행/전송 진행 중 invalidate_tool | 기존 구현은 inflight 승인을 대기 승인과 구별해 건너뜀. Task lock을 기다리는 정리도 이미 큐에 들어간 요청/진행 중 전송을 소급 취소하는 보장이 아님 |
| 전송 뒤 변경 | 이미 전송한 바이트는 되돌릴 수 없음. 지문 변경 자체가 기존 정책 변경 정지와 같은 결과 차단 신호를 만들지는 않으므로 READ 공개 차단·SEND 결과 불명 처리 연결도 합의 필요 |

따라서 이번 저장 구현과 연결 순서만으로 S03의 옛 정의 전송 0을 주장할 수 없다. 실제 wire 경쟁은 실행하지 않았고, 기존 Store 의미·Guard/Transport는 바꾸지 않았다.

후속 **합의 전 제안**은 (1) 실제 정의/등록 자격 변경에 증가하는 Registry generation을 요청·승인에 결속하고, (2) reserve_dispatch/consume_and_reserve의 같은 쓰기 TX에서 ACTIVE·generation·도구 지문을 원자 대조하며, (3) C의 즉시 admission 차단/사본 발행·Guard의 Task 처리·A worker의 대기 명령 폐기/전송 직전 세대 확인을 직렬화하는 것이다. 현재 row_revision은 검사·무변경 관측에도 증가하므로 그대로 쓰면 불필요한 충돌이 생긴다. 별도 정의 세대 또는 더 보수적인 revision 결속의 선택이 필요하며, 지문 A→B→A에서도 옛 승인을 되살리지 않아야 한다. DB 예약 조건만으로 이미 예약된 worker 큐 창은 닫히지 않는다.

이미 전송에 들어간 READ는 결과 격리/정지, SEND는 결과 불명·자동 재전송 금지의 기존 예약 후 의미를 유지해야 한다. 어떤 시점을 전송 시작으로 확정하는지, 취소 ACK/종료를 누가 보장하는지 A·B·C가 함께 정하고 C가 dispatch·wire·부작용 계수로 검증해야 한다. 기존 Store 포트와 실행 의미가 바뀌므로 이번에는 분석·제안만 남겼다.

## A·C에 전달할 것과 남은 한계

- **C 요청:** RegistryStore/DTO·오류·상한·이관 규칙을 검토하고 C4.10에 연결한다. 연결마다 tools/list를 비교하고 커밋 반환과 캐시 교체 사이 await를 없앤다. 추가/삭제를 포함한 변경 이름마다 invalidate_tool을 호출한다. 저장 실패 시 서버를 차단하고 별도 SQL 경로를 만들지 않는다. C4.11/17 Scanner 번역은 원문 description 없이 정제된 threat_summary·진단을 전달한다.
- **A 요청:** PENDING에서 검토 설명 입력·등록 revision·표시한 지문/검사 선택을 결속한다. 정책 준비→문서 저장→적용 ACK→Registry 활성화→사본 발행을 Task 생성과 직렬화한다. 부분 실패/커밋 ACK 불명을 성공으로 표시하지 않는다. worker 큐/전송 경쟁의 후속 계약을 C와 검토한다.
- **3인 합의:** 새 domain DTO·RegistryStore 포트, 검토 설명의 PENDING 제한·입력 형태, row_revision/정의 세대·S03 원자 예약/소비/전송 제안은 합의 전 제안이다. 기존 Store·Registry 포트 확정이나 S03 해결로 간주하지 않는다.
- 전체 DB 용량/보존·서버 삭제 API·행이 있는 v1 변환·백업/이관 시점·검증된 연결 설정의 서비스 결속은 후속이다. 기존 SQLite 잠금 대기 동안 이벤트 루프가 멈추는 B6.13 한계도 유지한다.
- GitHub 이슈·PR #28의 현재 상태와 다른 A/C 브랜치의 리뷰·연결 여부는 **확인 불가**다. 제공된 작업 설명과 현재 로컬 브랜치를 기준으로 구현했다. 현재 브랜치에 커밋하며 push·PR 생성은 하지 않는다. 추적되지 않은 Claude outputs/는 읽기만 했다.
