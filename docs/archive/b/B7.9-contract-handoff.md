# B7.9 계약·사유·상태·실패 경계 인계

## 1. 기준

대상은 작업 시작 시 `wip/b-next`의 `9604e74`다. 이 기록은 그 시점의 코드와 이미 확인된 시험·합의 상황을 기술하며 제품 연결이나 C의 독립 인수를 대신하지 않는다. 확정 계약은 `docs/contracts.md`가 우선이고, 합의 전 구현·제안은 각 표에서 표시한다. #76의 후속 A·C 회신은 B 상태와 대조 기록에 반영했지만 공통 계약의 미결 요청 표는 아직 갱신되지 않았다. 공통 문서는 이 작업에서 수정하지 않는다.

표기 차이: `docs/contracts.md`의 B6-02~06은 여전히 요청 초안이고 `ports.py::StoreQueries`도 B6-05를 합의 전으로 적지만, #76 후속 회신과 B 상태에는 B6-02·03·04·06 및 B6-05 합의가 기록돼 있다. 또한 `docs/technical-design.md`의 정책 변경 PENDING→CANCELLED 설명과 현재 B6-01 제안의 정책 불일치 한정 PENDING→INVALIDATED는 다르다. 공통 문서 반영과 C #89 인수는 별도다.

## 2. Reason 전수표

기준은 `domain/reasons.py::Reason`의 32개다. 발행자는 대표 경로이고 같은 사유가 복수 경로에서 쓰일 수 있다. 저장 열에서 **판정**은 `SQLiteStore._record_decision`의 요청 `reasons`와 첫 사유의 `DECIDED` 감사, **감사 가능**은 해당 경로가 연결된 내구성 감사 또는 상태·승인 감사에 넘길 때를 뜻한다. 고정 오류 반환이나 정상 종료만으로 항상 DB 행이 생기는 것은 아니다. 예외 메시지·원문은 기록하지 않는다.

모델 문구 열은 `core/model_messages.py::fixed_model_message`의 DENIED 사유 변환 기준이다. 일반 거부와 정지는 사유 코드를 포함하지 않는 기존 고정 문구다. 공개 사유만 코드가 붙는다. 실제 `Outcome` 종류와 확정 종결 원인에 따라 `outcome_model_message`·`final_model_message`는 별도의 고정 문구를 고른다. 거부 사유가 `GUARD_CLOSED`로만 이루어지면 정지 문구이고, 그 밖에 비공개 사유가 섞이면 일반 거부로 가린다. PENDING은 최종 응답이 아니다.

## 3. Task·요청·승인 상태 전이

상태는 `domain/enums.py::TaskStatus`·`RequestStatus`·`ApprovalStatus`다. 표의 이벤트는 실제 저장소가 쓰는 이름이다. 같은 상태 `set_task_status`는 revision 확인 뒤 no-op이고 감사도 추가하지 않는다. 복구는 일상 전이표와 별도이며 DB를 확인하고 한 트랜잭션으로 정리한다.

| 대상·전이 | Store 연산 | 같은 트랜잭션 감사·비고 |
| --- | --- | --- |
| Task 생성: 전달된 초기 상태 | `SQLiteStore.create_task` | Task·순번·회차 소유권·승격 근거 저장. 이 연산 자체의 Task 상태 감사는 없음 |
| Task READY → RUNNING | `SQLiteStore.set_task_status` | `TASK_RUNNING` |
| Task READY → HALTED | `SQLiteStore.set_task_status` | `HALTED` |
| Task RUNNING → WAITING_APPROVAL | `SQLiteStore.open_approval`(B6-01 합의 전), `set_task_status` | `TASK_WAITING_APPROVAL`; 원자 경로는 승인 생성과 `APPROVAL_PENDING` 함께 |
| Task RUNNING → HALTED / UNKNOWN_OUTCOME / CLOSED | `SQLiteStore.set_task_status` | 각각 `HALTED` / `TASK_UNKNOWN_OUTCOME` / `TASK_CLOSED` |
| Task WAITING_APPROVAL → RUNNING | `SQLiteStore.finish_approval`, `consume_and_reserve`, `set_task_status` | `finish_approval`·`set_task_status`는 `TASK_RUNNING`; 소비는 `CONSUMED` 한 건(별도 `TASK_RUNNING` 없음) |
| Task WAITING_APPROVAL → HALTED | `SQLiteStore.finish_approval`, `set_task_status` | `HALTED`; 원자 종결이면 `APPROVAL_<상태>`도 함께 |
| Task HALTED / UNKNOWN_OUTCOME → CLOSED | `SQLiteStore.set_task_status` | `TASK_CLOSED`; CLOSED에서 새 상태 전이 없음 |
| READ 미분류 시 RUNNING → HALTED | `SQLiteStore.commit_observation`, `core/taint.py::merge` | `OBSERVED` 감사의 사유 `RESULT_UNCLASSIFIED`; 개별 `HALTED` 이벤트가 아님 |
| 예약 후 실패 Task → RUNNING / HALTED / UNKNOWN_OUTCOME | `SQLiteStore.commit_request_failure` | `REQUEST_FAILED`(READ 무자료·RUNNING), `REQUEST_WITHHELD`(READ·HALTED), `REQUEST_UNKNOWN_OUTCOME`(SEND·UNKNOWN_OUTCOME); 불가 조합 거부 |
| Request 생성: DENY → DENIED, 그 외 → DECIDED | `SQLiteStore.record_decision` | `DECIDED`; DENY도 DECIDED 이벤트 하나 |
| Request DECIDED → DISPATCHING | `SQLiteStore.reserve_dispatch` | `DISPATCH_RESERVED` |
| Request DECIDED → WAITING_APPROVAL | `SQLiteStore.open_approval`, 구 `create_approval` | `APPROVAL_PENDING`; 새 원자 연산은 Task 감사 포함 |
| Request WAITING_APPROVAL → DISPATCHING | `SQLiteStore.consume_and_reserve` | `CONSUMED`; 승인 CONSUMED·Task RUNNING 동시 |
| Request WAITING_APPROVAL → DENIED | `SQLiteStore.finish_approval`, 구 `transition_approval`(비 APPROVED) | `APPROVAL_REJECTED` / `APPROVAL_EXPIRED` / `APPROVAL_CANCELLED` / `APPROVAL_INVALIDATED` |
| Request DISPATCHING → SUCCEEDED / WITHHELD | `SQLiteStore.commit_observation` | `OBSERVED`; READ 분류 성공 / 미분류 |
| Request DISPATCHING → SUCCEEDED | `SQLiteStore.commit_send_outcome` | `SEND_COMPLETED`; SEND는 Task 분류·상태 변경 없음 |
| Request DISPATCHING → FAILED / WITHHELD / UNKNOWN_OUTCOME | `SQLiteStore.commit_request_failure` | `REQUEST_FAILED` / `REQUEST_WITHHELD` / `REQUEST_UNKNOWN_OUTCOME`; 위 READ·SEND 허용 쌍만 가능 |
| Approval 생성 → PENDING | `SQLiteStore.open_approval`, 구 `create_approval` | `APPROVAL_PENDING` |
| Approval PENDING → APPROVED / REJECTED / EXPIRED / CANCELLED | `SQLiteStore.transition_approval`; 후자 셋은 `finish_approval`도 사용 | `APPROVAL_APPROVED` / `APPROVAL_REJECTED` / `APPROVAL_EXPIRED` / `APPROVAL_CANCELLED`; APPROVED만 Task·요청 상태 변경 없음 |
| Approval APPROVED → EXPIRED / INVALIDATED | `SQLiteStore.finish_approval`, 구 `transition_approval` | `APPROVAL_EXPIRED` / `APPROVAL_INVALIDATED`; 요청 DENIED |
| Approval PENDING → INVALIDATED | `SQLiteStore.finish_approval`만, reason이 `POLICY_CHANGED`일 때 허용하는 합의 전 제안 | `APPROVAL_INVALIDATED`, 요청 DENIED; Guard 정책 불일치는 Task HALTED를 요청한다. Store는 호출자의 RUNNING/HALTED 선택 또는 기존 종결 상태를 따른다. 구 `transition_approval`에서는 허용되지 않음 |
| Approval APPROVED → CONSUMED | `SQLiteStore.consume_and_reserve` | `CONSUMED`; 요청 DISPATCHING·Task RUNNING 동시 |
| 복구 Task READY / RUNNING / WAITING_APPROVAL → HALTED; 유효한 RUNNING의 미확인 SEND → UNKNOWN_OUTCOME | `SQLiteStore._recover_locked` | `HALTED` / `TASK_UNKNOWN_OUTCOME`; 이미 종결 Task는 그대로. READY·WAITING과 DISPATCHING 조합은 미해결로 복구 실패 |
| 복구 Request DECIDED / WAITING_APPROVAL → DENIED, DISPATCHING READ → WITHHELD, SEND/legacy → UNKNOWN_OUTCOME | `SQLiteStore._recover_locked` | `REQUEST_DENIED` / `REQUEST_WITHHELD` / `REQUEST_UNKNOWN_OUTCOME`; 예외적 미분류 legacy는 격리 |
| 복구 Approval PENDING / APPROVED → EXPIRED | `SQLiteStore._recover_locked` | `APPROVAL_EXPIRED`; 매 복구 실행 요약 `RECOVERY_COMMITTED` 한 건 |

## 4. Store 공개 연산

다음은 `ports.py`의 각 공개 포트가 `storage/sqlite_store.py::SQLiteStore`에서 쓰는 writer 분류다. R/W는 `_METHOD_WRITES`의 **큐 취소 경계**이고, 실행 열은 `_EXECUTION_GATED_METHODS`의 **새 실행 권한 검사**다. 둘은 별개다. 명시 시작 `RECOVERED` 허용 여부는 `_RECOVERED_WRITES`·읽기 예외에 따르며, 허용이 개별 연산의 입력·상태·회차 검증 성공을 뜻하지 않는다. 공통 `StoreError`는 별도 명시가 없으면 원문 없는 `INTERNAL_ERROR`이고, 전역 실행 게이트가 닫히면 `execution_state().reason` 또는 `INTERNAL_ERROR`를 쓴다. 예시 오류는 모든 오류의 배타적 목록이 아니다. COMMIT 불명은 `execution_state().commit_outcome=UNKNOWN`, 연결 폐기 및 권한 차단으로도 확인한다.

| 포트·연산 (`ports.py`) | SQLite 심볼·역할 | 큐 R/W | 실행 권한 검사 | RECOVERED | 고정 오류·결과 |

## 5. 실패·예외 경계
| 경계 | 실제 코드·결과 |
| --- | --- |
| 판정 및 예약 전 | `GuardService.submit`·`_submit_locked` → `fail_closed` → `_pre_dispatch_failure`: 정책 거부는 `Denied`; 검사기 예외 등은 고정 `INTERNAL_ERROR`와 `FAILURE_BEFORE_DISPATCH` 감사 경로. 예약 전 취소는 동일 Task 정지를 시도한다. |
| 승인 진입·종결 충돌 | `ApprovalService._open`·`_finish_record` / `SQLiteStore.open_approval`·`finish_approval`: 성공 ACK 전 발행 금지. 일반 revision 경합은 `APPROVAL_RACE`, 만료는 `APPROVAL_STALE`; 해당 원자 트랜잭션 롤백. `consume_and_reserve` 충돌은 롤백 후 `False`. |
| 승인 관계 손상 | `SQLiteStore._approval_integrity_result`가 롤백 뒤 `halt_execution(INTERNAL_ERROR)`·별도 `APPROVAL_INTEGRITY_FAILED` 감사를 시도하고 `StoreIntegrityError` 전달; `ApprovalService._pre_boundary` 또는 Guard가 명시적 전역 정지. 감사도 실패하면 연결 폐기. |
| 예약 후 전송/처리 예외 | `GuardService._dispatch_reserved` → `after_dispatch` → `_contain_post_dispatch`: READ는 `commit_request_failure(WITHHELD, HALTED)` 뒤 `Withheld`; SEND는 `(UNKNOWN_OUTCOME, UNKNOWN_OUTCOME)` 뒤 `OutcomeUnknown`, 재전송 금지. 정지 사유 등 제한된 예외 외 `POST_DISPATCH_ERROR`. |
| READ 응답 분류·커밋 | `ResponseGate._handle`·`SQLiteStore.commit_observation`: RAW 검증 후 Catalog 분류·원자 커밋 ACK 뒤 `Released`; 미분류면 Task HALTED + 요청 WITHHELD를 커밋하고 `Withheld(RESULT_UNCLASSIFIED)`. 알려진 무자료 실패는 요청 FAILED·Task RUNNING이며 `Withheld`. |
| SEND 응답·커밋 | `ResponseGate._handle`·`SQLiteStore.commit_send_outcome`: 요청 SUCCEEDED·`SEND_COMPLETED` ACK 뒤 `Released`. SEND 실패는 요청·Task UNKNOWN_OUTCOME·`OutcomeUnknown`; READ 등급 병합 없음. |
| 응답 커밋·실패 격리 자체 실패 | `ResponseGate.handle`이 `STATE_COMMIT_FAILED` 격리를 시도하고 실패 시 global halt; `GuardService._post_failure_fallback`은 READ `Withheld`, SEND `OutcomeUnknown`. 커밋 불명일 때 성공 추정·재시도 금지. |
| COMMIT 결과 불명 | `SQLiteStore._transaction`·`_connection_fault`: `CommitOutcome.UNKNOWN`, 연결 폐기 및 `execution_enabled=False`·재시작 필요. ROLLED_BACK과 구분한다. |
| 정상 종료 | `GuardService.aclose` → `_halt_globally(GUARD_CLOSED)`: 사유만 정상 종료로 구분하는 합의 전 제안. 이미 전역 정지되면 최초 사유 유지; `on_global_halt`가 `Store.halt_execution`에 연결된 경우 Store 실행 권한도 닫고 정리 쓰기는 허용. |

## 6. A가 쓰는 입구

신뢰된 구성 코드·사람 채널·세션 관리자와 모델 입력은 분리한다. `HumanControl`·`SystemControl`은 Python capability이며 프로세스 내 임의 코드 실행에 대한 격리는 아니다.

## 7. C 독립 인수: 주입 지점과 기대 계수
