## 1. SEQ-01 · Task ID 생애 계수

**A 요청/질문:** Task ID가 같은 동안 epoch와 관계없이 증가, 첫 신규 값 1, 공백 허용·커밋 배정 회수 금지에 동의했다.

**B 결정:** A 동의를 확인하고 원안을 유지한다. 독립 계수의 초기 last_issued는 0이고 신규 배정은 1부터다. 기존 기록의 순번 0은 유효한 이력이다. 같은 Task ID의 epoch가 달라져도 계수를 리셋하지 않는다. 새 Task ID는 독립 계수다. 배정 COMMIT 뒤 해석·판정 저장 실패, 취소, 반환 ACK 유실이 나도 배정값을 회수하지 않는다. 확인된 rollback의 비공개 후보만 미배정이다.

**이유:** UNIQUE(task_id, call_seq)와 승격 근거가 Task ID 기준이다. 번호는 호출 권한이나 model_call_id가 아니며 공백을 메우는 것이 보안 요건은 아니다.

**영향:** ports는 별도 할당 입구를 추가하되 기존 Guard 콜백을 유지한다. domain TaskState의 의미·기존 필드를 바꾸지 않는다. 스키마에 독립 계수와 같은 TX의 할당 감사를 추가한다. A는 메모리 카운터를 주입형 영속 구현으로 바꾸고 C는 여러 Task/epoch·중복·공백·상한을 검증한다. SQLite 정수 상한 (2**63−1)에서 증가를 거부하며 wrap하지 않는다.

## 2. SEQ-02 · 실패·COMMIT 불명·권위 조회

**A 요청/질문:** 한 인자 콜백을 유지하고 같은 Store의 B 할당기를 주입한다. 확실한 실패/rollback은 예약 전 거부, COMMIT 불명은 UI/Runner가 Store 조회로 알 수 있어야 하며 고정 실패 Reason이 필요하다. A 원문은 조건을 세 줄로 적었으며 실패 처리·가시성 두 축과 Reason 요구 모두 답한다.

**B 결정:** 기존 `Callable[[str], Awaitable[int]]`를 유지한다. B의 같은 writer/Store facade에 `allocate_call_seq(task_id)`를 두고 A가 그 bound method를 주입한다. expected_epoch를 콜백에 추가하지 않는다. 배정은 Task 행의 epoch·row_revision·security_version·등급·상태를 변경하지 않는다. 실행 결속은 기존 record_decision·예약/승인 CAS와 새 current-run 검사로 유지한다.

할당 TX는 현재 실행 회차의 정상 RUNNING Task와 계수 관계 확인→조건부 계수 +1→필수 할당 감사→COMMIT이다. 모든 단계가 같은 writer에서 수행되고 성공 ACK 뒤에만 int를 반환한다. 감사에는 신뢰 run/operation/Task ID·배정값·고정 사실/시각만 두며 인자나 문서/도구 원문을 싣지 않는다. 결과를 모르는 호출을 같은 프로세스에서 자동 재할당하지 않는다.

| 실패 | 기존 Reason 선택 | Store 권한/결과 |
| --- | --- | --- |
| 잘못된 입력·증가 상한 | INVALID_ARGUMENTS | 후보·dispatch 없음 |
| 없는 Task | STATE_MISSING | 새 Task/계수 자동 생성 없음 |
| 옛 실행 회차·종결/비정상 Task | TASK_NOT_RUNNING, 미분류는 TASK_UNCLASSIFIED | 순번/예약 권한 없음 |
| 계수 행 누락·기록 MAX보다 낮음·관계/저장 형식 손상 | INTERNAL_ERROR | Store 실행 권한을 닫고 무결성 실패로 보고 |
| BEGIN/쓰기/필수 감사 실패, rollback 확인 | STATE_COMMIT_FAILED | 미배정·예약 전 거부. 현재 실행을 정지하고 자동 재시도 없음 |
| COMMIT/rollback 결과 불명·반환 ACK 유실 | STATE_COMMIT_FAILED | 결과 UNKNOWN, Store와 Guard 실행 차단·연결 격리·재시작 필요 |

새 Reason을 만들지 않는다. 현재 Guard의 사전 실패는 StoreError.reason을 사용하지만 실패 감사까지 실패하면 fallback이 INTERNAL_ERROR로 바뀔 수 있다. 따라서 **A는 Denied 한 건의 사유나 DB TaskState.RUNNING만으로 실행 가능을 판단하지 않는다.** 예약 전 순번 실패는 SEND가 전송됐다는 증거가 아니며 OutcomeUnknown을 새로 만들지 않는다. 예약 후 실패의 READ Withheld/SEND OutcomeUnknown 의미는 별개로 유지한다.

### Store가 제공할 권위 상태

B6.13과 함께 `execution_state() -> StoreExecutionState`를 별도 수명 포트에 추가한다. A 백엔드는 이벤트 루프에서 이 동기 메서드를 바로 호출하고 A UI는 bridge의 projection을 통해 값을 받는다. Store controller의 **실제 연산 허용 상태**를 반환하며 SQL writer 큐 뒤에서 기다리는 조회로 만들지 않는다. SQL 잠금과 분리된 작은 상태 snapshot이므로 이벤트 루프에서 동기 호출을 허용한다. A는 같은 Store의 `allocate_call_seq` bound method를 기존 한 인자 콜백으로 주입한다.

| StoreExecutionState 필드 | B 정의 |
| --- | --- |
| run_id | 현재 DB 소유/실행 회차. 준비 전에는 None 가능 |
| phase | CLOSED / MIGRATING / RECOVERING / RECOVERED / READY / FAULTED |
| execution_enabled | READY의 정상 binding에서만 True |
| state_revision | 권한 상태가 실제로 바뀔 때 증가. 같은 fault 재보고로 재개하지 않음 |
| reason | 정상은 None, 실패는 위 기존 Reason |
| commit_outcome | 해당 실패 작업의 NOT_STARTED / ROLLED_BACK / COMMITTED / UNKNOWN 또는 해당 없음 |
| last_committed_run_state | 마지막으로 ACK를 받은 DB 회차 상태. 최신 DB 상태라는 뜻은 아니며 없으면 None |
| requires_restart | 불명/치명 실패에서는 True. 같은 객체에서 해제하지 않음 |

execution_enabled=True는 Store 전체의 실행 게이트 조건일 뿐 개별 Task의 현재 run·epoch·상태·정책·승인 검사를 대신하지 않는다.

쓰기 결과가 불명이면 Store controller가 먼저 FAULTED/실행 불가를 고정하고 대기 중인 후속 쓰기도 차단한 뒤 오류를 전달한다. load_task/get_approval 등 평소 조회가 실패한 연결로 RUNNING 사본을 반환하는 대신 고정 StoreError를 낸다. execution_state는 그 연결을 폐기한 뒤에도 조회 가능하다. A는 **새 turn/start 전, 도구 응답 반환 전, 새 Task·세션 준비 전, 상태 변화 감시**에서 이 권위 상태를 확인한다. Guard의 다른 global halt도 같은 controller에 고정 사유로 전달하는 연결을 둔다. 시작 실패는 이 snapshot과 8절의 별도 고정 시작 실패 분류로 표시하며 STORE_* 코드를 기존 reason 필드에 섞지 않는다.

상태 변화 콜백은 선택이다. 처음에는 A가 `state_revision` 비교로 감시하고, 필요하면 B6.13 구현 때 `loop.call_soon_threadsafe`로 호출하는 구독을 추가한다. 어느 쪽도 SQL 큐 완료를 기다리지 않는다. `execution_enabled=False`를 확인하면 A가 진행 중 turn을 interrupt하고 모든 Task 세션을 닫는다. 이 연결은 아직 구현되지 않았으며, NOTIFY-01 알림 콜백이 실패한 경우에도 호출별 감시 상한을 기다리지 않고 정지할 수 있게 하는 후속 조건이다([B7.13 예외 경로](B7.13-c-review-followups.md#notify-01-예외-경로)).

이는 Guard의 비공개 `_global_halt`를 UI가 복제하는 방식이 아니다. Store가 실제 권한을 막고 A가 같은 상태를 조회한다. 단, **고장 난 DB에 정지 행을 반드시 쓸 수 있다는 보장은 하지 않는다.** DB Task가 RUNNING으로 남을 수 있으면 그 사실과 COMMIT 불명을 분리해 보고한다. 불명 연결에서 추가 UPDATE로 HALTED 기록을 성공했다고 꾸미지 않는다.

v3에는 실행 회차 표식과 배정 operation ID/감사를 같은 TX로 남긴다. 할당 COMMIT이 실제 성공했다면 계수·할당 감사가 함께 남는다. 불명/rollback이면 남지 않을 수도 있다. 다음 프로세스가 C 단일 소유와 새 연결을 확보한 뒤 DB를 재검사해 판별하고 모든 옛 Task를 복구 규칙으로 종결한다. 메모리 권한 상태는 **현재 회차의 실행 허용에 대한 권위**, 확인된 DB 행은 **영속 사실의 권위**로 구별하며 디스크 장애 중 최신 영속 사실을 안다고 주장하지 않는다.

**이유:** A의 가시성 요구와 디스크 장애 시 기록 불가능성을 함께 처리해야 한다. 번호 배정과 요청 dispatch는 다른 TX다. SQLite는 일부 오류에서 TX를 유지할 수 있으므로 예외가 났다는 이유만으로 rollback 완료를 단정하지 않는다. [SQLite transaction/error 규칙](https://www.sqlite.org/lang_transaction.html)

**영향:** 별도 SequenceAllocator/StoreLifecycle 포트와 StoreExecutionState·고정 phase/outcome DTO가 **합의 전 제안**이다. 기존 Store 12개 서명은 유지한다. 스키마는 계수·회차·할당 감사가 필요하다. B가 Guard/global-halt·감사 실패 연결을 맡고 A는 bound method 주입·동기 snapshot 확인·state_revision 감시·실행 불가 시 전체 Task 세션 interrupt/종료를 연결한다. C는 COMMIT ACK 유실·SQL과 독립된 조회·추가 dispatch 0을 검증한다. A 동의(#37), C 회신 대기다.

## 3. SEQ-03 · 이관 시점·v3·백업

**A 요청/질문:** 독립 계수 표에는 동의했다. 생성자 자동 이관과 명시 단계 중 B 선택, 이관 전 백업 필요 여부와 책임을 물었다.

**B 결정:** v3 이관은 **bootstrap의 명시적인 저장소 준비 단계**로 분리한다. 사용자에게 매 실행 확인창을 요구한다는 뜻은 아니다. 합의한 정책에 따라 A가 B 준비 입구를 호출하고 이관 ACK와 복구 ACK를 각각 확인한다. 새 DB는 최종 v3로 초기화하며 기존 DB를 열 때는 먼저 쓰기 없는 스키마 확인/계획→필요한 백업→명시 이관→이관 후 검증을 수행한다.

현재 B6.14 생성자는 v0→v2 초기화와, 정확한 v1이고 registrations/scan_reports가 모두 빈 경우의 v1→v2 자동 이관을 한다. 이 선례의 **정확한 DDL 확인·비어 있지 않은 v1 Registry 거부·TX 원자성**은 유지하되, 더 큰 v3 이관을 생성자의 숨은 부수 효과로 늘리지는 않는다. 후속 구현에는 자동 이관 전에 검사/백업할 수 있는 새 준비 경로가 필요하다. 기존 생성자를 먼저 호출하고 나서 “이관 전 백업”을 했다고 보고할 수는 없다. 이번 문서는 현 생성자를 변경하지 않는다.

| 입력 | v3 준비안 |
| --- | --- |
| 새 빈 DB | 소유권 확인 후 v3 직접 생성, 이관 전 백업 불필요 |
| 정확한 v2 | 기존 Registry v2 자료까지 보존하며 v3로 이관 |
| 정확한 v1, Registry 두 표 모두 빈 경우 | B6.14와 같은 허용 조건을 적용한 검토된 v1→v3 변환. v2를 거치는지와 무관하게 공표된 이관 단위의 DDL/자료/버전은 한 TX |
| Registry 행이 있는 v1 | 현재와 같이 미지원. 자동 유추/삭제/빈 Registry로 대체 금지 |
| 정확한 v3 | 이관하지 않고 검사 뒤 시작 복구로 진행 |
| 다른 application_id·미래 버전·DDL 불일치 | 수정 없이 닫고 고정 오류 |

v3에는 task_call_sequences, 신규 요청 epoch/kind/row_revision·legacy 출처 표시, 실행 회차/Task 소유 관계, 복구 run/격리/새 Task 관계 기록을 함께 넣는 안을 고른다. 계수는 기존 요청·승격 이력 MAX 및 존재하는 신뢰 계수보다 낮추지 않고 빈 이력은 0이다. 이관 전 사라진 메모리 배정은 복원됐다고 주장하지 않는다. legacy kind/epoch는 NULL과 명시 출처로 보존한다. 새 요청의 NULL은 허용하지 않는다. 알 수 없던 과거 revision을 복원했다고 하지 않고 새 revision의 초기값임을 명시한다.

**기존 자료가 있는 DB의 v3 이관 전에는 일관된 백업을 필수**로 제안한다. C는 검증된 위치·권한·단일 소유·백업 공표/정리/보존을 제공한다. WAL이 있을 수 있으므로 살아 있는 DB의 본체 파일만 C가 단순 복사하는 방식을 택하지 않는다. 일관된 스냅샷은 SQLite Backup API 등을 B의 storage 경계에서 수행하고 C가 안전한 목적지/파일 연산을 제공하는 협력이 필요하다. A/B가 임의 파일 복사를 작성하지 않는다. C 입구가 없거나 백업 실패/불명이면 기존 자료 이관을 시작하지 않는다. [SQLite Backup API](https://www.sqlite.org/backup.html)

백업은 이관 실패 조사를 위한 사본이지 옛 Task/승인 재개 입구가 아니다. 임의 과거 백업 복원 뒤에도 모든 발급 번호·소비 사실을 자동 검출/보존한다는 보장은 없다. 통상 같은 DB의 재시작만 지원하고 복원은 C의 오프라인 관리 절차와 새 실행/Task 격리를 거친다. 자동 downgrade·rollback 복원은 하지 않는다.

이 백업은 DB 스키마 이관 전 사본에 대한 안이다. CFG-01의 설정 JSON 자동 백업을 끄자는 추천과 대상이 다르다.

이관 실패/미지원/불일치는 기존 원문 없는 Store 오류와 **8절의 고정 시작 실패 분류 STORE_* 표**로 A가 구별할 수 있게 한다. 이 분류도 **합의 전 제안**이며 새 Reason이 아니다. 이관 COMMIT과 복구 COMMIT은 별도다. 이관만 남고 복구가 실패해도 READY는 없다.

**이유:** 이관 전 백업·큰 DB 시간 예산·단일 소유·별도 ACK를 명확히 하기 위해 명시 단계를 고른다. v2 선례의 안전한 허용 범위를 넓게 추정하지 않으며 정수 계수 추가를 기존 스키마에 조용히 끼워 넣지 않는다.

**영향:** startup/migration ACK 포트·DTO 추가, v3 DDL/단위 시험이 필요하다. A는 생성자 성공을 READY로 쓰지 않고 단계별 ACK를 연결한다. C는 백업/소유권·v1/v2 데이터 보존·DDL/seed/버전 중단을 검증한다. 실제 v3 번호·DDL은 다른 브랜치와 충돌 여부를 공동 검토한 뒤 확정한다.

## 4. REC-01 · 앱 수명 소유권과 시작 이중 게이트

**A 요청/질문:** C 안전 연산으로 단일 인스턴스 잠금을 얻고 앱 수명 동안 보유, AsyncExitStack에 처음 등록해 마지막 해제한다. Store도 복구 ACK 전 실행을 거부하고 cleanup 미확인 뒤 같은 프로세스 재초기화를 막아 달라고 했다.

**B 결정:** #35 B 리뷰·A 동의와 #37 회신에 따라 **C2.13 app.lock + 사용자별 앱 폴더 안 고정 제품 DB**를 DB 단일 소유로 보는 조건부 안을 받는다. A는 app.lock을 창·DB보다 먼저 잡아 앱이 끝날 때까지 보유한다(#35 A102, 제공 요약 기준). 잠금의 안전한 획득·유지·해제와 AppPaths는 C 소유이며 BEGIN IMMEDIATE나 Store 메모리 mutex로 대신하지 않는다.

제품 DB와 SQLite 부속 `-wal`·`-shm`, v3 이관 전 백업을 같은 사용자 전용 앱 폴더에 둔다. C가 검증한 사용자 전용 DACL로 다른 Windows 사용자의 DB 접근을 막고, 제품에서 임의 DB 경로·별칭·링크를 선택하는 입구를 없애 같은 app.lock으로 같은 제품 DB를 보호한다는 안이다. DACL 하나가 모든 경로 별칭을 없앤다는 뜻은 아니다. 앱 폴더/고정 경로의 안전성은 C가 검증하고 의도적인 같은 사용자 우회는 기존 위협 모델에 따른다.

남은 조건은 **(1) C가 AppPaths에 DB·백업 경로를 제공하고 (2) A가 제품 모드를 그 경로로 바꾸며 `--demo`가 그 경로를 열지 못하게 하는 것**이다. 위 두 조건이 들어가면 REC-01의 제품 DB 단일 소유 미지원 조건은 해소하는 안으로 본다. 조건 충족/독립 검증 전에는 실행 게이트를 열지 않고 A가 임시 잠금/다른 파일 경로를 직접 만들지 않는다. 로컬 `77d314a`에는 AppPaths/app.lock 연결이 없어 실제 반영 여부는 확인 불가다.

시작 순서는 STARTING/실행·제어 닫힘→C 단일 소유→B 검사·백업 협력·이관 ACK→B 복구 ACK→C Registry 실제 지문·정책/접근 규칙·하네스 준비→A transport/새 Task·Guard·Runner 구성→Store 실행 회차 활성화 ACK→READY다. 오래된 A 회신의 AGT 시작 단계는 AGT 제거 결정에 따라 다시 도입하지 않는다. 최신 A/C 세부 조립 순서는 실제 연결 리뷰가 필요하다.

Store 상태 RECOVERED에서는 bootstrap의 제한된 새 Task 생성/확인만 허용하고 배정·일반 판정 저장·승인 소비·dispatch 예약은 닫는다. A가 다른 준비를 모두 끝낸 뒤 현재 run을 활성화하고 Store가 이를 ACK해야 실행을 연다. v3 회차 표식은 RECOVERY_COMMITTED/ACTIVE/CLOSED 같은 원문 없는 사실을 영속으로 남기되, ACTIVE 행 하나가 다음 프로세스의 실행 허가가 되지는 않는다.

실패 시 자원을 역순 정리하고 Store writer·이전 Guard/Runner/transport/harness의 실제 종료를 확인한 뒤에만 소유권을 정상 해제한다. **worker가 살아 있는 동안 소유권을 풀지 않는다. 프로세스가 실제 끝나면 OS가 writer 스레드와 app.lock의 잠금 핸들을 함께 정리하므로, 8절의 daemon writer 종료안은 이 조건과 충돌하지 않는다.** Store close 후 5초 관찰에도 닫힘이 확인되지 않으면 CLEANUP_UNCONFIRMED로 표시하고 app.lock을 먼저 해제하지 않은 채 프로세스 종료를 진행한다. 같은 프로세스에서 새 Store/Guard나 같은 DB의 새 실행자를 만들지 않고 단순 timeout을 “기존 실행자 종료”로 기록하지 않는다.

**이유:** 앱 접수 barrier와 Store 거부를 함께 적용해야 준비 전 SQL 실행이 빠져나가지 않는다. SQLite의 TX 잠금은 TX 밖 transport 실행을 보호하지 않는다. 종료 미확인 실행자와 새 복구가 겹치는 것도 막아야 한다.

**영향:** app.lock을 고정 제품 DB의 소유권으로 보는 범위와 C AppPaths DB·백업 경로, StoreLifecycle 회차/활성화 ACK·DTO가 **합의 전 제안**이다. A는 창/DB 전 잠금·고정 제품 DB/데모 분리·시작/정리 barrier를 연결한다. C는 사용자별 권한·제품 경로의 별칭/링크 통제·두 프로세스·강제 종료 뒤 잠금 해제를 검증한다. Task/승인/원문을 다음 run에 재결속하지 않는다. A 동의(#37), C 회신 대기다.

## 5. REC-02 · legacy 종류 유실 격리와 상태 표

**A 요청/질문:** v1 DISPATCHING의 종류 유실 때문에 앱 전체를 못 쓰는 대신 결과 불명 격리 후 새 Task만 허용하는 안을 선호했다. READ로 추정·결과 공개·추가 SEND/자동 재전송은 금지하고 UI/감사가 격리를 알려야 한다. U8 종결 Task+미완료 SEND의 선택은 B/C에 맡겼다.

**B 결정:** **관계가 검증된 legacy 유실에 한해 A 격리안을 받는다.** v2도 요청 열은 v1과 같으므로 같은 대상으로 본다. migration 출처로 입증된 kind/epoch NULL, 유효한 Task/요청/승인 FK·저장 형식·예약 사실, 등급/미분류/승격 감사 일치가 전제다. 현재 Registry/도구 이름/원문에서 과거 kind·epoch·지문을 채우지 않는다.

| 저장 상태/사실 | 시작 복구 선택 |
| --- | --- |
| 정상 비종결 옛 Task, 진행 중 예약 없음 | READY/RUNNING/WAITING_APPROVAL을 HALTED. Task 재개 없음 |
| 미예약 DECIDED/WAITING_APPROVAL 요청, 정상 split 중단 포함 | 요청 DENIED, 비종결 Task HALTED. 승인 사본/실행 권한 복원 없음 |
| PENDING/APPROVED 승인 | 둘 다 EXPIRED. 생성/직전 사건보다 이른 종결 시각을 쓰지 않고 expires_at은 유지 |
| CONSUMED·이미 종결된 승인 | 소비·종결 사실 보존. 승인 원문/권한 복원 없음 |
| 신뢰 kind/epoch의 DISPATCHING READ | 요청 WITHHELD, RUNNING Task HALTED. 결과 복원/공개 없음 |
| 신뢰 kind/epoch의 DISPATCHING SEND | 요청 UNKNOWN_OUTCOME, RUNNING Task UNKNOWN_OUTCOME |
| legacy DISPATCHING, kind/epoch 없음, Task RUNNING | READ로 추정하지 않고 요청 UNKNOWN_OUTCOME·Task UNKNOWN_OUTCOME, 별도 legacy 격리 기록 |
| Task HALTED/CLOSED/UNKNOWN_OUTCOME + DISPATCHING SEND 또는 legacy 종류 유실(U8 포함) | 요청 UNKNOWN_OUTCOME과 격리 기록. Task의 기존 종결 상태는 보존하고 projection에서 불명 위험을 별도로 표시 |
| DISPATCHING + READY/WAITING_APPROVAL 등 허용된 중단으로 설명되지 않는 조합 | 미해결로 gate 닫힘. 격리라는 이름으로 정상화하지 않음 |
| FK/감사 불일치·임의 신규 NULL·PENDING/APPROVED 승인과 DISPATCHING의 모순·지원하지 않는 상태/종류·알 수 없는 관계 | 전체 복구 실패·gate 닫힘 |

과거 요청의 kind/epoch 유실과 확인된 새 요청의 의미를 구별한다. legacy UNKNOWN_OUTCOME은 “SEND였음”을 확정하는 표시가 아니라 “SEND였을 수 있어 재전송할 수 없음”이라는 보수적 격리다. 이미 UNKNOWN_OUTCOME인 legacy 행에도 검토된 migration 출처/격리 관계를 유지한다. Task HALTED/CLOSED를 다시 RUNNING으로 열거나 정상 전이표를 전역으로 완화하지 않는다. U8은 별도 격리 projection을 선택해 종결 Task 불변과 SEND 불명 표시를 함께 만족한다.

한 Task의 목표 상태는 모든 요청 집합으로 계산한다. SEND/가능한 SEND의 불명을 뒤의 READ/HALTED 정리로 덮지 않는다. 기존 high_watermark·last_read_label·unclassified·승격 이력은 보존하고, 감사 이력보다 낮은 등급이나 사라진 미분류가 있으면 복구하지 않는다(2026-10-15 결정). 원문을 복원하거나 확인용 tools/call을 보내지 않는다.

격리 표에는 검증된 run/Task/request ID, 원래 상태, LEGACY_METADATA_MISSING/TERMINAL_TASK_DISPATCHING 같은 고정 분류·UTC만 저장한다. 원래 unknown kind/epoch는 NULL로 남긴다. 같은 요청/격리 사유는 중복 삽입/행별 감사하지 않는다. Task 목록과 별도의 복구 항목 projection을 A가 함께 표시하고, 기존 TaskState.status만 보고 “불명 없음”으로 표시하지 않는다.

### RecoveryItem 표시 필드 · 합의 전 제안

A의 #37 요청을 받아 복구 항목의 run/Task/request ID·원래 상태·고정 분류/UTC projection에 다음 필드를 포함한다. 현재 공개 `RecoveryItem` DTO는 없다. 현 v2 `requests`에는 server_id/tool_name/destination_id가 저장되지만 private `_StoredRequest`는 이 세 필드를 노출하지 않고 `stored_kind`·`stored_epoch`도 None이다. 따라서 기존 DTO에 이미 있다고 보고하지 않고 v3/복구 조회 구현 범위로 둔다.

| 필드 | 타입·출처/표시 |
| --- | --- |
| server_id | str. 관계/형식 검증을 마친 requests 행의 신뢰 등록 메타데이터 |
| tool_name | str. 같은 requests 행의 이름. MCP 서버가 정한 텍스트이므로 A는 일반 텍스트로만 표시하며 링크/HTML/명령으로 해석하지 않음 |
| destination_id | str 또는 None. 요청의 저장된 신뢰 목적지 식별자이며 인자 원문을 복원하지 않음. READ는 None |
| kind | `ToolKind \| None`. 검증된 저장 종류만 사용하며 신뢰 값이 없는 legacy 행만 None |
| epoch | `int \| None`. 검증된 저장 epoch만 사용하며 신뢰 값이 없는 legacy 행만 None |

`TERMINAL_TASK_DISPATCHING`에서도 kind=SEND는 “보냈을 수 있음”, kind=None은 “종류 미확정”으로 구별한다. 도구 이름·현재 Registry·현재 Task epoch로 legacy kind/epoch를 메우지 않는다. 원문 인자·문서/결과 본문은 필드에 넣지 않는다.

**격리됨은 실행 권한을 폐기해 안전하게 분리했다는 의미에서 unresolved에 넣지 않는다.** 수신 측 업무 결과가 해결됐다는 뜻은 아니다. UNKNOWN_OUTCOME/격리 수를 남기고 옛 Task는 계속 실행 불가다. 모든 격리 관계/감사가 같은 복구 TX에 커밋되고 실제 미해결 0인 경우에만 새 Task 준비로 진행한다. 사람 확인은 v1 구현 범위에서 표시만 하며 상태/재전송 권한을 만들지 않는다.

원안의 gate 닫기는 종류 유실에도 가장 보수적이지만 정상 legacy 행 하나로 앱 전체가 막힌다. 검증된 격리는 옛 결과·전송 권한을 전혀 재사용하지 않고 새 Task만 허용하므로 이를 선택한다. **다만 파손까지 격리로 통과시키는 안은 선택하지 않는다.** 미해결로 닫혔을 때 운영자는 앱 종료·C 소유권/안전 백업→B/C 오프라인 진단→합의된 별도 이관/새 DB 선택을 거친다. SQL 직접 수정·게이트 강제 해제·옛 Task 재개 버튼은 제공하지 않는다. 해결 전 원본을 삭제하지 않는다.

**이유:** I8은 기존 SEND가 0회였다고 가정하는 대신 복구로 생기는 추가 전송을 0으로 만드는 요구다. 종류가 없으면 SEND 가능성을 남겨야 하고, 유효하지 않은 관계는 다른 Task의 상태를 잘못 바꿀 위험이 있어 전체 실패가 필요하다.

**영향:** legacy 표시·격리 표와 위 RecoveryItem 필드, 시작 전용 상태 종결은 **합의 전 제안**이다. 기존 enum에 새 상태를 만들지 않는다. A는 Task 목록과 복구 항목 화면을 분리하고 이번 복구가 실제 업무 행을 바꿨을 때만 시작 알림을 낸다. 결과 불명 항목의 재실행 버튼은 없고 미해결이면 시작을 거부한다. 결과 불명/종류 미확정·수신처 직접 확인을 일반 텍스트로 표시한다. C는 U3/U7/U8·legacy provenance·추가 wire/effect 0을 독립 검증한다. A 동의(#37), C 회신 대기다.

## 6. REC-03 · 옛 epoch 보존과 새 Task 관계

**A 요청/질문:** 옛 Task epoch를 보존하고 새 Task ID/회차의 관계를 기록하는 B안을 골랐다. 대화·캐시·Runner는 새 Task로 분리하고 옛 명령을 거부한다.

**B 결정:** B안을 받는다. 복구는 옛 Task의 상태만 필요에 따라 종결하며 epoch와 과거 요청 epoch를 고치지 않는다. 현재 A 화면에는 옛 Task에서 이어 만드는 입구가 없으므로 **지금 연결할 새 Task는 모두 부모 없는 새 ID·epoch 1**이다. 승격/미분류·대화·인자·승인·결과는 승계하지 않고 같은 Task ID를 되살리지 않는다.

향후 사용자가 특정 옛 Task에서 명시적으로 새 작업을 만드는 기능을 추가할 때만 RestartLink/생성 입구를 연결한다. 그 경우 새 ID·`new_epoch = parent.epoch + 1`, parent/child Task ID·각 epoch·새 run ID·UTC의 관계를 새 Task 생성과 같은 TX에 남긴다는 규칙을 유지한다. int64 상한 또는 부모 관계 불일치는 실패다. 이번 A 연결에 없는 기능을 복구/시작 때 자동 실행하지 않는다.

재시작만으로 모든 옛 Task에 자식을 자동 생성하거나 임의의 부모를 선택하지 않는다. 현재 run의 새 Task 소유 관계를 Store가 검사하고 옛 ID/epoch의 배정·예약·제어는 거부한다. A의 옛 Task/approval 명령 입구 차단과 B의 Store/Guard 보호를 함께 유지한다.

**이유:** 기술설계 0.2의 회차 증가와 7.3의 새 Task 원칙을 옛 사실 수정 없이 연결한다. 이 해석은 공통 문서 반영이 필요한 합의 항목이며 이번에 그 문서를 고치지 않는다. 후속 복구가 같은 parent의 epoch를 계속 올리지 않게 관계 삽입은 명시적 새 Task 생성의 고유 요청과 결속한다.

**영향:** 현재 run 소유 관계와 독립 새 Task epoch 1은 **합의 전 제안**이며 A 동의(#37), C 회신 대기다. 기존 TaskState/TaskIdentity 필드는 유지한다. A는 현재 부모 없는 새 Task만 연결한다. RestartLink/parent+1 생성 입구·관계 스키마는 그 기능을 만들 때 연결할 후속 제안이다. C는 현재 옛 epoch 불변·옛 명령 0을 검증하고 child 원자 생성·관계 중복 검증은 해당 기능 추가 때 수행한다.

## 7. REC-04 · RecoveryReport의 B 확정 목록

**A 요청/질문:** 성공 ACK와 projection을 구별하고 스키마 버전·run ID·변경 수·불명/격리/미해결 수를 읽고 싶다고 했다. 미해결이 있으면 gate를 닫고 격리안 채택 시 격리는 안전 분리된 것으로 센다.

**B 결정:** 다음 10필드를 B 제안의 확정 목록으로 정하고 **A의 10필드 동의(#37)를 반영한다. C 회신 대기인 합의 전 제안**이며 공동 합의/구현 완료 목록은 아니다. DTO는 strict·frozen·extra forbid, 원문 없는 repr로 제안한다.

| 필드 | 타입/의미 |
| --- | --- |
| schema_version | int, 이번 대상 3. SQLite 버전과 구분 |
| recovery_version | int, 복구 규칙 버전 1. 파일 설정 schema_version과 구분 |
| run_id | 신뢰 공급자가 만든 복구/실행 회차 식별자 |
| committed_at_utc | 성공 ACK를 받은 복구 TX의 UTC 기록 |
| changed_task_count | 이 TX에서 실제 변경한 고유 Task 행 수 |
| changed_request_count | 이 TX에서 실제 변경한 고유 요청 행 수 |
| changed_approval_count | 이 TX에서 실제 변경한 고유 승인 행 수 |
| unknown_outcome_count | 복구 후 전체 요청 중 UNKNOWN_OUTCOME인 고유 요청 수. Task 수가 아님 |
| quarantined_count | 복구 후 영속 격리 관계가 있는 고유 요청 수. 과거 격리 포함 |
| unresolved_count | 안전 종결/격리할 수 없는 고유 미해결 요청·Task 항목 수. 성공 report는 반드시 0 |

unknown/격리는 겹칠 수 있으며 두 수를 더해 총 요청 수로 쓰지 않는다. 변경 수는 회차/감사/격리 표 행 수가 아니라 위 세 업무 테이블의 실제 변경 수다. 한 행을 여러 규칙이 건드려도 1로 센다. 격리됐어도 수신 측 결과가 알려졌다는 뜻은 아니다.

같은 run_id의 정상 재조회는 저장된 완료 기록을 반환하고 재적용하지 않는다. 새 프로세스의 새 run은 새 시작 기록을 남길 수 있지만 이미 종결/격리된 업무 행의 반복 변경·행별 복구 감사·번호 초기화는 0이다. COMMIT 뒤 ACK를 잃은 인스턴스는 성공 report를 재조회해 재개하지 않고 닫는다. 다음 소유자가 실제 완료 표식/자료를 다시 검증한다.

Task 실제 변경은 row_revision +1, 상태 등 보안 변화가 있으면 security_version +1, 변경 없는 행은 둘 다 보존한다. 변경 승인/요청만 해당 row_revision을 +1 한다. 승인 UTC는 기존 생성/결정/소비 사건 이상, expires_at 불변이다. 모든 변경·감사·run 완료 표식이 한 TX다. **A는 성공 report만 화면의 복구 결과로 사용한다.** 미해결/쓰기/감사 오류는 전체 실패이며 성공 report 대신 `execution_state()`와 **8절의 고정 시작 실패 분류 STORE_* 표**로 표시한다. 실패 projection은 READY 토큰이 아니며 STORE_*는 기존 Reason과 별도다.

**이유:** A가 안전 준비 결과와 단순 읽기 화면을 혼동하지 않게 한다. “격리로 새 작업 가능”과 “수신 측 업무 해결”도 다른 상태다. DB 복구 ACK 뒤에도 다른 구성요소와 Store 활성화 ACK가 남는다.

**영향:** RecoveryReport·MigrationReport·읽기 전용 RecoveryItem/페이지 DTO와 수명 포트가 합의 대상이다. A가 필요한 후보는 모두 포함했다. 현재 SQLiteStore에는 list_tasks가 이미 있지만 공개 Store 12개에는 없고 격리/회차 projection도 없으므로 이를 중복 구현하지 않고 후속 조회 포트와 대조한다. C는 +1/0·UTC·중복 실행·ACK 유실·I9를 검증한다.

## 8. REC-05 · 시간 예산과 실패 후 수명

**A 요청/질문:** #37에서 B 선택에 동의하고 deadline 뒤 창 닫기·writer 종료/잠금 유지, 준비 진행 코드와 시작 실패 분류의 이름을 B에 맡겼다. 같은 프로세스의 자동 재시도/Store 재열기는 하지 않는다.

**B 결정:** 아래 daemon writer·close·deadline·진행/시작 실패 코드를 선택한다. **A 동의(#37), C 회신 대기의 합의 전 제안**이며 현재 SQLiteStore 구현이라고 보고하지 않는다. 시간값은 **미측정 제안값**으로 성능 보장/시험 통과 수치가 아니다.

### 8.1 전용 daemon writer와 창 닫기

B6.13 writer는 연결 생성·사용·종료를 맡는 전용 스레드 **하나, `daemon=True`**로 정한다. `asyncio.to_thread`/기본 executor는 사용하지 않는다. 기본 executor의 ThreadPoolExecutor 스레드는 종료 때 join 대상이어서 막힌 SQL이 프로세스와 app.lock의 수명을 늘릴 수 있기 때문이다. daemon은 정상 정리를 생략하는 기능이 아니라 최종 종료가 writer join에 무한히 묶이지 않게 하는 선택이다. [Python executor 종료](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.ThreadPoolExecutor), [daemon 수명](https://docs.python.org/3.12/library/threading.html#thread-objects)

A가 향후 Store facade의 `close()`를 부르면 즉시 새 작업 접수를 닫고 진행 중 작업이 끝난 뒤 소유 writer가 연결을 닫는다. 대기 중 미시작 작업도 더 실행하지 않고 닫힌 결과로 끝내며 close/종료 관찰은 이벤트 루프를 막지 않는다. A는 5초 관찰 안에 닫힘이 확인되지 않으면 **CLEANUP_UNCONFIRMED**로 표시하고 app.lock을 먼저 풀지 않은 채 프로세스 종료를 진행한다. 늦은 성공을 받아 READY로 전환하거나 같은 프로세스에서 Store를 재열지 않는다. 현재 `SQLiteStore.close()`는 소유 스레드에서 연결을 닫는 동기 메서드다. 여기의 비차단 facade 의미는 B6.13 후속 구현이다.

**worker가 살아 있는 동안 소유권을 풀지 않는다. 프로세스가 실제 끝나면 OS가 writer 스레드와 app.lock의 잠금 핸들을 함께 정리하므로 이 종료안은 소유권 유지 조건과 충돌하지 않는다.** 5초는 정리 관찰 상한이지 fsync 중단이나 전체 프로세스 종료까지 그 안에 끝났다는 증명이 아니다. A가 DB·`-wal`·`-shm`을 삭제/복사하거나 같은 프로세스에 새 Store/worker를 만들어 해결하지 않는다. 3절의 B/C 협력 이관 백업은 별도 준비 단계다.

현재 `storage/sqlite_store.py`는 `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=FULL`을 설정하고 `_configure`에서 반환값 `"wal"`/`2`를 확인한다(foreign_keys=1도 확인). 후속 writer도 이 설정과 같은 DB 안의 원자 커밋을 유지한다. 정상적인 SQLite/파일시스템 전제에서 COMMIT 도중 프로세스가 끝나면 다음에 열 때 해당 TX는 **전부 반영됐거나 전부 없는 상태**이며 중간 성공으로 채택하지 않는다. 어느 쪽인지는 다음 단일 소유자의 검사·복구가 run/operation 표식·자료/감사를 대조해 판별한다. 저장 장치 손상/무결성 실패까지 정상으로 보장하지 않고 실패하면 게이트를 닫는다. daemon 종료는 close/rollback 성공 ACK가 아니며 실제 프로세스 중단 인수는 C가 수행한다. [SQLite 원자 커밋](https://www.sqlite.org/atomiccommit.html), [WAL·FULL 동작](https://www.sqlite.org/wal.html)

### 8.2 준비·복구 deadline

복구를 A 일반 구성요소 시작 10초에서 분리한다. A는 **바깥 60초 monotonic deadline을 B 준비 입구에 넘기고**, B가 준비 전체와 그 안의 복구 30초를 함께 집행한다. 복구는 큐 대기를 포함한 시작 시점+30초와 전달받은 바깥 deadline 중 빠른 쪽 안에서 끝내거나 `STORE_DEADLINE_EXCEEDED`로 닫는다. A가 복구 30초를 별도 타이머로 다시 재지 않는다.

| 예산 | B 선택 · 미측정 제안 |
| --- | --- |
| 복구 요청 전체 | monotonic 30초. 큐 대기·BEGIN 잠금·읽기/관계·감사 대조·쓰기·COMMIT/ACK 포함, B 준비 입구가 집행 |
| 저장소 준비 전체 | A가 바깥 60초 monotonic deadline 전달. C 소유권/백업 협력·B 이관/검증·복구가 이 예산을 공유하고 B가 남은 예산 안에서 닫힘 집행 |
| 그 뒤 A 일반 구성요소 시작 | 기존 기본 10초를 기준으로 A가 하네스/transport 단계별 실제 예산과 대조 |
| busy_timeout_ms | 현행 후보 1000ms 유지 검토. 전체 TX/COMMIT/취소 예산으로 해석하지 않음 |
| timeout 뒤 정리 관찰 | 추가 5초. 닫힘 미확인이면 CLEANUP_UNCONFIRMED, 실행 닫힘·app.lock 유지 상태로 프로세스 종료 진행 |

시간 상한은 **실행 허가를 닫는 deadline**이다. 스레드에서 진행 중인 fsync/COMMIT를 정해진 시각에 강제로 끝낼 수 있다는 보장이 아니다. deadline 뒤 늦게 온 성공을 READY로 채택하지 않으며 A shield가 SQL 작업 종료를 증명하지도 않는다. 같은 프로세스에서 worker를 교체하거나 app.lock을 먼저 풀지 않는 조건은 4절·8.1절과 같다. [SQLite busy timeout](https://www.sqlite.org/pragma.html#pragma_busy_timeout), [Python SQLite thread/connection 제약](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.connect)

### 8.3 저장소 준비 진행 코드

진행 순서는 **`STORE_CHECK` → `STORE_BACKUP` → `STORE_MIGRATE` → `STORE_VERIFY` → `STORE_RECOVER`**로 정한다. 이관할 것이 없으면 BACKUP·MIGRATE는 건너뛴다. 진행 코드는 CLOSED/MIGRATING/RECOVERING/RECOVERED/READY/FAULTED라는 권한 phase 안의 세부 작업 표시이며 phase나 실행 허가를 대체하지 않는다. B가 신뢰된 단계만 보고하고 A가 고정 문구로 표시하며 원문 경로/SQL/예외를 붙이지 않는다.

### 8.4 고정 시작 실패 분류

시작 실패 분류는 **기존 Reason과 별도인 원문 없는 고정 코드**다. execution_state snapshot과 함께 표시하되 Denied/outcome의 Reason 또는 정상 RecoveryReport로 바꾸지 않는다. app.lock 획득 실패는 C의 `APP_*` 코드이므로 아래 STORE_*에 합치지 않는다. CLEANUP_UNCONFIRMED는 8.1절의 정리 관찰 결과다.

| 코드 | 뜻 | A 안내 |
| --- | --- | --- |
| STORE_SCHEMA_UNSUPPORTED | 모르거나 더 새로운 스키마 | 진단 필요 |
| STORE_INTEGRITY_FAILED | 무결성·관계 검사 실패 | 진단 필요 |
| STORE_RECOVERY_UNRESOLVED | 미해결 항목이 있어 게이트를 닫음 | 진단 필요 |
| STORE_BACKUP_FAILED | 이관 전 백업 실패. 이관하지 않음 | 다시 시작 |
| STORE_MIGRATION_FAILED | 이관 실패, rollback 확인 | 다시 시작 |
| STORE_COMMIT_UNKNOWN | COMMIT 결과 불명 | 다시 시작. 다음 시작이 판별 |
| STORE_DEADLINE_EXCEEDED | 30초·60초 상한 초과 | 다시 시작 |
| STORE_IO_FAILED | 열기·읽기·쓰기 I/O 실패 | 다시 시작 |

“진단 필요”는 자료·스키마 문제를 처리하지 않고 다시 켜면 같은 실패가 반복되는 분류다. “다시 시작”도 자동 재시도/같은 프로세스 재열기가 아니며 정상 성공을 약속하지 않는다. rollback 확인 없는 실패를 STORE_MIGRATION_FAILED로 단정하지 않고 COMMIT 불명은 STORE_COMMIT_UNKNOWN으로 구별한다. 모든 실패는 실행 게이트를 닫는다.

### 8.5 측정과 한계

측정은 B가 실제 파일 SQLite 단위로, C가 독립 프로세스/Windows 환경으로 수행한다. 최소 빈 DB·약 1천/10만/100만 요청, 여러 Task/승격/승인/Registry/감사 조합, warm/cold·WAL·0/1초 이상 외부 잠금·디스크/감사 실패를 대조한다. 행 수는 벤치마크 준비 규모이며 지원 한도가 아니다. 읽기/검증/쓰기/COMMIT/전체 p50·p95·p99·최대, event-loop 지연, timeout 후 실제 정리 시간을 별도로 남기고 Python/SQLite/OS/저장 장치/DB 크기를 기록한다. 원문 sentinel은 노출 여부만 세고 보고에 원문을 붙이지 않는다. 측정 후 A/C가 예산을 확정한다.

**이유:** 10초 시작 timeout이나 busy_timeout만으로 큰 DB·I/O·스레드 종료를 보장할 수 없다. 작업 취소와 결과 불명도 같은 사건이 아니므로 ACK를 보수적으로 분류해야 한다.

**영향:** B6.13 전용 daemon writer·비차단 close·B 준비 입구의 deadline/진행/실패 분류와 A의 바깥 deadline 전달·고정 안내·프로세스 종료, C 종료/잠금/SQLite 원자성·성능 인수가 필요하다. A 동의(#37), C 회신 대기의 **합의 전 제안**이다. timeout은 권한 복원·자동 retry 근거가 아니며 기존 SEND 결과 불명과 읽기 미공개를 유지한다.

## 9. B6.13 · B-QA-03/10·잠금 대기의 관계

**A 요청/질문:** SEQ-02는 B-QA-03과 같은 가시성 문제라고 했다. 첨부는 B6.13에 SQLite 잠금 대기 중 이벤트 루프 정지를 함께 다루도록 요구한다.

**B 결정:** 원인을 구별해 같은 구현 묶음에서 처리한다. [A QA 원문](../tasks/a-b-qa-requests-2026-10-13.md)의 B-QA-03/10은 Guard만 정지하고 Store/UI가 RUNNING으로 보이는 문제다. SQLite가 동기 대기해 이벤트 루프를 막는 문제와 동일하지 않다. 현재 SQLiteStore의 async 메서드 23개는 내부 await 없이 소유 스레드에서 SQL을 실행하므로, async라는 이름만으로 비동기 I/O가 되지는 않는다.

| 문제 | 함께 할 B 범위 | 별도 검증 |
| --- | --- | --- |
| 전역 정지/COMMIT 불명이 Store·UI에 안 보임 | 2절 Store controller 권한 상태·권위 조회·Guard fault 연결·재시작 규칙 | SQL/감사 실패 뒤 DB Task가 RUNNING이어도 execution_enabled=False, A 다음 모델 호출 0 |
| DB 잠금/COMMIT 중 이벤트 루프 정지 | 연결 생성·사용·종료·메모리 binding을 전용 단일 writer 스레드로 옮기는 async facade | 외부 잠금 중 event-loop heartbeat/stop 접수, thread ownership, deadline 후 늦은 결과 미채택 |

매 호출을 임의의 `asyncio.to_thread`로 보내거나 check_same_thread=False로 바꾸는 안은 택하지 않는다. 같은 연결과 binding은 **8.1절의 전용 daemon worker 하나**가 소유하고 Store·RegistryStore·순번·감사·이관·복구 모두 같은 큐로 직렬화한다. UI/백엔드 이벤트 루프는 SQL이 끝나기를 동기 대기하지 않으며 close 관찰도 비차단이다. 작은 실행 권한 snapshot 조회는 SQL 큐와 독립시킨다. 큐 용량·반복 취소·부하 한도는 신뢰 설정과 B/C 측정으로 확정한다.

쓰기 작업의 대기 취소/timeout이 worker의 rollback 완료라는 뜻은 아니다. 이미 시작한 작업은 phase/ACK를 분류하고 불명은 controller를 닫는다. 후속 실행 연산을 차단하고 늦은 성공으로 재개하지 않는다. 전용 worker도 fsync 중 무조건 중단 가능한 장치는 아니며 실제 종료 확인 전 같은 DB의 worker 교체를 하지 않는다.

**이유:** worker 이동만으로 Store 권위 상태가 생기지 않고, health 플래그만 추가해도 이벤트 루프 정지는 해결되지 않는다. 두 조건이 모두 충족돼야 SEQ/REC와 B6.13을 끝냈다고 할 수 있다.

**영향:** B6.8과 B6.13은 별도 완료 조건을 유지하되 writer/ACK/controller 기반을 공유한다. ports는 기존 async 서명에 맞춘 facade와 별도 수명 포트를 검토한다. A는 shield·stop_task와 worker 종결을 구별하고 C는 응답성·가시성·단일 소유·예약 뒤 READ/SEND를 각각 검증한다.
