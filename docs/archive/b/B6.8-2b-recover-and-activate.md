# B6.8 2단계 27b: 시작 복구와 회차 활성화

2026-10-28 · B 단위 구현 · REC-01–05·SEQ-02

27a의 명시 스키마 준비 ACK 뒤에 옛 실행의 복구, 복구 보고·격리 조회와 새 실행 회차 활성화를 추가했다. B6.8의 B 단위 범위는 완료했다. 제품 시작 연결과 C 독립 인수까지 완료했다는 뜻은 아니다.

## 복구 계약과 v3

- `RecoveryReport`는 성공한 복구 TX의 스키마·복구 버전, run ID, 완료 UTC와 변경·불명·격리·미해결 수를 담는 불변 보고다. 성공 보고의 미해결 수는 0이다. 불명 요청 수와 격리 수는 겹칠 수 있다.
- `RecoveryItem`과 `RecoveryItemPage`는 격리 분류·원래 상태와 저장된 서버·도구·목적지·종류·epoch를 제공한다. legacy에서 종류와 epoch가 없으면 그대로 `None`이다. 도구 이름과 식별자는 repr에서 숨기며 인자·결과·경로·예외 원문은 보고나 감사에 싣지 않는다.
- `StoreLifecycle`에 `recover`, `activate_run`, `load_recovery_report`, `list_recovery_items`를 추가했다. 이관 ACK, 복구 ACK, 활성화 ACK는 서로 별개다. 성공한 복구 보고만 화면의 복구 결과로 쓴다.
- v3에 `store_runs`, `recovery_reports`, `recovery_quarantine`, `task_run_owners`를 추가했다. 새 DB 생성과 v1/v2 이관 모두 같은 스키마를 쓰며 이관 직후 네 표는 비어 있다. v3는 B6.8 PR 병합 때 확정한다. 기존 27a 초안으로 만든 v3 DB는 버전이 같아도 네 표가 없어 정확한 DDL 검사에서 거부된다. 이는 PR 병합 전 초안 사이의 한계다.

## 복구와 실행 권한

명시 모드는 `prepare_schema` 성공 뒤 `RECOVERING`에서 `recover`를 호출한다. writer의 `BEGIN IMMEDIATE` 한 TX에서 저장 관계와 보안 이력을 검사하고 옛 회차를 닫으며 Task·요청·승인 정리, 격리, 새 run과 보고, 감사를 함께 기록한다. 관계 손상이나 미해결 조합은 부분 적용 없이 롤백하고 고정 시작 실패 코드와 `FAULTED`로 닫는다. 복구는 `requests.reasons`를 해석하거나 과거 종류·epoch를 추정하지 않고, 결과를 복원하거나 `tools/call`을 보내지 않는다.

| 저장 사실 | 복구 결과 |
| --- | --- |
| 비종결 Task, 미예약 요청 | Task HALTED, DECIDED·WAITING_APPROVAL 요청 DENIED |
| PENDING·APPROVED 승인 | EXPIRED. CONSUMED와 이미 종결된 승인은 보존 |
| RUNNING Task의 DISPATCHING READ | 요청 WITHHELD, Task HALTED |
| RUNNING Task의 DISPATCHING SEND | 요청과 Task UNKNOWN_OUTCOME |
| RUNNING Task의 legacy DISPATCHING | 요청과 Task UNKNOWN_OUTCOME, 종류 유실 격리 |
| 종결 Task의 DISPATCHING SEND 또는 legacy 요청 | 요청 UNKNOWN_OUTCOME과 격리, Task 종결 상태 보존 |
| 종결 Task의 DISPATCHING READ | 요청 WITHHELD, Task 상태 보존 |
| 기존 legacy UNKNOWN_OUTCOME과 격리 누락 | 업무 행은 그대로 두고 종류 유실 격리 추가 |
| READY·WAITING_APPROVAL Task의 DISPATCHING, PENDING·APPROVED 승인과 DISPATCHING | 미해결로 전체 복구 실패 |

한 Task의 여러 요청 중 SEND 불명이 있으면 READ 정리가 그 목표를 HALTED로 덮지 않는다. 실제 변경된 업무 행만 revision을 1 올리고 Task 상태 변경은 security_version도 1 올린다. 단일 복구 UTC는 기존 사건 시각보다 이르지 않으며 승인의 만료 시각은 바꾸지 않는다. 기존 관찰·예약·소비 감사와 현재 저장 관계 및 보안 상태의 모순도 무결성 오류로 처리한다.

deadline은 바깥 deadline과 복구 시작부터 30초 중 더 이른 값이며 writer 큐 대기를 포함한다. 행 처리 중 초과는 롤백한다. COMMIT 뒤 초과나 ACK 유실은 성공으로 채택하지 않고 닫으며 다음 프로세스가 저장 사실을 다시 검사한다. 반복 복구에서는 이미 정리한 업무 행과 revision·시각이 그대로이고 행별 복구 감사도 늘지 않는다. 사용자 결정에 따라 새 run마다 개수만 담은 `RECOVERY_COMMITTED` 요약 감사는 정확히 한 건을 남긴다.

복구 성공은 실행이 닫힌 `RECOVERED`다. 읽기와 현재 run의 새 Task 준비, 세션·실패 감사 및 활성화를 제외한 Registry 준비는 허용한다. 순번 배정·판정·예약·승인 소비와 Registry 활성화는 닫혀 있다. `activate_run`의 ACTIVE 커밋 ACK 뒤에만 `READY`와 실행 권한을 연다. 명시 모드의 새 Task는 부모 없는 epoch 1이며 소유 run을 같은 TX에 기록한다. 순번 배정·예약·승인 소비와 Task 제어는 현재 run 소유를 확인한다. 이전 ACTIVE 행은 다음 프로세스의 실행 허가가 아니다.

연결이 정상인 전역 정지 뒤에는 실행 권한을 닫으면서 필요한 정리와 실패 감사를 허용한다. 연결 폐기나 커밋 결과 불명에서는 계속 차단한다. 명시 모드의 기본 감사 ID는 UUID4이며 주입한 factory를 우선한다. 기존 기본 생성자인 즉시 모드의 동작과 run_id `None`은 유지한다.

## 검증

Windows에서 각 단계의 전체 pytest는 실패 0, **4 skipped, 2 warnings, 20 subtests passed**다. 각 변경 단계에서 Ruff, format 검사와 mypy도 통과했다.

| 단계 | 전체 pytest 결과 |
| --- | --- |
| 작업 전 기준 | 5169 passed |
| 복구 계약 | 5172 passed |
| v3 네 표 | 5182 passed |
| 시작 복구 | 5219 passed |
| 회차 활성화와 결속 | 5233 passed |

복구 단위 시험은 위 상태표, 여러 요청의 SEND 우선, 승인 시각·revision, 실제 v1/v2 이관, legacy 이유 문자열 보존, 조회와 페이지, 격리·감사 관계 손상, 미해결 롤백, 반복 복구, deadline과 COMMIT ACK 유실 후 재시작을 확인했다. 활성화 단위 시험은 RECOVERED 게이트, 현재 run 결속, 옛 Task 거부, Guard READ, 활성화 경합·취소·ACK 유실과 전역 정지 후 정리를 확인했다. 이 결과는 아래 A·C의 제품 연결과 독립 인수를 대체하지 않는다.

## A·C 요청과 남은 범위

- A: `app.lock` → `SQLiteStore(folders.db_path(), startup="explicit")` → `prepare_schema` → `recover(run_id=...)` → Registry·정책·하네스 준비 → 새 Task·Guard 구성 → `activate_run` → READY 순서로 제품에 연결한다. Guard에는 `next_call_seq=store.allocate_call_seq`, `failure_audit=durable_failure_audit(store)`, `on_global_halt=store.halt_execution`을 연결한다. `RecoveryReport`·`list_recovery_items`를 쓰는 복구 화면과 고정 시작 실패 코드 문구도 필요하다.
- C: REC-02 상태표를 독립 인수하고 실제 강제 종료·재시작에서 복구와 소유권을 확인한다. 복구로 인한 실제 `tools/call` 추가 전송 0과 결과 공개 0도 별도로 센다. B 단위 시험만으로 실제 프로세스·전송 인수가 끝난 것은 아니다.
- 제품 시작·종료 barrier와 앱 잠금 연결, 복구 화면, C 독립 인수와 대량 자료·잠금·전원 장애를 포함한 성능 예산 측정은 남아 있다. 30초 복구 상한은 집행한 제안값이며 측정된 성능 보장은 아니다.
