# B3.10 · 정책 변경 준비·적용과 Task 정지

## main 동기화

- 사용자 요청에 따라 수정 전 `git fetch origin`을 실행했다. 첨부 기준 `f586cf9`보다 최신인 `origin/main 139e5a0`을 확인했다. PR #27의 C 변경이 추가되어 있었다.
- 기존 NOTIFY-01 `c2c26d3`를 보존하면서 `origin/main`을 병합했다. 병합 커밋은 `0deaa8a`이며 충돌이 없고 최신 main을 조상으로 포함한다. 추적 파일 변경 없이 `Claude outputs/`만 미추적 상태였다. 해당 폴더는 수정·add하지 않았다.
- 병합 뒤 Ruff·포맷·mypy와 C 추가 모듈·B Profile/알림 테스트를 확인하고 작업을 시작했다. C/A 소유 파일의 수동 수정은 하지 않았다.

## 한 일

- `catalog.py`에 부수 효과 없는 전체 정책 변경·서버 활성화 체크 목록 변경 준비 함수를 추가했다. 기존 로더로 현재·새 문서를 검증하고 입력과 분리된 불변 JSON 문서, LoadedProfile, 이전·새 정책 버전과 변경 여부를 반환한다. 파일·프로세스·Registry·Task 상태를 변경하지 않는다.
- 서버 활성화 요청은 설정된 READ/SEND 도구 각각의 정확한 bool을 요구한다. True는 allow, False는 deny로 해당 서버의 기존 양쪽 규칙을 대체한다. 다른 서버의 규칙은 보존한다. 누락·OTHER·미설정 도구·잘못된 서버 ID는 원문 없는 CatalogConfigError로 거부한다. 기본 체크 표시는 A 책임이다.
- `LoadedProfile.servers`는 전체 정책 해시에 포함된 전체 서버 설정임을 명시하고, 전체 설정 순서를 유지하며 Profile에 포함된 서버만 반환하는 `selected_servers`를 추가했다(PR #25 약속).
- Guard에 신뢰 구성 코드 전용 적용 메서드를 추가했다. 같은 버전은 조회·Task 정지·의존성 교체 없이 변경 없음 ACK를 반환한다. 준비 기준이 현재 버전과 다르면 적용 전에 거부한다.
- 변경 적용 중 새 submit은 판정 전에 대기한다. 이전 정책 호출은 기존 Task lock과 정지 신호로 정리하며, 모든 정리를 확인한 뒤 catalog·profile_id·policy_version·AccessChecker·taint_mode·승인 TTL·응답 게이트를 await 없는 구간에서 함께 교체한다. 이미 사용 중인 옛 규칙과 새 규칙을 섞지 않는다.
- 전체 Task 조회 공급자를 받아 처음부터 Guard에 호출되지 않았던 RUNNING Task도 정리한다. 포트를 바꾸지 않고 연결할 수 있도록 SQLiteStore에 읽기 전용 `list_tasks()`를 추가했다. lock 대기 중 생긴 옛 Task는 다시 조회한다. 잘못되거나 진전 없는 옛 조회 결과는 성공으로 숨기거나 반복하지 않고 global halt로 처리한다.
- 옛 정책의 RUNNING·WAITING_APPROVAL Task에 POLICY_CHANGED 정지 의도를 먼저 고정한다. Task lock 안에서 대기 승인을 종결하고 Task HALTED 기록 ACK 뒤 NOTIFY-01 알림을 한 번 낸다. 정책 정지와 승인 재평가가 경쟁해 자체 무효화한 경우도 같은 승인 무효화 계수에 포함한다.
- 처음부터 HALTED·CLOSED·UNKNOWN_OUTCOME인 Task 행은 재개·수정하지 않는다. 정책 정지 중 전송이 끝난 raw는 게이트에 넘기지 않고 기존 after_dispatch 경계로 처리한다. READ는 Withheld/HALTED, SEND는 OutcomeUnknown/UNKNOWN_OUTCOME이며 재전송하지 않는다. 이미 응답 게이트의 검사·커밋에 들어간 호출은 기존 정책으로 마친 뒤 전환한다. 새로운 STOP-01 API는 만들지 않았다.
- 상태·감사 기록 실패는 PolicyChanged 성공 ACK를 반환하지 않고 global halt와 고정 PolicyChangeError로 처리한다. 가능한 유휴·종결 중 승인 핸들은 원문 없는 실패로 깨우며, 실행 중 예약 후 결과를 예약 전 Denied로 바꾸지 않는다.
- B3.10의 B 구현을 완료하고 A81 화면·저장·Task 생성 직렬화·C 전송 0 연결 검증은 B3.12로 분리했다.

`stopped_task_ids`는 이번 변경이 정지 대상으로 선택한 옛 RUNNING/WAITING_APPROVAL 관계 중 종료를 확인한 Task의 정렬된 ID다. 전송 중 SEND가 UNKNOWN_OUTCOME으로 끝난 경우도 포함한다. 처음부터 정지·종결된 Task는 포함하지 않는다. `invalidated_approval_count`는 정책 변경 사유로 새로 확정된 단일 최종 알림의 수이며, 승인 재평가가 먼저 무효화한 경쟁도 포함한다. 같은 버전의 applied_at_utc는 변경 없음 확인 ACK 시각이다.

## 저장·적용 순서

1. A는 현재 문서와 요청으로 준비 함수를 호출한다. 문서 저장용 독립 사본은 `change.document.to_dict()`다. 자원형 READ를 쓰면 C의 검증 결과를 반환할 resource_resolver도 전달한다.
2. A·C가 새 문서를 저장한다. 파일 형식·경로·권한·실행 파일·저장 원자성은 B3.11 후속이며 B는 설정 파일을 쓰지 않는다. 저장 실패면 적용 메서드를 호출하지 않는다.
3. A는 `change.loaded_profile.access_rules`로 **기존 비동기 AccessChecker 포트** 구현을 만들고, `await guard.apply_policy_change(change, checker, task_source=store.list_tasks)`를 호출한다. 메모리 저장소도 전체 최신 Task를 반환하는 동등한 콜백을 공급해야 한다. Guard가 관찰한 ID만으로 추정하는 기본값은 없다.
4. A는 준비·저장·적용 전체와 새 Task 생성을 직렬화한다. ACK 전에는 적용 완료로 표시하지 않는다. 성공 이후 새 Task는 반환 profile_id·policy_version으로 생성한다. 오래된 준비 결과를 자동 재적용하지 않는다.
5. 기록 실패는 일부 옛 Task가 이미 멈춘 상태일 수 있고, 저장된 문서와 실행 중 설정이 다를 수 있다. 성공 ACK 없이 Guard는 global halt한다. A는 계속 실행하거나 자동 재시도하지 않고 종료·복구 흐름을 사용한다. 정책 파일 저장 자체의 성공을 이 메서드가 검증하는 것은 아니다.

정지 의도는 바로 고정하지만 예약 후 호출의 종결 ACK는 기존 Task lock과 Transport 완료/실행 상한에 의존한다. A가 Transport 종결을 보장해야 하며, B는 시간 초과를 성공이나 SEND 재시도로 바꾸지 않는다. 여러 Task 정지는 기존 Store 연산으로 각각 기록하므로 전체 DB 변경이 한 트랜잭션은 아니다. 재시작 전의 승인 원문은 복원하지 않으며 시작 복구·REC는 별도 B6 후속이다.

## 남은 연결·검토

- A 요청(B3.12/A81): READ/SEND 기본 체크·해제 표시, 전체 체크 목록 전달, 정책 변경의 Task 정지 안내, 저장 성공 후 적용, 전체 최신 Task 조회·새 AccessChecker 주입, 새 Task의 새 버전 생성, 준비/저장/적용·Task 생성 직렬화를 연결한다. 선택 서버 실행에는 selected_servers를 사용한다.
- C 요청: 실제 활성화·허용/거부·누락 쌍의 dispatch/wire 0과 SEND 재전송 0을 독립 계수로 확인한다. 파일·경로·실행 파일 검증과 저장 연결은 B3.11 후속이다.
- 새 domain·ports 변경이 없어 이번 작업 자체의 새 3인 합의 대상은 없다. 기존 NOTIFY-01 초안의 합의·A/C 연결(B5.13), B2.9·AGT-04·STOP-01은 이번에 확정·구현하지 않았다. 새 서비스 적용 API·조회 콜백은 A/C 연결 리뷰가 필요하다.
- GitHub 논의와 A/C 다른 브랜치의 실제 연결·리뷰 상태는 확인 불가다. 병합된 main의 코드와 첨부 작업 설명을 기준으로 구현했다.
