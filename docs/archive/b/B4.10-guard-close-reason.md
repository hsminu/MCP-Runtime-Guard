# B4.10 Guard 정상 종료 사유

2026-10-29 · B 단위 구현 · 합의 전 제안 · [#83 C 리뷰와 B 답글](https://github.com/hsminu/MCP-Runtime-Guard/pull/83)

Guard 정상 종료를 결함 정지와 구분하기 위해 `Reason.GUARD_CLOSED`를 제안한다. 공통 enum의 새 값이므로 A·B·C 합의와 A 제품 연결이 남아 있다.

## 변경과 유지

`GuardService.aclose()`는 정상 종료 시 전역 정지 callback에 `GUARD_CLOSED`를 전달한다. 이는 이 회차의 실행 권한을 닫는 것이며 결함을 뜻하지 않는다. 앞서 다른 사유로 전역 정지됐다면 기존의 한 번만 동작하는 경로가 첫 결함 사유를 보존한다. 모델 고정 문구는 사유 코드를 드러내지 않는 기존 정지 문구를 쓴다. 복수 사유가 섞인 거부의 비공개 처리는 유지한다.

실행 권한을 닫는 동작 자체, 정리 쓰기 허용, 결함 경로와 다른 제어 경로는 바꾸지 않았다. Store의 정상 종료 후 상태도 `FAULTED`, `execution_enabled=False`, `requires_restart=True` 그대로다. 이는 같은 Store 객체의 해당 회차를 다시 열지 않기 위한 상태다. 종료 후 새 submit은 기존대로 거부하고, callback이 없는 Guard도 기존처럼 닫는다.

## 저장과 연결

`halt_execution`이 갱신하는 실행 상태와 사유는 메모리에만 있다. 그러나 정지와 실행 허가 쓰기가 경쟁하면 Store가 `StoreError(GUARD_CLOSED)`를 반환하고, Guard의 실패 감사가 연결된 경우 내구성 감사의 `audit_events.reason_code`에 이 사유가 저장될 수 있다. 저장된 값은 enum을 통해 `_stored_reason`이 읽는다. 실제 실패 감사 저장을 시험했고, 공개 목록 조회의 같은 디코더는 합성 요청 사유로 별도 확인했다. 합성 요청은 정상 종료가 요청 사유를 직접 저장한다는 뜻이 아니다.

현재 이 브랜치의 `product_assembly.py`는 Guard 생성에 `on_global_halt`를 연결하지 않는다. [#83](https://github.com/hsminu/MCP-Runtime-Guard/pull/83)의 A 연결은 이 브랜치에 아직 반영되지 않았으므로 통합 시 A가 Store `halt_execution` 연결을 확인해야 한다. A 화면 문구표 `ui/presentation.py`에도 `GUARD_CLOSED`에 맞는 정상 종료 문구를 추가해 달라고 요청한다.

## 검증

수정 전 정상 종료 회귀 시험은 기존 `INTERNAL_ERROR` 때문에 실패했고 수정 후 통과했다. 첫 커밋의 Ruff·format·mypy와 집중 시험 457개가 통과했다. 집중 시험 파일은 `tests/unit/test_guard.py`, `test_guard_cancellation.py`, `test_guard_global_halt.py`, `test_guard_real_store.py`, `test_guard_closed_storage.py`, `test_model_messages.py`, `test_final_model_messages.py`다. 정리 쓰기와 최초 결함 사유 보존, callback 부재, 모델 문구 및 감사 저장·조회도 확인했다. 최종 전체 검증은 이 기록 작성 시점에 아직 수행하지 않았다.
