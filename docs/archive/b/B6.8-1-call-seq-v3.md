# B6.8 1단계: v3 스키마·영속 순번·실패 감사

2026-10-28 · B 단위 구현 · SEQ-01/02/03·B-SQL-04 · I3/I4/I6/I8/I9

이번 단계는 v3 DDL과 명시 이관 함수, Task별 영속 호출 순번, Guard 실패 감사의 저장 입구를 구현한다. B6.8의 전체 완료는 아니다. 백업 뒤 명시적 준비·v3 이관 연결, 시작 복구·회차 활성화와 deadline 집행은 2단계에서 수행한다. C 독립 인수와 A 제품 연결도 남았다.

## v3와 이관

- `MAX_SAFE_SEQUENCE = 2**53 - 1`을 순번·epoch 상한으로 쓴다. 새 `task_call_sequences` STRICT 표는 Task별 `last_issued`와 상한 CHECK를 두며, Task 생성 트랜잭션에서 0으로 초기화한다.
- `requests`에 nullable `epoch`·`kind`, 기본값 0인 `row_revision`, nullable `legacy_source`를 추가했다. 신규 요청은 epoch·kind가 모두 있어야 하며 옛 v1/v2 요청은 원래 버전을 `legacy_source`에 두고 epoch·kind를 NULL로 보존한다. call_seq와 epoch는 공통 상한으로 제한한다. Registry 표와 기존 문자열 reason은 그대로다.
- 새 빈 DB는 v3로 만들고 정확한 v3는 다시 연다. 생성자는 v1·v2와 그 밖의 스키마를 변경하지 않고 고정 오류로 거부한다. 백업 없는 숨은 이관을 수행하지 않는다.
- `_migrate_to_v3(connection, from_version)`은 정확한 v2 또는 Registry가 빈 정확한 v1만 받는다. `foreign_keys`를 트랜잭션 밖에서 끄고 기존 설정을 복원하며, 한 `BEGIN IMMEDIATE` 안에서 요청 표를 재구성하고 Task마다 `max(requests.call_seq, escalations.at_seq, 0)`으로 계수를 채운 뒤 `foreign_key_check`와 버전 변경을 마치고 커밋한다. 생성자에는 연결하지 않는다.
- 이관 테스트에서 v2 여러 Task·승인·승격·Registry·감사 행, v1 빈 Registry·legacy 요청, 없는 이력의 0 seed, v1/v2 생성자 거부와 파일 바이트 보존, 이관 도중 실패의 rollback·외래 키 설정 복원과 v3 정확 DDL·재개방을 확인했다. 기존 `AGT_*` reason 문자열은 변환하지 않는다.

## 순번과 Guard

- `SequenceAllocator.allocate_call_seq(task_id)`는 기존 한 인자 콜백과 호환된다. writer가 Task 상태·계수와 보존된 요청/승격의 최대 순번을 검증하고 조건부 증가와 `CALL_SEQ_ALLOCATED` 감사를 같은 쓰기 트랜잭션에서 커밋한다. 감사 detail은 `call_seq`와 현재 `run_id: null`만 담는다. Task의 epoch·상태·보안 버전·행 revision·등급은 바꾸지 않는다.
- Task별 첫 값은 1이며 다른 Task와 독립적이다. 성공 배정 후 판정 실패·취소·ACK 유실에서 값을 회수하지 않아 공백이 생길 수 있다. 시작된 쓰기의 취소는 기존 B6.13 writer 의미대로 완료 뒤 전파한다. 기존 이력 최대보다 낮거나 없는 계수는 `INTERNAL_ERROR`와 Store 권한 차단으로 처리한다. 상한은 되감지 않고 `INVALID_ARGUMENTS`로 거부한다.
- Guard는 allocator가 정확한 `StoreError` 타입으로 낸 `TASK_NOT_RUNNING`, `TASK_UNCLASSIFIED`, `STATE_MISSING`, `INVALID_ARGUMENTS`를 Task 범위 실패로 다룬다. 상한의 `INVALID_ARGUMENTS`는 해당 Task를 정지한다. `INTERNAL_ERROR`, `STATE_COMMIT_FAILED`와 기타 Store 오류는 기존 전역 정지 경계를 유지한다. 모형 오류와 원문은 결과에 싣지 않는다.

## 실패 감사

- `FailureAuditRecord`와 `FailureAuditStore.record_failure_audit`는 예약 전후 고정 사유·예외 형식·신뢰 식별자만 전달한다. 예외 형식은 64자 이하 ASCII 식별자이고 repr에서 원문성 필드를 숨긴다. 현 단계에서 신뢰된 실행 회차 바인딩이 없어 `run_id`와 `epoch`는 None만 허용한다.
- `durable_failure_audit(store)`는 Guard의 UTC 공급자로 찍은 `FailureEvent`를 record로 변환한다. `FAILURE_BEFORE_DISPATCH`/`FAILURE_AFTER_DISPATCH`와 고정 reason을 저장하며 detail은 `exception_type`, `run_id`, `epoch`만 담는다. 인자·도구 본문·예외 원문은 저장하지 않는다. 정지 상태에서도 허용되는 기록 연산이다.
- 예약 전 추가 실패 감사가 실패하면 기존 `fail_closed` containment fallback이 Guard를 전역 정지하고 고정 Denied를 반환한다. 예약 후는 원자 실패 저장을 먼저 확인하고 추가 감사가 실패하면 기존 `after_dispatch` fallback이 전역 정지하며 READ는 Withheld, SEND는 OutcomeUnknown으로 남는다.

## A·C 요청과 남은 범위

- A: 제품 조립에서 `next_call_seq=store.allocate_call_seq`, `failure_audit=durable_failure_audit(store)`를 주입한다. 기존 v2 개발 DB는 백업 뒤 명시 준비 입구가 구현되는 2단계 전까지 생성자로 열 수 없다.
- C: 이관의 실제 백업·중단·DB 무결성과 seed, 배정 COMMIT ACK 유실·취소 뒤 중복 없는 순번, Guard 전역 정지와 실제 전송·수신 효과 0, 실패 감사의 원문 비노출을 독립 검증한다.
- 신규 `record_decision`이 **배정되지 않은 call_seq**를 거부하는 검사는 A의 메모리 계수 대체 이후에 넣는다. 현재 그 검사를 하지 않는다. `run_id`는 아직 없고 신뢰 binding·회차 활성화는 2단계다.
- 옛 `AGT_*` reason 문자열은 이관 시 그대로 보존한다. 현 startup inventory의 기존 Reason enum 파서는 해당 옛 문자열을 읽지 못할 수 있으며, 읽기 쪽 변환은 B2.10에서 다룬다. 자동 보정이나 성공으로 표시하지 않는다.
- v1/v2의 안전한 백업·이관 준비와 복구 ACK, 영속 회차, 종료 deadline, 강제 종료/전원 차단 검증은 이번 범위가 아니다. 변경된 B 테스트는 새 v3 필수 열과 명시 이관 경로에 맞췄고, A·C 소유 코드와 테스트는 수정하지 않았다.
