## A가 쓸 새 공개 API

`core.model_messages.final_model_message(final: PendingFinal) -> tuple[bool, str]`

| cause | 변환 |
| --- | --- |
| executed | 기존 outcome_model_message 규칙. Released일 때만 공개 결과 본문 포함 |
| rejected | `(False, "승인 요청이 거절되었습니다")` |
| expired | `(False, "승인 요청이 만료되었습니다")` |
| cancelled | `(False, "요청이 취소되었습니다")` |
| invalidated | `(False, "승인 요청이 무효화되었습니다")` |
| failed | `(False, "작업이 정지되었습니다")` |
| shutdown | `(False, "작업이 정지되었습니다")` |

bool은 기존 함수처럼 Released 종류에서만 True다. 도구의 업무 성공 여부를 새로 판단하지 않는다. executed/Released의 문자열은 A의 현재 로컬 Runner 결과 형식과 같은 `{"text":...,"structured_content":...,"is_error":...}` JSON envelope다. Unicode를 보존하고 간결한 JSON으로 직렬화한다. is_error=True여도 bool의 기존 의미는 유지한다. Task/요청/승인 ID·등급·정책 버전은 본문에 넣지 않는다. 공개 게이트가 이미 만든 ReleasedResult만 받으며 RawResult를 공개하지 않는다.

기존 fixed_model_message와 outcome_model_message의 동작은 그대로다. 특히 outcome_model_message(Released)는 본문을 읽지 않고 `(True, "")`를 반환한다. 새 final_model_message만 executed/Released의 공개 본문을 읽는다. A는 이 최종 반환 문자열을 다시 JSON으로 감싸거나 본문을 중복 추가하지 않아야 한다.

executed/Denied는 MODEL_VISIBLE_REASONS의 기존 4개 허용 목록·복수 사유 우선순위·비공개 사유 혼합 시 일반 거부 규칙을 그대로 사용한다. 비실행 cause는 사유를 덧붙이지 않고 A가 요청한 고정 종결 문구만 반환한다. failed/shutdown·Withheld·OutcomeUnknown에는 내부 코드를 노출하지 않는다.

PendingFinal이 아닌 값, 알 수 없는/잘못된 cause, 비실행 알림의 잘못된 결과, 변조된 사유·공개 결과·직렬화 실패는 원문 없는 ModelMessageError다. 비실행 알림에 위조된 Released가 들어오면 본문을 읽지 않고 거부한다. 새 예외·repr에 결과 본문이나 예외 원문을 넣지 않는다. UTF-8 직렬화 실패도 원래 예외 context/cause를 전달하지 않는다.

## 예약 전 취소 동작

예약에 들어가기 전 CancelledError는 기존 Task 정지 경로 `_halt_task`로 해당 Task만 HALTED로 만들고 FailureEvent를 남긴다. 사유는 기존 INTERNAL_ERROR, phase는 before_dispatch, exception_type은 CancelledError다. 취소 메시지·인자·본문은 넣지 않는다. 정지 쓰기 ACK·반환 맥락을 확인하고, 실패 감사까지 성공하면 기존처럼 Denied를 반환한다. 다른 Task의 전역 실행 게이트를 닫지 않는다.

Task lock 안의 판정 취소는 그 lock 안에서 정리한다. 정책 장벽이나 Task lock을 기다리다 취소되면 아직 lock이 없으므로 기존 소유자가 끝난 뒤 lock을 얻어 정리한다. 승인 제어 lock 대기에도 같은 원칙을 적용했다. lock 밖에서 이미 예약된 같은 Task의 상태를 덮지 않는다. expected_epoch가 전달된 submit은 기다리는 동안 교체된 새 epoch를 HALTED로 만들지 않는다. 이미 HALTED·UNKNOWN_OUTCOME·CLOSED인 상태를 재개/되돌리지 않는다.

정지 조회·쓰기·ACK 검증·실패 감사가 실패하거나 그 정리 도중 다시 취소되면 기존 fallback이 전역 정지한다(B4.9). StoreError도 상태를 확정할 수 없어 기존 전역 정지를 유지한다. HALTED가 커밋된 뒤 별도 실패 감사가 실패하면 HALTED를 되돌리지 않고 전역 정지한다. SQLite의 Task HALTED와 그 내부 감사는 기존 트랜잭션을 사용하며 FailureEvent callback과 하나의 새 트랜잭션으로 묶은 것은 아니다. C의 failure_audit 내구성 연결은 기존 주입 계약이다.

취소를 삼키는 기존 체커는 실제 완료 전까지 추적·슬롯을 유지한다. 그 동안 기존 AGT 대기 장치가 새 접근 판정을 일시적으로 AGT_ERROR로 거부할 수 있다. 이 일시적 제한과 전역 정지를 구별한다. 체커 완료/늦은 예외 회수 후 다른 정상 Task는 실행되고, 취소된 Task는 HALTED로 계속 거부된다. 이 기존 대기 장치 제거는 ACCESS-01/B2.9 후속이며 이번에 바꾸지 않았다.

asyncio 관례로는 정리 후 CancelledError를 다시 올리는 것이 호출자의 취소 신호 보존에 유리할 수 있다. 이번에는 요청대로 기존 Denied 반환을 유지했으며 실제 Task.cancelled()도 False다. 예외 재전파로 바꾸는 제안은 A 호출자·반복 취소·예약 전후 정리 계약을 검토할 후속으로만 남겼다.

## 예약 뒤 취소가 예약 전 경계로 오는지 확인

성공 ACK를 받은 ALLOW는 `_Allowed` 반환 직후 `_dispatch_reserved`의 after_dispatch 경계로 들어간다. 승인 소비의 정확한 True ACK 이후도 `_approve`가 예약 후 경계로 dispatch한다. 전송·결과 저장 중 취소는 기존대로 READ Withheld/HALTED, SEND OutcomeUnknown/UNKNOWN_OUTCOME이고 자동 재전송하지 않는다. `_dispatch_reserved`, `_dispatch_and_commit`, `_contain_post_dispatch`, `_post_failure_fallback` 구현은 AST로 이전 커밋과 동일함을 확인했다.

단, **reserve_dispatch/consume_and_reserve 호출 안에서 ACK를 기다리는 중 취소되면 예약 전 실패 경계로 올 수 있다.** 저장 구현에 따라 DB는 이미 DISPATCHING/CONSUMED인데 반환만 받지 못했을 수 있다. 두 예약 호출의 CancelledError에는 기존 전역 정지를 명시적으로 보존했고, 그 뒤 기존 오류 처리의 Denied 반환도 유지했다. 이를 성공 ACK 이후의 단순 Task 취소로 축소하지 않는다. 예약 행이 있어도 전송을 시작하거나 재시도하지 않는다.

현행 SQLiteStore의 해당 메서드는 내부 await 없이 동기 커밋하므로 같은 이벤트 루프에서 SQL 트랜잭션 중간 취소가 끼지는 않는다. 다른 비동기 Store/미래 writer의 ACK 지연을 대역으로 주입해 이미 예약/소비된 행·전송 0·전역 정지가 유지됨을 검사했다. ACK 불명 자체의 새 공통 오류·복구 의미는 기존 B6 후속이다.

## 기존 테스트를 바꾼 이유

기존 일부 회귀는 CancelledError라면 전역 정지한다는 이전 정책을 고정했다. 요청한 Task 단위 취소와 충돌하므로 다음 기대값을 바꿨다.

- 승인/사람 제어의 lock 대기 취소: lock 소유자가 놓기 전에 취소 완료를 기다리던 테스트는 새 정리 경로와 서로 기다렸다. 소유권·미확정 정지 신호·상태 보존을 먼저 검사하고 lock 해제 뒤 HALTED·정리 ACK와 자원 해제를 확인하도록 수정했다. 실제 다른 Task 실행과 취소된 Task 전송 0 검사도 포함했다.
- 늦은 AGT 예외·체커 자체 취소·체커 정리 대기 중 두 번째 부모 취소: 전역 정지 대신 Task HALTED를 기대한다. 미완료 체커 추적, 늦은 예외 회수, 원문 비노출, 종료 전 슬롯 유지 검사는 유지했다. 체커 종료 뒤 다른 Task 회복을 추가했다.
- 정지 상태/감사를 기록하는 도중의 취소는 별도 새 테스트로 전역 정지가 유지됨을 확인한다. 체커 정리 대기 중 취소와 정지 기록 실패를 같은 경우로 합치지 않았다.

초기 집중 검증 범위에서 수명/긴급 제어 회귀의 이전 기대값을 놓쳤다. 사용자 전체 실행의 정지 위치와 실패 3건을 대조해 해당 B 테스트를 수정한 뒤, 최종 사용자 전체 실행에서 실패 없이 통과했다. 관련 검사를 제거하거나 B 밖 테스트를 고치지 않았다.

## A·C 전달 사항과 한계

- **A 요청:** PendingFinal의 모델 반환에 final_model_message를 사용하고 자체 cause 매핑을 대체한다. executed/Released의 문자열은 이미 공개 결과 JSON이므로 중복 포장/본문 추가를 하지 않는다. 반환 bool을 도구의 is_error와 혼동하지 않는다. 기존 shield 사용 여부와 세션 취소 전파는 A가 연결하고 검토한다.
- **A 요청:** 예약 전 취소는 Task HALTED·Denied, 정지 기록 실패/StoreError/예약 ACK 불명은 전역 정지, 성공 ACK 이후는 기존 READ/SEND 결과 의미임을 호출자에 반영한다. Task lock 대기 정리는 같은 Task의 기존 실행 종결을 기다릴 수 있고 Transport의 완료/중단 상한은 A 책임이다.
- **C 요청:** 내구성 failure_audit 주입과 실제 dispatch/wire·수신 부작용 계수로 취소된 요청 0·정상 다른 Task 실행·ACK 불명 재전송 0을 독립 검증한다. 이 변경의 새 기능 검증은 B 단위 대역과 SQLite 기반이며 A/C 실제 세션 연결 검증으로 확대하지 않는다.
- 기존 NOTIFY-01 계약 합의, A 연결, C 독립 인수, ACCESS-01 대기 장치 제거, Store ACK/복구 계약은 후속이다. 이번 작업은 ports/domain을 바꾸거나 그 합의를 확정하지 않는다.
- 현재 feat/b-security-core에 커밋하고 push·PR 생성은 하지 않는다. 추적되지 않은 Claude outputs/는 읽기만 했다.
