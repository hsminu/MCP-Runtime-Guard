# B6.8 2단계 27a: 명시 시작과 스키마 준비

2026-10-28 · B 단위 구현 · SEQ-03·REC-01·REC-05

이번 단계는 제품용 명시 시작 모드와 스키마 검사·백업·이관·검증 입구를 마련한다. 시작 복구와 회차 활성화는 다음 27b 범위이며, B6.8 전체 완료나 A·C의 연결 및 독립 인수를 뜻하지 않는다.

## 공개 계약과 시작 순서

- `SQLiteStore(path, *, startup="explicit", ...)`는 일반 Store와 RegistryStore 연산을 차단한 `MIGRATING` 상태로 시작한다. 기존 기본값인 `startup="immediate"`은 기존 동작을 유지한다.
- `await store.prepare_schema(deadline=..., begin_backup=..., on_step=...)`는 `time.monotonic()` 기준 바깥 deadline 안에서 `STORE_CHECK` → 필요한 경우 `STORE_BACKUP` → 필요한 경우 `STORE_MIGRATE` → `STORE_VERIFY` 순서로 준비한다. 성공 결과는 경로를 담지 않는 `MigrationReport`이고 상태는 실행이 계속 차단된 `RECOVERING`이다. 이관 ACK와 향후 복구 ACK는 별개다.
- `StorePrepareStep`, `StoreStartFailure`, `StorePrepareError`와 `BackupDestination`을 추가했다. 실패는 고정 시작 실패 코드와 `FAULTED`·재시작 필요 상태로 표현하며, 같은 객체에서 준비를 다시 시작하지 않는다. 오류·진행 값·보고서에 경로나 예외 원문을 싣지 않는다.
- v1/v2는 SQLite 백업을 독립 연결로 검증하고 발행한 뒤 이관한다. 이미 발행된 백업은 이후 이관 실패 시에도 보존한다. rollback 확인, COMMIT 결과 불명, I/O와 deadline을 고정 실패 코드로 구분한다.

## 원본 보존과 WAL 결정

사용자 결정에 따라 명시 모드 생성자는 WAL을 변경하지 않고, CHECK는 `query_only`에서 실행한다. 이는 B6.17의 지원하지 않는 파일을 수정 없이 닫는 조건과 원본 그대로의 백업을 지키기 위한 선택이다. 기존 v1/v2는 검사를 통과하고 백업이 발행된 뒤 WAL을 켠다. 새 빈 DB와 정확한 v3는 검사를 마친 뒤 WAL을 켜며 VERIFY에서 WAL을 확인한다. 따라서 지원하지 않는 버전과 무결성 오류를 검사 단계에서 거부할 때 원본 main DB와 WAL의 보존을 우선한다.

비정상 종료로 WAL이 남은 지원 불가 DB에서 마지막 연결을 일반적으로 닫으면 SQLite 체크포인트가 main DB를 변경하고 WAL을 제거할 수 있음을 확인했다. 명시 시작에서 종료 체크포인트 방지 설정을 사용해 main DB와 WAL의 보존을 확인한다. 이 설정은 SQLite의 `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` 지원이 필요하다. WAL 공유 메모리인 SHM은 읽기 검사 중에도 바뀔 수 있다. 지원 가능한 DB에 대해 백업 발행 후 WAL을 켜면 main DB 헤더가 바뀔 수 있다.

## 검증

Windows에서 전체 pytest의 각 결과는 **실패 0, 4 skipped, 2 warnings, 20 subtests passed**다.

| 단계 | 전체 pytest 결과 |
| --- | --- |
| 작업 전 기준 | **5112 passed** |
| domain·ports 계약 | **5124 passed** |
| 명시 시작 모드 | **5137 passed** |
| 스키마 준비 구현 `b27ec3d` | **5169 passed** |
| 기록 커밋 전 | **5169 passed** |

스키마 준비 집중 검증은 **32 passed**다. 실제 Windows `AppFolders.begin_backup`을 이용한 백업 발행과 기존 WAL이 남은 지원 불가 DB의 main/WAL 보존을 포함한다. 지원하지 않는 버전·다른 앱 ID·DDL 불일치 및 외래키 위반은 CHECK에서 원본 바이트를 유지했고, v1·v2는 검증된 백업 후 이관했다. 빈 DB는 백업 없이 v3를 만들고 기존 v3는 이관을 건너뛰었다. 이관 실패·ACK 불명과 deadline 세 시점도 시험했다. 지원 DB의 WAL 전환 이후 이관 실패 시에는 전환 전 바이트 동일성이 아닌 원본 데이터의 롤백과 발행된 백업을 확인한다.

## A·C 요청과 남은 범위

- A: 제품 시작 시 명시 모드로 열고 `prepare_schema`에 시작 시각 기준 60초 deadline, `folders.begin_backup`, 진행 콜백을 전달한다. 27b의 복구와 회차 활성화가 완료되기 전에는 실행을 열지 않는다. 단계·실패 코드에 맞는 화면 문구와 시작 연결을 검토한다.
- C: 백업 대상의 실물 경로와 publish/discard 경계, 기존 WAL·비정상 종료·프로세스 중단에서의 파일 보존 및 복구, 이관 COMMIT 불명과 deadline을 독립 검증·측정한다. Windows 실물 테스트는 이 독립 인수를 대신하지 않는다.
- 27b의 `RECOVER`, 미해결 항목 처리, 회차 결속과 실행 활성화는 아직 구현하지 않았다. 명시 모드의 성공 상태는 `RECOVERING`에서 머문다.
