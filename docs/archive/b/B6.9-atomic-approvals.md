# B6.9 승인 생성·종결 원자화

2026-10-29 · B 단위 구현 · [#76 B6-01 제안](https://github.com/hsminu/MCP-Runtime-Guard/issues/76) · 합의 전 제안

승인 생성과 거절·만료·취소·무효화 종결에서 Task·요청·승인과 감사가 각각 두 번에 나뉘어 기록되던 경계를 하나의 SQLite 쓰기 트랜잭션으로 묶었다. A·C 확인과 C 독립 인수가 남아 있다. 스키마·DDL·인덱스·`user_version`과 기존 Reason은 바꾸지 않았다.

## 제안 계약과 처리

`ApprovalCommit`은 바뀐 `ApprovalRecord`, `TaskState`, 요청 상태를 담는 불변·strict·extra 금지 모델이다. `Store.open_approval(approval, *, expected_task)`은 ASK 판정과 현재 회차 소유, Task 상태·epoch·revision을 검증하고 Task와 요청의 대기 전이, 승인 생성, Task·승인 감사를 함께 기록한다. `Store.finish_approval(approval_id, status, *, expected_approval_revision, task_after, expected_task_revision, reason, halt_reason=None, now_utc)`은 승인과 요청을 종결하고 Task를 RUNNING 또는 HALTED로 바꾸는 작업과 감사를 함께 기록한다. 이미 종결된 동일 생애 Task는 그 상태를 보존하고 승인·요청만 종결한다. 소비 전 APPROVED 전이와 `consume_and_reserve`는 기존 경로다.

사본 해시에는 Task의 상태와 `row_revision`이 들어가지 않는다(`core/snapshot.py`). 대기 진입은 `security_version`을 바꾸지 않으므로 대기 전 Task로 해시를 만든 다음 원자 연산의 반환 사본을 확인할 수 있다. `HumanControl` 공개 반환 타입은 바꾸지 않았다.

| 결과 | 처리 |
| --- | --- |
| 성공 | `ApprovalCommit`을 반환한다. Guard는 관계·상태·버전과 중첩 모델을 검사한 후 사본과 알림을 갱신한다. |
| 충돌 | 승인·Task revision 또는 상태 경합은 `StoreError(APPROVAL_RACE)`, 만료는 `StoreError(APPROVAL_STALE)`이다. 해당 연산의 업무 행은 바뀌지 않고 전송하지 않는다. |
| 불명 | COMMIT ACK 유실 등은 기존 B6.13 `CommitOutcome` 경로를 따르며 Store 실행 권한을 닫는다. 실제 커밋 여부를 추측하거나 재시도하지 않는다. |
| 손상 | writer가 보관한 승인·요청·Task 사본 및 관계와 DB가 다르면 rollback 후 `StoreIntegrityError(INTERNAL_ERROR)`를 전달하고 Store 실행 권한과 Guard를 닫는다. |

손상 전용 감사는 기존에 같은 뜻의 이벤트가 없어 `APPROVAL_INTEGRITY_FAILED`를 사용한다. 업무 트랜잭션 rollback 뒤 별도 쓰기로 Task ID와 고정 사유만 기록하며 요청 ID·본문·예외 원문을 넣지 않는다. 감사까지 실패하면 정지를 유지하고 연결을 폐기한다. writer 스레드는 일반 `StoreError`의 하위 타입을 제거하므로 손상 여부는 원문 없는 내부 결과로 경계를 통과시키고 공개 메서드에서 `StoreIntegrityError`를 재구성한다.

옛 `create_approval`·`transition_approval`은 기존 호출자와 A·C 시험 대역 호환을 위해 남긴다. 새 Guard 승인 대기·종결은 원자 연산을 사용한다. 옛 연산 제거는 A·C 연결과 합의 뒤 별도 결정이다.

## 정책 불일치와 경합

사용자 결정에 따라 Guard의 정책 불일치 처리에서 대기 승인이 있으면 Task lock 안에서 먼저 원자 종결을 수행하고 Task 정지 확인을 이어간다. `POLICY_CHANGED` 감사 사유는 승인과 정지 감사에 유지한다. 이 정책 불일치 경로에 한해 PENDING 승인도 `INVALIDATED`로 종결하도록 새 `finish_approval`이 허용한다. 기존 전이 계약의 PENDING→CANCELLED와 충돌하는 제한적 제안으로, 기존 `transition_approval`의 규칙은 바꾸지 않았다. 일반 B3.10 정책 변경의 PENDING 종결은 기존 `CANCELLED`를 유지한다. 승인 없는 Task는 기존 단독 정지 경로를 쓴다.

원자 종결 충돌이 다른 경로의 이미 끝난 승인 때문이면 같은 Task lock 안에서 그 관계를 확인하고 Task 정지를 완료한다. 승인과 요청은 경쟁 트랜잭션의 결과를 그대로 보존한다. 불명은 기존 실행 권한 차단, 손상은 전역 정지로 처리한다.

사용자는 C 조건의 부분 상태 0을 **각 Store 연산 단위**로 정했다. 다른 트랜잭션이 먼저 승인 `REJECTED`·요청 `DENIED`·Task `RUNNING`을 확정한 상태는 일관된 이전 거절 결과다. 그 커밋과 뒤따르는 정책 정지 사이의 중단은 REC-02 복구와 REC-03·04의 회차·복구 결과 규칙으로 처리하며 새 Store 연산은 추가하지 않는다. `test_competing_rejection_running_recovery_blocks_old_task_execution`에서 명시 시작으로 다시 열어 Task만 HALTED로 복구하고 승인·요청을 유지한 뒤, 활성화 후 이전 Task의 submit과 순번 할당 거부 및 전송 0을 확인했다.

## C 인수 조건 대응

| C3.5 조건 | B 단위 구현·검증과 남은 인수 |
| --- | --- |
| 1. 승인 생성 | Task·요청 대기, 승인 행, 감사 두 건을 한 쓰기 트랜잭션에서 처리한다. 시작 전, Task·승인·요청·감사 사이와 COMMIT 직전 실패를 주입해 부분 행이 없음을 확인했다. |
| 2. 승인 종결 | 승인·요청 종결, Task 복귀/정지, 감사를 한 쓰기 트랜잭션에서 처리한다. 동일 경계 실패 주입과 정책 불일치 전후 경계를 확인했다. 부분 상태 0은 각 연산 단위다. |
| 3. 조건부 갱신·결과 분리 | 승인·요청 관계와 Task 생애·revision을 검증하고 UPDATE 행 수를 확인한다. 성공·충돌·불명·손상 처리와 실행 권한 차단을 시험했다. |
| 4. 독립 실패·경합 인수 | B 단위에서는 COMMIT 직후 ACK 유실, 명시 시작 복구 및 동시 승인 중복 소비 0을 시험했다. C의 독립 강제 종료·COMMIT 실패 주입과 재시작 인수는 아직 남아 있다. |

C 인수 주입 지점: 각 연산의 BEGIN 전/직후, Task UPDATE, 승인 INSERT 또는 UPDATE, 요청 UPDATE, 감사 INSERT 사이, COMMIT 직전과 COMMIT 직후 ACK 전달 전. 정책 정지와 이미 끝난 별도 승인 트랜잭션 사이 중단도 REC-02 결과를 확인한다.

## 검증과 남은 요청

계약 단계 집중 시험 6개는 통과했다. 계약만 추가한 첫 단계의 mypy는 아직 SQLiteStore에 두 연산이 없어 2개 오류였고, 저장소 단계에서 구현한 뒤 통과했다. 저장소 단계 집중 시험 390개와 서비스 단계 집중 시험 650개는 통과했다. 이 기록 작성 시점에 최종 전체 검증은 아직 실행하지 않았다.

- 저장소 단계의 `tests/unit/` 시험 파일: `test_atomic_approval_store.py`, `test_sqlite_lifecycle.py`, `test_sqlite_decisions.py`.
- 서비스 단계의 `tests/unit/` 시험 파일: `test_atomic_approval_contract.py`, `test_atomic_approval_store.py`, `test_atomic_approval_guard.py`, `test_atomic_policy_boundary.py`, `test_guard.py`, `test_approvals.py`, `test_b_qa_approval_first.py`, `test_b_qa_approval_lock.py`, `test_pending_notifications.py`, `test_approval_review.py`, `test_guard_halt_reason.py`, `test_policy_change.py`, `test_system_stop.py`, `test_guard_cancellation.py`, `test_b_qa_guard_returns.py`, `test_b_qa_task_lifecycle.py`, `test_human_control_revision.py`.

기존 두 커밋 경로를 별도 프로세스에서 재현해 COMMIT ACK 유실 시험을 실행했을 때 Task 대기·요청 DECIDED의 부분 상태가 생겨 시험이 실패했다. 정책 불일치의 옛 Task 선행 정지 순서도 별도 프로세스에서 재현했을 때 경계 예외 시험이 HALTED·PENDING 부분 상태를 잡아 실패했다. 두 실험은 파일을 바꾸지 않았으며 정상 구현의 관련 시험은 통과했다.

A에는 새 Store 연산을 사용하는 호출 경로와 시험 대역 연결, 기존 UI·알림 호환 확인을 요청한다. C에는 C3.5 조건 1–4 독립 검증과 강제 종료·COMMIT 실패·재시작·중복 소비 계수를 요청한다. #76에서 세 담당의 계약 합의와 옛 연산 제거 시점 결정이 남았다.
