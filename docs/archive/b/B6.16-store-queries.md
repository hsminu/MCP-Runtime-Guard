# B6.16 화면용 권위 조회와 승인 revision

2026-10-29 · B 단위 구현 · [#76](https://github.com/hsminu/MCP-Runtime-Guard/issues/76) 합의 전 제안

승인 목록과 호출 로그에 필요한 원문 없는 조회를 SQLiteStore에 구현했다. A·C 확인 전인 제안이며 제품 연결이나 C 독립 인수 완료를 뜻하지 않는다. 스키마·DDL·user_version·인덱스는 변경하지 않았다.

## 조회 계약

`domain/queries.py`에 `ApprovalListLane`, `ListSort`, `ApprovalListQuery`, `ApprovalRow`, `ApprovalListPage`, `CallListQuery`, `CallRow`, `CallStage`, `CallDetail`, `CallListPage`를 추가했다. 불변·strict·extra 금지 모델이며 ID와 서버·도구 이름은 repr에서 숨긴다. 검색은 빈 문자열 또는 허용된 문자 1–64자다. offset은 0–10,000, limit은 1–100이다. `_`는 접두어의 문자 그대로 비교하며 `%`는 검색 입력 검증에서 거부한다.

`StoreQueries`와 `SQLiteStore.list_approvals`, `list_calls`, `get_call`은 한 읽기 트랜잭션에서 목록·개수·조회 시각 또는 호출 상세를 만든다. 승인 목록은 PENDING과 나머지 HISTORY를 나누고 생성 시각·승인 ID로 정렬한다. 호출은 Task가 지정되면 call_seq로, 아니면 판정 시각·요청 ID로 정렬하며 판정 감사가 없으면 뒤에 둔다. 감사 사유는 고정 Reason으로 읽고 예전 AGT 사유는 ACCESS 사유로 바꾼다. legacy 행의 epoch·kind는 None으로 보존한다. 호출 단계는 저장된 감사에서 공개 가능한 고정 단계만 취하고 같은 단계의 첫 시각을 쓴다. 인자·결과·감사 detail·예외 원문은 반환하지 않는다.

조회는 기존 저장소 게이트를 따른다. 명시 모드의 MIGRATING·RECOVERING·CLOSED는 거부하고 RECOVERED·READY 및 연결과 회차가 유지되는 FAULTED는 읽을 수 있다. 손상된 저장값은 고정 저장소 오류로 처리한다.

## C 인수 조건 대응

| 조건 | B 제안의 대응과 남은 확인 |
| --- | --- |
| 1. 한 읽기 트랜잭션 | 각 호출에서 행·전체 건수·조회 시각 또는 상세 단계를 하나의 읽기 트랜잭션으로 만든다. 별도 연결이 중간에 쓰는 경우에도 목록과 건수가 같은 스냅샷인지 시험했다. |
| 2. 원문 없음 | 공개 필드만 모델로 구성하고 인자·결과·감사 detail 표지가 반환 repr과 model_dump에 없는지 시험했다. |
| 3. 객체별 revision·명령 기대값 | 승인과 요청에 각 행의 revision을 반환하고 approve·reject에 선택적 기대 revision을 받는다. 아래 소유 관계 경계가 적용된다. |
| 4. 정렬·크기 고정 | 승인 생성 시각·ID, 호출 순번 또는 판정 시각·ID로 결정적으로 정렬한다. offset·limit 범위를 검증한다. |
| 5. 실패는 알 수 없음 | 저장값 오류는 고정 오류를 반환한다. A 화면 연결 시 실패를 0건으로 표시하지 않고 알 수 없음으로 표시하고 명령을 꺼야 한다. |
| 6. C 계수와 대조 | 이번 B 시험은 C 독립 계수 대조를 대체하지 않는다. A·C 확인과 C 독립 인수가 남았다. |

## 사람 명령의 기대 revision

`HumanControl.approve`와 `reject`에 선택적 `expected_row_revision`을 추가했다. 소유 관계가 확인되고 값이 있으면 Task lock 안에서 승인 행을 읽은 직후 비교한다. 불일치 시 `APPROVAL_RACE`로 거부하고 승인·Task·요청·메모리 사본을 바꾸거나 Task를 정지하지 않는다. 소유 관계가 확인된 경우 bool·음수·정수가 아닌 기대값은 `INVALID_ARGUMENTS`다. None은 기존 동작이다.

사용자 결정: 기대값 비교는 소유 관계가 확인된 경우에만 한다. 소유 관계가 없으면 Task를 추측하지 않고 기존 처리를 우선한다. 살아 있는 승인 행은 `APPROVAL_CONTEXT_LOST`이며, 이 경우 기대값의 형식도 검사하지 않는다. 없는 행이나 이미 종결된 행은 기존 `APPROVAL_RACE` 처리다.

`expire`, `cancel`, `emergency_halt`에는 기대값을 추가하지 않았다. 특히 cancel·emergency_halt는 오래된 화면의 정지 명령도 위험을 줄이는 방향이므로 revision 불일치로 막지 않는다.

Windows에서 실행한 결과다. 각 전체 실행은 실패 0, 5 skipped·2 warnings·20 subtests passed이며 Ruff·format·mypy가 통과했다. 계약 시험은 각 단계에서 45 passed다.

| 구현 단계 | 전체 pytest |
| --- | --- |
| 조회 모델·포트 | 5814 passed |
| SQLite 조회 | 5830 passed |
| 사람 명령 revision | 5860 passed |

집중 시험은 조회 계약 26개, 저장소 조회 16개, 사람 명령 revision 30개가 통과했다. 사람 명령 집중 검사와 기존 승인 회귀를 함께 돌린 결과는 201 passed다. revision 비교 helper를 비활성화했을 때 오래된 승인·거절 시험이 모두 실패하는 것도 확인했다.

문서 단계 전체 검사에서 `test_runtime.py::test_lifecycle_messages_are_current_korean_with_code_secondary`가 기대한 CLOSED 대신 CLEANUP_UNCONFIRMED로 한 번 실패했다. 해당 테스트만 독립 실행한 5회는 모두 통과했다.

`tools/ci`가 없어 lint-imports와 Bandit은 실행하지 않았다. Semgrep도 실행하지 않았다.

## A·C 요청과 남은 범위

- A: 승인 목록과 호출 로그를 연결하고 destination_summary를 destination_id와 Profile에서 만든다. call_id·boundary_tier는 A의 값을 붙인다. approve·reject에 화면의 row_revision을 전달한다. 조회 실패는 알 수 없음으로 표시하고 관련 명령을 끈다.
- C: #76의 제안과 조건 1–6을 검토하고 계수를 포함해 독립 인수한다. A·C 회신 전까지 합의 완료로 취급하지 않는다.
- 인덱스를 추가하지 않았으므로 데이터 증가 시 조회 성능은 별도 확인이 필요하다. 화면 연결과 최종 API 합의도 남아 있다.
