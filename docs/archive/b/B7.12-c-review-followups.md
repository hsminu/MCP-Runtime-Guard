# B7.12 C 리뷰 후속: 미소비 공개 본문과 예약 뒤 취소 알림

2026-10-19 · B7.2의 C 리뷰 후속 두 항목 · I5/I6/I8/I9·NOTIFY-01·STOP-01·T45·B4.9

첨부된 PR #28 C 리뷰 요약에 따라 완료 후 미소비 Released의 수명을 Task 정지와 연결하고, 승인 실행 중 취소에도 최종 알림을 확정했다. B7.12는 완료했으며 전체 A/C 리뷰와 실제 세션 연결·독립 검증은 기존 후속 항목에 남긴다.

착수 HEAD는 feat/b-security-core의 adda16a이고 로컬 origin/main 참조는 139e5a0이었다. 첨부가 설명한 PR #28의 main 013ecec 병합, NOTIFY-01·STOP-01의 3인 합의 완료 및 다른 A/C 브랜치의 실제 상태는 확인 불가다. 이번에는 현재 브랜치에서 구현·검증했고 원격 조회·main 병합은 하지 않았다. 공통 문서의 미결 표를 임의로 합의 완료로 바꾸지 않았다.

## 미소비 Released의 수명

cancel_pending은 일치하는 Task·epoch의 완료된 미소비 본문을 폐기한다. 대기 승인 정리 전후에 확인하므로 lock 대기 중 완료되는 실행도 포함한다. 이미 완료된 결과를 새 취소 알림 수에 더하지 않는다. 완료 결과만 있는 cancel_pending은 종전처럼 0을 반환할 수 있으며, 추가 Task 상태 전이를 만들지 않고 본문 참조를 놓는다.

시스템 stop_task, 정책 변경 정지, 기존 사람 취소 등 Guard가 검증된 Store 반환으로 Task의 HALTED·UNKNOWN_OUTCOME·CLOSED를 확인하는 공통 지점에서도 그 Task·epoch의 완료된 미소비 Released만 폐기한다. 다른 Task·다른 epoch의 결과나 미완료 알림을 이 폐기로 종결하지 않는다. 정책 변경으로 실제 정지하는 Task가 여러 개면 각각의 해당 생애가 대상이다. 이미 종결되어 정책 변경 정지 대상이 아닌 다른 Task까지 일괄 폐기하지 않는다.

폐기 시 핸들의 본문과 서비스의 결과/승인 관계를 제거한다. 그 핸들의 후속 wait는 기존 aclose 폐기와 같은 원문 없는 고정 PendingResultError다. 새 핸들을 재조회해도 복원할 수 없다. 완료 알림을 새로 발행하거나 기존 알림을 다른 cause로 덮지 않는다.

이미 wait 중인 대기자는 결과를 받는다. stop/aclose가 완료와 수신 사이에 끼어도 본문을 먼저 지우지 않는다. 그 대기까지 취소되면 wait의 finally에서 지연된 폐기를 수행해 본문을 남기지 않는다. aclose에도 같은 규칙을 적용한다. 이미 A가 소비하거나 approve 반환값으로 받은 결과의 외부 참조를 지울 수는 없으며, A는 Task·epoch·정지 상태에 따라 공개 여부와 참조 수명을 관리해야 한다.

Denied·Withheld·OutcomeUnknown처럼 Released 본문이 없는 완료 결과는 기존처럼 소비할 때까지 유지한다. 이 메타데이터와 중복 request ID 방지용 seen 집합에는 총량 상한을 추가하지 않았다. 장시간 실행에서 수명/상한을 별도로 정할 필요가 있다. 이번 변경의 보장은 서비스·핸들의 미소비 Released 참조 해제이며 메모리 전체의 강제 소거는 아니다.

## 예약 뒤 취소와 최종 알림

승인 소비·예약의 정확한 성공 ACK 이후 dispatch 중 취소되면 기존 예약 후 경계가 먼저 상태·감사를 기록한다.

| 도구 | 최종 outcome | Task 상태 | cause |
| --- | --- | --- | --- |
| READ | Withheld, 본문 미공개 | HALTED | executed |
| SEND | OutcomeUnknown | UNKNOWN_OUTCOME | executed |

정상 격리 사유는 기존 POST_DISPATCH_ERROR이고 실패 감사에는 CancelledError 같은 예외 타입만 전달한다. 원문·인자·취소 메시지·예외 메시지를 최종 알림이나 감사에 넣지 않는다. 격리 결과로 PendingFinal을 정확히 한 번 완료한 뒤 취소를 다시 전파하며 승인 coroutine의 Task.cancelled()도 True다. 소비 후 메모리 사본·타이머는 복구하지 않고, finally에서 in-flight 관계와 Task lock을 정리한다.

전송뿐 아니라 응답 커밋 대기 중 취소도 같은 규칙을 쓴다. 격리 저장이나 별도 실패 감사가 실패하거나 정리 중 다시 취소되면 기존 B4.9 fallback이 전역 정지한다. 이때도 READ Withheld / SEND OutcomeUnknown으로 알림을 완료하고 취소를 전파한다. 기록 ACK를 확인하지 못한 Task 상태를 성공적으로 HALTED/UNKNOWN_OUTCOME으로 저장했다고 주장하지 않는다. 평범한 처리 오류를 격리하는 중 처음 취소되는 경우도 전역 정지·알림·취소 전파를 확인했다.

**C 요약의 일괄 failed/Denied 완료 대신 executed와 기존 예약 후 outcome을 쓴 이유:** 예약 뒤 SEND는 이미 전달됐을 수 있다. 이를 Denied라고 알리면 모델이 전송되지 않았다고 받아들여 같은 전송을 다시 시도할 수 있다(I8). 확인된 예약 요청의 kind와 기존 fallback으로 READ/SEND 의미를 정할 수 있으므로 이번 취소 경로는 failed/Denied를 새로 만들지 않는다. 기존 `_complete`의 유효하지 않은/오연결 결과에 대한 failed·Denied 방어는 유지한다. 재예약·재전송 fallback은 없다.

예약 성공 ACK를 아직 받지 못한 consume_and_reserve/reserve_dispatch 내부 취소, 예약 전 취소의 기존 Denied 반환과 전역 정지 조건은 이번 작업 범위에서 바꾸지 않았다.

## A·C 전달 사항과 남은 한계

- **A 요청:** Task 종료/정지 뒤 미소비 Released 핸들의 wait에서 나는 PendingResultError는 STOPPED로 처리한다. 새 호출·재전송으로 보상하지 않는다. 이미 기다리던 wait는 Released를 받을 수 있으므로 Task·epoch·정지 상태를 확인해 종료된 세션에 본문을 보내지 않는다.
- **A 요청:** 예약 뒤 승인 coroutine은 알림을 완료하고 CancelledError를 다시 전파한다. 사람 제어 반환과 PendingFinal을 모델에 중복 전달하지 않는다. 모델 답변은 기존 final_model_message 경로로 한 번만 만들고 OutcomeUnknown은 재전송하지 않는다. 일반 submit·예약 전 취소는 이번에 전파 의미를 바꾸지 않았다.
- **C 요청:** T45와 STOP-01 실제 연결에서 READ 미공개·SEND 결과 불명, 단일 알림/응답, 추가 wire 전송·수신 부작용 0 및 기록 실패 시 전역 정지를 독립 검증한다. PR #28 의견 원문 및 C 브랜치의 연결 상태는 확인 불가다.
- Transport의 완료/중단 상한과 이미 소비된 결과의 외부 참조 정리는 A 책임이다. 본문 없는 결과·seen 집합의 총량 제한과 기존 Store ACK/복구 합의는 별도 후속이다.
- 현재 feat/b-security-core에만 커밋하고 push·PR 생성은 하지 않는다. Claude outputs/는 읽기만 했고 커밋에 넣지 않았다.
