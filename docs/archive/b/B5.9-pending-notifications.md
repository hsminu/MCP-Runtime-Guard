# B5.9 · NOTIFY-01 만료 타이머·최종 결과 알림

## 한 일

- Pending 승인마다 ApprovalService가 만료 타이머를 소유한다. UTC와 monotonic 중 하나라도 만료면 같은 Guard Task lock 안에서 다시 검사하고 EXPIRED를 확정한다. 기본 대기는 최대 1초 간격이며, 실제 만료 확정은 Task lock 대기 시간의 영향도 받는다. UTC가 lock 대기 중 되돌아와 미만료면 감시를 계속한다.
- 타이머는 사람 capability를 받거나 HumanControl을 호출하지 않는다. 시스템 만료는 `EXPIRED`·`APPROVAL_STALE`, 사람의 명시적 expire는 기존 `EXPIRED`·`OK`로 기록한다. SQLite 감사의 기존 `APPROVAL_EXPIRED` 사건과 `detail` 칼럼을 유지하면서 시스템 만료에만 고정 값 `{"source":"guard_expiry"}`를 넣는다. 승인 직전 자동 만료 검사도 같은 시스템 출처다. Store의 approver_id는 사본 소유자 대조용이며 시스템 사건의 사람 조작을 뜻하지 않는다.
- Pending을 반환하기 전에 단일 소비 대기 핸들을 등록한다. 완료 결과가 먼저 확정되어도 나중에 같은 request_id로 조회·소비할 수 있다. 승인 실행 결과·거절·만료·취소·무효화·지문 무효화는 같은 핸들에 한 번만 확정한다. 완료 결과에 Pending은 없고 기존 Released·Withheld·OutcomeUnknown·Denied를 재사용한다.
- 사람 approve/reject/cancel 반환형·값은 유지한다. B의 최종 알림은 별도의 단일 소비 경로이며, A는 사람 명령 반환값을 모델에 중계하지 않는다. READ는 응답 게이트의 관찰 커밋까지, SEND는 기존 실행 결과 확정까지 기다린다. 소비 이후의 실패를 예약 전 Denied로 바꾸지 않는다.
- C가 호출할 도구 지문 변경 입구와 A가 호출할 epoch 결속 대기 취소·앱 종료 입구를 추가했다. 생성 중인 승인 관계도 첫 Store await 전에 원문 없는 메타데이터로 등록해 종료·지문 변경이 생성을 놓치지 않게 했다.
- 취소 시 승인 관계 검증·종결을 먼저 하고 Task 정지 저장 뒤 알림을 낸다. 잘못된 승인 행을 반환하는 Store에서는 Task를 먼저 수정하지 않는 기존 보호를 유지했다. 정상 타이머 취소는 사람 명령의 lock 취소와 분리해 전역 정지를 일으키지 않는다.
- 원문은 기다리는 타이머 프레임에 보관하지 않는다. 승인 사본은 기존 소비·종결 시점에 폐기하고, 최종 공개 결과의 서비스 참조는 소비 또는 앱 종료 때 제거한다. DTO의 outcome은 repr에서 제외하며 핸들 repr은 고정 문구다. 새로운 넓은 예외 처리 경계는 만들지 않았다.
- B5.9의 B 구현·단위 검증을 완료했다. DTO·포트·종료 의미는 **합의 전 제안**이며 A/C 합의·연결·T45 독립 검증은 B5.13으로 남겼다.

무효화·취소의 정수 반환은 이번 호출이 대상으로 선택한 관계 중 완료가 확정된 수다. 경쟁 중에는 다른 최종 결과가 먼저 확정될 수 있고 그 결과를 다시 쓰지 않는다. 모든 입구는 신뢰된 백엔드 asyncio 루프용이며 MCP 도구나 운영자 인증 API가 아니다.

## 대기·취소·종료와 원문 수명

1. 콜백 구독 대신 완료를 보관하는 핸들을 택했다. `Pending`을 받은 A가 `guard.pending_result(pending.request_id).wait()`를 기다린다. A의 model_call_id는 B가 원문 사본에서 복원하지 않고 A가 요청·Task/epoch와 결속한다.
2. `wait()` 취소는 그 대기만 중단한다. 승인·타이머·완료 결과를 취소하지 않으므로 같은 핸들로 다시 기다릴 수 있다. 동시 대기나 성공한 소비의 반복은 고정 PendingResultError다. 구독 콜백·구독 해제 API는 없다. 세션 자체 종료는 A가 epoch를 지정한 cancel_pending으로 별도 확정한다.
3. 승인 소비 전 취소·무효화·정지는 원문 사본을 지우고 원문 없는 Denied 한 번을 확정한다. 이미 승인 소비·예약이 끝난 실행은 같은 Task lock 아래 실제 결과를 확정한 다음 정지한다. 결과 불명 SEND를 재시도하지 않는다. A는 종료 의도 뒤 늦은 결과를 모델에 보내지 않는다.
4. 앱 종료는 A가 transport 실행을 종결시키는 것과 함께 `await guard.aclose()`를 보장한다. 예약 후 실행이 끝나지 않으면 aclose도 그 Task lock을 기다린다. 임의 시간 초과 후 성공처럼 종료하지 않으며, 취소된 aclose를 완료로 취급하지 않는다. transport 강제 종결·실행 상한 집행은 A 책임이다.
5. 종료 중 미완료 Pending에는 shutdown 또는 저장 실패의 failed 결과를 한 번 확정한다. 이미 확정됐지만 미소비인 Released는 다시 확정하거나 다른 결과로 바꾸지 않고 본문을 폐기한다. 그 핸들의 이후 wait는 고정 오류다. 종료 중 폐기된 세션에 본문을 더 전달하는 것보다 I9의 원문 제거를 우선한 선택이다. 원문 없는 완료 결과는 한 번 소비할 수 있다.
6. 완료 본문은 늦은 소비를 위해 메모리에만 남으며 소비·aclose 때 서비스가 참조를 놓는다. 이미 사람 명령 반환값이나 wait 결과로 넘어간 객체는 A 소유다. A가 대기를 버리면 cancel_pending 또는 aclose를 반드시 연결해야 한다. 중복 방지를 위한 request_id 메타데이터는 서비스 생애 동안 보관한다.
7. 정확히 한 번은 살아 있는 Guard 인스턴스 안의 완료 확정·단일 소비 보장이다. 프로세스 중단을 넘는 전달·ACK·원문 복원은 제공하지 않는다. 기존 승인 생성·종결과 Task 상태의 분리 커밋 한계(B6.9)도 바꾸지 않았다. 앱 전체 Task 열거·영속 종료 복구·STOP-01 일반 API는 이번 범위가 아니다.

## 합의와 A·C 전달 사항

- **합의 전 제안:** 새 DTO·포트·종료 시 미소비 Released 폐기·시스템 감사 출처 표현은 A·B·C 검토가 필요하다. 기존 필드·이름·의미의 변경이나 삭제는 없다.
- A 요청(B5.13): Pending은 이 핸들만 기다리고 사람 명령의 bridge 반환값은 화면용으로만 사용한다. `(task_id, epoch, request_id, model_call_id)` 결속으로 중복·옛 epoch·정지 뒤 늦은 결과를 버린다. cause로 거절/만료/취소/무효화의 기존 고정 문구 분류를 고르고, 실제 Released만 공개한다. Withheld·OutcomeUnknown은 고정 문구 뒤 즉시 interrupt·종료한다.
- A 요청: 같은 Task의 호출은 도착순 직렬화하고 Pending 뒤 호출은 dispatch하지 않는다. 세션 종료에는 cancel_pending, 앱 종료에는 transport 종결과 aclose를 연결한다. 감시 상한은 B 알림이 오지 않을 때의 마지막 안전장치로 유지한다. runner.py·bridge.py는 이번에 수정하지 않았다.
- C 요청: Registry 지문 변경·PENDING 복귀 경로에서 `await guard.invalidate_tool(server_id, tool_name)`을 연결한다. 실제 registry 구현은 추가하지 않았다. T45 독립 검증으로 최종 알림·Codex 응답 각 1회와 차단 시 dispatch/wire 0, 예약 후 쓰기 재전송 0을 측정한다.
- GitHub 논의와 다른 브랜치의 합의·연결 상태는 확인 불가다. B5.13은 미완료로 남겼다.
