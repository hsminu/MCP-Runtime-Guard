# B7.5-2 SCHEMA-01 스키마 준비와 검증 경계

2026-10-30 · B 담당 2단계

등록된 FP-01 도구 지문과 `SCHEMA_JOBS_VERSION`으로 앱 실행 중 메모리 캐시를 묶는다. 준비 성공본과 실패를 모두 보관하며 같은 키를 다시 준비하지 않는다. worker 불가가 확인되면 같은 캐시의 남은 미준비 도구는 호출 없이 불가로 기록한다. 새 앱 실행은 새 캐시를 사용한다. 캐시와 진단은 실행 권한이 아니다.

`Catalog.aresolve`는 도구 확인, 인자 크기 확인, 캐시 조회, worker VALIDATE, 목적지·자원 해석 순서로 진행한다. 검증을 기다리는 동안 등록 정보가 바뀌면 오래된 경계를 사용하지 않도록 다시 확인한다. 캐시와 runner를 주입한 Catalog의 동기 `resolve`는 `INTERNAL_ERROR`로 거부한다. 둘 다 주입하지 않은 기존 조립에서는 `resolve`와 `aresolve`가 기존 in-process 스키마 검증을 사용한다. 제품 조립이 둘을 주입하면 그 동기 검증 경로를 사용하지 않는다.

ToolView에는 기존에도 원본 스키마를 가공해 닫은 준비본이 표시됐다. 주입 모드에서도 worker 준비본을 사용해 이 표시를 유지하며 부모에서 다시 준비하지 않는다. 화면용 Profile 로드는 캐시만 받아 진단에 사용하고 준비를 실행하지 않는다. 이 경우 Catalog 자체는 기존 미주입 경로이므로 실행 조립은 runner와 캐시를 함께 전달해야 한다.

## 상한과 시한

| 항목 | 값 | 상태 |
| --- | --- | --- |
| 인자 JCS UTF-8 크기 | 256 KiB | 미측정 잠정값; 주입·미주입 모두 적용 |
| 등록 스키마 JCS UTF-8 크기 | 256 KiB | Registry 저장 상한과 동일 |
| PREPARE deadline | 요청마다 5초 | 미측정 잠정값 |
| VALIDATE deadline | 요청마다 2초 | 미측정 잠정값 |
| 작업 요청·응답 | 각각 1 MiB, JSON 요소 100,000개, 깊이 64 | 미측정 잠정값; SCHEMA-01 합의와 C 측정 뒤 확정 |

## 도구 준비 진단

| 코드 | 뜻 |
| --- | --- |
| `SCHEMA_PREPARE_FAILED` | 등록 스키마 구성 또는 준비 실패 |
| `SCHEMA_PREPARE_TOO_LARGE` | 준비 요청의 바이트·요소·깊이 제한 또는 응답 크기 제한 초과 |
| `SCHEMA_PREPARE_TIMEOUT` | 준비 작업 시간 초과 |
| `SCHEMA_WORKER_UNAVAILABLE` | worker 미기동·종료·응답 불명 또는 예기치 않은 실패 |

진단에는 스키마·인자·내부 예외 원문을 넣지 않는다. 아직 준비되지 않았거나 준비가 실패한 도구는 목록에서 빠지고, 해석은 `TOOL_UNSUPPORTED`로 거부한다. 인자 위반은 `INVALID_ARGUMENTS`, VALIDATE worker 실패·불명은 `INTERNAL_ERROR`다. 취소는 Catalog·준비 경계에서 그대로 전파한다.

## A·C 인계

- A: `ProductInputs`에 runner와 캐시를 받고, runner가 `assemble_guard`보다 먼저 살아 있도록 한다. transport 시작과 Registry seal 뒤 GuardService 생성 전에 선택 서버의 등록 도구로 `prepare_tool_schemas`를 호출한다. 실행용 `load_profile_settings`와 Catalog에 같은 캐시·runner를 전달한다. 화면용 로드는 캐시만 전달하고 PREPARE하지 않는다. `AssembledGuard.aclose`에서는 Guard 종료 뒤 Store 종료 전에 `runner.aclose()`를 호출하고 `False`는 `CLEANUP_UNCONFIRMED`로 처리한다. 화면 문구·준비 중 표시·시작 상한 재계산은 A가 맡는다.
- C: 상주 worker launcher가 `SchemaJobRunner.run`과 `aclose`를 구현하고 TIMEOUT·TOO_LARGE·UNAVAILABLE 고정 실패를 반환한다. 시간 초과 시 worker 종료·재기동과 늦은 결과 폐기를 담당한다. 별도 프로세스 자원 제한과 실제 종료·wire 계수는 C가 검증한다.

B의 가짜 runner 시험은 C launcher의 실제 프로세스 종료 보장을 대신하지 않는다.

## B 검증

Ruff·format·mypy와 B 시험 2,743개 및 세부 사례 972개가 통과했다. 실제 SQLite를 이용한 제출·승인·예약 후 경계 시험도 포함한다. 계약 시험은 45개 통과했다.

전체 pytest 세 번 모두 시험 결과는 각각 4,816개 통과·26개 건너뜀이었지만, 요약 출력 후 프로세스가 비정상 종료했다. faulthandler를 켠 두 재실행에는 `Fatal Python error: Aborted`와 `<no Python frame>`이 기록됐다. 원인과 변경의 관련성은 미확정이며 전체 검증을 정상 종료로 기록하지 않는다.

변경 전 `c40d915`의 전체 시험 대조 1회는 정상 종료했다. 그러나 같은 변경 전 코드에서 UI 시험만 3회 실행하면 모두 137개 통과 요약을 출력한 뒤 2회 abort했다. 변경 후에도 UI만 3회 중 1회, 새 스키마 시험과 UI를 함께 실행하면 3회 중 2회 abort했으며, 새 스키마 시험만 3회는 정상 종료했다. 각 abort에서 Python frame과 별도 Qt fatal 메시지는 없었다. 같은 종료 증상은 변경 전 UI 시험만으로도 발생하지만 원인은 확정되지 않았다.
