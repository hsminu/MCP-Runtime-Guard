# B7.5 1단계: 제한된 JSON Schema 작업 제안

2026-10-29 · B 단위 구현 · **SCHEMA-01 합의 전 제안** · [B 연결안](../b-schema-validation-proposal.md)

## 범위와 현재 상태

정규식을 포함한 스키마 작업 전체를 나중에 종료 가능한 프로세스에서 실행할 수 있도록 B의 준비·검증 의미와 직렬화 경계만 분리했다. 이번에는 Catalog·Guard·승인의 실제 호출 경로나 A 모델 변환을 프로세스에 연결하지 않았다. `ArgumentSchema`는 새 연산을 **같은 부모 프로세스에서 동기로 호출**하므로 정규식으로 인한 이벤트 루프·Task lock 정지 위험은 아직 해결되지 않았다. 프로세스 실행·시간 초과·종료 보장, A·C 합의와 C 독립 인수가 남았다.

| 위치 | 이번 단계의 역할 |
| --- | --- |
| `services/schema_jobs.py::prepare` | 등록본의 루트·Draft·지원 범위·정규식 및 format을 검사하고 객체 폐쇄와 등록 원본 전체 AND를 적용한 불변 `PreparedSchema` 또는 원문 없는 `SchemaJobFailure`를 반환한다. |
| `services/schema_jobs.py::validate` | 준비본과 `Arguments`를 검증해 `SchemaJobResult`의 `OK`·`INVALID_ARGUMENTS`·`SCHEMA_INVALID` 중 하나를 반환한다. 성공은 정책 허용이나 승인 소비를 뜻하지 않는다. |
| `services/catalog_schema.py::ArgumentSchema` | 위 연산을 호출하고 기존 `schema`·예외 종류·고정 문구를 유지한다. 기존처럼 큰 정수 스키마도 받으며, validator는 검증마다 다시 생성한다. |
| `domain/schema_jobs.py::SchemaJobRequest`·`SchemaJobResponse` | PREPARE/VALIDATE와 job ID, 불변 스키마·인자 및 고정 결과를 표현한다. 인자·스키마·식별자 원문을 repr에 싣지 않는다. |
| `services/schema_jobs.py`의 `encode_request`·`decode_request`·`encode_response`·`decode_response` | 요청·응답 모두 제한을 확인하고 JCS 정규 UTF-8 바이트로 처리한다. 부모의 응답 해독에도 같은 검사를 적용한다. |
| `services/schema_jobs.py::run_schema_job`·`check_job_response` | 요청 바이트를 해독·연산·부호화하고 원문 없는 응답만 반환한다. 부모는 응답과 요청의 ID 및 PREPARE/VALIDATE 결과 형태를 대조한다. |
| `ports.py::SchemaJobRunner` | C의 종료 가능한 프로세스 실행을 위한 비동기 포트 초안이다. 이번에는 제품 구현체를 만들지 않았다. |

`core`는 domain과 표준 라이브러리만 사용하는 저장소 계층 규칙이 있다. 이 작업은 `jsonschema`·`referencing`과 JCS 구현을 사용하므로 지시서가 허용한 대안인 `services/schema_jobs.py`에 두었다. B 모듈에 subprocess·multiprocessing이나 프로세스 실행을 추가하지 않았다.

1단계는 등록 스키마 JCS 지문을 준비 결과나 응답에 싣지 않는다. 2단계의 캐시 결속은 Registry가 이미 사용하는 FP-01 도구 지문(`security/digest.py::tool_fingerprint`)을 기준으로 검토한다. 유효한 형태의 VALIDATE 준비본이라는 사실이나 `OK`만으로 등록본과의 일치가 증명되지는 않으므로, 2단계 부모 연결에서 신뢰된 등록·정책·FP-01과의 결속이 필요하다.

## 요청·응답 상한과 고정 실패

| 항목 | 값과 적용 범위 | 근거·상태 |
| --- | --- | --- |
| `MAX_JOB_BYTES` | 요청·응답 각각 JCS UTF-8 바이트 1 MiB 이하 | 새 IPC 경계의 미측정 잠정값. SCHEMA-01 합의와 C 측정 뒤 확정 |
| `MAX_JOB_ELEMENTS` | 요청·응답 각각 JSON 객체·배열·값을 합해 100,000개 이하. 객체 키는 별도 요소로 세지 않음 | 새 IPC 경계의 미측정 잠정값. SCHEMA-01 합의와 C 측정 뒤 확정 |
| `MAX_JOB_DEPTH` | 요청·응답 envelope 루트를 깊이 0으로 세어 64 이하 | 기존 JSON 타입의 깊이 64를 따른 잠정 경계. envelope도 깊이에 포함하므로 내부 스키마·인자만 따로 셌을 때의 최대 깊이와 같지 않다 |
| `MAX_REGISTERED_SCHEMA_BYTES` | PREPARE 등록 스키마의 JCS UTF-8 바이트 256 KiB 이하 | 기존 Registry 저장 상한과 동일한 공개 domain 상수. 저장소의 기존 한도 동작은 그대로 공유한다 |

바이트·요소·깊이 한도는 도메인 상수 한 곳에 모았다. 기존 `FrozenJsonObject`·`Arguments`에는 깊이 64 제한이 있었지만, 공통 바이트·요소 수 상한은 없었다. 직렬화 경계의 바이트·요소 수치는 새 잠정 제안이지 기존 타입의 한도가 아니다. 요청·응답은 상한 직전·정확히 상한·초과를 검사하고 부모가 받은 응답도 초과 시 고정 실패로 거부한다.

해독은 중복 키·비유한 수·잘못된 UTF-8·비정규 JCS·모르는 종류·추가 필드와 형식 오류를 거부한다. 정상 요청은 예약된 `SCHEMA_JOB_INVALID` ID를 쓸 수 없다. 해독 불가 요청에는 이 예약 ID와 `SCHEMA_INVALID`의 고정 응답을 쓰고, 부모는 실제 요청 ID와 결과 형태를 대조해 사용하지 않는다. VALIDATE는 변조된 준비본의 구조와 지원 범위도 검사하며 `SCHEMA_INVALID`로 고정한다. 준비 결과가 응답 상한을 넘으면 같은 요청 ID의 `SCHEMA_INVALID`만 반환한다. stdout·stderr와 응답에 인자·예외 원문을 싣지 않는다.

사용자 결정에 따라 안전 정수 범위 밖의 Python `int`를 포함한 기존 스키마도 `ArgumentSchema`와 `prepare`는 그대로 받지만, 프로세스 경계의 JCS `encode_request`·`encode_response`는 고정 실패한다. 이를 다른 직렬화 형식이나 반올림으로 우회하지 않는다. 다만 JCS는 큰 유한 binary64 `float`를 허용하고 정수 모양으로 직렬화할 수 있다. 그 정규 JSON 숫자 표기만으로 원래 Python `int`와 `float`를 구별할 수 없으므로 해독은 표현 가능한 binary64로 복원하고 정규 바이트를 다시 대조한다. Python `int`의 encode 거부를 임의의 원시 JSON 숫자 표기 전체를 구분한다는 뜻으로 해석하지 않는다.

## 큰 정수의 제품 등록 경로 확인

실제 SDK 목록 수집 대역, `ServerRegistry`와 SQLite, `product_assembly` 조립을 이용해 안전 범위 밖 정수형 스키마 값을 확인했다. SDK 목록 수집 자체는 완료되고 정수형을 보존했으나 `listing_fingerprints`와 신규 `ServerRegistry.register`는 FP-01 JCS 단계에서 `REG_FINGERPRINT_FAILED`로 거부했고 신규 등록 행은 없었다. 기존 정상 ACTIVE 등록의 실시간 목록에 같은 정수형 정의가 나타나면 그 서버는 이번 실행에서 차단됐으며 기존 DB 등록은 ACTIVE 그대로였다. 따라서 **정수형 사례는 등록·실시간 목록 대조에서 걸리지만 목록 수집 자체가 실패하거나 기존 DB 상태가 바뀌는 것은 아니다.** 같은 크기의 `float`나 `1e20`은 지문 계산이 가능하므로 모든 큰 숫자가 거부된다는 뜻도 아니다. 직접 만든 Store 등록도 `test_registry_store.py::test_unsafe_integer_schema_is_rejected_without_recomputing_fingerprints`가 안전 범위 밖 정수형 스키마를 거부함을 확인한다.

## 2단계 연결과 실패 의미 제안

아래는 [연결안](../b-schema-validation-proposal.md)의 제안이며 이번 단계에서 호출 경로를 바꾸거나 새 실패 사유를 확정한 것은 아니다.

| 위치·결과 | 연결 뒤 제안 처리 |
| --- | --- |
| Catalog 도구 목록 PREPARE | 등록 원본 검사를 제한된 프로세스에서 수행하고 성공한 폐쇄·원본 AND 준비본만 ToolView로 공개한다. 시간초과·출력 초과·오류를 성공으로 삼지 않는다. |
| 최초 제출 검증 | 검증 성공 후에도 기존 정책·등록 확인을 계속한다. 인자 위반은 기존 `INVALID_ARGUMENTS`, 구성 오류는 고정 설정 오류, 시간초과·자원 초과·비정상 종료·응답 불명은 예약 전 DENY다. |
| 승인 소비 전 재평가 | 같은 snapshot 인자와 현 등록·지문·정책 및 만료를 재확인한다. 실패 시 새 소비·예약 없이 기존 승인 프로토콜에 따라 종결한다. |
| 예약·소비 뒤 전송 직전 재확인 | 일반 DENY로 되돌리지 않는다. READ는 Withheld/HALTED, SEND는 OutcomeUnknown으로 격리하고, 실제 dispatch·wire·외부 부작용은 0이어야 한다. 이미 기록된 예약·승인 소비는 보존하고 자동 재시도하지 않는다. |
| 부모와 worker의 불명 결과 | 시간초과·취소·자원/출력 초과·비정상 종료에서 성공을 추측하지 않는다. 늦은 결과를 버리고 종료를 확인하지 못한 worker의 재사용·실행 개방 금지를 A·C와 정한다. |

C에는 `security/launcher.py` 경계로 `run_schema_job`을 종료 가능한 프로세스에서 실행하고, 제한된 IPC·monotonic deadline·입출력/동시성 및 OS별 자원 상한·취소와 종료 확인·늦은 결과 폐기를 설계하고 측정해 달라고 요청한다. 지연 `pattern`·`patternProperties`·`propertyNames`·format 컴파일·원본 AND와 정상 스키마를 모두 인수 범위에 포함해야 한다.

A에는 모델 인자 변환의 현재 동기 검증을 같은 제한 경계로 옮기고, 이미 준비된 ToolView의 재준비를 피하며, 앱 시작 주입·Task lock·취소·전송 0 계수를 C/B와 함께 검토해 달라고 요청한다. Catalog·Guard·승인 연결과 단계별 실패 사유는 A·C 합의 뒤 2단계에서 진행한다.

## B 검증

Windows에서 각 단계의 Ruff·format·mypy와 Catalog 및 관련 B 집중 시험을 실행했다. 1단계 순수 연산 207개, 2단계 직렬화·등록 저장소 포함 385개, 3단계 포트 275개가 각각 통과했다. 기존 Catalog 동작에 대한 대표 묶음은 일반 스키마·`pattern`·`patternProperties`·`propertyNames`·`oneOf`·지원 format 6종, 참조·Draft 불일치 거부와 큰 정수를 확인한다. 원본 AND를 별도 프로세스에서 고의 제거했을 때 `test_original_and_prevents_oneof_weakening`이 실패하고 정상 구현에서 통과했다.

바이트·요소·깊이 상한의 요청·부모 응답 경계, 256 KiB Registry JCS 길이와 유니코드·binary64 표기, 큰 정수 encode 거부, 응답 상관관계, 잘못된 준비본, 원문 비노출과 결정성을 단위 시험했다. 이 기록 작성 시점의 마지막 전체 테스트는 아직 실행하지 않았다. B 단위 시험은 C의 실제 프로세스 강제 종료·wire·외부 부작용 독립 인수를 대신하지 않는다.

A 시험 한 곳(OTHER_SERVICES에 schema_jobs 추가), B 11차 PR에서 A 리뷰 요청.
