# B6.13 SQLite writer와 Store 실행 권한

2026-10-28 · B 담당 단위 구현 · SEQ-02·REC-05(2026-10-27 결정) · I6/I8/I9

B의 SQLite 작업을 전용 daemon writer로 옮기고 SQL 큐와 독립된 실행 권한 조회를 추가했다. 이 기록의 완료 범위는 B 구현과 실행한 단위·회귀 검증이다. A 제품 연결, C 독립 측정·인수와 #55의 정지 완료·종료 경합 해결은 남았다. 영속 순번 배정, v3 이관·백업·복구는 B6.8의 별도 범위다.

## 구현과 권한

- `StorePhase`, `CommitOutcome`, 불변 `StoreExecutionState`와 `StoreLifecycle`을 추가했다. `execution_state()`는 SQL 큐와 분리된 작은 잠금만 사용한다. `execution_enabled=True`는 전체 Store의 필요 조건이지 개별 Task의 run·epoch·정책·승인 검사를 대신하지 않는다. `Denied` 한 건이나 DB의 RUNNING 행도 단독 실행 권한이 아니다.
- `SQLiteStore`의 공개 async SQL 작업은 단일 이름 있는 daemon writer 큐에서 직렬 실행한다. 연결 생성·사용·종료와 결정 컨텍스트는 writer에 속하며 `check_same_thread=True`를 유지한다. 이벤트 루프와 writer는 future와 `call_soon_threadsafe`로 결과를 주고받는다. `audit_id_factory`·`utc_now`도 writer에서 호출한다.
- 제한 큐가 가득 차면 작업을 실행하지 않고 고정 `StoreError`를 반환하며 권한 상태는 유지한다. 미시작 작업 취소는 실행되지 않는다. 시작된 쓰기는 종료·커밋 또는 실패까지 기다린 뒤 취소를 전파한다. 시작된 읽기는 기다리지 않고 취소를 전파할 수 있다.
- 연결 폐기는 Store를 `FAULTED`, 실행 불가·재시작 필요로 고정한다. COMMIT 실패 뒤 rollback과 트랜잭션 종료가 확인된 경우는 `ROLLED_BACK`, 실제 COMMIT 뒤 ACK 유실 또는 rollback 불명은 `UNKNOWN`이다. COMMIT 전 rollback 실패는 COMMIT을 보내지 않았으므로 `ROLLED_BACK`이다. 연결 폐기 뒤 읽기 포함 후속 연산은 연결에 접근하지 않고 거부한다. 현재 고정 이유는 기존 `INTERNAL_ERROR`다.
- `halt_execution(reason)`은 멱등이며 연결이 정상일 때 새 실행 허가만 차단한다. `close()`는 어느 스레드에서나 비차단·멱등으로 새 접수를 닫고 미시작 작업을 거부한다. 진행 중 작업은 끝내고 writer가 연결을 닫는다. `wait_closed(timeout)`은 연결 종료가 확인된 경우만 True이며, 폐기 중 close 실패도 미확인으로 보존한다. 닫기와 dequeue 경쟁에서 시작된 작업은 완료된다.
- Guard의 선택적 `on_global_halt`는 첫 전역 정지에서 한 번 호출하고 알려진 고정 사유를 전달한다. 제품 조립의 연결은 A 담당이다.

| Guard 전역 정지 뒤 Store 연산 | 처리 |
| --- | --- |
| `create_task`, `record_decision`, `reserve_dispatch`, `create_approval`, `consume_and_reserve`, APPROVED `transition_approval`, `activate_server` | 실행 허가이므로 거부 |
| 읽기, `set_task_status`, `commit_observation`, `commit_send_outcome`, `commit_request_failure`, 그 밖의 `transition_approval`, `record_session_event`, 나머지 Registry 쓰기 | 연결이 정상이면 정리·기록을 위해 허용 |

writer는 한 작업의 실패를 호출 결과로 옮겨 다음 큐 작업까지 스레드가 죽지 않게 하는 경계에서만 넓은 예외 처리를 사용한다. 공개 오류에는 예외 원문·SQL·경로를 넣지 않는다. 테스트 전용 writer 도우미는 직접 연결 접근과 결함 주입을 writer 스레드에서 수행한다.

## 알려진 실패와 A 요청

`tests/unit/test_codex_product_flow.py::test_l3_violation_halts_only_this_task_and_interrupts_codex`는 writer 도입 뒤 A `StopChannel.stop`이 정지 작업을 백그라운드로 시작하고 완료 ACK를 기다리지 않아, snapshot이 HALTED 커밋 전 RUNNING을 읽는 경우다(#55). 정지 latch는 먼저 설정되지만 이것만으로 종료 경합 전체의 안전성을 단정하지 않는다. 이전 실행에서는 종료 중 미완료 정지 작업이 `SystemControlError`로 끝난 것도 관찰했다.

원인 분리를 위해 A 테스트를 임시로 바꿔 snapshot을 10 ms 간격으로 최대 2초 기다린 실험 3회에서 HALTED까지 약 **0 / 0 / 15 ms**로 관찰하고 모두 통과했다. A 테스트는 실험 직후 원복했다. 이는 정지 ACK를 기다릴 때의 관찰이며 제품 종료 순서가 이미 해결됐다는 뜻은 아니다. 정식 테스트에는 skip·xfail을 두지 않았다. B6.13 PR은 **#55 답을 받은 뒤 올린다**.

A는 제품 조립에 `on_global_halt=store.halt_execution`을 연결하고 새 turn·도구 응답·새 Task/세션 전 및 `state_revision` 감시에서 권위 상태를 확인해야 한다. 실행 불가면 진행 중 turn과 모든 Task 세션을 중단한다. 종료 전에 진행 중 정지 작업을 정리·확인하고 `wait_closed(5.0)`를 관찰해 미확인이면 `CLEANUP_UNCONFIRMED`로 표시하며 잠금을 유지한 채 프로세스를 끝내야 한다. 현재 생성자는 이벤트 루프 안에서 동기 대기하므로 B6.8 비동기 준비 입구를 연결할 위치도 조정해야 한다.

## C 요청과 남은 한계

C는 실제 환경에서 SQL 잠금·fsync·종료 지연과 적절한 큐 용량 및 시간값을 측정하고, 장애·취소·종료 뒤 실제 wire/부작용 0을 독립 검증한다. C4.19(#53)의 위 통합 시험은 B의 단위 확인이며 C 독립 인수로 간주하지 않는다.

생성자의 연결·이관 준비는 동기 대기이고 지속 시간은 busy timeout과 실제 I/O에 좌우된다. B6.8 전 임시 READY에서는 `run_id=None`이다. 상태 구독은 구현하지 않았으므로 A가 `state_revision`을 비교해야 한다. 큐 기본 용량 및 5초 등 시간값은 배포 기준으로 측정·확정되지 않았다. 실제 전원 차단·강제 종료·백업·복구도 이 작업의 검증 범위가 아니다.
