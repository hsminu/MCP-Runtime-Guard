# B6.13 SQLite writer와 Store 실행 권한

2026-10-28 · B 담당 단위 구현 · SEQ-02·REC-05(2026-10-27 결정) · I6/I8/I9

B의 SQLite 작업을 전용 daemon writer로 옮기고 SQL 큐와 독립된 실행 권한 조회를 추가했다. 이 기록의 완료 범위는 B 구현과 실행한 단위·회귀 검증이다. A 제품 연결·정지 중 표시와 종료 순서, C 독립 측정·인수는 남았다. 영속 순번 배정, v3 이관·백업·복구는 B6.8의 별도 범위다.

## 구현과 권한

- `StorePhase`, `CommitOutcome`, 불변 `StoreExecutionState`와 `StoreLifecycle`을 추가했다. `execution_state()`는 SQL 큐와 분리된 작은 잠금만 사용한다. `execution_enabled=True`는 전체 Store의 필요 조건이지 개별 Task의 run·epoch·정책·승인 검사를 대신하지 않는다. `Denied` 한 건이나 DB의 RUNNING 행도 단독 실행 권한이 아니다.
- `SQLiteStore`의 공개 async SQL 작업은 단일 이름 있는 daemon writer 큐에서 직렬 실행한다. 연결 생성·사용·종료와 결정 컨텍스트는 writer에 속하며 `check_same_thread=True`를 유지한다. 이벤트 루프와 writer는 future와 `call_soon_threadsafe`로 결과를 주고받는다. `audit_id_factory`·`utc_now`도 writer에서 호출한다.
- 제한 큐가 가득 차면 작업을 실행하지 않고 고정 `StoreError`를 반환하며 권한 상태는 유지한다. 미시작 작업 취소는 실행되지 않는다. 시작된 쓰기는 종료·커밋 또는 실패까지 기다린 뒤 취소를 전파한다. 시작된 읽기는 기다리지 않고 취소를 전파할 수 있다.
- 연결 폐기는 Store를 `FAULTED`, 실행 불가·재시작 필요로 고정한다. COMMIT 실패 뒤 rollback과 트랜잭션 종료가 확인된 경우는 `ROLLED_BACK`, 실제 COMMIT 뒤 ACK 유실 또는 rollback 불명은 `UNKNOWN`이다. COMMIT 전 rollback 실패는 COMMIT을 보내지 않았으므로 `ROLLED_BACK`이다. 연결 폐기 뒤 읽기 포함 후속 연산은 연결에 접근하지 않고 거부한다. 현재 고정 이유는 기존 `INTERNAL_ERROR`다.
- `halt_execution(reason)`은 멱등이며 연결이 정상일 때 새 실행 허가만 차단한다. `close()`는 어느 스레드에서나 비차단·멱등으로 새 접수를 닫고 미시작 작업을 거부한다. 진행 중 작업은 끝내고 writer가 연결을 닫는다. `wait_closed(timeout)`은 연결 종료가 확인된 경우만 True이며, 폐기 중 close 실패도 미확인으로 보존한다. 닫기와 dequeue 경쟁에서 시작된 작업은 완료된다.
- Guard의 선택적 `on_global_halt`는 첫 전역 정지에서 한 번 호출하고 알려진 고정 사유를 전달한다. 제품 조립의 연결은 A 담당이다.

| Guard 전역 정지 뒤 Store 연산 | 처리 |
| --- | --- |
| `create_task`, `record_decision`, `reserve_dispatch`, `create_approval`, `consume_and_reserve`, APPROVED `transition_approval`, `activate_server` | 실행 허가이므로 거부 |
| 읽기, `set_task_status`, `commit_observation`, `commit_send_outcome`, `commit_request_failure`, 그 밖의 `transition_approval`, `record_session_event`, 나머지 Registry 쓰기 | 연결이 정상이면 정리·기록을 위해 허용 |

writer는 한 작업의 실패를 호출 결과로 옮겨 다음 큐 작업까지 스레드가 죽지 않게 하는 경계에서만 넓은 예외 처리를 사용한다. 공개 오류에는 예외 원문·SQL·경로를 넣지 않는다. 테스트 전용 writer 도우미는 직접 연결 접근과 결함 주입을 writer 스레드에서 수행한다.

## #55 테스트 수정과 A 요청

`tests/unit/test_codex_product_flow.py::test_l3_violation_halts_only_this_task_and_interrupts_codex`는 writer 도입 뒤 A `StopChannel.stop`이 정지 작업을 백그라운드로 시작하고 완료 ACK를 기다리지 않아, snapshot이 HALTED 커밋 전 RUNNING을 읽었다(#55). A 동의에 따라 커밋 `1d1575c`에서 정지 완료를 기다리도록 테스트를 고쳤으며 이 커밋은 A 리뷰 대상이다. 정지 직후 RUNNING 표시("정지 중")는 A가 별도로 본다. 정지 latch는 먼저 설정되지만 이것만으로 종료 경합 전체의 안전성을 단정하지 않는다. 이전 실행에서는 종료 중 미완료 정지 작업이 `SystemControlError`로 끝난 것도 관찰했다.

원인 분리를 위해 A 테스트를 임시로 바꿔 snapshot을 10 ms 간격으로 최대 2초 기다린 실험 3회에서 HALTED까지 약 **0 / 0 / 15 ms**로 관찰하고 모두 통과했다. A 테스트는 실험 직후 원복했다. 이후 A 동의에 따른 정식 테스트를 적용해 5회 모두 통과했으며 첫 snapshot 이후 추가 대기는 약 **15 / 0 / 16 / 0 / 0 ms**였다. 이는 정지 ACK를 기다릴 때의 관찰이며 제품 종료 순서가 이미 해결됐다는 뜻은 아니다. 정식 테스트에는 skip·xfail을 두지 않았다. **#55 답을 받았다(2026-10-28).**

PR 본문 정정: #47 본문의 판정기 예외 설명은 일반 예외에 대해 틀렸다. 일반 예외는 정상 실패 처리 시 `INTERNAL_ERROR` DENY이고 Task를 유지하며, 판정기가 던진 `CancelledError`만 그 Task를 정지한다(C #56 확인, B2.9 기록·`AccessChecker` 설명과 같음).

A는 제품 조립에 `on_global_halt=store.halt_execution`을 연결하고 새 turn·도구 응답·새 Task/세션 전 및 `state_revision` 감시에서 권위 상태를 확인해야 한다. 실행 불가면 진행 중 turn과 모든 Task 세션을 중단한다. 종료 전에 진행 중 정지 작업을 정리·확인하고 `wait_closed(5.0)`를 관찰해 미확인이면 `CLEANUP_UNCONFIRMED`로 표시하며 잠금을 유지한 채 프로세스를 끝내야 한다. 현재 생성자는 이벤트 루프 안에서 동기 대기하므로 B6.8 비동기 준비 입구를 연결할 위치도 조정해야 한다.

## C 독립 검증과 측정(#58)

C는 [#58 리뷰 댓글](https://github.com/hsminu/MCP-Runtime-Guard/pull/58#issuecomment-6468999539)에서 실제 stdio·HTTP 서버와 계수 하니스를 사용한 독립 검증을 보고했다. Store 실행 권한만 닫힌 경우, 예약 COMMIT 결과가 불명인 경우, Store를 닫은 뒤의 경우 모두 실제 `tools/call`은 0이었다. 예약 COMMIT ACK 유실에서는 `FAULTED`·`UNKNOWN`·재시작 필요로 판정했으며 실제 전송은 0이었다. 이때 남은 `DISPATCHING` 행은 B6.8 2단계 시작 복구가 REC-02 표에 따라 처리하며, 실제 복구 결과는 C3.10·REC-02 인수에서 확인한다.

C의 Windows 11 측정에서 단일 쓰기 중앙값은 약 2.0ms, 외부 쓰기 잠금 중 이벤트 루프 최대 간격은 17–21ms, 진행 중 쓰기와 겹친 `close()` 반환은 7–15ms였다. C는 이 독립 시험·측정 기록을 #58 병합 뒤 C PR에 올릴 예정이다. 이 수치는 C가 보고한 측정치이며 B의 측정이나 배포 기준 확정치가 아니다.

큐가 가득 차면 실행 전 거부라도 `StoreError(INTERNAL_ERROR)`여서 Guard가 저장 장애와 구분하지 못하고 전역 정지하며 재시작이 필요하다. C 측정에서 기본 대기 큐는 1,024개였고 동시 쓰기 2,000개 중 실행 중 1개를 포함해 1,025개가 성공하고 975개가 거부됐으며 약 2.5초에 비워졌다. 큐 포화와 다른 Store 오류를 구분하려면 새 Reason이 필요하므로 domain 합의 대상이다. Store 자체는 해당 측정에서 READY로 유지됐고 Guard 전역 정지는 별도 사례에서 관찰됐다.

## C 리뷰 후속: 전역 정지 사유

Task 읽기 중 전역 정지되면 `_policy_matches`가 False여서 제출 경로가 정책 변경으로 오인하던 문제를 커밋 `ce0916a`에서 고쳤다. 제출은 전역 정지를 다시 확인해 Task 정지·승인 무효화 없이 `Denied(INTERNAL_ERROR)`를 반환한다. 승인 경로의 정책 불일치 사유는 전역 정지 시 `INTERNAL_ERROR`, 실제 정책 변경 시 `POLICY_CHANGED`로 구분하며 승인 종결 상태와 Task 정지 동작은 유지한다. `_policy_matches`의 전역 정지 조건과 실행 차단 방향은 그대로다. 승인 종결이 이미 커밋된 뒤 재개용 Task 조회 중 전역 정지가 생기는 경우, 기존 종결 사유는 그대로 두고 Task 정지 사유만 `INTERNAL_ERROR`로 기록한다.

신규 테스트 6개 통과, 수정 전 코드에서는 회귀 4개 실패·실제 정책 변경 대조군 1개 통과를 확인했다. 관련 승인·정책 집중 검사 116개와 수정 후 전체 pytest **4991 passed, 4 skipped, 2 warnings, 20 subtests passed**, Ruff·format·mypy가 통과했다(Windows, 전체 pytest는 샌드박스 밖).

## C 요청과 남은 한계

C는 실제 환경에서 SQL 잠금·fsync·종료 지연과 적절한 큐 용량 및 시간값을 측정하고, 장애·취소·종료 뒤 실제 wire/부작용 0을 독립 검증한다. C4.19(#53)의 위 통합 시험은 B의 단위 확인이며 C 독립 인수로 간주하지 않는다.

생성자의 연결·이관 준비는 동기 대기이고 지속 시간은 busy timeout과 실제 I/O에 좌우된다. B6.8 전 임시 READY에서는 `run_id=None`이다. 상태 구독은 구현하지 않았으므로 A가 `state_revision`을 비교해야 한다. 큐 기본 용량 및 5초 등 시간값은 배포 기준으로 측정·확정되지 않았다. 실제 전원 차단·강제 종료·백업·복구도 이 작업의 검증 범위가 아니다.
