## 취소 콜백 예외

`after_dispatch(..., on_cancelled=...)`에서 콜백이 Exception 또는 CancelledError를 내면 기존 동기 `on_containment_error`에 넘긴다. Guard 연결은 기존 `_post_failure_fallback`을 통해 global halt를 설정한다. 콜백을 재시도하지 않고, 해당 정지 처리 자체가 실패해도 원래 CancelledError를 `from None`으로 다시 올린다. 콜백 실패의 메시지·repr·traceback을 로그나 결과에 복사하지 않는다.

넓은 catch를 새 서비스 위치에 추가하지 않았다. 기존 허용 경계인 `after_dispatch` 안에서 취소 알림 실패를 처리한다. 성공 경로·콜백 없는 호출의 기존 결과 변환·일반 submit의 예약 후 취소 의미는 유지했다. READ는 미공개/정지, SEND는 결과 불명이며 재전송·Denied 전환은 없다. 이미 완료된 알림을 콜백 실패 뒤 다시 발행하지 않는다.

2026-10-27 PR #36 C 리뷰에 따라 docstring에 **on_containment_error는 멱등이어야 한다**고 명시했다. 격리 중 취소와 취소 콜백 실패가 겹치면 같은 핸들러를 두 번 호출할 수 있다. 실제 after_dispatch의 B 호출자는 Guard의 `_post_failure_fallback` 하나이며 `_halt_globally`의 bool=True 고정과 같은 request_id/kind의 고정 Withheld/OutcomeUnknown 반환뿐이라 반복 호출에 추가 SQL·감사·알림 부작용이 없다. `_pre_failure_fallback`도 같은 정지 플래그/고정 Denied 경로다. 기존 취소 회귀 테스트의 격리 취소+콜백 실패 조합을 유지하고 핸들러 두 번 호출을 명시적으로 확인했다. 비멱등 호출자 수정은 없고 실행 의미를 바꾸지 않았다.

`fail_closed`에 전달하는 다른 B 핸들러도 소스로 대조했다. global halt는 플래그 고정, snapshot 폐기는 이미 없는 항목을 다시 소비하지 않고, `_fail_policy_change`·`_fail_system_stop`·`_complete`는 완료 핸들을 다시 발행하지 않는다. 비멱등 누적 부작용은 발견하지 않았다. 이번 두 번 호출 경로의 실행 회귀 검증 대상은 after_dispatch이며 나머지 핸들러의 임의 반복 실행 시험을 새로 했다는 뜻은 아니다.

경계 단위 테스트는 원래 취소 객체의 동일성, callback RuntimeError/CancelledError, 격리 중 취소, 최종 halt 핸들러 실패, halt 호출·콜백 호출 1회·원문 비노출을 확인한다. Guard 단위 테스트는 승인된 READ/SEND의 취소 알림 후 콜백이 실패해도 global halt·기존 종결 상태·취소 전파·추가 dispatch 없음이 유지되는지 검사한다. 실제 wire/수신 부작용 독립 인수는 C 몫이다.

### NOTIFY-01 예외 경로

A의 #36 리뷰와 B 답변대로 **최종 알림 핸들이 완료되기 전에 콜백 자체가 실패하는 경로는 “정확히 한 번”의 예외: 알림 0회 + Guard 전역 정지**로 기록한다. 승인 실행은 `ApprovalService._approve`가 `on_cancelled=lambda outcome: self._complete(..., "executed")`를 주입한다. `ApprovalService._complete`가 `PendingFinal`을 만들고 `PendingResultHandle._complete`가 결과 저장·완료 플래그·대기 Event를 설정하는 것이 최종 알림이다. 콜백에 들어갔다는 사실만으로 알림을 보냈다고 세지 않는다.

현재 코드 순서는 `after_dispatch`의 `on_error`→Guard `_contain_post_dispatch`→`commit_request_failure` ACK·Task/요청 상태 검증→추가 failure_audit→`on_cancelled`다. **on_error가 정상 완료한 경로에서는 콜백을 부르기 전에** READ의 WITHHELD/HALTED 또는 SEND의 UNKNOWN_OUTCOME이 이미 원자 커밋됐다. 이어 콜백이 완료 전에 실패하면 `on_containment_error`→`_post_failure_fallback`→`_halt_globally`로 닫고 원래 CancelledError를 `from None`으로 다시 전파한다. 이 경계는 알림을 재시도하거나 새 성공/Denied를 만들어 대기자에게 보내지 않는다. `on_error` 자체의 저장/감사 실패로 fallback에 들어온 경우에는 커밋 ACK를 확보했다고 단정하지 않으며 기존 결과 불명/전역 정지를 유지한다.

**요약의 보완점:** 콜백 실패가 항상 알림 0회를 뜻하지는 않는다. 핸들 완료 뒤 콜백의 나머지 부분에서 실패하면 이미 알림 1회이고, 현재 READ/SEND Guard 회귀 테스트는 원래 `_complete`를 호출한 뒤 예외를 주입해 바로 그 경로를 검사한다. 이때도 전역 정지·원래 취소 전파를 유지하며 이미 완료한 핸들을 재발행하지 않는다. 완료 전 실패의 0회 경로를 이 테스트가 실행 검증했다고 보고하지 않는다. 이번에는 코드/테스트를 추가하거나 실행하지 않았다.

`_global_halt`는 현재 메모리 플래그만 설정하고 미완료 핸들의 Event를 깨우지 않는다. A `ApprovalOutcomes.wait`는 그 핸들의 wait를 기다리므로 알림이 없으면 Codex 세션의 호출별 watchdog이 대기를 끝내고 Task를 정지하는 마지막 장치다. [SEQ-02의 execution_state 제안](B6.17-seq-rec-decisions.md#2-seq-02--실패commit-불명권위-조회)을 연결하면 Guard fault를 같은 controller에 반영하고 A가 `execution_enabled=False`를 확인해 감시 상한을 기다리지 않고 turn interrupt·모든 Task 세션 종료를 할 수 있다. 현재 `77d314a`에는 이 Store 조회/연결이 없다.

최종 핸들·`_pending`·`_results`·`_seen_requests`·승인 원문 사본은 ApprovalService의 메모리에만 있다. 저장소의 요청 상태 커밋은 알림 outbox/소비 ACK 저장이 아니다. 재시작 뒤 **복구는 영속 요청/승인/Task의 안전 종결·격리·Report만 만들고 옛 최종 알림을 재생성하지 않는다.** 따라서 옛 Task/세션·원문/승인 권한을 복원하거나 알림 손실을 재전송으로 보상하지 않는다. 현재 시작 복구 구현은 없으며 이는 A·C 동의(#37), 사용자 contracts 반영 대기의 복구 규칙이다.

사용자가 `contracts.md`의 NOTIFY-01 행에 반영할 **A·C 동의(#37), 사용자 contracts 반영 대기 문안**:

> 정확히 한 번의 예외: 최종 알림 콜백 자체가 핸들 완료 전에 실패하면 해당 실패 경로는 알림 0회와 Guard 전역 정지로 닫는다. 완료 뒤 실패했다면 기존 알림 1회를 보존하고 재발행하지 않는다. 세션은 execution_state 또는 호출별 감시 상한으로 정지한다. 재시작 복구는 옛 최종 알림·Task 실행 권한을 다시 만들지 않는다. A·C 동의(#37), 사용자 contracts 반영 대기.

C는 이 예외 문안에 동의했고 C6.10에서 핸들 `_complete` 전에 결함을 주입해 **알림 0회와 전역 정지**를 따로 센다. 이 C 독립 시험은 계획이며 이번 B 테스트의 실행 결과로 세지 않는다.

## 변경 없는 지문 관측

`record_fingerprint_change`는 기존 신뢰 입력 검증과 같은 `BEGIN IMMEDIATE` 안에서 현재 등록을 읽어 이름 집합·정의·지문을 대조한다. 정의는 기존대로 `reviewed_description`을 제외한 ToolSpec 값이다. 추가·삭제·필드/지문 변경이 없으면 UPDATE/INSERT/DELETE 없이 `FingerprintChange(entry=current, changed_tools=())`를 반환한다. revision·감사 ID/행·상태·도구 저장 순서·검토 설명·검사 포인터·reviewed_by·시간값을 모두 유지한다. 도구 목록 재정렬이나 관측 입력의 검토 설명은 새 정의 변경으로 취급하지 않는다.

무변경도 입력 검증·현재 사본 검증·트랜잭션 종료 실패는 기존 StoreError 의미를 유지한다. 값이 바뀌는 관측의 ACTIVE→PENDING, BLOCKED 유지, 새/변경 도구 설명 비우기, 변경 이름 정렬·추가/삭제 감지, 검사/검토 포인터 해제는 그대로다. SQLite schema/DTO/공개 메서드 시그니처는 바꾸지 않았다. **RegistryStore ports 의미 정정은 합의 전 제안**이며 A/C 검토가 남는다.

기존 테스트 2개를 바꿨다. 동일 정의+재정렬의 revision 증가/새 순서 기대는 현재 저장 사본/도구 순서 보존·전체 DB 행 동일·SQLite total_changes 동일로 바꿨다. 원문 비노출 테스트의 감사 5행/revision 1~5/`REGISTRY_FINGERPRINT_OBSERVED` 기대는 무관측 감사 4행/revision 1~4로 바꿨다. 원문 비노출 단언과 실제 변경/롤백/불명 ACK 테스트는 유지했다. 최초 집중 실행은 옛 `FINGERPRINT_OBSERVED` 이벤트 기대 1개가 남아 실패했고, 그 기대를 정정한 뒤 431개가 통과했다.

PR #36 C 리뷰의 병합 조건에 따라 이미 main에 있던 [B6.14 기록](B6.14-registry-store.md)은 `origin/main` 내용으로 되돌렸다.
