# B3.11 설정 파일 형식·저장 제안

2026-10-19 · 사용자 결정 대기 · CFG-01 제안 · I6/I7/I9·B3.9/B3.10/B3.12

B 추천은 **UTF-8 JSON 단일 파일, `schema_version`/`settings` 봉투, 사용자별 LocalAppData 아래 고정 위치, 파일이 없으면 설정 화면만 시작**하는 안이다. 원자적 교체는 C의 안전 파일 연산으로 제공하고 A가 준비·저장·적용과 Task 생성을 직렬화한다. 자동 이전 파일 백업은 v1에서 끄는 안을 추천한다. 크기·깊이 상한을 포함해 이 문서의 값은 미측정 제안이며 사용자 결정이나 구현 완료가 아니다.

이번에는 이 제안서와 `docs/b-status.md`만 작성했다. B3.11은 제안 작성까지 끝났고 형식·위치 결정, B 파싱/직렬화 구현, C 검증, A 시작/저장 연결은 남아 있다. PR #29의 ProductInputs, PR #32의 실제 상태·리뷰 원문 및 다른 A/C 브랜치 구현은 확인 불가이며 첨부 설명만 참고했다.

## 1. 형식 비교와 추천 이유

| 기준 | JSON | TOML | YAML |
| --- | --- | --- | --- |
| Python 3.12·추가 의존성 없는 읽기/쓰기 | 표준 `json`으로 양쪽 가능 | 표준 `tomllib`은 읽기만 제공. 별도 writer 또는 자체 구현 필요 | 범용 YAML 파서·writer가 표준 라이브러리에 없음. JSON 부분집합만 쓰면 실질적으로 JSON 안과 같음 |
| 중복 키 | 기본 파서는 마지막 값을 남기므로 `object_pairs_hook`에서 모든 객체의 중복을 거부해야 함 | 사양에서 키 재정의 금지. 로컬 tomllib에서도 거부 확인 | 사양의 mapping 키는 유일해야 함. 선택할 라이브러리의 실제 거부 동작을 별도로 검증해야 함 |
| 주석·사람이 정한 키 순서 | 주석 불가. 앱의 정렬 저장은 키 배치를 바꿈. 배열 순서는 유지 | 주석은 가능하지만 tomllib의 dict에는 주석/서식이 없음. 다시 쓰려면 보존 가능한 writer가 별도로 필요 | 주석 가능. 주석·서식 보존은 라이브러리 기능에 달리며 단순 Mapping 변환으로는 보존되지 않음 |
| 설정 값과의 적합성 | 현재 JSON Mapping·null·배열과 바로 맞음 | null이 없고 날짜/시간 등 JSON 밖 타입을 제한·변환해야 함 | 태그·alias·복잡한 키·타입 해석 등 허용 범위를 추가로 제한해야 함 |
| 직접 편집 위험 | 쉼표·역슬래시 escaping 오류. 중복 검사와 strict 검증 필요 | 보기 편하지만 dotted key/테이블 재정의와 타입 차이를 주의해야 함 | 들여쓰기·타입 해석·alias 처리 차이를 주의해야 함 |
| JCS 연결 | 검증·정규화한 JSON 값에 기존 JCS 적용 | JSON과 같은 값으로 정확히 변환된 경우에만 같음 | JSON과 같은 값으로 정확히 변환된 경우에만 같음 |

**JSON을 추천하는 이유:** A가 변경을 다시 저장해야 하므로 읽기뿐 아니라 쓰기를 현재 의존성 안에서 제공해야 한다. 현재 B3.9/B3.10의 입력·준비 결과가 이미 JSON 형태여서 추가 타입 변환도 가장 작다. 주석과 수동 배치는 보존하지 않는다는 저장 규칙을 사용자에게 알린다. JSON을 읽을 수 있다는 것과 안전한 설정 파싱이 구현됐다는 것은 다르다. 중복 키·비유한 수·예산 제한은 별도 구현 대상이다. [Python json](https://docs.python.org/3.12/library/json.html), [tomllib의 writer 미지원](https://docs.python.org/3/library/tomllib.html), [TOML 1.0 키/타입 규칙](https://toml.io/en/v1.0.0), [YAML 1.2.2 mapping 모델](https://yaml.org/spec/1.2.2/#321-representation-graph)

직접 편집은 앱을 닫은 상태에서만 하는 운영 방식을 추천한다. 실행 중 변경은 자동 재로딩하지 않고 명시적 재로딩·검증·정책 적용으로 처리한다. GUI 저장도 수동 변경을 조용히 덮어쓰지 않아야 한다.

## 2. 파일 구조·스키마 버전·정책 해시

| 구조 | 장점 | 한계 |
| --- | --- | --- |
| 전체 설정 한 파일, 추천 | profile·servers·destinations·policy·access_rules의 같은 세대를 한 번에 읽고 교체 | 작은 변경에도 전체 재직렬화. 파일 전체 상한 필요 |
| profile/servers/policy 등 분리 | 영역별 편집·주석 관리에 편리 | 개별 파일 replace만으로 전체 설정의 원자성이 생기지 않음. 세대별 디렉터리·manifest 교체 등 추가 프로토콜과 복구 규칙이 필요 |

v1에서는 한 파일을 추천한다. SQLite Registry의 ACTIVE 상태·지문·검사 보고서, Task 상태와 승인 원문을 이 파일로 복원하지 않는다. 파일에는 B3.9가 받는 운영자 설정만 둔다.

제안하는 봉투와 서버 없는 설정 예시는 다음과 같다. 제품 파일을 생성한 것은 아니다.

```json
{
  "schema_version": 1,
  "settings": {
    "profile": {
      "id": "default",
      "servers": [],
      "destinations": [],
      "sources": []
    },
    "servers": [],
    "destinations": [],
    "policy": {
      "taint_mode": "accumulate",
      "approval_ttl_seconds": 300
    },
    "access_rules": {
      "allow": [],
      "deny": []
    }
  }
}
```

봉투는 두 키만 허용한다. schema_version은 bool이 아닌 정확한 정수 1이어야 하며 누락·다른 버전·추가 키·settings가 객체가 아닌 경우를 거부한다. 이름과 달리 이 버전은 파일 해석 규약의 버전이지 Task의 policy_version이나 SQLite 스키마 버전이 아니다. 지원하지 않는 버전을 알아서 v1으로 읽거나 자동 이관하지 않는다.

현재 `_Configuration`은 `_Settings`→`Frozen`을 상속하고 `extra="forbid"`다. 허용하는 최상위 필드는 profile·servers·destinations·policy·access_rules다. **현재 로더에 봉투 전체를 넘기면 거부된다.** 결정 뒤 만들 파서가 봉투를 검증하고 settings만 기존 `load_profile_settings`에 넘긴다. 기존 로더의 계약을 봉투로 바꾸지 않는다.

policy_version은 기존대로 **settings를 strict 검증하고 기본값·접근 규칙을 정규화한 전체 설정의 JCS SHA-256**으로 계산하는 안을 추천한다. 봉투·파일 경로·BOM·들여쓰기·바깥 공백·객체 키 배치·원본 파일 바이트 해시는 넣지 않는다. 선택된 Profile 밖 서버·목적지도 계속 포함한다. v1 봉투 추가만으로 기존 동일 설정의 policy_version을 바꾸지 않는다. 향후 파일 버전이 해석 의미까지 바꾸면 명시적 이관과 정책 해시 의미를 다시 검토해야 한다.

같은 검증·정규화 결과라면 표현 차이는 해시를 바꾸지 않는다. 다만 다음을 구별한다.

- 객체 키 순서·문자열 바깥 공백은 영향이 없다. 문자열 안 공백/줄끝은 데이터라 영향이 있고 Unicode NFC 변환도 하지 않는다.
- 접근 규칙 allow/deny 쌍은 기존처럼 정렬·중복 제거된다. 다른 배열 순서는 보존하므로 배열 재배치는 해시가 바뀔 수 있다.
- JCS 숫자 표기와 **스키마의 타입 허용**은 별개다. 현재 TTL은 정수 300만 받고 300.0·3e2는 float라 거부한다. JCS가 이들을 같은 숫자로 쓸 수 있다는 이유로 검증 전에 정수로 고치지 않는다.
- 현재 JCS 구현은 정수를 ±(2**53−1) 안에서, float를 유한 binary64로 제한한다. 이 범위 안에서도 필드별 strict 타입·범위를 먼저 만족해야 한다. TOML/YAML 날짜·큰 정수·임의 타입을 문자열로 바꿔 통과시키지 않는다. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html)

**저장할 문서는 `PreparedPolicyChange.document.to_dict()`다.** 해시용 `_Configuration.model_dump(mode="json")` 사본은 등급 이름을 숫자로 바꾸므로 저장용 외부 스키마와 다르다. 그 사본을 저장하면 현재 로더가 다시 거부한다. 저장은 PUBLIC/INTERNAL/CONFIDENTIAL 등 현재 외부 표현을 유지하고 해시 정규화는 기존 로더 안에서만 한다. 파일 bytes 비교용 해시가 필요하면 policy_version과 다른 값으로 C/A가 관리한다.

## 3. 읽기 규칙과 고정 오류

아래 상한은 v1 추천값이며 성능·실제 최대 설정으로 측정한 값은 아니다. 사용자 결정 뒤 B/C가 경계값을 검증한다.

| 항목 | 추천 규칙 |
| --- | --- |
| 인코딩 | UTF-8 strict. 맨 앞 UTF-8 BOM 한 개는 호환성을 위해 허용·제거하고 저장할 때는 쓰지 않음. UTF-16/32 자동 감지·대체 문자 디코딩 금지 |
| 크기 | BOM·공백까지 포함한 파일 바이트 최대 1,048,576(1MiB). C는 최대 상한+1바이트까지만 읽어 초과를 감지하고 B도 받은 bytes 길이를 다시 확인 |
| 중첩 | 봉투 전체 기준 최대 64단계. 루트 객체가 1, settings 객체가 2이며 배열/객체마다 1 증가. 문자열 안 괄호는 세지 않음 |
| 파싱 전 예산 | JSON 파서 호출 전에 문자열·escape 상태를 구별하는 깊이 검사를 수행. 단순 괄호 개수나 파싱 후 검사만으로 깊이 제한을 대체하지 않음 |
| 중복 키 | object_pairs_hook에서 모든 객체를 검사. escape 해석 뒤 같은 키도 거부. 뒤 값 채택·자동 병합 금지 |
| 비유한 수 | parse_constant로 NaN·Infinity·-Infinity 거부. 별도의 유한 float 검사로 1e999 같은 overflow도 거부. `strict=True`만으로 이 조건이 충족되지는 않음 |
| 값/문법 | 정확한 JSON 값·문자열 키만 허용. 안전 범위 밖 정수·비정상 Unicode surrogate·후행 쓰레기·주석·trailing comma 거부. 알 수 없는 키/필드 타입·참조는 기존 로더가 거부 |
| 오류 처리 | 잘못된 파일을 기본 설정·기본 허용으로 바꾸지 않음. 경로·파일 읽기·봉투·설정·C 검증 중 하나라도 실패하면 Task 시작/새 설정 적용 금지 |

Python 기본 json은 중복 키와 비유한 수를 받아들이므로 위 검사가 필요하다. JSONDecodeError는 문서 원문도 보유한다. 원래 예외를 노출하지 않고 고정 코드로 번역하며 cause/context에 연결하지 않는다. 로그·repr·UI 오류에 경로·키 이름·값·원문 조각·예외 메시지를 붙이지 않고 traceback locals도 기록하지 않는다. [Python JSON 동작과 오류 필드](https://docs.python.org/3.12/library/json.html#standard-compliance-and-interoperability)

## 4. 쓰기·원자적 교체·실패 처리

동일한 settings Mapping 값의 결정적 출력은 schema_version 1 봉투를 만들고 문자열 키 정렬, 들여쓰기 2칸, `ensure_ascii=False`, `allow_nan=False`, 구분자 `(',', ': ')`, UTF-8 BOM 없음, 줄끝 LF, 마지막 LF 한 개로 정한다. 배열은 정렬하지 않는다. 출력 bytes도 읽기 크기·깊이·숫자/문자 제한을 만족해야 한다. 임의 객체를 `str()`로 바꾸는 fallback이나 비문자열 키 자동 변환은 금지한다.

이 pretty JSON은 저장용 표현이다. 키 정렬 등에서 JCS와 동일한 바이트를 약속하지 않으며 그 bytes를 policy_version으로 해시하지 않는다. UI 저장이 주석/기존 키 배치를 보존하지 않는다는 점도 안내한다.

권장 순서는 다음과 같다.

1. A가 구성 변경/새 Task 생성용 직렬화 잠금을 잡고 최신 설정 사본과 저장 파일 세대를 확인한다.
2. B3.10으로 변경을 준비하고 전체 설정을 검증한다. B 순수 직렬화 함수에 `PreparedPolicyChange.document`를 넘긴다. C가 변경된 경로·실행 파일·endpoint·권한을 검증한다.
3. C 안전 파일 연산이 검증된 같은 디렉터리에 예측 불가능한 이름의 임시 파일을 독점 생성한다. 원래부터 사용자 전용 권한을 적용하고 전체 bytes를 기록한다. 기존 파일을 truncate해 덮지 않는다.
4. C가 버퍼 flush→파일 fsync→필요한 핸들 닫기→같은 파일시스템의 최종 파일 교체를 수행한다. 부모/대상 바꿔치기·reparse point·기존 임시 경로 재사용과 교체 후 ACL을 검증한다. 실제 API 선택과 내구성 ACK 조건은 C가 정한다.
5. **저장 성공을 확정한 뒤** A가 `Guard.apply_policy_change`에 준비 결과·새 AccessChecker·최신 Task 조회를 전달한다. 성공한 버전만 새 Task의 Profile/버전에 사용하고 그 뒤 A 잠금을 푼다. 실패하면 성공 UI를 표시하거나 새 Task를 시작하지 않는다.

파일 flush/fsync와 rename은 다른 단계다. Python 문서의 os.replace 원자성 설명은 POSIX 요구도 명시하고 있어 Windows의 전원 차단·권한 보존까지 검증됐다고 확대할 수 없다. C는 os.replace 또는 Windows 교체 API를 선택해 파일시스템·잠금·백신 간섭·전원/프로세스 중단 시 의미를 확인해야 한다. 폴더 메타데이터 반영과 저장 성공 ACK 범위도 C 검토 항목이다. [Python fsync/replace](https://docs.python.org/3.12/library/os.html#os.fsync), [Windows ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

| 중단/실패 지점 | 추천 처리 |
| --- | --- |
| 검증·직렬화·임시 파일 기록 중, 공표 전 실패 확정 | 새 Guard 설정을 적용하지 않음. 기존 설정으로 저장 성공을 가장하지 않음. 임시 파일은 C가 안전하게 정리 |
| 교체 ACK 유실 등 파일 세대 불명 | CFG_SAVE_UNCERTAIN. 구성 변경/새 Task 시작을 막고 C의 권위 있는 재조회와 검증으로 확정. 자동 재교체·임의 백업 복원 금지 |
| 저장 성공 뒤 Guard 적용 실패 | 파일은 새 설정일 수 있고 런타임과 불일치함을 표시. 새 Task 시작을 막고 기존 Guard의 실패/전역 정지 의미를 유지. 화면에서 옛 설정으로 성공 처리하거나 자동 rollback하지 않음 |
| 저장과 적용 사이 프로세스 종료 | 다음 시작에서 최종 파일 전체를 다시 읽고 B/C 검증. 과거 Task·승인 실행 권한을 이 파일에서 복구하지 않음 |

파일 교체와 Guard 적용은 하나의 트랜잭션이 아니다. 현재 Guard는 apply 호출 시점부터 자체 장벽/Task lock으로 정지·승인 무효화하므로 **디스크 저장부터 apply 진입 전까지 기존 호출이 옛 정책으로 실행될 수 있는 간격**을 파일 교체만으로 없애지 못한다. 변경 접수 즉시 모든 호출을 막아야 한다면 A의 실행 접수 일시 중지와 C 계수 검증을 별도로 합의한다. 기존 B3.10이 그 간격까지 원자적이라고 주장하지 않는다.

자동 백업은 v1에서 **없음**을 추천한다. 경로·인자 사본이 누적되는 것과 두 파일의 세대/권한/복구 관리를 피하기 위해서다. 임시 파일은 백업으로 채택하지 않는다. 사용자가 백업을 원하면 같은 보호 디렉터리의 이전 한 세대까지만 허용하는 안을 C가 검토하고, 복원은 사용자의 명시적 선택 뒤 전체 검증·새 정책 적용으로 처리한다. 잘못된 파일에서 조용히 이전 정책으로 돌아가지는 않는다.

A의 잠금은 한 프로세스 안의 동시 저장·활성화·새 Task 생성을 직렬화한다. 외부 편집/다른 앱 인스턴스까지 보호하지는 못한다. C에 같은 파일의 단일 writer 보장과 읽은 파일 bytes 세대의 조건부 교체를 요청한다. policy_version이 같아도 수동 서식 편집은 파일 세대가 다를 수 있다. 다중 프로세스를 허용한다면 단순 비교 후 replace 사이 경쟁까지 막는 OS 잠금 등은 C가 정해야 한다.

## 5. 위치·권한 후보

| 후보 | 평가 |
| --- | --- |
| `%LOCALAPPDATA%\MCPRuntimeGuard\config\settings.json`, 추천 | C2.13의 사용자별 앱 폴더 방향과 맞고 PC별 실행 경로·endpoint를 로밍시키지 않음 |
| `%APPDATA%\MCPRuntimeGuard\settings.json` | 로밍 용도지만 PC별 절대 경로·실행 파일이 다른 PC로 넘어가 재검증과 충돌 처리가 필요 |
| 실행 파일 옆·현재 디렉터리·프로젝트/문서 폴더 | 설치 위치 권한·작업 디렉터리·공유/동기화 영향 때문에 기본 탐색 위치로 추천하지 않음 |

LocalAppData가 사용자별 폴더라는 근거는 Windows Known Folder 정의다. **최종 경로·해석·소유권·권한 검증은 C가 정한다.** 환경변수 문자열만 신뢰해 열지 않고 C의 Known Folder/경로 검증 경로를 쓴다. [Windows FOLDERID_LocalAppData](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid#folderid_localappdata)

상위 디렉터리·최종 파일·임시 파일·선택적 백업에 같은 사용자 보호 정책을 적용한다. 다른 일반 사용자의 쓰기를 허용하지 않고 교체 뒤에도 권한이 넓어지지 않아야 한다. SYSTEM/관리자 권한 등 OS 신뢰 범위의 예외는 C가 명시한다. `chmod`만으로 Windows 사용자 전용 ACL을 구현했다고 보지 않는다. Task 로그 정리 대상·CODEX_HOME과 분리해 설정을 잘못 삭제하지 않도록 한다.

설정은 평문이며 경로·인자·URL이 민감할 수 있으므로 로그·진단 첨부에 원문을 싣지 않는다. 비밀값 저장소로 사용하지 않고 자격증명 관리자의 기존 담당 경로를 사용한다. 현행 스키마에 없는 비밀값 참조 필드를 이번 제안으로 추가하지 않는다.

## 6. 첫 실행과 재로딩

추천은 **파일이 없으면 설정 화면을 열고, 설정 저장/검증이 끝날 때까지 모델 Task·도구 실행을 시작하지 않는 것**이다. 작업 디렉터리나 다른 폴더에서 같은 이름의 파일을 찾아 자동 채택하지 않는다. 파일 없음과 권한/손상 오류를 구별하고, 손상을 첫 실행 성공으로 바꾸지 않는다.

화면의 새 설정 초안에는 위 예시처럼 서버·목적지·출처·접근 허용이 모두 빈 Profile을 쓸 수 있다. 현재 로더에서 그 값은 유효하고 허용 목록도 비어 있음을 확인했다. 그러나 파일이 없는데 그 초안을 자동 적용·저장하지 않는다. 사용자가 서버 없는 파일을 명시적으로 저장해도 사용할 등록/허용 도구가 없으므로 실행 준비 완료로 표시하지 않는다.

설정 저장 전의 서버 활성화·접근 허용 기본값으로 실행 권한을 만들지 않는다. 기존 A81의 활성화 체크는 사용자 확인·준비·저장·적용을 거친다. 외부에서 편집한 파일의 재로딩도 C 읽기→B 파싱/설정 검증→C 경로/실행 검증→정책 변경 준비/적용 순서로 연결한다. 실행 중 파일 감시와 자동 이관은 v1 제안 범위에 넣지 않는다.

## 7. 결정 뒤 B 구현과 A·C 요청

아래는 기존 B 소유 `services/catalog.py`에 둘 수 있는 **미구현 시그니처 제안**이다. 파일·경로·프로세스·Registry에 접근하지 않는다. domain/ports 변경 제안은 아니다.

```python
def parse_settings_bytes(
    data: bytes, *, max_bytes: int = 1_048_576, max_depth: int = 64
) -> dict[str, object]: ...

def serialize_settings_bytes(
    settings: Mapping[str, object],
    *,
    max_bytes: int = 1_048_576,
    max_depth: int = 64,
) -> bytes: ...
```

parse는 bytes/예산·UTF-8·JSON·봉투·JSON 값 범위를 검사해 **봉투를 제거한 독립 settings Mapping**을 반환한다. Profile의 필드·참조·정책 검증은 기존 load_profile_settings가 맡으므로 파싱 성공만으로 실행 가능이라고 보지 않는다. serialize는 JSON 값/예산을 검사하고 v1 봉투의 결정적 bytes를 만든다. 호출자는 먼저 B3.10으로 문서를 검증·준비해야 한다. 두 함수는 입력을 수정하거나 임의 값을 기본값으로 보정하지 않는다. max 인자는 신뢰된 호출자가 정하며 파일 내용으로 검사 상한을 완화하지 않는다.

SettingsFileError(code) 같은 고정 오류형은 이 서비스 내부 제안으로 검토한다. 코드 이름만 포함하고 원래 예외·원문을 보유하는 필드를 추가하지 않는다. 예상 가능한 decode/파싱/형식 오류를 좁게 번역하며 새로운 넓은 예외 처리 경계를 만들지 않는다. 나중에 ports/domain에 입구·DTO가 필요해지면 별도로 3인 합의를 받는다.

| 담당 | 요청/구현 |
| --- | --- |
| B | 사용자 결정 뒤 위 순수 파싱·직렬화·경계값/오류 비노출 검사. 기존 Profile 로더·전체 설정 policy_version·PreparedPolicyChange와 연결 |
| C 요청 | 최종 경로·사용자 권한·크기 제한 안전 읽기·원자적 교체·단일 writer/파일 세대 충돌·불명 ACK·임시 파일 정리. 설정에 든 실행 파일/경로/endpoint 검증과 Windows 중단·권한 독립 시험 |
| A 요청 | ProductInputs에 settings Mapping을 공급하는 시작 경로, 미설정 화면·고정 오류 표시, 준비→저장→적용과 새 Task 생성 직렬화(B3.12), 적용 실패 gate, 기존 Task 정지 안내 |
| 사용자 | 형식·구조·위치·첫 실행 및 부속 저장 규칙 결정. 공통 계약/기술 설계에 결정을 반영 |

C/A의 새 파일 연산 인터페이스·Windows 내구성 보장·실제 연결이 준비됐다고 가정하지 않는다. 이 제안서는 이를 직접 구현하거나 다른 담당의 API를 확정하지 않는다.

## 8. 사용자 결정 질문과 미결 요청 행 문안

| 질문 | B 추천 선택 | 다른 선택의 영향 |

| 파일 구조·버전은 어떻게 할까? | 단일 파일, schema_version 1/settings 봉투, 해시는 기존 정규화 settings만 | 분리 파일은 전체 세대 공표/복구 프로토콜 필요. 봉투까지 해시하면 기존 동일 설정 버전이 달라짐 |

함께 확인할 저장 세부 추천은 1MiB·깊이 64, 선두 UTF-8 BOM 한 개 읽기 허용/쓰기는 BOM 없음, 자동 이전 파일 백업 없음, 앱 종료 상태의 직접 편집이다. 상한은 실측값이 아니므로 사용자 결정 및 B/C 검증 뒤 조정할 수 있다.

## 실제 확인과 남은 한계

현재 catalog.py의 _Configuration/Frozen 상속·strict 검증·기본값/접근 규칙 정규화·해시 범위, PreparedPolicyChange 저장 순서, pyproject.toml의 직접 의존성, 기존 Profile/정책 변경 단위 검사를 읽었다. 공식 Python·TOML·YAML·RFC·Windows 자료를 위 링크로 대조했다. Python 3.12 tomllib의 읽기 전용 입구와 중복 키 거부는 설치된 환경에서도 확인했다.

샌드박스 안에서 저장소에 코드를 쓰지 않는 최종 읽기 전용 Python 프로브 **15개를 실행해 통과**했다. JSON의 중첩/escape 키 중복 2건·비유한 수/overflow 4건을 좁은 hook으로 거부, Configuration extra forbid, tomllib writer 부재·중복 거부, 빈 Profile·접근 허용 없음, 서식/키 배치의 해시 동일, 봉투 직접 입력 거부, float TTL 거부, 해시용 숫자 등급과 저장 스키마의 비호환을 확인했다. 이것은 기존 동작과 제안에 쓸 표준 함수의 확인이며 미래 파서·파일 교체 구현의 검증은 아니다.

제안서의 JSON 예시를 파싱해 기존 Profile 로더로 읽을 수 있는지와 문서 변경 범위·공백 오류를 확인했다. 이번 변경은 문서 2개뿐이므로 Ruff·format·mypy·pytest 전체 검사는 다시 실행하지 않았고 이번 작업의 통과 결과로 주장하지 않는다. B3.11의 구현·C Windows 원자성/권한/파일 경쟁·A 실제 ProductInputs와 시작/저장 경로·전송 계수는 미검증이다.

현재 feat/b-security-core에 문서만 커밋하며 push·PR 생성은 하지 않는다. Claude outputs/는 읽기만 했고 커밋에 넣지 않았다.
