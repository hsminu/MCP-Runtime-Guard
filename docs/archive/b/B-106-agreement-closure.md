C의 B1.9 동의 조건은 `[A-Za-z0-9_ ]{1,64}` 전체를 허용하는 것이다. B는 `^[A-Za-z0-9_ ]{1,64}$`와 길이 1~64를 적용하고, C는 같은 본문을 `fullmatch`한다. 소문자와 공백을 모두 허용한다. 과거 저장 보고서에 이전 `Identifier`가 허용한 하이픈 등의 코드가 있으면 새 검증에서 등록 조회가 실패할 수 있으며 실제 사용자 DB의 존재 여부는 미확인이다. 자세한 호환 확인은 [54번 기록](B1.7-B1.9-code-s.md)에 있다.

## C 독립 검증과 B6.8

C3 독립 검증 [#103](https://github.com/hsminu/MCP-Runtime-Guard/pull/103)과 [#104](https://github.com/hsminu/MCP-Runtime-Guard/pull/104)는 병합됐다. #103의 C3.9·C3.10은 재시작·변조를, #104는 다섯 Store 연산의 쓰기 경계에서 강제 종료 후 복구를 60회 확인했다. #103의 C-C3-01에서 요청의 epoch·kind·row_revision 불일치 세 사례는 복구됐지만 옛 승인 실행 0이었고, B는 [시작 점검 범위 밖으로 판단](https://github.com/hsminu/MCP-Runtime-Guard/pull/103#issuecomment-6504498759)했다. 따라서 모든 변조를 시작 단계에서 거부한 결과는 아니다. B6.8 전체 항목 중 영속 순번과 허용된 실패 감사의 C 독립 인수는 이 근거만으로 확인되지 않아 해당 부분은 후속으로 남긴다. B7.6의 C Store 독립 검증 기록은 닫되 전체 통합 인수를 뜻하지 않는다.

## #94 출처 규칙

[#94 B 제안](https://github.com/hsminu/MCP-Runtime-Guard/issues/94#issuecomment-6505157878): 자원형 출처 규칙(`prefix != ()`)은 Guard가 기대 자원 ID를 계산하고 신뢰 코드가 응답 ID를 만드는 서버(현재 C 파일 서버)에만 적용한다. 그 밖의 서버는 도구 단위 READ만 사용한다. 도구 단위 READ 등급은 운영자가 그 도구의 모든 결과에 붙이는 선언이고, 응답 `resource_id`는 거부에만 사용한다. 파일 서버 인정 조건의 실행 파일 확인은 A·C 결정 대기다. 이는 #106의 8개 답과 별도인 제안이다.
