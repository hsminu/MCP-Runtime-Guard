## Scanner 정책 사용자 결정

2026-10-13 사용자가 "llm을 기본으로 하고 위험 발견해도 경고만 띄우는 식으로"라고 결정했다. C의 도구 정의 Scanner는 Luna low LLM을 기본 분석기로 사용하며, 유효한 검사에서 발견한 위험은 경고로 표시한다. 위험 발견 자체를 자동 등록 차단·도구 실행 중단 조건으로 사용하지 않는다. 원래 Finding의 코드·심각도는 보존하며 HIGH를 INFO로 낮추지 않는다.

이 결정은 기술 설계 원문 10.2절의 HIGH 이상 PENDING 유지 규칙보다 우선하는 Scanner 정책이다. 원문은 보존한다. 관리 대상 호출의 Guard 경계·등급·승인 판정은 별도이며 이 결정으로 변경하지 않는다. 관리자 활성화 절차는 별도다.

같은 날 사용자가 "1안으로 가자"라고 선택했다. 키 누락·시간 초과·API/응답 오류처럼 LLM 검사를 완료하지 못한 경우에도 **검사 실패·미완료 경고를 표시하고 사용은 계속**한다. 이 Scanner 실패만을 이유로 자동 등록 차단·실행 중단하지 않는다. 실패 상태와 고정 오류 코드는 보존하며, 이를 findings 0개·정상 완료·안전 판정으로 바꾸지 않는다. 이 결정은 Scanner의 진단 실패에 한정하며 Guard·저장소·실제 도구 실행의 fail-closed 처리를 완화하지 않는다.

같은 날 사용자가 "함께 돌리자"라고 결정해 YARA를 보조 분석기로 병행한다. 같은 전체 도구 정의를 LLM과 YARA에 각각 전달하고, 어느 한쪽이 발견한 위험도 경고 대상으로 보존한다. 두 분석기의 판단 일치를 요구하거나 서로의 Finding을 지우지 않는다. 기존 경고 정책을 두 분석기에 적용하며 실패·미완료도 경고 후 사용을 계속한다. 한쪽의 실패로 다른 검사를 생략하지 않고 각 분석기의 실제 완료·실패 상태를 따로 기록한다. 중복 경고의 표시 방식과 실행 순서는 후속 구현에서 정리한다.

현재는 결정 문서만 반영했다. 두 분석기의 병행 실행·집계 경로와 경고 UI·Registry 정책은 미구현이며 B ScanReport 미연결 지시도 유지한다. 관리자의 활성화 절차·도구 지문 변경 시 PENDING/승인 무효화 규칙은 별도다. 도구별 입력 상한·목록 페이지 수신 상한·서버별 누적 수신 상한은 아래 사용자 결정으로 확정했으며, 도구 수 등 나머지 제한은 미확정이다.

입력 크기의 근거로 C가 [실제 MCP metadata 조사](tasks/c-real-mcp-metadata-survey.md)를 수행했다. 공개 서버 6종·설정 7개의 Tool 정의 189건에서 최대 단일 정의는 8,360바이트, 최대 페이지 result는 259,485바이트였다. 조사 당시 도구별 64KiB와 별도 목록·누적량·도구 수 제한을 제안했으며, 후속 사용자 결정은 아래에 기록한다. 추가 정의 필드와 지문 범위의 일치, A transport의 파싱 전 수신 제한은 별도 계약 검토 대상이다. 이 기록은 크기 조사이며 실제 정의의 LLM/YARA 검사나 공통 API 합의가 아니다.

## Scanner 입력 크기 사용자 결정

2026-10-13 사용자가 "너 추천대로 해 다음 설명"이라고 결정해 **도구 하나의 검사 입력 상한을 기본 64KiB(65,536바이트), 설정으로 변경 가능**으로 확정했다. 설명·입출력 schema·annotations·추가 필드를 모두 포함한 Tool 객체를 키 정렬·공백 없는 JSON으로 직렬화한 UTF-8 바이트 수로 계산한다. 설정한 상한 이하를 검사 대상으로 삼는다.

초과하면 내용을 자르거나 일부 필드를 빼지 않고 `SCAN_METADATA_TOO_LARGE`와 검사 미완료 경고를 남긴다. 기존 사용자 결정대로 이 Scanner 미완료만으로 도구 사용을 자동 차단하지 않는다. 이를 findings 0개·검사 완료·안전 판정으로 바꾸지 않는다. LLM/YARA에 같은 전체 정의를 전달하는 정책과 Guard·저장소·정의 변경 무효화 규칙은 유지한다.

현재 반영 범위는 결정 문서다. 기존 C 어댑터의 명시적 `max_definition_bytes`와 초과 입력 오류 처리는 구현돼 있지만, 제품 기본값·설정 로딩·경고 UI·Registry 연결은 아직 반영하지 않았다. B ScanReport는 미연결 지시를 유지한다. 이 사용자 결정은 C의 입력 정책이며 A·B·C의 새 공통 API 합의를 대신하지 않는다.

`tools/list` 한 페이지와 서버별 누적 수신 상한은 아래 후속 결정에 기록했다. A transport가 받는 응답 메시지의 제한으로, 도구별 직렬화 후 상한과 구분한다. 도구 수 등 나머지 제한은 후속으로 정한다.

## MCP 목록 수신 크기 사용자 결정

2026-10-13 사용자가 "ㅇㅇ 그렇게 해 다음 정할거"라고 결정해 **`tools/list` 한 페이지의 수신 상한을 기본 1MiB(1,048,576바이트), 설정으로 변경 가능**으로 확정했다. A transport가 응답을 받는 도중 JSON 파싱 전에 크기를 제한해야 한다. 도구별 기본 64KiB는 파싱된 Tool 정의의 직렬화 크기 제한이고, 이 값은 한 페이지 전체 응답 메시지의 수신 제한이다.

측정 대상은 프레이밍을 제거하고 HTTP 압축이 있으면 해제한 뒤의 응답 JSON-RPC 메시지 UTF-8 바이트다. 실제 메시지의 공백과 JSON-RPC envelope를 포함하며, 파싱 후 재직렬화해서 수신 제한을 대체하지 않는다. stdio에서는 해당 JSON-RPC 메시지, HTTP에서는 해당 JSON 응답 또는 SSE 이벤트의 JSON-RPC payload에 적용한다. 장시간 유지되는 SSE 연결의 전체 누적 스트림에 페이지 상한을 적용하지 않는다. 조사한 259,485바이트는 정규화한 `result`의 크기이며 원래 수신 메시지 길이는 아니었다.

초과하면 해당 응답 수신을 중단하고 **목록 수집 미완료 경고**를 남긴다. 잘린 JSON·목록을 정상 응답이나 완성된 도구 목록으로 취급하지 않는다. 앞 페이지를 받았더라도 전체 목록 수집 완료로 표시하지 않는다. 원문·인증정보를 경고에 포함하지 않는다. 도구 정의가 수집되지 않은 경우에 정의를 추정해서 호출하지 않으며 기존 Guard·등록·정의 변경 규칙은 유지한다.

현재는 결정 문서만 반영했다. A transport의 수신 제한·설정·중단 처리, C의 stdio/HTTP 초과 응답·미완료 검증, 경고 UI·Registry 연결은 미구현이다. B domain·ports·ScanReport와 A 제품 코드를 변경하지 않았으며 새 공통 API 합의 기록이 아니다. 서버별 누적 수신량은 아래 후속 결정에 기록했다. 도구 수·페이지 수·시간 제한은 별도로 검토한다.

## MCP 목록 누적 수신량 사용자 결정

2026-10-13 사용자가 "그렇게 하자"라고 결정해 **서버 하나의 전체 목록 조회 한 번의 누적 수신 상한을 기본 8MiB(8,388,608바이트), 설정으로 변경 가능**으로 확정했다. 같은 조회에서 모든 `tools/list` 페이지 응답의 수신 크기를 합산하며, 페이지를 넘길 때 누적 계수를 초기화하지 않는다. 서버·조회별 예산으로 구분하며 서버의 전체 수명에 걸친 누적량은 아니다.

바이트 측정 기준은 위 페이지 수신 상한과 동일한 실제 응답 JSON-RPC 메시지의 UTF-8 크기다. 페이지당 기본 1MiB와 서버별 조회 누적 기본 8MiB를 모두 적용하며 A transport가 수신 중 제한한다. 전체 Tool 객체를 파싱 후 정규화한 크기의 합으로 수신 제한을 대체하지 않는다.

누적 상한을 초과하면 해당 조회의 추가 수집을 중단하고 **전체 목록 수집 미완료 경고**를 남긴다. 수신 중 초과한 응답과 앞서 받은 페이지 일부를 완성된 전체 목록으로 취급하지 않는다. 초과 상태를 도구 0개·검사 완료·안전 판정으로 바꾸지 않는다. 원문·인증정보를 경고에 포함하지 않으며 기존 Guard·등록·정의 변경 규칙은 유지한다.

현재는 결정 문서만 반영했다. A의 누적 수신량 계수·설정·수집 중단, C의 다중 페이지·누적 초과·조회별 계수 검증, 경고 UI·Registry 연결은 미구현이다. B ScanReport는 미연결 지시를 유지하며 제품 소스와 공통 API는 변경하지 않았다. 다음 미확정 항목은 **서버별 도구 수 상한**이다. 페이지 수·조회 시간·검사 동시성 등의 제한도 후속으로 검토한다.

사용자의 "이런 자잘한 거 다 추천하는 거 적어봐" 요청으로 C가 [운영 설정 일괄 추천안 v1](tasks/c-scanner-operating-proposal.md)을 작성했다. 남은 개수·시간·동시성·오류·경고·재검사 설정과 현재 구현값을 정리한 제안이며 새 사용자 결정이나 A·B·C 공통 API 합의로 기록하지 않는다.

후속 "검증 ㄱㄱ" 요청의 [실행 보고](tasks/c-scanner-operating-validation.md)에서 실제 정의 변형 144개의 Luna low/YARA 검사·API 144건 HTTP 200·stdio/HTTP 경계 관찰 22개를 확인했다. 동시 LLM 4개·YARA worker 1개는 실험 코드의 제한이며 A 수신 상한·제품 병행 runner·Registry·경고 UI·Guard 인수를 대신하지 않는다. 새 추천값은 아직 미확정이고 B ScanReport는 미연결 상태를 유지한다.

## Scanner 입력 범위 구현 기록

2026-10-13 사용자의 "반영해보" 지시로 C의 [도구 정의 입력 어댑터](tasks/c-cisco-metadata-implementation.md)를 구현했다. 네 기본 필드의 전체 중첩 구조와 추가 정의 필드를 보존하고, LLM SDK의 description에 전체 JSON을 넣는다. 실행 인자·결과·연결 설정을 입력에 합치지 않는다. 구현상 크기 상한은 호출자가 명시하며, 후속 기본 64KiB 정책은 위 사용자 결정에 기록했다. 기본 repr·입력 오류에는 원문을 노출하지 않는다.

B의 `FrozenJsonObject.to_dict` 입력과 호환되며 domain·ports·digest는 변경하지 않았다. 추가 필드·float를 포함한 검사 범위와 지문 범위의 일치, ScanReport 번역·필수 분석기 집계·Registry 연결은 후속 계약 검토 대상이다. 이 기록은 C 입력 구현에 대한 사용자 지시와 실제 검증이며 A·B·C의 새 공통 API 합의 기록을 대신하지 않는다.

후속 사용자 지시 "연결해 b scanreport는 연결하지마"로 [Luna low 요청 연결](tasks/c-cisco-luna-connection.md)을 구현했다. 환경·OpenAI 요청·고정 오류 처리는 C 내부 구현이며 B ScanReport·domain·ports는 연결하거나 변경하지 않았다. 이 제외 지시는 현재 작업 범위에 적용하며 새 공통 DTO·필수 분석기·등록 정책의 합의를 뜻하지 않는다.

## 저장소 원자성

- [ ] `commit_observation`: READ 등급 병합, security_version, 승격 근거, 감사, 요청 상태가 한 트랜잭션에서 확정된다.
- [ ] `commit_send_outcome`: SEND 요청 상태와 감사만 갱신하며 READ 등급 병합을 호출하지 않는다.
- [ ] `consume_and_reserve`: 승인 CONSUMED, 요청 DISPATCHING, Task RUNNING 전이가 한 트랜잭션이다. 해시·만료·상태·security_version과 각 변경 행 수를 검사한다.
- [ ] 연결은 백엔드 단일 writer가 소유하며 WAL·foreign_keys·synchronous FULL·명시적 트랜잭션을 사용한다.
- [ ] 저장소 오류·상태 충돌·감사 기록 실패가 도메인 결과로 바뀌는 경계를 합의한다. 원문을 오류 메시지로 공개하지 않는다.

C가 작성한 [Store 계약 요구 초안](tasks/c-store-requirements.md)은 세 연산의 입력 의미·관계 검사·rollback·실패 전달과 후속 검증 기준을 제안한다. B 검토·A·B·C 합의는 아직 없으며, 특히 상태 전이의 `security_version`, 소비 감사 원자성, SEND 결과·커밋 실패의 처리, 재시작·제어 경쟁은 초안 U1–U8의 미확정 항목이다. 이 링크 추가는 계약 확정이나 위 체크리스트 통과를 뜻하지 않는다.

C의 [Store 계약 처리 제안 v1](tasks/c-store-proposal.md)은 정상 승인 상태 전이의 보안 버전 유지, 승인 생성·종결 원자 연산, 커밋 불명 오류·취소, DB 처리 시점의 만료·시작 정리 규칙을 구체적으로 제안한다. 새 API·DTO·오류 이름과 시계·스키마 변경은 B 검토·A·B·C 합의 대상이다. 제안 작성과 실제 구현·검증·합의를 구분한다.

SQLite 이관 후에도 C 요구·제안 문서는 B의 설계 검토와 C의 독립 인수 기준으로 사용한다. Registry 상태·지문 영속화, 변경 시 승인 무효화와 단일 writer 사용 인터페이스는 B·C가 구체화하고 공통 계약 변경을 기록한다.

[Cisco Scanner 4.8.6 확인 보고](tasks/c-cisco-scanner-spike.md)에서 개별 오프라인 API와 CLI를 실행했다. 정적 검사 경로의 실패 완료 오판·생략과 원문 출력 때문에 C가 도구별 필수 분석기 완료·실패를 직접 집계해야 한다. B ScanReport의 필수/완료/생략/실패·지문·severity로 번역하는 계약과 필수 분석기 목록은 후속 검토 대상이며, SDK 결과나 종료 코드만으로 ACTIVE를 확정하지 않는다. MCP 1.30.0·B lock과의 설치/단위 검증은 A의 실제 연결·AGT 호환 확정을 대신하지 않는다.

## 합의 기록

API 세부 사항에 대한 A·B·C 합의 기록은 없다. SQLite 담당에 대한 사용자 결정은 위 담당 변경 기록에 남겼으며, 아래 표의 동의를 대신 채우지 않는다. 아래 표는 실제 검토 후에만 채운다.

| 날짜 | 변경 대상 / 커밋 | 결정과 영향 | A 확인 | B 확인 | C 확인 |
| --- | --- | --- | --- | --- | --- |

해결되지 않은 사항은 미확정 상태로 남기고, 구현 중 발견한 설계 충돌은 근거 절과 영향을 적어 합의한다. 제공받은 원본 사본을 조용히 고쳐 합의된 것으로 만들지 않는다.
